# 读《Super-agent 设计探索》: 拿 HXLoLi 这三天的账去对

R4 · 2026-11-02 01:10 CST · 原文抓取与引文见同目录 `SOURCE-NOTES.md`

先交代立场. 这篇文章我认一半, 而且认的那一半恰好是它写得最轻的部分; 它写得最重、最得意的几处 (静默投机执行, 让 Watchdog 在线改规则, Session 对用户隐身), 放到我们这几天的真实账本上都站不住. 下面每一条都先摆我们仓库里发生过的事, 再说我对原文那句话的态度.

## 0x00 先看我们自己是什么形态

这篇读后感本身就是一个现场. 用户同时开了 R1 到 R4 四个写手, 每个写手收到同一份映射说明 (同一个目录地址, 同一个 token, 同一句"不许看别人的"), 然后用户自己在中间收结果、比高下. 这就是原文的双层架构, 只是 Router 是人.

再往前看一天. `.agents/notes/implemented/feature/` 里 2026-11-01 一天落了 15 篇 Agent Note: 番剧分享一条线就是 4 篇接力 (`anime-share-image-and-list` -> `anime-share-link` -> `anime-share-on-index` -> `anime-share-table-view-and-preview`), 详情页又是 3 篇 (`anime-detail-redesign` / `anime-detail-sidebar-and-hero` / `anime-page-refactor`). 晚上 22:08 到第二天 00:35, `.hxnote-trial/` 里又连跑了 T1、T2、IMPACT、A/B、B3 五轮. 最后三个提交 (00:42 / 00:47 / 00:50) 把番剧这一天的东西收进主干.

所以原文那句"一个人通常只能同时跟进 3 到 5 个活跃 Session", 我认. 用户这一天就是贴着这个上限在跑, 而且已经开始用"四个写手并发 + 人工对比"的方式绕它.

## 0x01 我认的: 链式召回, 我们其实已经在手工做

`anime-share-link.md` 开头第二段直接写着"此前的 /anime/share (2026-11-01-anime-share-image-and-list.md) 只读 URL 筛选出 PNG". 每篇 note 都带 `Decision-ID`, 后一篇用文件名指向前一篇. 这就是原文 3.3 节说的"每次召回的对象均内联下一跳关联对象的 ID", 只不过在我们这里, 这张引用图是人逼着 agent 写进 Markdown 的, 不是系统自动维护的.

我认这一节, 是因为它在我们这里真的救过命: 分享页被用户一句"你这个分享页面里面为什么不能进行筛选?" 推翻重做时, 新的 session 不需要读上一轮的对话, 只读一篇 5.4 KB 的 note (`2026-11-01-anime-share-image-and-list.md`, 5387 字节) 就知道上一版的约束 (纯静态站点, 没有后端, 不新增依赖, 不改 filters.ts). 原文说"浪费上下文窗口, 就是浪费模型的智能", 我们的 note 体系就是这句话的笨办法实现.

但我要补一句原文没说的: 链条断在"写错地方"上, 而不是"没写". REPORT.md 自己承认 `HXLoLi/.agents/research/hxnote-trial-*` 有 11 个平铺文件是"选错位置的临时落点", 另有一份 `hx-note-trial.tar.gz` (27890 字节) 掉到了外层 `HXLoLis/.research_scratch/`, 根本不在这个仓库里. ID 再全, 落点错了, 下一跳就召回不到.

## 0x02 我认的: Fast Path / Slow Path, 但 Fast Path 自己也会错

`anime-graph-refactor.md` 是这篇文章 3.1 节最好的反面教材, 也是最好的正面教材.

旧代码判续作用的是名字前缀 (`name.length > 4` 取前 4 字符, 连边时又用 `> 3`, 两处口径不一致). 这是一条典型的"把高频判断固化成确定性代码"的 Fast Path. 实测 160 部番, 前缀规则连出 157 对, 其中 94 对在 bangumi 的 `relations` 里根本不存在, 还漏了 12 对. Fate/kaleid liner 和 Fate/Grand Order 被连成续作.

修法是把顺序倒过来: 先用 `relations` 这份确定性的结构化数据出 59 条系列边, 前缀只做兜底, 而且要同时满足三个条件才补, 最后只补了 5 条.

所以我认两级过滤, 但不认原文那种"已经明确且稳定的高频判断固化为确定性代码"的乐观. "稳定"是要量出来的: 157 对里错 94 对的规则, 在没人去数之前也一直被当成稳定的 Fast Path.

## 0x03 我认的: 单一序点. 一个 CDN 按钮的教训

`navbar-slim-and-cdn-first-load.md` 里的 bug: 首屏 CDN 按钮一直是灰的 `CDN`, 点开面板才出读数. 根因是两个引擎各持一张延迟表, `ensureInit()` 只在 mainEngine 上测速, 按钮却读 musicEngine 的表, 永远是空的. 修法是只留一个 probeEngine, 经 `useSyncExternalStore` 给出唯一快照.

这和原文 2.1 节让 Router 当"全局的序点 (Sequence Point)"是同一件事: 状态一分两份, 每份都自洽, 合起来就是错的. 我们 R1 到 R4 四个写手如果各自往仓库里写, 也会是这个形状, 所以用户才给每人划了独立目录 `.hxnote-trial/REVIEW/R4/`.

## 0x04 我不认的: "否则全程保持安静"

原文 3.4 节最得意的一条策略是"静默复现并修复": 找到简单修复才交付, 否则全程保持安静. 我不同意这条, 理由全在 `.hxnote-trial/` 里.

这三天最有价值的产出不是成功, 是失败和推翻:

- 00:10 的 `AB/VERDICT.md` 得出"是 skill 把配图压成了框线图", A2 的 patch 把"生图后端可用时每篇至少一张生图当主视觉"写成了硬规则. 看上去这是一个漂亮的"找到修复方案".
- 25 分钟后, 00:35 的 `FIG/B3/NOTE.md` 用去图自检把它推翻了: A2 的三张生图 (cow-hero / refcount-touch / gc-freeze) 删掉以后"正文一个数字都不少, 读者也不缺任何事实", 而 B3 的三张数据图删掉以后, b3-2 的 18 个点只剩 3 个, b3-3 的 10 个点只剩 2 个.
- B3 的原话: "A1 的 drawio 和 A2 的生图是同一个错误的两种外观."

如果按原文的策略, A2 那个"找到了修复"的 patch 会被安静地交付, 而 B3 这种"上一轮的修复方向不对"的结论, 因为没有产出新修复, 会被安静地丢掉. 静默投机执行天然偏向交付 A2 这一类看起来闭环的东西. 对一个还在摸规则的系统, 失败报告应该比成功报告更响, 而不是更安静.

## 0x05 我不认的: 让 Watchdog 在线"增删提示词、调整触发规则"

原文第 6 节说 Watchdog 可以在线修正主系统, "例如增删提示词、调整触发规则". `IMPACT.md` 给了我们一个反例的数字.

hx-note 改造只是新增了几条 lint (`section-visual` E 级, `table` 放宽到超过 5 行才报), 拿去扫存量 44 篇 ai-docs: 旧门禁通过 9/44 (20.5%), 新门禁通过 0/44. 其中 9 篇是"旧过新不过", 完全是新规则单独造成的. 来源门槛对存量 0 篇可查, 因为没有一篇带 S 编号.

这次之所以没出事, 是因为 IMPACT 是"只查不改", 人看完再决定. 一个能自己改规则的 Watchdog, 做这种改动时不会先跑一遍 44 篇, 改完全仓库就红了. 规则改动必须带影响面扫描, 这一步我认为不能交给在线自修.

## 0x06 我不完全认的: 用模型判断"有没有实质进展"

原文说 Watchdog "还会由模型判断各个 Worker 是否有实质进展". 方向我认, 进程活着不代表任务活着. 但我们的门禁数据说明, 光有判断者不够, 判据要能证伪.

- T1 和 T2 的 `doctor` 都是 16/16 PASS, 三道门禁全部 exit 0. 但 REPORT.md 写明: 第 4 步"人类逐题对齐两篇都没有真的发生", 是 `--force` 推过去的. 门禁全绿, 流程的核心一步是空的.
- B3 第 4 节: `section-visual` 只数 `![`, A2 的三张氛围图照样让它通过. 门禁"分不出'撤掉丢证据'和'撤掉什么都不缺'".

一个模型 Watchdog 去看这些 Worker, 看到的也是 16/16 和 0 E. 真正起作用的是 B3 那种可执行的反事实检查: 把图删掉, 重跑 lint, 数剩几个点. 我的看法是, "实质进展"要落成这种能跑的检查, 否则 Watchdog 只是第二个会被绿灯骗的人.

## 0x07 我不认的: 薄 daemon 是免费的

原文第 5 节把端侧 daemon 写得很轻: "只负责执行命令与返回结果". 我们正在用的就是这个形态: Hark 沙箱是云端的 Agent Loop, `fs.lolioa.com` 这条隧道就是端侧 daemon, 把 HXLoLi 留在用户机器上. 我认这条路线, 但不认"薄"没有代价. 这几天隧道的能力缺口直接改写了仓库结构:

- 写接口不能建目录. P4 原计划的新域目录 `scripts/cli/sources/` 只能改成 `scripts/lib/sources_core.py` 加一个 `hx_flow.py sources` 子命令. 代码放哪, 是由隧道决定的, 不是由设计决定的.
- 探测建目录时 POST 到目录路径, 结果生成了 0 字节的 `HXLoLi/.trial` 文件; 覆盖写会留 `.hark-bak`, REPORT.md 专门提醒"提交前需清掉", 否则会混进 diff.
- 隧道在 Cloudflare 边缘按 User-Agent 过滤, Python-urllib 一律 403 (error code 1010). 这次映射说明里专门为此写了一段警告.
- 沙箱缺 `rsvg-convert`, T1、T2、A1 三张 drawio 都"需要人类在站点上看一眼", 执行环境的缺口又把一步验收推回给人.

原文说"把执行环境留在云端之外, 由 Agent 按需读取", 读这件事确实便宜. 但写、建目录、预览这些动作, 每缺一个, 就要么扭曲产物, 要么把活退回给人. daemon 的能力面应该和 Agent 要做的动作对齐, 而不是越薄越好.

## 0x08 最认、也最该警惕的: 8.4 节的凭据

原文 8.4 节说要让 Agent "在完全不接触凭据本身的情况下使用凭据". 这是全文我最认的一句, 而我们现在的做法正好反着来: 这条可写隧道的 token 是明文写在派给 R1 到 R4 的任务说明里的, 四个写手的上下文里都有它, 拼在每一条 curl 的 URL 上. 本文和 `SOURCE-NOTES.md` 都刻意没有抄这个 token.

对比我们自己在 `anime-local-overlay.md` 里的做法: 写入口只在 `docusaurus start` 下挂, 要求本机 Host、`application/json` 和 `X-HX-Overlay: 1` 头, 生产构建后 `grep -r "__hx/anime-overlay" build/` 必须为空. 一个番剧标注的写口子都做了这几层, 能改整个仓库的隧道却只靠一个 URL 参数. 原文 8.4 节没有给答案, 但它点出的问题在我们这里是现成的.

## 0x09 我不认的: Session 对用户隐身

原文 2 节: "Session 应当是系统的实现细节, 而不应是用户的认知负担". 在交付型工作里我同意. 但我们这几天有一类工作, 隔离本身就是目的:

- 保真盲审和 AI 味盲审都要求"新鲜 sub-agent, 只给 index.md". T2 的保真盲审跑了三轮 (第 1 轮 4 新增 2 歪曲, 第 2 轮 3 新增 2 歪曲), 每一轮都必须是没见过上一轮的人.
- A/B 的前提是 A1 和 A2 "同一执行者, 同一份实测数字, 唯一变量是 skill 版本".
- 本文也是: R1 到 R4 "独立写, 不许看别人的".

原文的 Router 是全局记忆, 什么都汇总. 对评测和盲审来说, 一个"什么都知道"的 Router 恰恰是污染源. 用户需要能看见并且亲手划定 session 边界. 所以我的立场是: Session 对交付隐身, 对评测必须可见.

## 0x0A 原文实验看不到我们的失败模式

7.1 节的消融实验里"编码工作用一个只消耗时间的工具代替", 衡量的是调度, 不是质量; 读缓存 token 从 2323 万到 3177 万、Router 分摊推理时间从 6.4 秒降到 1.6 秒, 都是吞吐账. 原文自己也说明了这一点, 我不挑这个.

但我想指出, 我们这几天真正卡住的地方没有一处是吞吐: 是保真盲审多跑一轮 (T1 两轮过, T2 三轮过, REPORT 的解释是"文字压短以后, 每句话更容易'讲过头'"), 是 A2 的规则方向错了, 是门禁全绿但第 4 步空着. 这些在"只消耗时间的工具"里都不会出现. 双层架构能让我们同时跑更多轮, 但不会让任何一轮更对.

## 0x0B 落到下一步

如果要把原文的思路搬到 HXLoLi 的 agent 工作流里, 我会按这个顺序, 而不是按原文的模块顺序:

1. 先把 note 的落点规则写死 (REPORT 里 11 个平铺文件的教训), 让链式召回的下一跳一定在仓库里.
2. 门禁加反事实检查, 照 B3 的去图自检: 每张图后第一句要带数字或代码标识符, 这条 B3 已经提了, 还没实现.
3. 规则改动先跑存量影响面 (照 IMPACT.md 的 44 篇扫描), 再上线; 不给任何自动回路直接改规则的权限.
4. 隧道补上建目录和凭据不入上下文, 这两件比加 Router 更急.
5. 失败报告单独一类, 和成功一样上报, 不做"找不到修复就安静".
