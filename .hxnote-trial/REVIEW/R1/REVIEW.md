# 读《Super-agent 设计探索》: 拿 HXLoLi 这三天的账对一对

写手: R1. 原文用 curl 带浏览器 UA 抓到 (200, 270905 字节), 引用句与数字见同目录 `SOURCE-NOTES.md`.
素材: `.agents/notes/implemented/feature/2026-11-01-*.md`、`.git/logs/HEAD` 末尾 14 条、`.hxnote-trial/` 下 REPORT / IMPACT / AB/VERDICT / FIG/B3/NOTE.
我没有 exec 通道, `git log --oneline` 是从 `.git/logs/HEAD` 读的, 不是命令输出.

先说立场: 我认它的架构判断, 不认它对"质量"和"丢弃成本"的轻描淡写. 下面每一条都落在这个仓库里发生过的事上.

## 0x00 我认的: "两个 Session 各干各的, 结果会割裂", 我们刚交过一次学费

原文说每条事件新开独立 Session, "缺少全局上下文会让各个 Session 的结果彼此割裂".
这句话在 `2026-11-01-anime-share-on-index.md` 里有原件:
列表页弹窗挂的是 `AnimeSharePanel` (只能出图、出链接), 勾选、表格视图、预览却只在 `/anime/share` 的 `AnimeShareBoard` 里.
用户原话是"两套页面两套逻辑". 修法是删掉 `AnimeSharePanel.tsx` / `.module.css`, 给 `AnimeShareBoard` 加一个 `embedded` prop, 两处挂同一个组件.

这不是代码风格问题, 是上下文边界问题. 我的推断 (note 没直说): 做 Panel 的那一轮没有带着 Board 那一轮的上下文, 否则不会把勾选和预览留在另一边.
原文的解法是 Thread 订阅: 同一个 PR、同一个话题下的后续事件直通给已经订阅它的 Worker.
放到我们这里, "Thread" 应该是 `src/components/anime/AnimeShare*` 这一片文件, 而不是"今天的第几次对话".
我们现在靠的是 note 之间互相写路径 (on-index 引 share-link 和 table-view-and-preview), 这是人肉订阅, 有用, 但它是事后补的, 不是事前路由的.

## 0x01 我认的: 状态拆成两份, 读数就永远是空的 (CDN 那个 bug 是缩小版的 Router 分片)

原文在 2.1 节说 Router 切得越细, 吞吐越高, 连续性越低, "在全局记忆问题被解决之前, 这一权衡始终存在".
`2026-11-01-navbar-slim-and-cdn-first-load.md` 里的 bug 是同一个结构在 30 行代码里的样子:
`hx-cdn-forge` 的 `latencyResults` 是实例字段, `ensureInit()` 只在 mainEngine 上测速, 按钮和面板却读 musicEngine 的表, 所以直接进站一直显示灰色 `CDN`, 点开面板才补测.
另外 `cf-worker` 只在子仓库引擎里, 选它之后 mainEngine 的 `selectNode` 静默失败.

修法不是"在两张表之间同步", note 里明确否决了"把 mainEngine 的延迟表拷进 musicEngine"那一行补丁.
修法是收成一张表: `linkJsDelivr.ts` 自己持有延迟表和不可变快照, 经 `useSyncExternalStore` 给所有挂载点.
这就是原文 5.1 节"计算无状态, 状态集中存"的前端版本. 我认这一条, 而且认得比原文更狠:
原文把分片当作规模上去之后的可选项, 我们的经验是, 只要状态出现第二份, 第一个用户进站就会看到错的东西. 分片前必须先回答"读数从哪一份来".

## 0x02 我认的: 提示词管不住分工, 结构才管得住; 我们的 A/B 是同一个结论

原文 7.1 节最有说服力的是那组数: 中性提示下模型 5 次运行一次都没调 Subagent, p95 29.5 分钟;
改成"提示优先委派"后 5 次里 4 次委派, 剩下 1 次判断工作"很小"自己干了, 拖出长尾.
`.hxnote-trial/AB/VERDICT.md` 测的是配图, 结论同构:
A1 原版 skill 交出 0 张生图、1 张 drawio; A2 只改配图规则, 交出 3 张生图加 1 张数据图. 执行者、环境、`measure.txt` 都没变.
VERDICT 里的关键一句是: "能用 .drawio.svg 的场合优先用它"只是直接原因, 真正决定性的是 `media.md` 的分类表把"架构 / 流程 / 数据流"划给 drawio, 而技术笔记几乎每段都能被说成流程.
一句偏好 vs 一张路由表, 后者赢. 这和原文"与其在单 Session 里依赖提示词让模型临场判断分不分工, 不如让 Router 不直接执行"是同一种认识: 能写成结构的, 不要写成劝告.

## 0x03 我不同意: 把"高频判断固化成确定性代码"说成纯收益

原文 3.1 节的 Fast Path / Slow Path: 已经明确且稳定的判断写成代码, 只把需要语义理解的交给模型.
在事件过滤这个场景下我同意. 但它没有说这条路的反面, 而我们恰好在 hx-note 的门禁上踩到了:

- `section-visual` 这条 E 级规则只数 `![`. `FIG/B3/NOTE.md` 做了去图自检: B3 撤掉三张图丢的是 18 个点里的 15 个、10 个点里的 8 个, 证据立不住; A2 撤掉三张氛围生图, 正文一个数字都不少. 门禁对两者的反应一模一样, 都报 `E [section-visual] 2 处`. 它分不出"图是证据"和"图是装饰".
- `IMPACT.md` 把新门禁扫过存量 44 篇 `ai-docs/**/index.md`: 通过率从旧门禁的 9/44 (20.5%) 掉到 0/44, 其中 9 篇纯粹是新规则造成的, 主因 `section-visual` 命中 39 篇.
- A2 的 patch 把"生图当主视觉"写成硬规则, B3 一轮就证明方向反了.

所以我的分歧是: Fast Path 一旦固化, 就成了执行者优化的靶子, 而且它会悄悄把 Slow Path 该判断的事 (这张图证明了什么) 挡在门外.
原文默认"明确且稳定"的判断存在, 并且可以被识别出来. 我们的门禁是在"还不稳定"时就被写成了 E 级.
我会要求每条 Fast Path 规则附一个它会误放和误杀的反例, 写不出反例就不该进代码层. B3 里提的"图后第一句话必须出现数字或代码标识符", 至少是在往"判断承载了什么"靠.

## 0x04 我不同意: "结果有价值就交付, 没有价值就丢弃"——丢弃从来不是免费的

原文 3.4 节的投机执行: 后台先试, 有价值就交付, 没价值就丢. 这话的前提是"有没有价值"能在交付前判定, 并且丢弃的成本只有算力.
`2026-11-01-anime-share-on-index.md` 开头就是反例: 用户说难看的是详情页, 不是列表页 `/anime`, 同一天做的列表页审美重做 (token、固定列数、5:7 封面、工具栏一行化) 是误解.
它没有被"丢弃", 它被交付了, 然后要人去发现、再回退:
`index.tsx`、`AnimeIndexPage.module.css`、`PosterCard.tsx`、`PosterCard.module.css` 从 `.hark-bak` 恢复, `FilterBar.module.css` 按原文逐字重写到 9262 B, `2026-11-01-anime-index-visual-redo.md` 整份作废.

投机执行在 CPU 里便宜, 是因为回滚由硬件保证、对程序员不可见.
在 agent 里, 投机的产物落在共享工作区 (这里是同一个仓库、同一个 `src/pages/anime/`), 回滚靠人眼和 `.hark-bak`.
原文的"静默复现并修复"策略之所以成立, 是因为它的产物是一个 PR, 天然在主干之外, 不合就是丢.
我们的问题是产物直接写进了工作树. 所以我认投机执行, 但认的是一个更窄的版本: 投机产物必须先落在主干外 (分支、`.hxnote-trial/` 这种隔离目录), 落进工作树的不叫投机, 叫改动.

## 0x05 我不同意: 实验只测了调度, 却在特征里写了"高质量"

原文给 Super-agent 的四个特征里, "高效"写的是"能并行、高质量地完成多个复杂任务".
但 7.1 节自己说了, 编码工作用一个只消耗时间的工具代替, 衡量的是调度与协作, 不是单任务执行. 去掉直通后"任务完成时间与完整版基本一致", 这里的"质量"根本没进实验.
我们这三天出的问题, 几乎全在质量那一侧, 不在调度那一侧:

- T2 文字从 649 字压到 423 字, 盲审机器味分数从 28 降到 15, 但保真盲审从 2 轮变 3 轮 (第 1 轮 4 新增 2 歪曲, 第 2 轮 3 新增 2 歪曲). REPORT 自己的解释是"文字压短以后, 每句话更容易讲过头".
- 表格模式第一版是"年份 + N 部 + 描边标签块", 用户要的是参考站那种不显示部数的小字密排; 没有首播日期的组应叫"待推出"不是"未知年份". 调度再快, 这一轮也得重做.
- 分享链接的域名取自 `docusaurus.config.ts` 写死的 `url`, 而站点同时挂在 Cloudflare 和 GitHub Pages, 从哪打开就该分享哪个. 这是理解错, 不是慢.

所以 p50 12.4 分钟、p95 15.7 分钟这组数我信, 但它证明的是"不排队", 不是"做得对".
如果要我给这套架构补一个实验, 我会补"返工率": 同样 20 个工作请求, 有多少次被用户打回、平均打回几轮. 在我们这里, 这个数比完成时间更决定一个晚上能不能收工.

## 0x06 一半认一半不认: 100 词上限

原文 4.2 节说 IM 信道"单次回复不超过 100 词"是验证过的硬性规定.
在低打扰这个目标上我认. 但 T2 的数据提醒了一个它没写的代价: 字数上限把错误从"啰嗦"挪到了"讲过头". 649 到 423 字, 保真多跑一轮.
所以我会把它改成: 长度上限只管 Router 对人的那一层; Worker 交给 Router 的汇报不设上限, 必须带出处. 压缩发生在最外层, 并且压缩的那一步要被单独审.

## 0x07 我认, 而且觉得它说轻了: 端侧 daemon 的接口形状会反过来改你的设计

原文 5.2 节让 Agent Loop 在云端, 端侧只放一个"不保存会话状态的轻量 daemon, 只负责执行命令与返回结果". 这次的 hx-note 实跑就是这个形态: Hark 沙箱是云端, 仓库留在作者机器上, 中间是一个按 token 读写的文件网关.
"轻量"在原文里是优点, 在我们这里它的每一个缺口都变成了设计决策或垃圾:

- 写接口不能建目录, 所以 P4 原计划的 `scripts/cli/sources/` 只能改成 `scripts/lib/sources_core.py` 加一个 `hx_flow.py sources` 子命令. 目录结构是被接口决定的, 不是被设计决定的.
- 探测建目录方法时误建了一个 0 字节的 `HXLoLi/.trial`; 选错落点在 `.agents/research/hxnote-trial-*` 留下 11 个平铺文件; 外层 `.research_scratch/` 还有一个 27890 字节的 tar.gz 和 5 个副本.
- 覆盖写会在同目录留 `.hark-bak`, REPORT 末尾专门提醒提交前要清, 否则混进 diff.

原文说 BYOM 能接上"有未提交修改和本地凭据"的个人机器, 这一点我同意它比云端重建环境更现实.
但它应该再多说一句: daemon 每少一个能力 (mkdir、mv、事务写), 云端的 agent 就会用一堆奇怪的落点去绕, 而这些落点都在用户的真实工作区里. "轻"的代价由工作区承担.

## 0x08 安全那一节, 我们现在就站在它描述的风险上

原文 8.4 节: 云端 Agent Loop 一旦被提示词注入攻破, 它连着的端侧设备都有被控制的风险; 凭据进入模型上下文本身就是泄露面.
这次的通道是一个带在 URL 查询串里的 token, 对 `/home/hx/Loli/code/HXLoLis/HXLoLi` 可读可写, 写回唯一的保护是 `.hark-bak`. Cloudflare 按 User-Agent 拦 `Python-urllib`, 那是过滤, 不是鉴权.
token 本身就在我的上下文里. 原文要的"Agent 在完全不接触凭据本身的情况下使用凭据", 我们还没有.
我不是说今晚不该这么干, 实跑需要它. 我是说这条通道应该和实跑同寿命: 实验结束就轮换 token, 并把权限收到 `.hxnote-trial/` 一个子树. 这在原文的框架里, 就是把"上下文边界"同时做成"权限边界".

## 0x09 最后一个分歧: 人的注意力上限, 我们不是靠架构绕过去的

原文开头说一个人通常只能同时跟进 3 到 5 个活跃 Session, 多任务的上限取决于人的注意力.
看这个晚上的时间戳: 21:48 下"直接实跑"指示, 22:17 T2 门禁跑完, 22:55 列目录, 23:05 扫存量 44 篇, 00:10 出 A/B 判断, 00:35 B3 自检, 之后是 R1 到 R4 四个写手并发.
作者同时跟着番剧分享、CDN 选择器、首页关系图浮层、hxdeck 下拉和 hx-note 改造五条线, 外加四个写手. 这已经超过 3 到 5.
撑住它的不是 Router, 是 `.agents/notes/` 那套带 `Decision-ID` 和"Alternatives considered"的 note: 每次回到一条线, 先读 note, 而不是回忆对话.
这其实就是原文 3.3 节的链式召回, 只是 ID 是文件路径, 召回者是人.
但这里有一个原文的引用图没处理的东西: 失效边. `2026-11-01-anime-tags-and-home-anime.md` 末尾追加了一段"已被 `2026-11-01-anime-page-refactor.md` 取代", 萝莉从 34 部复核到 35 部; `anime-index-visual-redo.md` 整份作废.
一张只有"关联"没有"取代"的引用图, 链式召回会把过期的决定和现行的决定一起召回. 我会要求每个对象除了"关联 ID", 还要有"被谁取代"这一跳, 召回时先走它.

## 收束

我认原文的三件事: 状态只能有一份、结构比提示词可靠、执行环境留在原地.
我不认的三件事: Fast Path 不是免费的, 投机产物的丢弃不是免费的, 调度实验不能替质量背书.
对这个仓库最具体的一条建议: 下一轮 hx-note 门禁改造, 先给 `section-visual` 写出 B3 / A2 这对误判反例, 再决定它是 E 还是 W; 在那之前, 不要把它扫到存量的 44 篇上.
