# 读《Super-agent 设计探索》: 我在 HXLoLi 这几天手搓出来的, 正是它说的那套架构, 也正好撞上它没写的那几堵墙

R3 独立稿. 原文引用与抓取方式见同目录 `SOURCE-NOTES.md`. 业务素材全部来自本仓库: `.hxnote-trial/` 下的 REPORT.md / IMPACT.md / AB/VERDICT.md / FIG/B3/NOTE.md, `.agents/notes/implemented/feature/` 下 2026-10-31 到 2026-11-01 的 note, 以及 `.git/logs/HEAD` 末尾的提交.

## 0x00 先说一个尴尬的事实: 这几天的工作流就是一台人肉 Super-agent

把这几天的分工摆出来:

| 原文的模块 | 我们这里实际是谁 |
|---|---|
| Router 层 (只分派, 不干活) | 你本人. 你在聊天里下指令, 把 hx-note 改造拆成 T1 / T2 / A1 / A2 / B3, 现在又把读后感拆成 R1 到 R4 四个写手 |
| Worker 层 (上下文隔离, 挂完整工具) | Hark 沙箱里的一个个会话. "R3 独立写, 不许看别人的" 就是原文说的上下文隔离 |
| 端侧 daemon (BYOM, 不存会话状态) | `fs.lolioa.com` 那条文件隧道, 列目录 / GET / PUT, 覆盖前备份到 `.hark-bak/` |
| 链式召回 / Inline & Spill | `.agents/notes/implemented/feature/*.md`: 每篇有 Decision-ID, Code 段列文件, 正文互相引用 (anime-share-link 指向 anime-share-on-index) |
| Watchdog | `hx_flow.py doctor` 16 项, `validate_skill.py --strict`, `prose_rules.py`, `check_layout.py` 三道门禁 |

所以我读这篇文章不是在读一个远方的架构, 而是在对照自己的流水账. 下面按 "认 / 不认" 写, 每条都落到这个仓库里真踩过的坑.

## 0x01 我认的: Watchdog 要盯 "有没有实质进展", 不能只盯 "进程活着"

原文说许多异常 "并非进程崩溃, 而是模型在执行中陷入无效循环或偏离目标". 这句我完全认, 而且我们的门禁就是反例的标本.

- T2 的 `gates.log` 里 doctor 打出 `PASS 16/16 项通过`, 三道门禁全部 `exit_code=0`. 但 REPORT.md 自己承认: 第 4 步 "人类逐题对齐两篇都没有真的发生", 是按 21:48 的 "直接实跑" 指示用 `--force` 推进的, 答题卡 A 栏留空. 绿灯全亮, 最关键的那一步根本没人做.
- 更狠的是 FIG/B3/NOTE.md 的去图自检: 把 B3 的三张数据图删掉, lint 报 `E [section-visual] 2 处`; 把 A2 的三张生图删掉, lint 也报 `E [section-visual] 2 处`. 门禁对两者反应一模一样. 但 B3 撤图丢的是 18 个点只剩 3 个、10 个点只剩 2 个的证据, A2 撤图 "一个数字都不少". `section-visual` 只数 `![`, 它是存活探针, 不是进展判断.

结论: 我们的门禁目前全是 "进程活着" 那一层. 原文让 Watchdog 由模型判断 "是否有实质进展", 这正是我们缺的一层. B3 NOTE 里提的那条可机械化规则 (每张图后第一句话必须出现数字或代码标识符) 是往这个方向挪的第一步, 本轮还没实现.

## 0x02 我认的: Router 要当 "全局序点", 状态分两份就一定出鬼

原文把 Router 定义为 "全局的序点 (Sequence Point)、协调点和记忆". 这个我在一个跟 agent 完全无关的 bug 上见过一模一样的形状.

`2026-11-01-navbar-slim-and-cdn-first-load.md`: CDN 按钮首屏一直是灰的 `CDN`, 点开面板才出延迟. 根因是 `hx-cdn-forge` 的 `latencyResults` 是实例字段, mainEngine 测速, musicEngine 被读, 两张表永远对不上. 修法是统一用一个 probeEngine, 由 `linkJsDelivr.ts` 持有唯一快照, 经 `useSyncExternalStore` 分发.

番剧库那篇 (`2026-11-01-anime-page-refactor.md`) 也是同一个病: 观看状态存 localStorage, 标签写 URL, 排序存 localStorage, 三套状态互不相干, 只能靠一个 effect 补丁对齐. 修法是把筛选收成一个对象完整写进 URL.

两次都是 "有两个以上的地方以为自己是真相", 两次的修法都是 "指定一个序点". 所以我认原文的判断: 多 Worker 系统里, 谁是唯一的序点必须是架构决定, 不能指望 Worker 之间自己对齐.

## 0x03 我不认的: "Router 层的任务常常没有想象中复杂, 较轻量的模型往往就能兼顾速度与效果"

这是我最不同意的一句. 它在原文的场景 (Issue 分派、PR 评审路由) 里可能成立, 但在这个仓库里, 最难、最贵、最容易错的决定恰恰都在 Router 层, 而不是 Worker 层.

证据是 A/B 那条线:

1. AB/VERDICT.md 的结论原话是 "是 skill 把配图压成了框线图, 不是执行者做不到". 同一个执行者、同一个环境、同一份 `measure.txt`, A1 交 1 张 drawio, A2 交 3 张生图加 1 张数据图. Worker 能力没变, 变的只有规则.
2. 然后 A2 的 patch 把 "生图后端可用时每篇至少一张生图当主视觉" 写成了硬规则. 半小时后 B3 NOTE 就推翻了它: "生图后端可用不等于该用", A1 的 drawio 和 A2 的生图 "是同一个错误的两种外观".
3. 也就是说, 一个晚上里规则方向改了两次. 每一次改的都不是 Worker 的执行, 而是 "什么叫好图" 这个判断.

在原文的架构里, 这种判断要么落在 Router, 要么落在提示词策略里, 无论哪种, 都不是 "轻量模型就够" 的活. 原文自己的消融实验也恰好绕开了它: 编码工作 "用一个只消耗时间的工具代替", 衡量的是 "调度与协作能力, 而非对单个任务的执行能力". 所以 p50 12.4 分钟、p95 15.7 分钟这组数字我认, 但它只证明了 "分派" 轻, 没证明 "验收" 轻. 我们这里真正的瓶颈是验收: T1 保真盲审 2 轮过, T2 要 3 轮 (第 1 轮 4 新增 2 歪曲, 第 2 轮 3 新增 2 歪曲), 以及那个被 `--force` 跳掉的人类第 4 步.

我的立场: 把 Router 拆成 "分派" 和 "验收" 两件事. 分派可以轻, 验收是全系统最需要强模型 (或者人) 的地方. 原文把两者合在一个 "Router 层" 里, 再说它轻, 这个结论扩到品味驱动的工作上就不成立.

## 0x04 我不认的: "Session 应当是系统的实现细节, 而不应是用户的认知负担"

原文认为让用户手动管理 Session 是 "从底层 LLM API 延续下来的设计惯性". 方向我理解, 但这几天你恰恰在把 Session 当一个主动使用的工具, 而且用得对.

- 这次读后感的要求是 "4 个并发写手, 独立写, 不许看别人的". 触发它的原因是上一批 "太简单了, 完全就无法体现出任何的差异化".
- 差异化需要的正是隔离. 如果按原文那样由一个常驻 Router 维持全局连续上下文, 四个写手会读到同一份全局记忆、同一份摘要、同一套 "上次用户说过什么", 结果只会更像.
- A/B 也是同一个道理: VERDICT.md 能下结论, 前提是 "唯一变量是 skill 版本". 一个会自动跨会话共享上下文的系统, 反而做不出干净的 A/B. VERDICT 自己都在 "边界" 里担心 "执行者知道自己在做 A/B, 可能下意识把 A2 做得更用心", 共享上下文只会让这个污染更重.

原文在 8.3 节把 "划分上下文共享与隔离的边界" 当成组织扩大以后才出现的问题. 我不同意这个时间点: 一个人自己的任务之间就已经需要隔离边界, 而且这个边界得是用户能直接操纵的东西. Session 不只是认知负担, 也是用户手里唯一的 "别让它们互相看见" 的开关.

## 0x05 我半认的: 投机执行 "结果有价值就交付, 没有价值就丢弃"

原文说投机执行是 "消耗额外的后台算力来减少人类的等待与介入成本". 算力确实是额外的, 但在这个仓库里丢弃不是免费的, 丢弃的成本是人的注意力, 而原文开篇就说注意力才是瓶颈.

`2026-11-01-anime-share-link.md` 记了你的原话: "你这个分享页面里面为什么不能进行筛选? ... 它本身应该是可交互的". 前一轮 (`anime-share-image-and-list`) 做出的是 PNG 加文本清单, 方向错了, 你得先看、再判断、再写一段话把它推翻. 后一轮才做出 `pick=` 变长 base64url 编码 (148 部 402 字符, 整条链接 456 字符) 的可交互番单.

这就是投机执行失败的真实代价: 错的产物不会自己消失, 它要占用一次人类验收. 原文的 "静默复现并修复" 能成立, 是因为 "确认问题并找到简单的修复方案" 有客观判据 (测试能不能过). 在番剧页、笔记文风、配图这种品味判据上, 投机越多, 要人看的东西越多. 所以我只在 "有可执行判据" 的地方认它.

## 0x06 我认, 但要补一句的: BYOM 的 daemon 没有原文说得那么 "薄"

原文说端侧 daemon "只负责执行命令与返回结果", 让执行环境留在原地. 这个思路我认, 文件隧道就是这么用的, 它让沙箱里的会话能直接改 `/home/hx/Loli/code/HXLoLis/HXLoLi`. 但 daemon 能做什么, 会反过来塑造上层的设计, 这一点原文没写:

- REPORT.md: "远端写接口不能建目录, 所以 P4 原计划的新域目录 `scripts/cli/sources/` 改为 `scripts/lib/sources_core.py` 加 `hx_flow.py sources` 子命令". 一个 daemon 的能力缺口, 直接改了 skill 的目录结构.
- 为了探测能不能建目录, 误建了一个 0 字节的 `HXLoLi/.trial`; 选错落点在 `.agents/research/hxnote-trial-*` 平铺了 11 个重复文件; 覆盖备份留下的 `.hark-bak` 会混进 diff, 提交前要清.
- 隧道在 Cloudflare 边缘按 User-Agent 过滤, 带 `Python-urllib` 的客户端一律 403 1010. 这是一条跟业务毫无关系、但每个 Worker 都得事先知道的知识.
- drawio 在沙箱里不能栅格化 (`delegate failed 'rsvg-convert'`), graphviz 装不上 (`Permission denied` 后 `no installation candidate`), matplotlib 要现装 3.11.2 再下中文字体. "执行环境留在原地" 的另一面是: 预览环境也只在原地, 云端的 Worker 看不到自己画的图.

所以 daemon 薄是理想, 现实是 daemon 的每一个 "不能" 都会变成上层的一条约束或一个垃圾文件. 我会希望这类约束集中写进一份 Worker 必读清单, 而不是每个会话重新踩一遍.

## 0x07 我认, 而且觉得原文说轻了: 凭据不该进上下文

原文 8.4 说 "只要端侧环境中的凭据能够进入模型的上下文, 正常执行过程中同样存在凭据泄露的风险". 这一条在这里不是推演: 这条文件隧道的 token 就是明文写在给我的任务说明里的, 持有它就能读写你家目录下的仓库. 按原文的标准, 我们现在的 BYOM 处在 "云端与端侧彼此受信任" 这个最乐观的假设上. 我不在这份文件里重复那个 token, 但建议它按任务签发、限目录、限时.

## 0x08 我顺手不认的一点: Watchdog "在线修正主系统的行为, 例如增删提示词、调整触发规则"

IMPACT.md 给了一组很直白的数字: 新门禁一次性用于存量 44 篇 ai-docs, 通过率从旧门禁的 9/44 (20.5%) 变成 0/44, 其中 9 篇是新规则单独造成的, `section-visual` 一条就命中 39 篇. 来源门槛对存量没有可检查的输入, "只能用于新写的笔记, 不适合回溯".

这就是 "在线改规则" 的代价: 规则一改, 历史一片红. 一个能自己增删提示词的 Watchdog, 如果没有 "新规则只管新产物" 这类版本边界, 会把系统的历史状态一起判死. 原文把它当成 Watchdog 是完整 Agent 的便利, 我认为它需要和规则版本绑定, 否则就是一个能改法律的警察.

## 0x09 我会怎么改我们自己的流水线

1. 门禁加一层 "进展" 判断, 先从可机械化的做起: `--force` 跳过第 4 步时 doctor 不能是 16/16 全绿, 至少要有一项明确标黄.
2. 把 "分派" 和 "验收" 分开记账: 每轮 A/B 或多写手任务, 最后要有一份像 VERDICT.md 那样的验收文件, 而且要写清 "这个判断的边界".
3. 隔离是一等公民: 多写手、A/B 这种任务, 明确不共享记忆, 落点目录 (R1 到 R4) 事先建好, 就像这次一样.
4. daemon 的限制集中成一份清单 (不能建目录、UA 过滤、`.hark-bak` 要清、沙箱不能栅格化 svg), 每个 Worker 开工前读.
5. 规则改版时附带 "只对 hxid 晚于某日期的笔记生效" 这类边界, 避免 IMPACT.md 那种 44/44 全红.

## 0x0A 最后一句

原文的结论是 "瓶颈正在转向人的注意力". 我认这个诊断, 但这几天的账告诉我, 注意力不是花在 "盯着 Session" 上, 而是花在 "判断这份产物对不对" 上: A2 的规则被 B3 推翻, 分享页被一句 "为什么不能进行筛选" 推翻, 上一批读后感被 "太简单" 推翻. 原文的架构能省掉的是调度的注意力, 省不掉验收的注意力. 真正值得设计的, 是让验收也能被拆开、被隔离、被留下证据的那一层.
