# 代码质量上限 (code-quality)

**适用范围**: 本 skill 创建或改写的 skill 里的一切代码  `scripts/` 下的脚本、assets 里的工具源码、以及该 skill 生成出来的代码. 文档类文件 (SKILL.md、references/) 走 `references/prose-rules.md`, 不走这份

门禁

```bash
uv run <this-skill>/scripts/check_layout.py <skill-dir>
```

## 五条硬上限

| 规则 | 判据 | 例外 |
|---|---|---|
| C1 目录文件数 | 一个目录内 **不超过 6 个文件** | `assets/` 里的运行期素材; 该 skill 自己声明的产物目录 |
| C2 单文件行数 | 单文件 **不超过 300 行** (物理行, 含注释与空行) | 自动生成的文件与 vendored 第三方 |
| C3 源码扩展名 | 只允许 `.ts`. **禁止 `.js` / `.mjs` / `.cjs`** | 无 |
| C3 转译产出 | 中间产物 (编出来的 `.mjs` / `.js`) 单独放一个目录, 默认 `dist/` | 无 |
| C4 注释块 | 一段连续注释 **不超过 10 行** | 无 |

目录文件数超限时**拆目录**, 不是删文件. 单文件超限时**拆模块**, 不是压缩注释  压掉注释会把"为什么这么写"一起压掉, 下一个人重踩

## 为什么禁 `.js` / `.mjs`

同一个仓库里两种模块形态并存时, 类型信息只覆盖一半, 而那一半会随着 import 关系扩散失效本仓实测过的代价: `.mjs` 门禁脚本与 `.ts` 库混用, 类型检查器完全不看 `.mjs`, 于是库函数的签名漂移在脚本侧永远不报错. 统一到 `.ts` 后, 这一整类静默失效消失

## 注释只说明做什么

| 该写 | 不该写 |
|---|---|
| 这个函数做什么、返回什么 | 这个功能是哪次需求加进来的 |
| 一个反直觉的实现为什么要这样 | 我调试时踩过的坑与排查经过 |
| 边界条件与失败模式 | 与上一个版本的对比 |
| 引用一条 note 的路径 (如果决策已经被记下来) | 把 note 的内容复述一遍 |

一段连续注释超过 10 行即判违规, 由 `check_layout.py` 的 C4 检查. 判据: **删掉这段注释, 读者会不会误用这段代码?** 不会, 就删. 来龙去脉属于 Agent Note (`hx-agent-notes`), 不属于代码旁边的注释

注释是唯一该写"为什么"的地方是**约束无法从代码本身读出**的时候  那种情况写一句, 并指向 note

## 拆分的顺序

1. 先按职责切模块 (一个模块一件事)
2. 再按目录归组, 每个目录 ≤ 6 个文件
3. 超 300 行的模块里, 把纯函数搬进同目录的兄弟文件
4. 常量、阈值、白名单这类"多处引用同一组数字"的东西, 收进唯一一个模块并被其余文件 import  同一组数字写两处之后, 改一处忘一处就会变成"文档说 300, 脚本判 500", 而两边看起来都对

## 两种声明

目录确需超出上限时, 在**那个目录里**放 `layout.json`

```json
{"maxFiles": 12, "maxLines": 400, "maxCommentBlock": 20, "reason": "<为什么这里需要>"}
```

豁免随目录走 (别人 clone 到也能复现), 写在 skill 根目录的会被其下所有目录继承

上游拥有布局的 vendored skill, 在**根目录**改声明这一条

```json
{"vendored": true, "reason": "<上游仓库 + 为什么本地改动会让同步变成三方合并>"}
```

两条门禁都会打印一行 `VENDORED ...` 并跳过它  那是一个被记录下来的决定, 不是静默放过. 判据: **这份布局归谁改?** 归上游就声明, 归本仓就拆

## 与其他规则的关系

- 与 `hx-code-quality`: 那份是**具体项目**的全景与门禁建设, 要按项目现状裁决阈值; 这份是**skill 自身**的默认上限, 不因为某个项目现状宽松就放宽
- 用户明确指定的阈值优先于本文件; 要调整就先写理由并让用户确认, 不要静默放宽
