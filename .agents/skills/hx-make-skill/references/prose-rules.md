# 产物文本规范 (prose-rules)

**这份是硬要求, 不是风格建议.** 凡是用本 skill 创建或改写的 skill, 它写入磁盘的每一份文本产物(SKILL.md、references/、assets/ 里的文档、步骤契约、模板、以及该 skill 自己生成的文档) 都必须过这道门禁

```bash
uv run <this-skill>/scripts/prose_rules.py --check <skill-dir>
```

退出码 0 才算过. 有不被判定的地方就按 `references/spec-checklist.md` 的裁决走, 不要自行放宽

## 四条规则

| 规则 | 要求 |
|---|---|
| 标点形态 | 只用英文标点: `, . ? ! : ; ( ) "`. 全角 `，。？！：；（）“”` 一律判违规 |
| 标点后空格 | 标点后接内容时补**一个**空格; 后面没有内容时不补 |
| 句末 | 正文行末尾**只允许** `?`. 其余 `, . ; : !` 出现在行尾即违规 |
| 折行 | 禁止把一个句子拆到两行: 折点落在句子中间即违规 |

## 规则 3 与规则 2 不矛盾

两个细节容易看成打架, 它们是同一条规则的两半

- 行尾的 `.` 是**判违规**, 不是"可以留着". 所以行中最常见的形态就是标点后接内容`先取证, 再裁决`, 空格出自规则 2
- `,` `.` `;` `:` 出现在**行尾**只可能是折行的残留, 于是规则 3 与规则 4 在同一个位置兜住它

`?` 是唯一的例外: 疑问句该以 `?` 收尾, 归属 hx-note 的 `hx_voice.py` (`atom-rhetorical` 规则)按产物类型另行裁决. 两道门禁管的是不同的事, 不冲突

## 判据编号 (门禁输出里就用这些 id)

| id | 判定 | 例外 |
|---|---|---|
| P1 | 出现全角标点 | 代码块、行内代码、frontmatter、链接目标内不查 |
| P2 | 标点后没有空格 | 标点是块尾最后一个字符时不查; 小数 `3.14` 与文件名 `a.mjs` 不查 |
| P3 | 正文行以 `. , ; : !` 收尾 | 标题、表格行、列表项的 `-` 前缀不参与此行尾判定 |
| P4 | 句子被折成多行 | 列表项、逐行结构 (表格/时间线) 各自成块, 不参与 |
| P5 | 正文行以 `. , ; : !` 开头 | 同 P3 |

## 自动修复

```bash
uv run <this-skill>/scripts/prose_rules.py --fix <skill-dir>   # 就地改写
```

它做三件事: 全角转半角、标点后补空格、把被折行的段落合并回一行. 改完必须重跑 `--check`并且**逐块比对合并前后的语义**  合并是重排, 不许顺带改字

## 不适用

- frontmatter、围栏代码块、行内代码、URL、链接目标: 一律原样保留
- vendored skill 的正文 (上游同步的三方合并代价大于收益): 在它的 note 里写清豁免理由
- 引用的第三方原文: 保持原样, 不要为过门禁改别人的话
