# 目录分类学: 三层语义与切分维度

这份文件规定**目录树该长什么样**. 单篇笔记该去哪由 [decision-matrix](decision-matrix.md) 判定; 这里管整棵树的形状.

## docs/ 树给的经验 (实测)

站点另一棵树 `docs/` 有 929 篇, 结构是稳定的三层:

```text
docs/
  0NN-大类/          L1 学科: 程序语言 / 数据库 / 中间件 / DevOps与版本控制 / 游戏引擎 / 嵌入式 …
    0NN-领域/        L2 具体技术: C++ / Java / Python / Redis / MySQL / Linux / ROS …
      0NN-文章/      L3 文章目录, 内含 index.md
```

可复用的三条:

1. **每层职责单一.** L1 是哪个学科, L2 是哪个具体技术, L3 就是文章本身. 没有哪一层只是容器.
2. **层级跟着内容长.** 实测 " + o("docs/") + " 的深度分布是 3~7 层 (L3:78 / L4:278 / L5:344 / L6:206), 它并不追求全树同深度 —— 需要细分的地方就往下长 (虚幻引擎/蓝图/第一章/文章), 不需要的就停在两层. **深度是结果, 不是目标.**
3. **大类少而稳.** 只有 11 个 L1, 且不轻易新增.

它的反面教材 (别学): `docs/010-面试/` 把散装 `.md` 直接放在分类下, 没有 `index.md`; 另外它的 L2 有时是技术 (C++), 有时是用途 (第三方库), 有时是活动 (刷题), 同类不同级.

## 切分维度: 什么能当大类

**唯一合法的切分维度是「这是什么知识」.** 其它维度一律不能拿来分大类:

| 维度 | 能否当分类 | 例 | 为什么 |
|---|---|---|---|
| 学科 / 领域 | **能** | 编程语言、LLM与Agent、浏览器验证与AI逆向 | 读者按「我想找哪个方向」导航 |
| 知识来源 | 不能 | 项目学习、视频笔记、论文 | 同一来源的东西彼此无关, 分类名对读者没有导航价值 |
| 体裁 | 不能 | 想法探索、教程、踩坑记录 | 体裁是 tag 该管的, 不是位置 |
| 时间 | 不能 | 2026-09 | 那是 `blog/` 的结构, 不是知识库的 |

**判别法: 这个产品背后是什么机制?**

产品**可以**当目录, 但**不能当第一层**. 它必须先归到一个机制大类下, 再作为该类的一个实例存在.

| 层级 | 放什么 | 例 |
|---|---|---|
| L1 大类 | **机制 / 学科** | `003-Agent-Harness` |
| L2 实例 | **具体产品 / 实现** | `DSH` / `Codex` / `Claude-Code` |
| L3 文章 | 笔记目录 | `001-DSH-Agent-Loop源码剖析` |

这和 `程序语言/C++/` 是同构的: **C++ 也是「程序语言」的一个实例** —— 没有人会因此说「C++ 不能当目录」.

```text
002-AI/
  003-Agent-Harness/        机制层
    DSH/                    实例层
      001-Agent-Loop源码剖析
      002-Runtime设计思想
    Codex/                  以后新写
    Claude-Code/
```

自问三句:

1. **这个产品背后是什么机制?** 答不出, 说明还没想清楚它属于哪.
2. **这个机制下还有别的产品吗?** 有 -> 产品该是机制的子层, 不是平级.
3. **它的上级会不会变?** DSH 会改名或被替代, 但「Agent Harness」不会 —— 所以大类用后者.

**反例**: 直接建 `003-DSH` 并在其下放文章, 就永远说不清它为什么和 `002-Agent架构` 平级; 建 `004-Multica` 则盖住了「多智能体协作」这个更大的概念.

**混维度是分类失控的头号原因.** 一旦「A 类按学科分、B 类按体裁分」, 读者就无法预测任何一篇该在哪. 检查一棵树是否健康: 它的 L1 列表能不能被一个问题问完 —— 「你想找哪个方向的知识?」 答不上就说明混了维度.

## 三层定义

```text
ai-docs/
  00N-大类/            L1  学科或机制. 5~8 个, 稳定, 新增需人类同意
    00N-领域|实现/     L2  具体技术、子方向, 或产品的具体实现 (C++ / DSH / Redis)
      00N-文章/        L3  文章目录, 内含 index.md + 侧车
```

- **L3 是文章**: 一个目录一篇笔记, 正文固定 `index.md`, 侧车与它同目录.
- **L2 是领域**: 只有 1 篇的 L2 是**伪结构信号**, 不是绝对禁止 —— 如果它是一个真实存在、预期会长的子方向, 保留; 如果只是为了整齐而挖的坑, 把文章上提一层.
- **L1 是大类**: 不要为 1~2 篇开一个大类 —— 先问它能不能并进已有大类.
- **禁止容器层**: 把真正的学科再压一层的中间层 (如按「知识沉淀」再分一层) 没有信息量, 应当去掉, 让学科直接当 L1.
- **root 名字要短**: 根目录是读者最先看到的一屏, 名字长度直接决定它能不能一眼扫完. 用「AI」「程序语言」「工具链」这种 2~4 字的词, 不要用「浏览器验证与AI逆向」这类复合长名 —— **复合长名是「两个方向被硬捏在一起」的信号**, 应当拆开各自归位.

## 两种合法形态

```text
大类/文章/index.md            该大类只有 1~2 篇时, 省掉 L2
大类/领域/文章/index.md        该领域有 ≥2 篇时
大类/机制/产品/文章/index.md   按机制分了, 且同一机制下会有多个产品时
```

同一个大类里, 有的分支走两层、有的走三层是**正常**的 (取决于该分支有没有真实存在的子领域). 需要警惕的不是深度参差, 而是**同一个主题在树里出现两种深度** —— 那说明有一批文章还没想清楚该归属哪一层.

## 深度不一致怎么读

体检看到深度分布超过两种时, 不要直接压平, 先分辨原因:

| 症状 | 含义 | 处理 |
|---|---|---|
| 某领域下只有 1 篇, 所以少一层 | 伪结构 | 把文章上提一层 (B 档) |
| 同一个主题分散在不同深度 | 该领域边界没定 | 先定这个领域的 L2 清单, 再统一归位 (B/C 档) |
| 多出一层容器 | 历史遗留 | 删容器, 整体上提 (C 档) |

## 前缀与命名

- L1 / L2 / L3 都用三位前缀 `NNN-`, 从 `001-` 起.
- 名字里**不含空格与等号**, 用中文或连字符连接.
- 重命名只改前缀之后的字符, 并同步修链 (见 [migration](migration.md)).
- 回收编号: 删掉某个分类后**不要**把后面的编号往前挪 —— 挪动会让相关 URL 一起变. 留空洞是可接受的.

## 应用: 怎么读现在的 ai-docs

按上面的规则, 现在的 `ai-docs/` 有三类结构问题 (具体清单以每次体检结果为准):

1. **容器层**: 有一个把 编程语言 / LLM与Agent / 浏览器验证 等本应是 L1 的学科压在第二层的中间层.
2. **混维度**: 「按来源分」的分类 (项目学习) 与「按学科分」的分类平级 —— 两者不是同一个维度.
3. **体裁当大类**: 若「想法探索」这类体裁分类与学科分类平级, 就是体裁与学科平起平坐.

**这些改动的档位**: 去掉容器层、把学科提为 L1、拆掉按来源分的分类 —— 全是 **C 档**, 必须逐条申请. 本文只给判据, 不代替人类拍板.
