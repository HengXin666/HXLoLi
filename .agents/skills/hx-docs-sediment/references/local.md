# 本地变更沉淀 (code / git / 脚本配置)

适用于: 本仓库或本机的代码改动、git 历史、脚本与配置调整带来的经验沉淀.

## 链路

1. **找变更**: `git log` / `git diff` / `git show <sha>` / `git status` 定位"改了什么"; 未提交的改动同样可以沉淀.
2. **读源码确认**: 打开相关文件确认实际行为. **禁止**只凭 commit message 或 diff 摘要推断实现细节.
3. **提炼三层**:
   - 动机: 为什么要改 (原来的做法坏在哪)
   - 决策: 为什么这么改 (被否决的方案与代价)
   - 代价与验证: 新做法的限制、怎么验证有效
4. **关联 commit**: 在正文里给出 commit URL.

   ```markdown
   [`50c931c`](https://github.com/<owner>/<repo>/commit/<full-sha>) — [feat] 实现了串行调度器 (生命周期敏感)
   ```

5. 回到固定契约: 模板初始化 → 成文 → 标点检查 → sidebar 注册.

## 关键约束

- **结论必须有代码依据**: 每条论断能指到 `文件:行` 或 commit hash. 指不到就不写.
- **踩坑才是核心价值**: 只写"做了什么"等于看 diff; 要写清"哪一步本以为对、实际错在哪、怎么发现的".
- **区分事实与判断**: 代码现在是这样 (事实) vs 我认为该这样 (判断), 不要混.
- **读者定位必须先谈清**: 本地变更最容易写成"只有作者看得懂"的流水账. 动笔前按 hx-docs-grill 确认: 读者是未来的自己? 团队? 还是要教一个外部读者复现?
- 私有仓库的路径、内网地址、凭据不要出现在正文.

## 适合沉淀的信号

- 同一个坑踩了第二次
- 做了非显然的取舍, 半年后自己会忘记理由
- 踩坑过程能推广到别的项目 (可复用方法论)
- 与已有笔记形成"上篇/下篇"关系

反之, 单纯的格式化改动、依赖升级、配置同步, 不值得单独成篇.
