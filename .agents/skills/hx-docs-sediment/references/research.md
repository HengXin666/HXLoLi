# 调研模式沉淀

适用于"调研一下 / 对比一下 / 业界怎么做的"这类需要多源交叉的任务. 与单篇定向沉淀的区别: **先建证据, 再下结论**.

## 链路

1. **界定问题**: 把"调研 X"收敛成可回答的具体问题 (范围、时间、要对比的维度). 问题太宽就先问人类.
2. **多源采集**: 用 `wide_research` 做多轨并行调研 (自带来源账本与不确定度披露); 单点补充用 `argo_search` / `argo_fetch`.
3. **交叉验证**: 同一结论至少两个独立来源; 只有一个来源的标注为单源.
4. **先出结论表, 再沉淀**: 把"结论 / 依据 / 可信度 / 反例"列成表给人类确认, **确认后再写笔记**.
5. 沉淀时回到固定契约: 模板初始化 → 成文 → 标点检查 → sidebar 注册.

## 证据分级 (写进笔记时必须能区分)

| 级别 | 含义 | 写法 |
|---|---|---|
| 共识 | 多个独立来源一致 | 正常陈述 |
| 单源 | 只有一个来源, 未复核 | 明确写"据 <来源>" |
| 推测 | 由证据推出的判断 | 标为个人判断 |
| 未知 | 查不到 | 写"未找到公开资料", 不要填空 |

- **厂商宣传不是事实**: README / 官网 / 发布会说法要标为"官方声称", 与第三方评测分开.
- **区分版本**: 结论要带版本号或时间点, 否则半年后就是错的.

## 与"沉淀笔记"的关系

- 调研的中间产物 (原始抓取、对比表、来源清单) 放 `research-output/`, 它是**过程目录, 不是交付物**.
- 正式交付永远是 `ai-docs/` 下的笔记; **不要把 HTML/报告丢在 research-output 里当成品**.
- 调研结论进正文时, 末章引用只列真正用到的来源, 不要把来源账本整份搬进去.

## 反模式

- **只列不判**: 罗列十个项目的功能对比, 却不给结论 → 读者要的是判断, 不是清单.
- **均等化对待**: 把一周更新一次的玩具项目和成熟项目并列 → 必须标注成熟度与维护状态.
- **忽略反面证据**: 只收支持预设结论的材料 → 主动找反例, 并写进笔记.
