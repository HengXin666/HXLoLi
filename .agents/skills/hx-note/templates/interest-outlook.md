# 模板: 兴趣&展望 (默认)

读者是**带着好奇**来的。任务: 读完想去试一试。

## 槽位表

| 槽位 | 上限 | 必填 | 渲染成什么 |
|---|---|---|---|
| 引入 | 50 字 | ✅ | `# 标题` 下面的第一段, **不带小标题** |
| 正文 | 不限 | ✅ | 多个 `## 0xNN <具体内容标题>` |

## 引入

50 字以内, 一段, 没有小标题。

### 唯一的硬判据: 那件事在动笔之前就发生过

动笔前自问一句:

> **这个引入写的那件事, 在我决定写这篇文章之前就发生过吗?**

- 答「是」-> 引入落在真实的遭遇上, 可以写。
- 答「不, 是我为了开头想的」-> **倒推的, 重选。**

这条比下面所有格式要求都重要, 因为**它是唯一一条形式检查抓不到的**。实测对照过:
有一版引入写的是「我为什么做这件事」(落点真实、第一人称、句长 26 字、没有套话),
形式上全部合格, 但作者读起来仍然觉得「写不出来这种内容」。

**反例的形状**: 交代动机 -> 形式全过 -> 读者仍觉隔一层。凡是"先定主题、再找一个合适的
入口"的引入, 都是这个形状 —— 不必记具体那几句话, 认形状就够。

差别在因果方向:

```
作者的引入: 遇到事 -> 有情绪 -> 写下来        (情绪是输入)
倒推的引入: 决定写文 -> 找个合适的情绪 -> 写  (情绪是装饰)
```

作者 40 篇手写引入里, 感叹/欢呼出现 29 次、具体时间地点 19 次、情绪词 14 次 ——
因为那些文章都是**先有遭遇**。倒推的引入即使写得好, 读者也会觉得隔一层, 但说不出为什么,
因为它不是某句话的特征, 是整篇的来路。

**推论: 选题顺序要反过来。** 从**已经积累的遭遇**里挑一篇来写, 不要先定主题再回找入口。
「为了某个主题硬写」写不好的原因不是文笔, 是那件事没真的发生过。

### 格式要求 (都过不了上面那条时, 先别管这些)

**必须**:

- 第一人称, 写"我为什么会碰到这个问题"。
- 落在 `[用户画像]` 里**真实存在**的项目或调研方向上。挑一个真的会碰到这个问题的。
- 具体到能被反驳: 说清卡在哪, 而不是说"这很重要"。

**禁止**:

- 把画像念一遍: `最近我在做 A、B、C, 而这篇讲 D`。
- 设问式开场 (`当一个系统反复向你证明…时, 它到底在看什么?`) —— 这是旧模板的固定套路,
  现有 29 篇 ai-docs 全都这么开头, 已经成了指纹。

**关于第二人称**: 不是一律禁止, **看它后面有没有具体场景**。

```
可以 (笔吧评测室的真实开场):
  你有没有这种经历啊, 一直在用的电脑包旧了, 想换个新的。
  打开电商页面, 一时竟然想不出来该搜什么关键词, 那就搜个电脑包吧,
  各种结果琳琅满目, 每一款看着都不一样, 但仔细看看, 好像又都一样。
  -> 紧接着给了三个具体动作, 读者能对上号

不行:
  相信你也遇到过 / 如果你也在搞 X / 你最近在做…
  -> 没有场景, 只是招呼
```

**关于"预告目录"**: 同样不是一律禁止。教学向的视频常这么开场 (灵茶山艾府:
「首先我会讲…然后对比…接着…最后…」), 它让读者先知道**这趟值不值得跟**。
但写成 `本文将介绍…` 这种公文腔就不行 —— 差在**说的是"我要讲什么"还是"你能拿到什么"**。

**判据统一成一句**: 引入里出现的每一句话, 后面有没有**具体的东西接着**?
有 (三个动作 / 一份清单 / 一个数字) 就成立; 没有就是凑字数。

画像里**找不到**真实关联时, 就写一个具体的技术困惑当切入, 并在对话里告诉人类
"这篇没找到和你近期项目的真实关联, 引入段用了 X, 要不要换"。**编造的共鸣比没有共鸣更伤。**

参照作者自己的开场:

```
因为最近要写简历, 但是之前用那个破平台, 写的有水印. 而且不好用. 还有那个数量限制. 所以决定自己做一个.
```

## 正文

小标题用 `## 0x00` `## 0x01` …, 每个标题是**具体内容**, 不是 `## 正文`, 也不是
`## 核心结论` `## 关键细节` 这种模板残留。

每个 `## 0xNN` 段必须至少有**一个可验证物**: 代码块 / 图 / 命令 / 具体数字。
一段从头到尾只有形容词, 就是没讲清。

### 两条跨素材验证过的内容判据

拿三种不同领域的真人素材对照过 (算法教学 / 硬件评测 / 技术直播), 它们的**手法各不相同**,
但只有两条是共有的。**其余风格差异不要当规则** —— 把某一种的细节写成规范, 就会把另外两种判为不合格。

**一、取舍要说清.**

做了什么简化、为什么简化、代价是什么 —— **说全, 但不道歉**。

```
灵茶山艾府 (顺带提了整数溢出):
  那对于 java c++ 这些语言来说呢, 这里的加法可能会有溢出的问题。
  那待会讲代码的时候呢会讲怎么解决。

笔吧评测室 (主动划边界):
  先声明一下啊, 本期视频并不是什么电脑包具体型号的大横评啊,
  毕竟呢服饰、箱包这类产品型号太多了, 更新换代也快, 根本测不过来。
  我想做的是一期授人以渔的选购指南。
```

反面写法: 要么不提 (隐瞒取舍), 要么写「为篇幅所限, 此处略去」这种套话。
**读者能接受你有取舍, 不能接受你假装没有。**

**二、给读者能带走的东西.**

不只是一篇讲完就结束的内容, 而是一个**能用在别处的概念或方法**。

```
灵茶山艾府: 那这这个我把它叫做循环不变量。
            -> 读者带走一个名词, 能用在别的二分题上

笔吧评测室: 我想做的是一期授人以渔的选购指南。
            -> 明确说"学会看维度, 比记住型号有用"
```

反例: 只解决眼前这一个问题, 读者看完学不到能迁移的东西。

### 书面文章的四条手法 (与口播不同, 别混用)

拿**真人写的技术文章**对照过 (edsionte 内核博客 / 博客园 luconsole / LittleHann / CSDN)。
**口播的多数手法在文章里不成立** —— 原因见下, 先记住这条, 免得照搬。

**一、开场给「背景 + 问题 + 思路」三件套, 不寒暄.**

全文可以很短。edsionte 那篇 1533 字讲完一个完整问题, 开头三句就交代完:

```
背景
在Linux内核中，已知一个进程的pid和其打开文件的文件描述符fd，如何获取该文件的绝对路径？
基本思路是先获取该文件在内核中的file结构体，再通过d_path()获取到整个文件的绝对路径。
```

没有「本文介绍」、没有「随着…的发展」、没有目录。

**二、小标题要短。4~17 字, 名词短语, 不要写成句子.**

```
作者手写 (中位 8 字):
  7 字   与 AI 斗智斗勇
  4 字   修复过程
  8 字   2.1 小组的管理
 10 字   0.4 交流的推荐方式

真人技术文章 (16~18 字, 已经是上限):
  <1> inline hook 是什么
  <2> inline hook 基本原理
  <4> inline hook 线程安全
  <5> inline hook 推荐库
```

**不要写成完整句子。** 下面是踩过的坑 —— 我按「用想做什么的说法」推成了整句, 结果 20~31 字,
比真人上限还长一倍:

```
差:  ## 0x03 想知道 server 支持哪个版本、能干什么, 就问 server/discover
差:  ## 0x04 想让 AI 动手就 tools, 想喂数据就 resources, 想套问法就 prompts
好:  ## 0x03 版本与能力发现
好:  ## 0x04 三个服务端原语
```

「用想做什么」指的是**角度** (从用途切入, 而不是从术语定义切入), **不是长度**。
标题就是标题, 不是句子 —— 你翻任何一本书都能看到这一点。

**三、正文开头从一件具体的事入手, 不要从定义串联开始.**

```
差 (定义串联 —— 读者不知道为什么要知道这些定义):
  MCP 里有三个名字: MCP Host、MCP Client、MCP Server. Host 是那个 AI 应用本身,
  负责协调和管理一到多个 client. Client 是 host 为了连某个 server 现造出来的对象…

好 (从一件能想象的事入手, 定义是解释它时带出来的):
  VS Code 连上 Sentry 之后, 又连了本地文件系统. 这两条连接互不知道对方存在.
  它们在 VS Code 里面是两个独立的东西: 连 Sentry 时造一个, 连文件系统时再造一个.
  所以 MCP 里的三个名字是这样分工的: VS Code 本身叫 host, 它为每个 server 现造的
  那一个叫 client, 对面提供东西的程序叫 server.
```

**这条最容易漏**: 把小标题改成「想做什么」之后, 人容易以为开头也改好了 —— 其实开头可能
还是定义串联。**判据**: 第一段有没有出现一件**读者能想象出画面**的事 (连了两个 server、
报了个错、量了一次)。没有就是定义串联。

**四、给两种以上做法, 并说清各自适用条件.**

```
edsionte:
  方法一 ... 如果理解了进程和文件系统数据结构之间的关系，那么这种方法可以采用。
  方法二 ... 使用比较简单，程序更加安全，不过就是少了对数据结构关系的思考过程。
```

不推单一解法, 而是**摆出选择 + 代价**。读者自己要哪种, 自己判断。

**五、结尾允许一句态度, 不必强行收束成总结.**

```
其实也可以将 fget() 函数的实现过程作为参考，欣赏内核中代码实现的严谨性。
```

「欣赏内核中代码实现的严谨性」是作者自己的态度。**不要改成「综上所述」。**

### 口播手法为什么不写进这里

从技术直播/教学视频总结过七条手法 (接住困惑、自问自答、失败讲成交互、用问题引出动作、
报菜单…), 但**逐条核对后只有两条在文章里成立** (就是上面那两条内容判据)。

原因是**媒介差异**:

| | 口播 | 书面 |
|---|---|---|
| 读者能否回看 | **不能** | **能** |
| 所以讲者要做的 | 一路确认对方跟上了 | 直接给结构 |
| 表现 | 自问自答、接住困惑、反复确认 | 背景+思路三件套、给选择 |

**把口播习惯写进文章规范, 等于把「陪着听众走」硬塞给可以自己走的读者。**
所以模板只收两条内容判据 + 这四条书面手法。

硬约束:

- **禁止表格.** 需要对照就用带分组名的代码块或图。确实非表格不可时, 向人类申请,
  并说明为什么行文讲不清 (`lint --allow-table` 才放开)。
- **禁止大段文本.** 连续纯文字不超过 4 行, 超了就拆段 / 插图 / 给代码。
- **代码块必须带标题**: ` ```cpp [组名-标题] `。同前缀的块会被合并成 tab 组, 所以
  **不同主题必须用不同前缀**, 否则两段无关代码会被并进同一个切换组。
- **必须有图**, 且每张图在正文里被一句话引用 ("上图里第二层就是…")。
  纯装饰的图不要放。
- 深层细节放 `> [!TIP]` 块, 主线保持初学者能跟 (见 `references/layering.md`)。

配图怎么来、drawio 怎么生成、生图后端怎么选见 `references/media.md`。

## 展望

50 字以内, 接在最后一个内容段末尾, **不要单独起一个 `## 展望`**。

**必须**:

- 针对一类**抽象领域**的走向 (这类机制接下来往哪走), 不是某个具体细节的改进计划。
- 和 `[用户画像]` 里的调研方向有真实关联。
- 是判断, 所以要能被反驳。

**禁止**:

- `个人判断:` / `我倾向于认为` 开头 —— 现有 ai-docs 篇篇如此, 已经是指纹。
- `未来可期` / `前景光明` / `值得期待` 这类空洞收尾。
- 把局限和待办写成给读者的道歉。待办写进 `.hx-mitemite.md`。

作者真实的收尾长这样, 学它的**短**和**不端着**:

```
感觉不错, 反正也算是一种推荐. 感觉有意思就再看一次就完事了~
```

## 这个模板拒绝什么

- **API / 配置速查**: 那种内容适合表格和穷举, 与本模板的"禁表格 + 讲故事"冲突, 直接写进 `docs/`。
- **纯故障复盘**: 用 [problem-solution.md](problem-solution.md)。
- **没有真实素材的主题**: 本模板的所有事实都必须能在 `.hx-info.md` 里找到依据。
