# 调研模式沉淀

**与单篇定向沉淀的区别: 先建证据, 再下结论.**

## 固定路线

1. 把「调研 X」收敛成可回答的具体问题 (范围、时间、要对比的维度). 太宽就先问人类
2. 多源采集. 按能力选工具, 不认工具名: 会话里有多源调研工具 (自带来源账本的那一类) 就用它; 没有就用检索工具找候选, 再按 `article.md` 的抓取探测表逐个抓正文
3. **先找 T1, 再补 T2, T3 只当线索**. 每个核心论断都要回溯到一手来源
4. **先出结论表给人类确认, 确认后再写笔记.** 表列: 结论 / 依据 / 可信度 / 反例

## 来源等级 (provenance 每个来源必须标一个)

| 等级 | 是什么 | 正文里怎么写 |
|---|---|---|
| T1 一手 | 规范 / RFC / 标准组织文档 / 官方文档 / 源码 / 论文 | 直接陈述, 带小节号 |
| T2 权威二手 | 维护者或核心作者的文章, 知名机构的评测, MDN 这类长期维护的参考站 | 写「据 某某」 |
| T3 社区 | 论坛, 个人博客, 问答, 视频 | 只当线索, 不当依据; 结论必须另找 T1 或 T2 |

## 广度门槛 (`done collect` 机械检查, 也可单独跑 `hx_flow.py sources --slug <slug>`)

对 `--kind article` 与 `--kind research` 生效

- 全稿至少 3 个独立来源
- 至少 1 个 T1 来源
- `material.md` 里每条要点至少引 1 个 T1, 或 2 个不同的 T2. 只引 T3 的要点不算数
- `material.md` 有 `## 反例` 一节, 至少 1 条反例或反对意见

格式

```markdown [provenance-来源表]
| 编号 | 来源 | 等级 | 获取方式 | 获取时间 | 实际读的 URL |
|---|---|---|---|---|---|
| S1 | RFC 9111 HTTP Caching | T1 | curl 纯文本 | 2026-11-01 | https://www.rfc-editor.org/rfc/rfc9111.txt |
```

```markdown [provenance-要点引用]
- 新鲜度判定只比较新鲜寿命与当前年龄 [S1 §4.2]
```

## 证据分级 (写笔记时必须能区分)

| 级别 | 写法 |
|---|---|
| 多源一致 | 正常陈述 |
| 单源未复核 | 明确写「据 <来源>」 |
| 由证据推出的判断 | 标为个人判断 |
| 查不到 | 写「未找到公开资料」, 不要填空 |

## 人类踩过的坑

- **厂商宣传不是事实**: README / 官网 / 发布会说法标为「官方声称」, 与第三方评测分开
- **结论要带版本号或时间点**, 否则半年后就是错的
- 中间产物 (原始抓取、对比表、来源清单) 放 `research-output/`  那是**过程目录, 不是交付物**. 正式交付永远是 `ai-docs/` 下的笔记

## 反模式

只列不判 (罗列十个项目却不给结论); 均等化对待 (玩具项目和成熟项目并列, 必须标维护状态); 只收支持预设的材料 (要主动找反例, 所以门槛里要求 `## 反例` 一节)
