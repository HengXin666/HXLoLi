# frontier 操作细则与完整示例

SKILL.md 给出机制; 本文件回答"这一轮到底该问什么、问几个、怎么写".

## 一、怎么建树

1. 先写下一句**根目标**: "这篇笔记要让人相信/学会 ___".
2. 从根目标岔出第一层决策 (通常 2~5 个), 例如: 读者是谁 / 素材范围 / 主线论点 / 呈现形态.
3. 对每个决策问: "要回答它, 必须先知道什么?" 那些"必须先知道的"就是它的子节点.
4. 只把**前置已闭环**的节点标为 frontier.

不要预先展开整棵树 —— 树会随着回答长出来. 展开太深只会问出基于猜测的下游问题.

## 二、本轮该问几个

没有固定数量, 判据只有一条: **这题现在问, 需要猜测别的未决答案吗?**

| 情况 | 处理 |
|---|---|
| 两个问题互不依赖 | 同一轮一起问 |
| B 的答案取决于 A 的答案 (A 本轮未决) | A 本轮, B 下一轮 |
| 问题需要环境事实 | 自己查 (可派 sub-agent), 不作为问题; 只有查完的结论需要人类拍板时才成为决策题 |
| 人类已经答过 / 事实已经明确 | 不问, 直接当作已知事实使用 |

一轮里塞进大量互相依赖的问题, 会让人类无法回答; 一轮只问一个互不依赖的问题, 是浪费会谈.

## 三、推荐答案写到什么程度

推荐答案必须是**可被否决的具体主张**, 不是"看情况". 好的推荐答案包含:

- 具体选择 (不是选项罗列);
- 一句理由, 指向上下文/事实/工程常识;
- 如果推荐有代价, 明说代价.

```
❓ **Q1** - **主线该聚焦"机制"还是"用法"**: 原文既讲了 Turnstile 的检测维度, 也给了现成脚本用法.

➡️ 推荐聚焦机制 (检测面建模), 用法只在结尾点一句. 理由: 这类工具用法几周就会过期, 而"系统在检测什么"是可复用判断; 与本栏已有 003/004 两篇形成互补而非重复.
```

反例 (等于没给推荐): "➡️ 看你想强调哪方面, 两种都可以."

## 四、人类回答后做什么

1. **复述**: "所以约束更新为: 正文只讲机制, 脚本用法不进正文." 这一步防会错意.
2. **重算 frontier**: 哪些节点的前置刚刚闭环, 它们现在可以问了.
3. **判断是否还需要下一轮**: frontier 为空就直接进入成文, 不要为了"问满 6 轮"而凑问题.
4. **落盘下一轮**: 用 `hx_mitemite_add.py` 或手写, 只写本轮新问题.

## 五、完整一轮的样子

```markdown
先给出当前阶段性成果: 一句话主线 + 三个二级标题草案 (略).

❓ **Q1** - **读者定位**: 这篇主要写给"想自己写脚本过盾的人", 还是"想理解风控在看什么的人"?

➡️ 推荐后者. 理由: 前者与网上大量教程同质, 且会很快过期; 后者是本栏 001~004 的一条暗线.

---

❓ **Q2** - **是否包含可运行的绕过脚本**: 正文要不要贴完整代码?

➡️ 推荐不贴完整脚本, 只贴关键判定片段. 理由: 完整脚本会成为维护负担, 且与"讲机制"的主线冲突; 需要跑通的人可以去看原文仓库.

---

❓ **Q3** - **结尾要不要展望**: 是否加一段对"检测面会怎么演进"的判断?

➡️ 推荐加, 但控制在 3 句内, 且明确标注为个人判断而非事实.
```

## 六、常见走偏

| 走偏 | 症状 | 纠正 |
|---|---|---|
| 问卷式 | 一口气抛出 10 个问题, 全都不带推荐 | 每个问题必须带推荐答案; 超出 frontier 的移到下一轮 |
| 挤牙膏 | 每轮只有一个互不依赖的问题, 拖十几轮 | 同一 frontier 的问题合并到一轮 |
| 替人决策 | 直接把"我认为应该是 X"写进正文 | 决策必须显式交给人类并等待 |
| 问事实 | "请告诉我这个 PR 改了什么" | 自己能查的一律自己查 |
| 无终点 | 问题永远问不完, 从不落笔 | frontier 为空即停止追问, 进入成文 |
