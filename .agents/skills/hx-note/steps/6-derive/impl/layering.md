# 分层: 初学者读得懂, 精通者不觉得无聊

## 这是一个矛盾目标, 所以必须用结构解决

"降低门槛"和"有深度"在**同一条文字线**上是互斥的: 补足够的前置知识会让懂的人划过好几屏, 不补则新人看不懂. 靠"写得通俗一点"是解决不了的

解法是**分两层**, 让两类读者走不同的路径

```
主线 (正文段落)  -> 初学者能一路读完, 不需要跳转
支线 (> [!TIP])  -> 精通者才会点开的深层细节
```

判据: **把所有 `> [!TIP]` 块删掉, 主线仍然完整成立. ** 不成立就说明该进主线的东西被藏进了支线

## 门槛定在哪

`[用户画像]` 给出的读者是**作者本人和他这个水平的人**. 所以

- **可以直接用**的概念: 画像里出现过的方向、作者项目里用过的技术、他 `docs/` 里已有笔记的内容 (可以直接双链过去, 不必重讲)
- **必须解释**的概念: 跨领域的术语、素材原文引入的新名词、需要背景才能理解的前提. 解释放在**第一次出现的地方**, 一句话, 不要单开一节"预备知识"
- **不要解释**的东西: 编程语言基础语法、常识性工具用法. 解释这些就是在侮辱读者, 也是 AI 味的一种 (机器倾向于把所有东西都铺一遍)

## 主线怎么写

1. **从一个具体场景开始, 不从定义开始.** 先给"要解决什么", 再给"它叫什么". 反过来写就变成教科书
2. **一次只引入一个新概念.** 一段里出现两个新名词, 初学者就断了
3. **每个概念给一个可验证物**: 一段代码、一个数字、一张图. 抽象说明后面不接可验证物, 读者无法判断自己有没有懂
4. **不要预告也不要回顾.** `下面我们将看到` / `如前所述` 都是凑字

## 支线 (`> [!TIP]`) 放什么

按价值排序

- 实现细节、边界条件、性能数字
- 和另一种方案的对比 (对比是精通者最想看的)
- 为什么**不**这么做 (被否掉的路径)
- 版本差异、编译器差异、平台差异
- 可以往下挖的入口 (源码位置、规范条款号)

反过来说, `> [!TIP]` **不放**: 名词解释 (那属于主线一句话)、免责声明、待办事项(待办进 `.hx-mitemite.md`)

仓库里 `> [!TIP]` / `> [!NOTE]` / `> [!WARNING]` 已有大量真实用法 (29 个文件), 风格拿不准时去看 `docs/` 下的既有笔记

## 让精通者不觉得无聊的三个具体做法

1. **给出一个他大概不知道的事实.** 素材里最具体的那个数字/反例/边界, 一定要留在文里  它是全篇唯一无法被"我大概懂"替代的东西
2. **写出取舍, 不只写方案.** "为什么不用 X" 比 "Y 怎么用" 有价值得多
3. **承认没搞清的地方.** 标 `[不确定]` 并说明卡在哪. 精通者会因此相信文章其余部分. 现有 ai-docs 通篇自信 = 通篇不可信

## 反面清单

| 写法 | 问题 |
|---|---|
| `## 预备知识` 单开一节 | 初学者被劝退, 精通者被迫翻页 |
| 每个术语都加括号英文 | 第一次给就够了 |
| 主线里塞性能数字和版本差异 | 打断叙述, 应进 `> [!TIP]` |
| 支线里放名词解释 | 初学者恰恰需要它在主线 |
| 通篇一个难度 | 说明没分层, 只是在写平均值 |
