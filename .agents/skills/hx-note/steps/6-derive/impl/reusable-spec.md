# 可复用规格: 让笔记能被照着用

## 什么时候写这一节

素材本身就是**一套可照做的做法**时 (外部项目的实现方式 / 自己刚搭好的一套约定 / 一套工程流程)。
判据只有一条:

> 读者拿着这一节, 能不能在自己的项目里得到**同样的结果**?

答"不能, 但能大概明白原理" -> 这一节不该写, 这篇笔记是"讲解"不是"规格"。
答"能" -> 光写原理不够, 必须把**照做所需的一切**摆出来。

这一节是 `index.md` 里唯一**不派生自 `.hx-info.md` 而派生自素材本身**的部分, 所以它的事实
仍要回写进 `.hx-info.md` (见 `steps/3-atom/impl/rules.md` 第七节), 只是叙述方式换成了规格。

## 为什么用 skill 的结构写

一个 skill 之所以能被反复使用, 靠的不是文字质量, 是它的结构: 触发条件、契约、约定、偏好。
**规格缺任何一层都会退化成"读过就忘"**:

| 缺 | 症状 |
|---|---|
| 触发层 | 读者不知道什么时候该用它, 于是永远不用 |
| 契约层 | 照做到一半发散, 每个人得到不同结果 |
| 约定层 | 每个项目重新选一遍库和布局, 规范等于没有 |
| 偏好层 | 代码能跑但风格杂乱, 下一个接手的人重写一遍 |

所以规格按这四层写。**层与层不能混**: 契约是不能变的, 约定是已选定的, 偏好是风格习惯 ——
把它们混成一段话, 读者就分不清"哪条必须遵守、哪条可以换"。

## 第一层: 触发场景

一段话, 写清**这套规格用在什么项目上**。要能被反驳:

    ✅ 这套规格给"单个应用外壳 + 若干设置页"的桌面式 Web 界面用; 纯内容站不适用.
    ❌ 适用于各种前端项目.

## 第二层: 契约 (不能变的)

契约的定义是: **换掉它, 整套做法就失效**。写成可直接验证的形式:

- 入口命令 (如 `npm run gate`) 与它必须通过的退出码;
- 需要 import 的唯一来源 (设计令牌 / 契约常量 / 通道名);
- 目录骨架与文件命名;
- 每条硬约束对应的**机械判据** (能跑、会失败)。

**这一层里每一条都要给判据。** 只写"禁止硬编色值"是文字规范, 写成校验脚本里的一条正则
才是契约 —— 前者每次只被遵守一部分, 而且**违反时没有任何反馈**。

## 第三层: 约定 (已选定的选择)

同一件事有多种做法时, 这套规格**已经替你选了一个**。要写清选了什么、以及为什么,
读者才能判断自己该不该换:

| 要定死的 | 写成什么 |
|---|---|
| 标准页面的骨架 | 每个页面都长什么样 (头部 / 左栏 / 内容区 / 空态), 给出可复制的组件树 |
| UI 库 | 一个来源, 不并列。列**唯一来源 + 版本** |
| 目录与分层 | 基础件放什么、版式件放什么 |
| 状态与数据流 | 状态放哪一层, 放大还是放近 |

**约定层不许写"可以选 A 也可以选 B"。** 那是没定。真要保留两个, 就说明各自的代价与切换成本。

## 第四层: 偏好 (写法习惯)

这一层最容易被漏, 也最影响复用 —— 它决定"别人照着做出来的东西像不像"。

**每一条偏好都要写成可检查的禁令**, 而不是"注意规范":

| 偏好 | 可检查的写法 |
|---|---|
| 格式化统一 | 给出配置文件全文与命令, 不写"保持风格一致" |
| 每个组件都有类型 | 开 `strict`; 组件 props 必须有显式 interface, 不许 `any` |
| 函数与注释 | 导出的函数一律显式返回类型; 注释只写"为什么", 不写"做什么" |
| **每个页面必须有自己的 URL 路径** | 一个根组件用 state 切页面 = 违反。判据: 每个可见页面在路由表里能查到条目 |
| 路径写法统一 | 一律用绝对别名 (`@/...`), 禁止相对回溯 |

最后两条是**结构偏好**, 不是风格偏好 —— 它们决定项目三个月后还能不能改。所以也要给判据
(路由表能查到 / 校验脚本禁止回溯), 而不是只写一句要求。

## 第五层: 可直接拷走的件

规格写得再好, 读者仍要从零敲一遍。所以规格必须配**能直接使用的文件**:

| 件 | 形式 | 落在哪 |
|---|---|---|
| 契约件 | 令牌 / 配置 / 校验脚本 / 骨架组件 | 与笔记同目录的侧车, 或独立包 |
| 复现件 | 最小可跑示例 (单文件 `.html` / `.tsx`) | 与笔记同目录, 正文里内嵌 |
| 演示页 | `.tsx` 内联演示页 (默认) 或 `.html` 侧车 | 与笔记同目录 |

三种都是**与 `index.md` 同目录的侧车**, 不受"两个知识产物"的限制 —— 那条红线管的是
仓库里不留垃圾目录, 不是禁止侧车。见 `SKILL.md` 的红线一节。

最小复现件从哪来: 采集阶段的"最小复现" (见 `steps/2-collect/impl/repo.md`) 如果在验证后仍是**可迁移的那一层**,
就把它提升成正式侧车, 而不是留在暂存区当证据。

## 反例 (这几条都是实测踩过的)

| 写法 | 为什么不算规格 |
|---|---|
| 只写"为什么好看"的设计原则 | 读者读完知道好在哪, 但搭不出来 |
| 罗列上游依赖清单, 不给版本与接线 | 半年后照着做会失败 (前端库 API 一年一变) |
| 贴整个文件 | 读者找不到该改哪一行。只贴**改动点**与**边界** |
| "可以参考官方文档" | 把规格的责任推回给读者, 等于没写 |
| 只给结论不给判据 | 无法自查, 也就无法复现 |

## 一条自我检查

写完这一节, 用这个问句过一遍:

> 把事实源和所有图都拿掉, 只留这一节和它的侧车, 一个没读过素材的人能不能照着做出来?

答"能" -> 这节成立。答"能看懂但做不出来" -> 缺的是契约层或侧车。
