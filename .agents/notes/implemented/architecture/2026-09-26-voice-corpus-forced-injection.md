# Agent Note: 表达语料强制注入 status 输出, 不依赖模型自觉去读

Status: implemented

Decision-ID: voice-corpus-forced-injection

- **引入于**: `f28d9cfd13`

## Code

- `.agents/skills/hx-note/scripts/cli/flow/flow_read.py`

## Problem

语料库 (好句 / 坏句 / 梗) 的积累机制一直是有的, 但**积累的东西从未出现在写作现场的上下文里**。

实测症状: 攒到 37 条时, 写引入仍然一条都想不起来, 写出来还是 AI 腔。
更早一次: 34 条语料存在点开头的 toml 里, 站点不渲染、没有页面引用, 人一次都没看到过。

根因不是没记, 是**没有任何机制让它出现在眼前**。

此前试过两种无效做法, 都失败在同一个点上:

1. 写在 SKILL.md 里说 写作前读一遍语料库 -> **依赖模型自觉**。模型不会在写引入时想起去读。
2. 写在模板的引入一节 -> 同上; 且模板是 要写引入时 才读, 那时已经在写了。

## Decision

把语料挂进 hx_flow.py status 的输出。它是**每一步都必须调用的入口**, 所以语料每一轮都在场。

**关键区别: 这不是 提示模型去读 (依赖自觉), 而是 把东西摆在眼前 (不依赖)。**

两个实现细节是有意的:

- 注入点放在 print_status() **最开头**。后面有提前 return 的分支 (流程走完时), 放末尾会被跳过 
  而语料必须在每一个阶段都出现。
- 逐行解析 toml 而不用正则。第一版用正则拼字符串, 转义连续出错; 这个格式简单到不需要正则。

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **写进 AGENTS.md 之类的常驻配置** — 最强理由: 那是真正的 每轮都注入, 不依赖任何命令被调用。
  否决: 那份配置属于整个仓库, 而语料只对写作流程有意义; 放进去会污染其它任务的上下文。
  另: 语料会持续增长, 常驻配置的体积不好控制。
- **让 lint 报错时顺带打印语料** — 理由: lint 是写作中必然会跑的。否决: lint 是**改完之后**跑的,
  那时引入已经写好了; 时机太晚, 要在动笔前看到。
- **加一条 lint 规则去查有没有用上语料** — 否决: 语料是 可以学的表达, 不是 必须满足的约束;
  硬查会变成要求每篇都必须出现某句话, 那是新的指纹。它的作用是启发, 不是判据。

## Consequences

- 成本: 每次 status 多约 1000 token (37 条正文合计 1017 字符)。相对一次写作的整体上下文可忽略。
- 顺带修了一个真 bug: load_voice_db 的返回值硬编码了 bad|good 两个键, cmd_samples 的循环同样只列两组 
  加 meme 类别时两处都漏改, 表现为 学进去了但看不见。
- 局限: 语料仍只覆盖**措辞层**。第三层 (来路: 情绪是输入还是装饰) 与手法层 (读者在不在场)
  测不出来也注入不了, 只能靠读。这一点写在 research-output/spoken-style-corpus.md 里。
