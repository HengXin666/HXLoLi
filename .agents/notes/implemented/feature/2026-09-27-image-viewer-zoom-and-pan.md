# Agent Note: 图片查看器自己管缩放与平移, 不复用幻灯架构图那套

Status: implemented

- **引入于**: `0a7374e73d`
- 影响: `src/components/common/ZoomImage/` (index.tsx + ZoomImage.module.css)
- 使用方不变: `src/theme/MDXComponents/Img` / `src/pages/friends` / `src/pages/anime/*` / `src/components/anime/AnimeCard`

## Problem

点开图片只能得到一个"铺满视口的等比放大图": 滚轮不动、拖不动、没有倍率读数。而站内图片里有大量
长截图与宽表格截图, 全屏等比放大之后字依然糊 —— 需要的是"滚到那一段再放大看清", 现在的实现做不到。

组件原本把全部样式内联在 JSX 里、用一个 `isOpen` + `isAnimating` 两个布尔维持状态,
图片与遮罩的点击互相冒泡, 关闭判据是"点到了遮罩"。要加缩放与拖拽, 得先把坐标系和事件归属定下来。

## Decision

查看器自持一套坐标系, 缩放、平移、滚轮锚点、边界钳制全部由它一条公式推出来。

坐标系只有一套, 单位统一为**屏幕像素**:

```
fit  = 图片按舞台 "contain" 放下后的完整尺寸 (fitW x fitH), 由 JS 量出
显示尺寸 = fit * f        f = 1 表示整张刚好装下
p    = 图片**中心**相对舞台中心的偏移, 单位是屏幕像素
渲染: transform: translate(p.x, p.y) scale(f)
```

居中**不写**进 transform, 而是量出尺寸后用 JS 写 `margin-left/-top` 负半尺寸。这样图片中心的屏幕
位置恰好是"舞台中心 + p", 于是三条不变量同时成立:

1. 光标锚点缩放: 令锚点处对应到图片上那个点不动, 解出 `p' = a + (p - a) * f'/f`, 与"拖没拖过"无关。
2. 拖拽: 鼠标位移**直接**加在 p 上, 不按倍率折算。
3. 边界: 图比舞台大时 `|p| <= (fit * f - 舞台) / 2`, 小的时候中心钉死 —— 永远拖不出空白。

交互面覆盖鼠标与触屏, 用 Pointer Events 统一: 单指/左键平移, 双指捏合缩放, 滚轮缩放,
双击在光标处 1.8x → 3.5x → 复位, Esc 关闭, 工具条给 −/倍率/+/复位/×。

## Evidence

无头 Chromium 在临时页面上真鼠标/真触摸事件驱动, 31 条断言:

| 用例 | 实测 |
| --- | --- |
| 光标锚点缩放 | 3 档滚轮, 锚点归一化坐标 du = 0.00000 (修前 0.25 → 0.37) |
| 拖拽位移 | 鼠标 -100/+50 → 图 -100.0/+50.0; 倍率 2.94468 不变 |
| 拖到极右上 | 左/上间隙 <= 0.5px, 图铺满舞台无空白 |

## Alternatives considered

**复用 `src/hxdeck/diagram.tsx` 的缩放/拖拽实现。**
它最强的地方是真的已经跑通: 缩放、拖拽、边界、放大全屏、导出都验过。
否决的理由是它的解法建立在一个本站图片不具备的前提上 —— 容器高度由 viewBox 宽高比算死,
缩放靠给内部画布设 `width = zoom * 100%` 参与布局, 这样 `scrollWidth/scrollHeight` 天然等于缩放后尺寸,
滚动边界交给浏览器。图片没有 viewBox, 也拿不到"内容固有比例"这个先验, 照搬等于先给图片编一个;
而它那套 deck 层 / 语义护照 / 导出与查看图片无关, 一起搬进来是把两件事绑死。

**什么都不做, 保持全屏等比放大。**
它的理由是最充分的: 五处调用方一行不用改, 零回归风险, 而且"点开能看大"这个原始需求确实已经满足。
否决是因为用户报的就是这条 —— 站内的长截图与宽表格缩略图放成全屏之后仍然读不清, 这不是可接受的上限。

**引第三方库 (medium-zoom / photoswipe)。**
最有力的一点是成熟度: 手势、边界、无障碍、移动端都被反复打磨过, 而且 medium-zoom 只有几 KB。
否决是因为本项目的图片查看器还要跟"幻灯卡片弹层"共存: 宿主自己会写 `body.overflow`,
外层还有 `position: fixed` 的弹层与 deck 的 `stage scale()`。要把它调对需要读进库的事件与样式假设,
工作量不比自持一套坐标系小, 却多一个要跟着升级的依赖。

**把居中继续写成 `transform: translate(-50%, -50%) translate(p) scale(f)`。**
这是最省事的写法, 也是本次第一版的实现。否决是因为那个百分比按**未缩放**的元素尺寸取,
`scale()` 之后它不再把中心放回原位 —— 多出来的 `(f - 1) * fitW / 2` 让光标锚点越放越偏
(实测 u 从 0.25 漂到 0.37)。改用负 margin 之后 transform 里只剩 `translate(p) scale(f)`, 不变量才成立。

**让 p 用 fit 系 (即"以整张图的宽度为单位") 而不是屏幕像素。**
理由是这样写边界公式更短, 系数全是纯数, 看起来更"数学"。否决是因为一旦把屏幕像素量当成 fit 系量
去参与加减, 锚点和拖拽都会按 f 缩水: 实测拖 100px 只走 42px、锚点漂到 0.37。统一成屏幕像素后,
只有"跟图片尺寸相乘比较"那一处才需要换算, 出错的面积更小。

## Consequences

- 组件从 143 行涨到约 440 行, 并多出一个 CSS Module。样式不再内联, 因为 Portal 到 `document.body`
  的子树里宿主组件的 CSS Module 类名会解析成 undefined (PptCard 踩过这个坑)。
- `wheel` 必须原生绑定加 `{ passive: false }`: React 17 起把 wheel 注册为 passive,
  `onWheel` 里的 `preventDefault()` 会被静默忽略 —— 那正是"在查看器里滚轮同时滚动了背后的文章"。
- 舞台调用 `setPointerCapture` 后, 合成 `click` 的 target **永远是舞台**。判断"点的是图片还是背景"
  只能取 `pointerdown` 时的 target, 拿 `click.target` 会恒为 false, 单击会直接把查看器关掉。
- 放大之后"点图片"不再关闭 (它是放开鼠标的动作), 退出走点背景 / Esc / × / 双击复位。
  这是为拖拽让路的代价: 关闭判据必须先看"这次手势有没有位移"。
- 关闭会锁 `body.overflow`, 还原时写回**打开前记下的值**而不是清空 —— 宿主 (幻灯卡片弹层)
  可能自己就设了 hidden, 无条件清空会把它的锁一起拆掉。
- 操作提示条全站只弹一次 (模块级标志), 只在客户端渲染时出现。
