# Agent Note: ai-docs 存量笔记按最新规范全量重写

Status: implemented

- 影响: `ai-docs/` 全库 29 篇笔记正文 + `data/aiDocTags.ts` / `sidebarsAiDocs.ts` / `src/hxdeck/decks.generated.ts` 三个派生索引

## Problem

`ai-docs/` 的目录结构与 tag 树在 2026-09-13 已完成重分类, 但**正文本身**从未按规范统一过.
沉淀流水线 (`hx-to-ai-docs`) 的规范一直在演进, 而库里 29 篇是不同时期用不同版本沉淀的, 结果是同一套规范下有五种写法:

1. **frontmatter 不齐**: 3 篇缺 `created_at`/`model`/`skill` (早期用 `date:` 字段), `001-关于` 作为站点页脚页完全没有 frontmatter.
2. **开头引入缺失或错位**: 16 篇的 `> [!NOTE]` 块是空的, 或只写了"本文记录…/来自某视频转写"这类**出处说明**——规范要求的是设问式引入, 出处属于末章.
3. **末章不是参考来源**: 10 篇把"总结""回顾与自查""文件地图"放在最后, 参考来源章被埋在中间, 读者顺着读到最后拿不到出处.
4. **结尾没有升华展望**: 大量笔记以"小结/总结"收尾, 复读前文, 缺少"这套机制会怎么演进"的一层, 也没有事实与个人判断的分野.
5. **过程痕迹留在正文**: `AI 辅助沉淀`、`需要用户 review`、Transcript 来源与转写时间、本地文件路径、`git commit` 命令等面向作者而非读者的内容混在正文里.

这些不是笔误, 是**规范演进后存量没跟上**. 而规范本身没有强制手段——没有门禁能拦住"旧写法继续存在", 只能靠一次全量重写把基线拉平.

## Decision

**对全部 29 篇做一次格式/结构规范化, 技术内容零删减.** 逐篇满足九条:

1. frontmatter 七字段齐备且顺序固定 (`hxid` 沿用不更换, `model` 未知写 `"Unknown"` 不编造);
2. `# H1` 等于 frontmatter 的 `title`;
3. 开头 `> [!NOTE]` 设问式引入 2~4 行 (已有合格的不重写);
4. 主章节统一 `## 0xNN`, **不重排已有编号**, 只追加;
5. 结尾新增"拓展升华展望"章, 且必须显式分 `**事实层面**` / `**个人判断**` 两段;
6. 末章必须是 `## 0xNN 参考来源`, 只列真正引用过的外部来源;
7. 跨文章引用写 `[标题](../路径/index.md "hxid:hx-xxxxxxxx")`;
8. 正文零过程痕迹;
9. 标点过 `format_cn_punct.py --check`.

关键取舍:

| 决策 | 结论 | 理由 |
|---|---|---|
| **技术内容动不动** | **一字不删** | 规范化不是编辑. 一旦允许"顺手精简", 重写的边界就没了, 也没法向作者解释哪句是原文哪句是改的 |
| 补写展望章是否算"新增事实" | 允许补写, 但**判断必须标为个人判断** | 规范明确要求结尾升华; 用事实/判断分野把它和原文陈述隔开, 读者能分清哪层是原文哪层是作者此刻的判断 |
| `001-关于` 怎么处理 | **只改文风, 不补 frontmatter / 不加 tag** | 它是站点页脚页, 已登记在 `.hx-tags.toml` 的 `ignore_notes`; 硬补七字段只会让"非笔记页面"这个既有区分失效 |
| 演示页要不要顺带迁移 | **不做** | `.html` 侧车转 `.tsx` 内联页要重做 slide 与 archify 图, 是独立工作量; 混进来会让本轮无法验证 |
| 标点 | 用脚本归一化, 不手工改 | 手工改标点在 29 篇规模上必然漏, 且无法复验 |

## Alternatives considered

- **什么都不做, 只在新沉淀时遵守规范**: 最有吸引力的选项 —— 零风险、零工作量, 且新笔记确实会是对的. 否决理由: 存量占全库 100%, 规范只对新内容生效等于读者面前永远是五种写法; 而且"旧笔记可以不合规"会立刻变成下一位作者绕过规范的先例.
- **只补硬缺口 (frontmatter / 末章 / hxid 链接 / 过程痕迹), 不动开头与结尾**: 风险最低, 且能机械验证. 否决理由: 这四项恰好是"能被脚本检出"的部分, 而开头引入与结尾展望才是规范里定义一篇笔记**成不成文**的两条; 只修前者会得到一个"检查全绿但读起来仍然不是笔记"的库.
- **先做一个分类试点再铺开**: 稳妥, 但 29 篇的规模不足以摊薄两次沟通成本, 且五批本来就按分类切分并行执行 —— 试点能发现的口径问题在并行执行中同样会暴露.
- **把规范化写成一个自动重排脚本**: 结构项 (`## 0xNN` 编号、frontmatter 顺序、标点) 可以脚本化, 但"设问式引入"和"升华展望"是写作, 不是重排. 脚本只能覆盖一半, 却会给人"已经合规"的错觉.

## Consequences

- 29 篇正文全部改写; 结构项与标点项可复验, 写作项 (引入质量、展望质量) **依赖人工复核**.
- 五批笔记由五个并行 subagent 改写, 同一批内文件互不重叠; 跨批只共享 `hxid` 映射 (只读).
- `data/aiDocTags.ts` 等派生索引会因为 tag 引用变化而需要重建 —— 这是守卫路径, 本次提交必须连带提交 Agent Note 才能在 coverage 门禁下通过.
- `001-关于` 仍是唯一没有 frontmatter 的页面, 由 `hx_docs_id.py` 按豁免跳过, 与本次改动前一致.
- 规范与存量之间的差距被拉平一次, 但**没有加任何门禁**去阻止新笔记再次偏离——下一轮仍会积累同样的漂移.
