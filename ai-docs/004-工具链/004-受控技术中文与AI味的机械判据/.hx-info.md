# 受控技术中文: 把「啰嗦、不精准」变成可机械检测的判据 知识点

一句话: 受控写作把「这段文字读着啰嗦」拆成一组**可判定的判据** (句长、段长、虚动词、端点歧义、无信息程度词), 每条都有阈值和误报率.

给不出误报率的规则只能进提示层, 不能进失败层.

适用: 技术说明、接口文档、操作步骤、机器撰写的解释性回答. 不适用: 营销文案、叙事文章、观点评论.

## 这套方案由三件东西组成

| 件 | 内容 | 出处 |
|---|---|---|
| 规范 | 6 节 40 条规则, 分【必须】与【建议】两级 | [simplified-technical-chinese/规范.md](https://github.com/mzopedia/simplified-technical-chinese) |
| 词表 | 约 170 条: 禁用词 / 选词表 / 一词一义限定 | 同仓 词表.md |
| 检查器 | 零依赖 Python, 660 行, 只查句法层 | 同仓 tools/check.py |

它自称独立于 ASD-STE100, 规则按中文的歧义来源重新设计. 这句话解释了为什么不能直接搬英文受控词典.

## 骨架: 先分句类, 再判据

整套方案的第一层是**分类**, 早于任何规则:

- **操作句**: 指示读者执行动作, 通常以动词开头, 出现在编号步骤里
- **描述句**: 其他句子

阈值、祈使句要求、被动语态检查全都依赖「这句是操作句还是描述句」. 判错了, 后面全错. 所以检查器里有一个 `is_operation()` 专门做这件事.

两套级别: **【必须】**违反即不合规; **【建议】**违反只提醒.

## 判据 1: 句长与段长 (有实测分位支撑)

| 项 | 阈值 | 依据 |
|---|---|---|
| 操作句 | 不超过 30 字 | 350 万字真实技术文档的 85..90 分位 |
| 描述句 | 不超过 40 字 | 同分布 90 分位附近 |
| 段落 | 不超过 6 句 | 规范规则 3.2 |
| 定语 | 不超过 15 字 | 没有校准, 脚本查不出 |

字数算法: 每个汉字计 1; 每个连续拉丁字母串或数字串也各计 1 (`API`、`v2.0`、`3000` 各计 1); 行内代码整体计 1; 标点、空格、括号不计. 「重启服务」计 4 字.

阈值不能随手改. 同一份规范被 answer-me-with-html 搬去做双语版时放宽成 35/45 字, 没有给出理由. 有校准报告的 30/40 优先.

## 判据 2: 中文特有的歧义来源 (英文规则搬不来的)

规范附录 B 专门列了这类, 共 6 项:

| 歧义 | 改法 | 例子 |
|---|---|---|
| 「进行」类名词化 | 直接用动词 | 对配置进行修改 → 修改配置 |
| 长定语 | 拆句 | 「用于在系统启动时自动加载位于用户目录下的配置文件的模块」拆成三句 |
| 「以上 / 以下」端点歧义 | 写清含不含 | 10 MB 以内 → 不大于 10 MB |
| 「可以」许可与能力 | 表能力用「支持」 | 可以跳过 → 支持跳过 |
| 「打开 / 关闭 / 启动」对象限定 | 按对象换词 | 打开日志功能 → 启用日志功能 |
| 相对时间 | 写绝对日期 | 近期下线 → 2026-12-31 下线 |

反方向也成立: 英文有而中文不需要的规则是动词形态 (-ing / 过去分词)、冠词时态、词性限定.

## 判据 3: 词表三部分, 每条自带「自动检查」列

| 部分 | 作用 |
|---|---|
| 禁用词 | 不用的词与替换方式 (如 `进行` → 直接用动词) |
| 选词表 | 同一意义只批准一个词 (`点击` / `单击` / `点按` 只留 `点击`) |
| 一词一义限定 | 批准词只按一个意义用 (`打开` 只用于文件窗口页面连接) |

**这一列是整套方案最值得抄的设计**: 每条词表项都有一列「自动检查」, 只填「是」或「否」. 填「是」的脚本见到就提醒; 填「否」的依赖语境, 只供人工参考. 它把「能自动查」和「只能人看」分开声明, 而不是假装全都能查.

判据 (规范附录 D): 自动检查的条目**只保留精确率不低于 80% 的词**.

## 判据 4: 主动声明查不了的规则

规范附录 D 列出了脚本**不查**的规则及实测精确率. 这一节是整套方案的 credibility 来源:

| 规则 | 为什么不查 |
|---|---|
| 缩写写法 | 大小写差异几乎都来自代码与链接锚点, 精确率 0% |
| 指代是否清楚 | 指代词数量不能代表清楚程度, 精确率 0% |
| 「的」的数量到定语长度 | 不能代表定语长度, 精确率 2% |
| 长定语 | 脚本查不出定语长度 |
| 正文串联步骤 | 精确率 40% 与 30% |
| 警告位置 | 精确率 19% |
| 前置条件 | 精确率 12% |
| 步骤里解释原因 | 精确率 34% |
| 一句多事与双重否定 | 53% 与 22%, 降为建议 |

「『的』的数量不能代表定语长度」这条特别值得记: 它直接否定了「数『的』字」这类看起来聪明的土办法.

## 判据 5: 与「啰嗦」对应的用词规则

规范点名了一批「不说明具体做了什么」的词, 正是被称作 AI 味的那类:

- 空泛黑话: `赋能` `抓手` `闭环` `拉通` `沉淀` `落地` `赛道` `心智` `颗粒度` `组合拳` `痛点` `底层逻辑`
- 无信息程度词: `非常` `很` `极其` `相当` `十分` `大量` `少量` `大部分` `基本` `比较` `相对`
- 无时限承诺: `尽快` `及时` `必要时`
- 废话开头: `众所周知` `显然` `不难看出` `其实` `事实上`

判据 (规则 1.7): 这些词不说明具体做了什么, 要写出具体的动作或对象. 改法示例:

- 不批准: `通过平台能力赋能业务, 形成数据闭环`
- 批准: `业务系统调用平台接口写入数据, 平台每天把统计结果发送给业务系统`

## 判据 6: 与本仓 hx_voice.py 的关系 (实测)

同一篇真实笔记 `ai-docs/003-AI/003-Agent-Harness/DSH/001-DSH-Agent-Loop源码剖析/index.md` 跑两个检查器:

| 检查器 | 输出 |
|---|---|
| `simplified-technical-chinese/tools/check.py` | 15 条: 必须 13, 建议 2 |
| `hx_voice.py lint` | 14 errors, 23 warnings |

两套的交集只有**句长**一维, 且阈值不同 (40 字与 43 字).

| 维度 | STC 独家 | hx_voice 独家 |
|---|---|---|
| 句长硬线 | 是 (必须级, 40 字) | 有软线 43 字, 只报 W |
| 虚动词 `进行` | 是 | 否 |
| 端点歧义与相对时间 | 是 | 否 |
| 禁用词 `其实` `沉淀` `众所周知` | 是 | 否 |
| 破折号 | 否 | 是 (E 级) |
| 表格禁用 | 否 | 是 (E 级) |
| 抽象名词密度 | 否 | 是 |
| 助手口头禅 | 否 | 是 |

结论: 两者互补, 不是替代. STC 补「精确」那一维, hx_voice 管「像不像人写」那一维. 但句长阈值必须统一成一个基准, 不能同一份文本用两套判.

## 边界 (这套方案做不到什么)

- 不判事实保真. 检查器只做句法层, 不能判断内容对不对
- 不判文风好坏. 它自己声明不适用于叙事文章与观点评论. 治的是说明文, 不是文风
- 没有阅读理解对照实验. 校准量的是误报率, 不是读者的理解速度
- 禁问句这条对本仓是危险的. 规则 2.9 禁一切问句与感叹句 (必须级), 但本仓 `ai-docs/` 里实测有 237 个问号: 转写稿里的「对吧?」「你能理解吗?」是被引述的原话, 不是 AI 腔. 加这条规则必须同时给引用段、转写稿与 `atom` 之外的 profile 开豁免, 否则 237 处全是假阳. 本仓 `hx_voice.py` 的禁问句规则也只挂在 `atom` profile, 与本仓实测吻合
- 词表按领域裁剪. 通用词表约 170 条, 项目专有术语要另建术语表

## 应用它之后还有人味吗

这一节的结论来自本仓实测, 不是素材里的说法.

**它不会把文本变成 AI 味, 但会让人味变淡, 淡向一种手册味. **

为什么不会变成 AI 味: 受控写作的规则全是否定式的 (不许长句、不许虚动词、不许问句), 而删东西不会生成特征. AI 味来自生成套路 (破折号、`不是X而是Y`、凑数排比、抽象名词堆叠), 那些不是受控写作的产物. 两套病不在一条轴上.

那"淡"在哪里? 人味的来源恰好是受控写作要删的东西:

| 人味来源 | 受控写作的要求 |
|---|---|
| 短句碎断 (`. 而且不好用. 还有那个数量限制.`) | 一句一事, 拆成编号步骤 |
| 设问推进 (`那么是否可以通用的?`) | 禁一切问句 (必须级) |
| 自嘲括号 (`(说是不是故意的?)`) | 条件写在动作前, 不放在括号里 |
| 语气词 (`使用喵~`) | 无对应条款, 但语气词不属于技术语 |
| 省略号 (`然后出现八嘎了...`) | 无对应条款, 但它就是不确定语气 |

实测规模 (口径: 人写 = `blog/` + `docs/`, AI = `ai-docs/` 排除 `.hx-staging`):

| 项 | 人写 | AI |
|---|---|---|
| `进行` | 1845 次 / 451 篇 (其中 docs 1808 次) | 15 次 / 5 篇 |
| 问号 | docs 332 个, blog 6 个 | 237 个 |

`进行` 在作者手写的技术文档里有 1808 次. 按规范它该直接用动词, 即作者这份 docs 里有 1808 处要动. 这个规模说明**这套规范按"技术手册"校准, 与作者手写技术文档的句式不是同一套习惯**.

结论两条: 写技术说明时用它收益最大; 写随笔与观点时别用. 它自己也是这么声明的.

## 落地到本仓 (实测)

按本仓 `voice_rules.py` 既有的约定 (只有"人写近乎不出现、AI 常出现"的词才算套话), 实测候选词 (口径同上):

| 词 | 人写 (977 篇) | AI (73 篇) | 结论 |
|---|---|---|---|
| `沉淀` | 2 次 / 1 篇 | 67 次 / 23 篇 | 加 (约 30 倍差距) |
| `其实` | 124 次 / 82 篇 | 55 次 / 31 篇 | 否决 (人写更多) |
| `进行` | 1845 次 / 451 篇 | 15 次 / 5 篇 | 否决 (人写 100 倍以上) |
| `颗粒度` | 3 次 / 3 篇 | 3 次 / 3 篇 | 否决 (无差距) |
| `众所周知` | 7 次 / 7 篇 | 3 次 / 2 篇 | 否决 |

第一轮凭印象判断 `其实` 与 `进行` 都该加, 实测把两个都打翻了: 它们是正常词, 只是 AI 文本里的密度让人误判. 若按印象加进去, 会误伤作者 82 篇手写笔记.

`沉淀` 也有细节: 作者那 1 篇里是活用 (想着一定要沉淀下来), 是具体动作而非空话. 故它只挂 `article` profile, 不管随笔.

改动效果: `ai-docs/` 全量 article profile 由 1125 errors 升到 1174 errors (多出的 49 处全是 `沉淀`), warnings 不变; 作者语料零误伤.

## 可复用的迁移做法 (本仓适用)

前三条**已落地** (2026-10-06), 后一条是明确不做的:

1. **词表旁记双向频次与阈值** (已落地): 新增 `CLICHE_COUNTS` 记每个词的 `(人写次, 人写篇, AI 次, AI 篇)`; 阈值: 人写篇数占比须低于 2% (977 篇里少于 20 篇). 同时把被否决的候选词连数字写进注注释, 免得下次重试
2. **区分「全 profile」与「只约束派生文章」两类词** (已落地): 新增 `CLICHE_ARTICLE_ONLY` 与 `cliche-article` 规则. 判据: 频次校准通过, 但作者在随笔里会把它当具体动词用
3. **补「自动检查」列这个机制** (部分): 频次证据已进数据层; 规则表尚无独立的"能自动查 / 只能人看"字段
4. **句长保持软警告** (不做): 实测 `进行` 在作者 docs 里 1808 次、问号 332 个, 说明作者的技术文档本来就是这个句式. 升硬线等于把作者自己的写作习惯判违规
5. **不搬虚动词、端点歧义、相对时间三族** (不做): 实测在本仓正式笔记里近乎零命中 (`进行` 15 次 / 5 篇已属正常用词). 它们对新生成内容是防线, 但当前无可验证收益
6. **不搬禁问句与禁表格** (不做): 本仓 `ai-docs/` 有 237 个问号, 多在转写稿里, 那是被引述的原话
