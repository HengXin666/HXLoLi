# 怎么判断自己写的东西有没有 AI 味 知识点

## 中文技术文本的 AI 味差距主要在文体与选材, 不在用词
- 把作者手写语料 (blog 801 段 / 1926 句) 与另一批笔记的正文 (803 段 / 3595 句) 逐维度对齐后, 段数几乎一致, 句数差近一倍
- 用词类的指标 (口语词、程度副词) 在两类语料里几乎相同, 有差异的指标全部落在句子长度、人称、情绪、疑问、排版密度上
- 依据: `research-output/spoken-style-corpus.md` 第 103-124 行 (副本 `ai-docs/.hx-staging/spoken-style-corpus/source/raw-analysis.md`, 下称 raw)

## 语气词计数是口播语料里差距最极端的一项, 机器稿为 0
- 真人技术口播 215 句里, 七个高频词的出现次数: 「啊」136 / 「吧」88 / 第一人称复数 81 / 「呢」77 / 「哎」62 / 「对吧」44 / 「其实」28
- 同一作者按同一主题手写的讲稿 94 句里, 上述七个词的出现次数全部为 0
- 依据: raw 第 21-28 行

## 句子长度是 AI 味里最容易量的信号, 且对照组分三类
- 三类语料的实测分布 (2026-09-26): 作者手写 blog 1752 句的中位 17 字 / 均值 22 / p90 43; 作者手写 docs 32781 句的中位 25 字 / 均值 30 / p90 58; ai-docs 正文 3177 句的中位 34 字 / 均值 39 / p90 71
- 真人技术口播的句长中位是 29 字 (215 句样本), 均值 34 / p90 63 / 最长 120 字; 同一作者手写的讲稿中位 50 字 / 均值 62 / p90 113 / 最长 385 字
- 依据: raw 第 13-19 行; `hx_voice.py:72-84` 的注释 (常量 `SENTENCE_SOFT_LIMIT = 43`)

## 切句只认全角句号会让整条统计失效
- 本仓库的中文正文用半角句点结尾 (标点归一化把全角句号转成半角), 切句只认全角句号时整段会被当成一句, 于是得到句长中位 90 字的假数据
- 阈值凭估计取 60 时的实测后果是 32 篇人写笔记里 31 篇被误报共 700 处, 所以阈值必须取自分布
- 依据: `hx_voice.py:80-84` 的踩坑注释; `hx_voice.py:307-310` 的切句正则

## 抽象名词密度的原词表是错版, 已换成「只收空壳词」的第二版
- 密度本身仍是 AI 写的正文唯一显著超标的形式指标, 实测为手写的 7.4 倍: 每千段抽象名词计数, 作者手写 51.2 个, AI 写的 379.8 个
- 第一版词表含 `机制 / 链路 / 形态 / 维度 / 范式 / 层级 / 要素 / 场景 / 能力 / 体系 / 模型 / 框架 / 流程 / 方案 / 策略 / 结构 / 架构 / 模式 / 方式 / 方法 / 路径 / 视角 / 层面 / 角度 / 逻辑 / 语义 / 闭环 / 抓手 / 赋能 / 生态 / 矩阵 / 组合拳`
- 第二版 (现行) 词表移出了 `方法 / 路径 / 结构 / 模型 / 框架 / 模式` 六个词, 并移出 `能力`: `机制 / 链路 / 形态 / 维度 / 范式 / 要素 / 场景 / 体系 / 流程 / 闭环 / 抓手 / 赋能 / 生态 / 矩阵 / 组合拳 / 层面 / 视角 / 定位 / 方法论 / 语义层`
- 移出的理由 (逐个有对照): edsionte 那篇《Linux内核中通过文件描述符获取绝对路径》全文命中旧表 700/千段, 逐条看上下文全是「绝对路径」「文件系统数据结构」「方法一/方法二」, 在该语境里都指具体的东西; `能力` 在 MCP 那篇里指 capabilities 字段, 也是具体术语
- 换表后同一篇从 700 降到 0; 作者自己的 MCP 稿从 765 降到 183, 仍高 8 到 30 倍, 说明词表修对了但写法问题仍在
- 阈值仍取每千段 200 个 (手写基线 51, 留 4 倍余量)
- 该指标的语义是「在陈述一个机制」与「在讲一件具体的事」之别: 手写样本是 `咱们以C++为例, java方法名太长了, 没有Tab我怎么活`, 对照的机器样本是 `v2 移除了 EventLoop 依赖后, 这个问题交给了调用者管理`
- 词表只能当提示不能当判据: 同一个词在不同文章里性质不同, 报出来时该做的动作是判断它在这里是术语还是空壳, 不是直接删除
- 依据: `hx_voice.py:87-136` (常量 `ABSTRACT_NOUN_SOFT_PER_1K` 与 `ABSTRACT_NOUNS`, 含移出 方法/路径/结构/模型/框架/模式 与 能力 的两段理由); raw 第 136-148 行

## 抽象名词的真人技术文章对照: 五篇每千段 0 / 17 / 9 / 18 / 11, 上限约 18
- 对照素材是作者一篇手写博客里引用的 12 个技术链接, 能抓正文的有五篇, 命中 (每千行正文, 去 frontmatter 与代码块, 分母取 >20 字的行): edsionte 内核短文 0; CSDN weiqifa0 9; 博客园 LittleHann #2 11; 博客园 LittleHann #1 17; 博客园 luconsole 18
- 上限约 18, 而作者自己写的 MCP 稿换表后是 183, 高约 10 倍
- 这组比手写 blog 那组强, 因为体裁对上了: 手写 blog 是随笔, 与机器稿的技术笔记本来就不同体裁, 7.4 倍里混着体裁差; 五篇真人技术文章同样是技术文章, 里面有大量技术术语, 仍只有 0 到 23, 剩下来的差只能归到写法上
- 依据: `hx_voice.py` 里 `ABSTRACT_NOUNS` 常量的对照注释; 五篇素材正文抓取于 2026-09-26 (路径见当时的会话产物)
- **口径必须一起引用**: 这组数对切分口径敏感. 曾有一版按「分母取全部非空行、不去代码块」得到 0 / 23 / 13 / 9 / 18, 与本节的口径差在中间几篇的分母. 两版都被写进过文档, 造成前后不一致, 所以现在锚死本节这一种口径; 换口径时必须同时改本节与 `hx_voice.py` 的注释

## 从口播总结的七条手法, 拿真人技术文章复核后只有两条成立
- 七条口播手法: 先接住困惑 / 自问自答推进 / 失败讲成交互 / 用问题引出动作 / 报菜单 / 取舍要说清 / 给读者能带走的东西
- 逐条核对结果: 成立的只有 `取舍要说清` 与 `给读者能带走的东西`; `先接住困惑`、`自问自答`、`失败讲成交互`、`用问题引出动作` 四条不成立; `报菜单` 是视频用而文章不用
- 原因 (媒介差异): 口播听众不能回看, 讲者必须一路确认对方跟上了, 所以自问自答与接住困惑是必需的; 书面读者可以回看, 直接给结构更高效
- 这条直接影响判据的表述方式: 上面那五条不能写成通用规则, 写进文章规范等于把「陪着听众走」硬塞给可以自己走路的读者
- 两条成立的手法之所以可信, 是因为跨领域复现: `取舍要说清` 在一个硬件评测里复现 (开场先声明不做具体型号大横评 + 给理由 + 说明真正做的是什么); `给读者能带走的东西` 在算法教学 (给一条推理结论命名为循环不变量) 与硬件评测 (明说学会看维度比记住型号有用) 两侧都有
- 依据: `research-output/spoken-style-corpus.md` 第七层第 637-654 行; `HXLoLi/.agents/notes/implemented/process/2026-09-26-spoken-vs-written-medium.md`

## 真人技术文章的小标题中位 16-18 字, 作者手写中位 8 字
- 作者手写小标题样本: 7 字「与 AI 斗智斗勇」/ 4 字「修复过程」/ 8 字「2.1 小组的管理」/ 10 字「0.4 交流的推荐方式」, 中位 8 字
- 真人技术文章样本 (已是上限): 「inline hook 是什么」「inline hook 基本原理」「inline hook 线程安全」「inline hook 推荐库」, 落在 16-18 字
- 写成整句会超上限一倍: 按「用想做什么的说法」推成整句后实测 20-31 字; 对照的正确写法是「版本与能力发现」「三个服务端原语」这类名词短语
- 「用想做什么」指的是切入角度 (从用途切入而不是从术语定义切入), 不是长度
- 依据: `templates/interest-outlook.md:154-181`; 本次复算: luconsole 15 个标题中位 18 字 / LittleHann#1 23 个中位 10 字 / LittleHann#2 112 个中位 7 字 / CSDN 12 个中位 22 字

## 篇幅与深度: 素材覆盖率低于 70% 时先查是不是漏了整节
- 同一分类的字数对照: 作者写的 MCP 篇 5664 字, C++20 协程篇 5759 字, 自维护可插拔记忆层设计 11780 字, 自建 Agent 检索栈与凭证治理 12682 字. 前两篇只有后两篇的一半, 链接也只有 2 个
- 根因是素材用了不到三成: 原始素材 566 行里, 机制说明 (Scope / Concepts / Layers / Primitives / Notifications) 占 148 行 (26%), `## Example` 那节占 418 行 (74%) 完全没用
- 三个症状同源: 短 (机制说明本来就只占四分之一) / 引用少 (Example 那节全是可引的报文与方法名) / 深度不够 (知道字段含义与知道字段怎么串起来是两件事)
- 判据: 素材总行数与产物引用到的素材行数之比, 覆盖率应大于 70%; 机制类主题必须有一节按时间顺序走一遍流程且每步给出实际报文; 与同分类已有篇目比字数, 低于中位数的 60% 时先自查是不是漏了整节
- 依据: `research-output/spoken-style-corpus.md` 第八层第 665-710 行

## 人称、感叹、省略号与疑问句的差距都在一个数量级以上, 指向同一件事
- 每千段计数 (手写 -> 机器稿): 感叹句 224.7 -> 7.5; 省略号 209.7 -> 11.2; 第一人称复数 54.9 -> 5.0; 第一人称代词 389.5 -> 36.1; 疑问句 147.3 -> 18.7; 元话语 7.5 -> 3.7; 括号插话 188.5 -> 208.0 (括号插话是其中唯一机器稿略高的一项)
- 口语词 (其实 / 反正 / 就是 / 好像) 219.7 -> 190.5, 程度副词 (非常 / 极其) 13.7 -> 10.0, 两项均判为无差异
- 解释: 差异项全部是「文本里有没有一个在说话的人」的不同侧面, 而口语词无差异说明机器稿缺的不是口词汇表, 是没有需要表达的情绪
- 依据: raw 第 111-134 行

## 句首连接词是手写多于机器稿的指标, 判据方向与直觉相反
- 句首连接词 (因为 / 所以 / 但是 / 然后等) 占比: 手写 9.9%, 机器稿 1.9%, 手写是机器稿的 5 倍
- 解释: 手写文本在推进思路, 机器稿在并列事实, 并列结构不需要连接词
- 依据: raw 第 157-167 行

## 排版密度差一个数量级, 是最不需要统计工具就能自查的一项
- 加粗密度: 手写 0.03 处/段, 机器稿 0.31 处/段
- 含加粗的段落占比: 手写 2%, 机器稿 23%
- 段落首句为加粗标记的比例: 手写接近 0, 机器稿 15.9%
- 段落首句长度中位: 手写 21 字, 机器稿 34 字
- 加粗密度已落成 lint 规则, 上限 25% (`hx_voice.py` 的 `bold_density` checker); 列表项一律写成「加粗小标题 + 冒号」的格式另有一条 `bold-bullet` 规则
- 依据: raw 第 155-163 行; `hx_voice.py:117-199` 的规则表

## 段内长短句交替不是 AI 味判据, 两类语料的句长变异系数几乎相同
- 实测段内句长变异系数: 手写 0.364, 机器稿 0.351
- 这条推翻了作者的预设 (原以为手写长短交替、机器句子均匀), 说明凭直觉补判据会把噪声当成信号
- 依据: raw 第 150-153 行

## 判据分两批落地, 句长与加粗密度已进 lint
- 已落地三条 lint 规则: `long-sentence` (单句 > 43 字, W 级)、`bold-density` (加粗行占比 > 25%, W 级)、`abstract-density` (抽象名词 > 200 每千段, W 级)
- 尚未落地的两条候选判据: 第一人称出现次数为 0, 疑问句与感叹句出现次数为 0
- 素材原文第 179 行写「前两条已进 hx_voice.py, 后三条待做」, 该表述在写作时已过时: 抽象名词密度在源码里存在且能触发, 实跑 lint 一篇机器稿命中 765/千段
- 三条已落地规则的严重级都是 W 而不是 E, 因为长句与高密度本身不是错误, 只是提示这一句读起来会喘一口气
- 依据: `hx_voice.py:117-199`; raw 第 169-179 行; 2026-09-26 实跑 lint 输出

## 形式指标只能判断像不像人写, 判断不了值不值得读, 后者靠选材
- 手写 blog 讲的是作者自己卡住的那件事, 机器稿正文讲的是某个主题是什么; 前者的样本是「没有Tab我怎么活」, 后者的样本是「架构概述」「选型指南」
- 对应的自查动作是问一句: 这件事作者本人真的卡过吗. 这是判断题, 任何正则都测不出
- 依据: raw 第 181-191 行

## 引入的判据是「那件事在动笔之前就发生过」, 形式指标抓不到
- 40 篇作者手写引入的实测特征: 感叹/欢呼 29 次, 具体时间地点 19 次, 情绪词 14 次
- 一版机器写的引入这三项全是 0, 且形式指标全过 (第一人称有、落点真实、没有套话、句长 26 字在线内)
- 差别在因果方向: 手写是「遇到事 -> 有情绪 -> 写下来」(情绪是输入), 倒推是「决定写文 -> 找个体面的情绪 -> 写」(情绪是装饰)
- 依据: `templates/interest-outlook.md:18-46`; `HXLoLi/.agents/notes/implemented/process/2026-09-26-intro-must-precede-writing.md`

## 真人讲述允许成分不完整, 而书面语的成分完整正是「像教科书」的来源
- 口播样本「哎, 长这个样子」缺主语, 「其实没那么难, 对吧」缺宾语, 语境里该有的信息都在
- 抽象规则在口播里会被翻成动作描述: 讲数据流向时说「从 channel 出来, 这不就是读嘛」, 而不说「箭头方向表示数据流向」
- 依据: raw 第 34-56 行

## 口语词进正文的判据是它有没有在推进, 而不是出现次数的多少
- 推进型用例: 「哎, 长这个样子」在指认一个东西, 「那这样的话相当于什么呢」在引出下一步
- 口水型用例: 不含新信息的应答性词语
- 依据: raw 第 69-73 行

## 这套判据是方向性的, 不能倒过来照抄成每句都加语气词
- 口播要照顾听觉的即时性, 所以短句与重复多于书面; 书面阅读可以回看, 不需要这么碎
- 口播语料只覆盖一个讲者 (一个 C++ 协程系列视频的第 7 讲), 学到的一部分是该讲者的个人口癖而不是讲述的通性
- 依据: raw 第 75-80 行

## 边界

- 口播语料的讲者只有一位 (ASR 转写 674 行 / 215 句有效句), 样本量不足以支撑「真人都是这样讲」的结论
- 第二轮的对比对象是手写 blog (随笔) 与技术笔记, 两者体裁本来就不同; 抽象名词 7.4 倍这一项里混着体裁差异, 不能全部归因到机器写作. 素材原文没有区分这一层, 后续补的五篇真人技术文章只拆掉了一部分
- 五篇真人技术文章全部落在系统编程方向, 覆盖面窄, 不足以代表所有技术文章
- 口播与书面写作的媒介不同, 判据只能是方向性的 (句子别太长、别都写完整), 不是「每句都必须加语气词」
- 口播文字来自 ASR, 转写错字未逐句校对
- 素材里的数字全部是 2026-09-26 单次抽样的结果, 没有第二个人独立复算过
- [不确定] 阈值 43 字与 200 每千段是按「减少误报」取向选定的软阈值, 在偏理论的题材上是否仍然合适, 缺少验证样本
- 换表后 ai-docs 全库 32 篇的命中篇数从 30 降到 9 (口径同上一节: 去 frontmatter 与代码块, 分母取 >20 字的行, 阈值 200/千段). 早期曾记录过 29 / 16 这一组, 但那是另一种脚本口径下的结果, 复现不出来, 已作废
- 两处句子数口径不同: 上文的 1926 / 3595 句出自素材第一轮的统计, 而 1752 / 3177 句出自 `hx_voice.py` 注释里的统计. 两次统计的切句规则不同, 数字不能相互换算
