# 把 Agent 的纠正变成确定性检查 (事实源)

## 一个月 3000 个 PR, 回滚率稳定在约 0.5%, 靠的是对环境的投入

- 演讲者 Lauren Tan (网名 poteto), SpaceXSI, 做 Grok Bot (自动字幕里写成 Growth Bot / Grabot 等, 中文编译稿写作 Grok Bot)
- 她个人上个月往生产上线 3,000 个 PR
- 团队上个月上线 11,000 个 PR, 大约每天切一个稳定版
- 10 月约 227 人至少提交过一个 PR, 其中不少是没有完整上下文的路过贡献者
- 被回滚的 PR 相对比例更低, 稳定在约 0.5% (原话 about half a percent)
- 启动、打字、新开对话、切换对话都比刚上线时快
- 她把这件事归结为信任: 不是盲目信任, 而是投入 Agent 的运行环境, 让人有底气相信它会做对
- 从低信任到高信任她用了 6 个月, 很多 PR 是她睡觉时上的

依据: [S1 0:44, 1:25-1:51, 13:37-14:32] [S2]

## 倒金字塔: 前两层是确定性的, 文字放在最后

- 第 1 层: API 设计、架构、重构
- 第 2 层: lint 规则、类型系统、编译器、各类测试
- 前两层都是确定性的, 合起来约束 Agent 能做什么, 让它默认就做对
- 第 3 层: 验证, 包括运行时验证和形式化验证. 既找 bug, 也确认 Agent 是否理解了目标和意图
- 最后一层: 规则、skill、AGENTS.md 这类需要判断力的文字, 只放一点

依据: [S1 2:05-2:50] [S2 「代码库是 Agent 最大的输入」节]

## 每纠正一次, 先想能不能变成确定性检查

- 原话: whenever you're correcting your agent, think about how you can make that a deterministic check instead of adding another line to your rules or your agents.md
- 理由: 写在代码里更可复现, 更值得信任
- 另一条出路: 用更好的 API 设计或架构把这一类问题整类消灭
- 做够次数后, review 要留心的东西越来越少, 最后没什么可审, 大多数 PR 让 Agent 自己合

依据: [S1 3:12-3:27, 9:23-9:34] [S2]

## 代码库是 Agent 最大的输入之一, 反模式会被照抄

- 2024 年她去上班审同事的 3 个 PR, 现在约 300 个
- 每个工程师手下都是成百上千个 Agent, 代码涌入像一股不停的水流
- 临时变通、反模式、废弃代码、技术债, 会被下一个 Agent 当成既定写法照抄
- 她的比喻: 代码库像花园, 工程师的活越来越像园艺
- 收尾时的建议: 写一条 lint 挡住新的反模式, 顺手把旧的也清掉

依据: [S1 3:27-4:26, 结尾] [S2 「先打牢底座, 再搭软件工厂」节]

## 需要分寸感才能用好的东西, 往往导致垃圾代码

- 原话: anything that requires nuance to use well often leads to slop
- 例子: React 的 `useEffect`. 他们在业务代码里禁用, 只在自研框架 Dune 内部少数地方开放, 这一整类问题不用再在 review 里抓
- Dune 可以大致看作面向 Electron 应用的 Next.js, 内置大量约束和 lint 规则
- 目录结构传递上下文: Cursor 里 Agent 常把主线程代码导入渲染线程, 导致长任务和卡顿. 他们设了 `electron-main` 和 `electron-renderer` 两个顶层目录, 用依赖图分析器和 lint 禁止互相导入

依据: [S1 5:26-6:40] [S2 「需要分寸感才能用好的, 干脆禁掉」节]

## 注释无法强制执行, 还给了 Agent 找借口的地方

- Agent 会把文档、代码注释、规则、skill 这类 Markdown 当成写辩解词的地方
- 也会对一次小纠正反应过度, 把它当成永不能破的铁律
- Cursor 的例子: Agent 爱用 `setTimeout` / `requestAnimationFrame` / `requestIdleCallback` 给 VS Code 命令式风格和 React 声明式风格的冲突打补丁, 并写大段注释说明为什么合理. 大量定时器频繁创建销毁引发主 GC, 应用变卡
- Grok Bot 禁掉了 99% 的注释: 注释容易过期, 人不爱看, 给 Agent 留了逃生口, 而且无法强制执行
- 替代: lint 规则, 报错信息清晰实用, 让 Agent 去修根因

依据: [S1 6:57-9:00] [S2 「禁掉 99% 的注释, 改用 lint 规则」节]

## review 浓缩成看验证产物

- 验证产物: 视频、截图、图表、形式化验证
- 运行时验证: 让 Agent 自己把应用跑起来, 用 Chrome DevTools Protocol 这类人也在用的调试工具
- 功能地图 (feature map): 从用户视角列出应用里所有功能的「站点地图」, 给人和 Agent 一套共同词汇
- skill 里用自定义 CLI, Agent 每次复用同一个 CLI 和驱动, 省 token, CLI 本身也可测
- 形式化: TLA+ 对跨设备跨平台通知这类核心流程做模型检测; Lean 证明特定算法, 例如自研虚拟化库不闪烁. 仍在试验, 已找出一些 bug, 她说不是银弹
- UI 属性测试: 库叫 Bombadil, 已抓到几个 UI bug
- statechart: 她在插件 pstack 里做的 skill, 从用户视角把状态机画出来, 和截图视频放一起审
- 她引用 Cindy Sridharan: 6 个月前因为隐蔽 bug 被合入而不信任 Agent, 现在每天 70% 的 token 花在验证上. 她说自己的情况一致
- 这些都不是新技术, 以前因为难懂、难写、难维护而太贵, Agent 把成本压了下来

依据: [S1 9:43-13:00] [S2 「代码评审变成了看验证产物」「大部分 Token 都花在了验证上」节]

## 内循环还在产垃圾时, 自动化只会放大垃圾

- 内循环产垃圾代码时, 把它自动化只会产出更多垃圾, 然后往问题里砸更多 token
- 先投入代码库、静态分析、运行时验证、形式化验证, 再搭外循环
- 外循环例子: 每切一个新版本, 自动拉起项目对整个构建做模糊测试, 像真实用户一样用, 每个 bug 自动提修复 PR 并自动合入
- 能这样做的前提: 代码库够好, PR 默认质量过关, 大多数业务代码不再需要深度人工 review

依据: [S1 15:00-16:40] [S2 「先打牢底座, 再搭软件工厂」节]

## 本仓的规则已经按执行方式分了三档

- `.agents/coding-rules.md` 分为: 自动拦截 (`scripts/redlines/agent_notes.py` 本地非零退出, CI 评论诊断); 改技能后手动运行 hx-make-skill 校验 (尚无 hook 或 CI 接线); 约定, 尚无自动 checker
- 「约定」一档目前有 4 条: hx-agent-code 的 scripts 只写 `.ts`; 修改 hx-code-quality 的决策记录交接时 SKILL.md 与 note 的 Decision 互相引用; 改本仓技能须同次提高 `metadata.version` (PR CI 由 `scripts/skills/sync.py version-check` 检查); 默认不写测试, 只在调用 hx-tdd 时写

依据: 本仓 `.agents/coding-rules.md` (2026-11-22 读取)

## 本仓 Agent Notes 的锚点注释是受检查的引用

- 代表声明紧邻上方的多行块注释引用 note 的完整仓库相对路径, Python 用至少两行 `#` 或函数首条 docstring
- 同一 diff 里代码与 note 必须配对修改, 由 `verify.py` 核对, 单边 diff 阻断

依据: 本仓 `.agents/notes/AGENTS.md`, `.agents/coding-rules.md` (2026-11-22 读取)

## 边界

- [不确定] 演讲数字 (3,000 / 11,000 / 约 0.5% / 227 / 70%) 都是演讲者自述, 没有可核对的公开数据
- [不确定] S1 是 YouTube 自动字幕, 产品名识别不稳 (Growth Bot / Grabot / Gulp bot 都出现过), 本文按中文编译稿写 Grok Bot
- 失效条件: 她的做法建立在代码有编译器、类型、测试兜底上. 文字类产物没有真值, 检查会有误报, 只能拦一部分
- 失效条件: 禁 99% 注释的前提是有 lint 能替代; 没有对应检查的地方直接删注释会丢信息
- 已知反例: 形式化验证她自己说仍在试验, 不是银弹
- [不确定] 回滚率下降与这套做法的因果, 演讲没有给对照
