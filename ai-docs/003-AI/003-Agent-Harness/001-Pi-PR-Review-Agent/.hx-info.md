# Pi 能做什么: API、工具并发与 PR Review 实例 知识点

## Pi 1.1.0 的模型 API、Agent 循环与 coding 会话分别由三个包提供

- 满足: G2.
- 本次固定源码 commit `f1b2e77f5b13b2a199b1052cb79c235451afe7d7`, npm 示例固定 1.1.0. badlogic/pi-mono 地址当前可获取迁移后的 earendil-works/pi 源码, 包名前缀为 `@earendil-works`.
- `pi-ai` 负责 provider/model、流式响应与工具参数的模型表示; `pi-agent-core` 负责状态、工具执行、事件与多轮循环; `pi-coding-agent` 提供 CLI、文件工具、SessionManager、扩展、会话压缩.
- 小型 PR 审查工作流可直接用 agent-core, 注册两个只读工具和一个结构化结束工具. 已有交互会话需要持久化、内置工具和压缩时使用 coding-agent SDK.
- 旧版 `@mariozechner` 包、旧 `getModel` 示例及“Pi 总是串行执行工具”的说法不适用于当前固定版本. 不同版本 API 不混用.
- 依据: source/provenance.md P1、P2、P5、P6; 本次 npm 固定依赖安装记录 source/package-lock.json.

## Pi 的 Agent 构造接收模型、工具与 streamFn, prompt 启动完整循环

- 满足: G2, G3.
- 1.1.0 通过 `createModels()`、`models.setProvider(anthropicProvider())` 建立模型集合, `models.getModel(provider,id)` 选择模型, `models.streamSimple.bind(models)` 传给 `Agent` 的 `streamFn`.
- `initialState` 放 `model`、`systemPrompt`、`tools`; `await agent.prompt(text)` 等待本轮运行结束; `agent.subscribe(listener)` 接收事件; `agent.abort()` 触发合作式取消; `agent.state.messages` 保存消息状态.
- coding-agent 的入口是 `createAgentSession()` 返回 `{session}`; `await session.prompt(text)` 执行会话; `SessionManager.inMemory()` 可使用内存会话. 默认 factory 会发现工作目录的设置与资源, 并非纯粹无配置构造.
- 一个 Agent 拥有一段可变对话. 多个独立 PR 应各建 Agent/会话; 一个 Agent 里的多工具并行不等于多个 Agent 同时审查.
- 依据: P2 AgentOptions/Agent、P5 Quick Start、P6 createAgentSession 与会话生命周期; source/review.ts.

## Pi 每次调用模型前转换上下文, 工具结果进入下一轮模型请求

- 满足: G3, G5.
- 主链为 `prompt -> transformContext -> convertToLlm -> streamFn -> assistant message -> tool calls -> toolResult -> 下一轮`.
- `transformContext` 处理 AgentMessage 数组; `convertToLlm` 过滤或转换应用自定义消息; 最后 normalizeContext 生成 provider 接口需要的消息结构. 1.1.0 的 system 消息还承载工具声明变更, 裁剪时必须保留有效工具声明.
- 模型响应结束后, 循环从 content 取出 toolCall, 完成工具校验和执行, 把工具结果附入上下文. 普通最终回答不再调用工具时可自然结束; `finishTurn` 可在完成一轮后返回 `{action:"end"}` 主动停止.
- 生命周期事件包括 agent_start/end、turn_start/end、message_start/update/end、tool_execution_start/update/end. 事件是观测接口, 不要求为每种事件都写业务处理.
- 依据: P3 runLoop、streamAssistantResponse, P4 AgentEvent; source/check.ts 真实循环.

## Pi 工具 schema 约束参数, execute 实现副作用并返回模型可读结果

- 满足: G3.
- 最小工具包含 `name`、`label`、`description`、`parameters` 与 `execute`. 本例用 TypeBox `Type.Object` 声明 JSON Schema, 限制页大小与整数行号.
- `execute(toolCallId, params, signal, onUpdate)` 返回 Promise. `content:[{type:"text",text:...}]` 是模型可读结果, `details` 可附宿主/UI 信息; 需要模型使用的证据必须出现在 content, 不能仅塞 details.
- 参数校验不能替代业务检查. `finish_review` 仍要验证文件属于 PR、行号属于新增 HEAD 行.
- 抛异常或显式 `isError:true` 表示工具失败. 只在正文写“失败”而不设失败状态会被当普通结果. 本例抛出错误行号异常, Pi 回传失败 toolResult, 后续模型修正参数重试.
- onUpdate 用于进度而非最终结果; signal 需要传递给底层 I/O. 工具结果的 id 用于关联调用, 不能靠完成先后猜对应关系.
- 依据: P3 prepareToolCall/executePreparedToolCall/createToolResultMessage, P4 AgentTool; source/check.ts 的 line=99 重试通过.

## Pi 默认并行执行同轮工具, 完成事件与对话结果有不同顺序

- 满足: G4.
- `toolExecution:"parallel"` 是当前 Agent 默认值. 每个调用先串行做参数准备、校验与 beforeToolCall, 然后把允许执行的任务交给 Promise.all.
- `tool_execution_end` 随真实完成发出; toolResult 消息等整批完成后按 assistant 原调用顺序追加. 两种顺序都依靠 toolCallId 关联.
- 任意一个工具声明 `executionMode:"sequential"`, 整批就回退到串行; 全局 `toolExecution:"sequential"` 也可强制串行. 设置 sequential 不会让模型自动知道上一工具的运行结果, 同轮参数已经生成.
- 本次实测: `start:slow,start:fast,end:fast,end:slow`, 执行峰值 2; 消息结果顺序仍为 slow,fast. 工具设 sequential 后变成 start:slow,end:slow,start:fast,end:fast, 峰值 1.
- 并发是异步 I/O 重叠, 不自动提供 CPU 多线程、事务回滚或跨进程互斥. 已检查的调度入口没有通用 `maxConcurrency` 参数; 需要限额时在工具实现包 semaphore, 或提供显式的批量读取工具.
- 依据: P2 Agent constructor、P3 executeToolCalls/executeToolCallsParallel; source/verification.log.

## 依赖未知结果的调用应分轮, 已知独立输入的读取可同轮并行

- 满足: G4, G6.
- 本次设计: 同一固定 commit 的 file A 与 file B 可同轮读取; “先查符号位置再按位置读取”需要等上一轮结果, 或由一个工具内部先查后读.
- “先写文件再运行测试”包含顺序依赖, 不应把两者当普通独立读取. 全局串行只保证执行顺序, 不会修复提前猜出的参数.
- 同轮多个读调用的错误应保留到各自 toolResult; `Promise.allSettled` 可用于自定义批量工具收集各项成功/失败, 再保留输入索引输出. 裸 Promise.all 遇 reject 不会取消已经开始的兄弟任务.
- 批量工具示意可把 paths 每 4 个一批, 使用 Promise.allSettled 收集每项结果并按路径回传; 分批范围只覆盖该函数, 不约束同时出现的其他工具调用.
- 限制同一时刻的读操作数量, 仍不能降低最终回传文本总量; 并发预算和上下文预算要分别控制.
- 依据: P3 先有 assistant message 再执行工具的顺序; source/check.ts; Promise 执行语义; 本次设计推导见 source/divergence.md.

## 固定 Git SHA 的读取让 PR 审查免于工作区变化造成的证据漂移

- 满足: G1, G4, G5.
- 本次示例 `acquire()` 只接受 GitHub PR URL 或 `owner/repo#number`, 从 gh 读取 base/head 元数据, 临时创建 bare 仓库, fetch 两个固定引用, 验证 PR head 未变化, 计算 merge-base.
- 审查比较 `merge-base..head`, 文件内容通过 `git show SHA:path` 读取. 不会执行被审程序, 也不需要让模型管理 git checkout. 固定 SHA 是此次工作流选择, 并非 Pi 的强制架构.
- 每份结果记录 ref/base/head; 以后复核要对同一 head, 新提交需要重新审查. 并发读取的对象是不可变 blob, 主例不用工作区文件变更锁.
- `read_file` 可以读取不在 diff 的消费者代码, `read_diff` 只读取变更文件. diff 页的显示行号与真实源码行号分开; findings 使用 hunk 的 HEAD 行号.
- 依据: source/review.ts acquire/review; source/check.ts 的真实本地 fetch + merge-base 校验; source/divergence.md.

## PR review 的结束工具可验证报告坐标, 但不能证明模型查全了漏洞

- 满足: G1, G3, G6.
- 本例提供 read_diff、read_file、finish_review 三个工具. finish_review 接受 findings 数组, 每项含 path/line/priority/title/evidence.
- 报告只允许在新增 HEAD 行定位, priority 为 0..3. finish_review 必须单独成批, beforeToolCall 拒绝与读取混用; 接受后返回 terminate:true, finishTurn 也在 report 已存在时结束.
- 宿主验证坐标与参数结构, 模型判断 bug 是否真实存在. 离线 fixture 的预设模型输出只验证工作流行为, 不衡量推理准确率.
- 默认不发送 GitHub 评论. stdout 写 JSON, `> review.json` 交给 shell 存盘, 后续 CI 发布应在固定 head 上另行映射坐标.
- 依据: source/review.ts finish_review/beforeToolCall/finishTurn; source/check.ts 和 verification.log.

## 上下文优化先限制取证量, 会话压缩由 coding-agent 的会话层提供

- 满足: G5.
- 本例首次只发送变更文件清单、base/head 和 PR 引用, 模型按需请求单文件 diff 和源码片段. 单页上限 120 行、16000 字符, 返回 next 指示续读; 过长行报错要求更小页.
- 扩展设计: 原始大输出存为宿主 artifact, content 只保留摘要和可再读标识; 摘要保留 path、SHA、行号、未验证假设. 读过的片段可按 `(sha,path,offset,limit)` 缓存.
- `transformContext` 是可注入裁剪的接口, 原始 state 不会因返回一个新消息数组就自动变成持久化摘要. 不要用 `messages.slice(-N)` 破坏 toolCall/toolResult 配对或抛掉工具声明.
- coding-agent 自动压缩在 `contextTokens > contextWindow - reserveTokens` 时触发, 默认 reserveTokens=16384、keepRecentTokens=20000; 通过 SessionManager 保留原始会话并建立摘要投影. 裸 agent-core 的本例不含自动 compaction.
- 依据: P3 streamAssistantResponse、P6 SessionManager、P7 When It Triggers/How It Works; source/review.ts page 与初始 prompt. artifact 与缓存为本次扩展建议.

## Pi 内置 write 和 edit 按目标文件排队, edit 当前接收 edits 数组

- 满足: G4, G5.
- 内置 read 支持 offset/limit, 默认截断 2000 行或 50 KiB; write 创建或覆盖整个文件; edit 以 `edits:[{oldText,newText}]` 精确替换.
- 每个 edits 项对原始文件匹配, 要求唯一且不重叠, 不把前一项的输出作为后一项输入. edit 结果 details 包含展示 diff、unified patch 和 firstChangedLine.
- edit/write 都经过 `withFileMutationQueue(absolutePath,...)`: 同一目标排队, 不同文件并行; 存在的路径先 realpath 归一化. 该队列属于进程内文件变更协调, 不是跨进程锁或全仓库事务.
- 取消时等当前文件 I/O settled 再释放队列, 避免调用方看到取消后后续写入与前次写入重叠. 取消后仍应检查真实文件状态.
- 可通过 coding-agent 导出的 createReadTool/createWriteTool/createEditTool 注册内置工具; 小型 review 主例保持只读, 修复演示在临时工作区单独执行.
- 依据: P8 createReadTool、P9 createEditToolDefinition、P10 createWriteToolDefinition、P11 withFileMutationQueue.

## Unified diff 可写成补丁文件, 应用前应检查基线与可应用性

- 满足: G5.
- `git diff --binary base head > fix.patch` 把固定版本间的变更保存为补丁. `git apply --check fix.patch` 只检查, `git apply fix.patch` 修改工作区.
- GitHub PR diff、Pi edit 的展示 diff、unified patch 和结构化 findings 作用不同. 展示行号不能直接拿来当 PR 评论位置, hashline 也不能直接交给 git apply.
- 应用补丁属于修复流程, 不能与同文件另一写入并发. 可在临时副本先 check/apply, 再跑目标项目测试.
- 本次 fixture 从 base 内容生成并应用 patch, 最终 `git diff head -- sum.ts` 为空, 验证文本与 head 一致.
- 依据: source/check.ts PATCH_ROUNDTRIP; P9 generateUnifiedPatch. 修复流程顺序为本次设计建议.

## 小型 PR review 复用件具有固定输入、工具、预算与输出契约

- 满足: G1, G6.
- 触发场景: 希望从一个 PR 引用得到本地 findings JSON, 用于学习 Agent 循环与工具调用.
- 已定选择: TypeScript/Node、Pi 1.1.0 agent-core、gh 元数据、bare Git 临时目录、固定 SHA 只读工具、结构化 finish_review.
- 机械判据: 主例不超过 180 行; TypeScript 检查通过; fixture 验证并发峰值、结果顺序、错误恢复、PR 获取和 diff 应用.
- 写法偏好: 主例只保留 3 个工具, 调度、会话 SDK、读写补丁和 context 扩展分成短片段解释, 不搭 web 服务或 review 平台.
- 安装: Node 22.19+ 满足包引擎要求, 直接运行本例采用支持 TypeScript 类型擦除的 Node 版本, 本次实测 Node 26.10.0. `npm ci --ignore-scripts` 使用侧车锁文件; 实际模型调用需要 gh 登录和 ANTHROPIC_API_KEY.
- 运行: `node review.ts https://github.com/owner/repo/pull/123 > review.json`. 无凭据验证: `node check.ts`.
- 依据: source/package.json、source/package-lock.json、source/run.md、source/verification.log.

## Pi 的六类应用可以按需要控制的层次选择接口

- 满足: G7, G8.
- 多 provider 聊天、摘要和流式 UI 可只使用 pi-ai 的 createModels、streamSimple、completeSimple; AsyncIterable 事件以 type 区分, stream.result() 汇总响应. 业务代码仍要按模型实际能力选择输入和工具.
- 领域 Agent 如 PR reviewer、日志诊断或知识库检索可使用 agent-core, 宿主提供业务工具与预算. 此处后两者是可实现的设计用途, 不是库附送的完整产品.
- 嵌入代码助手可用 createAgentSession, 复用读写工具、会话树、压缩、资源加载. session.getLastAssistantText 取最终正文, finally 调用 session.dispose; SessionManager.inMemory 明确选择不落盘会话.
- 增强现有 CLI 可写 TypeScript extension, 默认导出工厂接收 ExtensionAPI, 用 pi.registerTool/registerCommand/on 添加工具、命令和事件. pi --extension ./hello.ts 加载, jiti 不要求单独编译. 长期资源从 session_start 或实际工具调用创建, session_shutdown 释放.
- 自己做 Web/IDE 前端可消费 Agent/session 事件, 或让独立进程运行 CLI print/JSON/RPC 模式. 这些是接线接口, 前端、鉴权和任务服务仍由应用实现.
- 接外部系统可用 MCP; 当前 CLI 随带 MCP/codemode/tool_search 内置扩展, codemode 中可写 JS 调用工具并过滤输出, 工具暴露支持 direct/codemode/deferred. SDK 不自动加载这三个 CLI 扩展, 需 DefaultResourceLoader 的 extensionFactories 注册 createCodemodeExtension/createToolSearchExtension/createMcpExtension, 启用工具并 session.bindExtensions.
- Pi 上游 README 明确不内置 subagents 和 plan mode, 可用 extension/package 扩展. 工具调用与 extension 运行在宿主权限下, 没有内置 OS 沙箱; 容器/权限边界须由部署者提供.
- 依据: P15 pi-ai README, P16 coding README, P17 extensions, P18 MCP, P19 CLI integration, P6 SDK; 用途映射是据接口作出的应用设计.

## Pi API 现代程度可以由异步接口和控制点判断, 不等于成品平台完备

- 满足: G8.
- TypeScript 类型、TypeBox runtime schema、async execute/AbortSignal/onUpdate、带判别字段事件、可替换 streamFn、上下文 hooks 和 beforeToolCall/finishTurn 组成可组合接口. 无需自己写工具循环, 同时能控制取证和结束条件.
- 当前 AgentTool<any> 数组上下文里的参数推导不总是具体对象; 主例通过 Static<typeof schema> 做局部断言, 前提是 loop 已完成运行时参数校验. 类型断言不能代替业务验证.
- fauxProvider 可代替付费远端模型驱动真实 loop, 让调度和失败恢复测试确定可复现; 不模拟真实推理质量.
- API 的代价是层次需要自己挑、裸 core 不附送自动压缩或持久任务调度、取消依赖下游支持, 版本迁移会变更包名和工具参数. 把这些具体特征称为现代 API 是评价, 不作跨框架优劣排行.
- 补充代码以相同 1.1.0 包验证类型; MCP、extension 生命周期来自固定文档, 不宣称做过外部服务器集成实测.
- 依据: P2/P4/P13/P15/P17, source/review.ts/check.ts.

## 正文短代码与完整复用件的具体字段已固定

- 满足: G1, G2, G3, G6, G8.
- 主例 review.ts 实际 118 行, TypeScript 参数导出使用 agent-core 的 StreamFn、pi-ai 的 Model/Api 组成 Model<Api>; 第一次 getModel 选择 anthropic/claude-sonnet-4-6, 安装的 1.1.0 模型集合可获取此 ID.
- pi-ai 的 stream/streamSimple 暴露解析后的 AsyncIterable 事件, 调用方消费 text_delta 等事件时不需要自己解析 SSE; 底层传输由 provider/SDK 处理. extension 在 Pi 进程内运行, 同进程与同权限分别依据 P17 原文.
- pi-ai 输入 user message 使用 role/content/timestamp (Date.now 毫秒); 流式 event.type 为 text_delta 时文本在 event.delta, stream.result 返回 AssistantMessage, 含 stopReason. 短片段已经用固定依赖通过 tsc.
- 当前主例 tools 数组上下文的 args 实际推导为 unknown, execute 内用 Static<typeof schema> 断言. Agent 状态含 errorMessage; 无 report 时使用此字段或宿主 Incomplete review 错误.
- 无变更文件时直接返回 ref/base/head/findings:[] 而不启动 Agent. diff 使用 --literal-pathspecs、--no-ext-diff、--no-textconv、--no-renames、--unified=3; read_file 拒绝绝对路径和点/双点路径分段. 依据: 已运行的 source/review.ts 与 check.ts, 为教学工作流的确定选择.
- reportSchema 的 findings 最多 20 条, 每页最多 120 行/16000 字符, git 子进程 maxBuffer=8*1024*1024; beforeToolCall 检查 assistantMessage.content 里的 toolCall 数量. accepted result 返回 terminate:true, finishTurn 在 report 存在或第 12 轮结束.
- article 配套 package.json 的 scripts.test 已设 node check.ts, scripts.review 已设 node review.ts, 故 npm test 与 node check.ts 等价. review.ts 的 console.error 把 tool_execution_end 日志输出到 stderr, console.log 把最终报告写 stdout. 该脚本变化不改变锁文件依赖.
- extension 的 registerCommand 配置含 description 和 handler: async(args,ctx); hello 例将 args 命名 name, 用 ctx.ui.notify(text,'info') 通知. 扩展也有 registerProvider 和 registerMcpServer; 它们并非只属于模型集合或 SDK.
- 跨笔记指向的 OMP 18.8.7 提供 DAP debug、LSP、内置 reviewer 和 task 子代理; 只是同主题阅读指引, 不表示 Pi 示例兼容 OMP. 依据为配套 OMP 知识稿 O1/O2/O11/O14/O18.
- 依据: source/review.ts (wc 118)、source/check.ts、source/package.json、正式侧车 package.json; P4/P15/P17 与 pi-ai 的 types.ts; /tmp/hx-run-pi-api 片段 tsc 退出 0.

## 边界

- 结论限定 Pi 1.1.0 和固定源码 commit, 不回推旧版串行 loop.
- 本例上限 40 变更文件、12 轮模型调用、120 秒 Agent 运行, 每个 Git 子进程输出缓冲 8 MiB. 获取仓库阶段未单独设总超时; 完整历史 fetch 对大仓库有成本.
- 单页按字符限额; 不提供可靠 token 计量. 没有记录每行已被模型理解的覆盖率, findings 空数组不构成正确性证明.
- 新增 HEAD 行限制不支持 LEFT 侧删除行评论; 重命名按 delete/add 处理; 二进制、submodule、大 blob、复杂路径展示与生产权限边界需进一步实现.
- 宿主不暴露 bash 给模型, 仍不能宣称提示注入被完全解决. 真实 GitHub API 取证和真实模型推理未做端到端验证; 本次获取流程使用 mock gh 元数据及本地远端映射.
- AbortSignal 是合作式取消, 不是撤销已完成 I/O. 跨进程文件修改不受 Pi 进程内队列保护.
- 依据: source/review.ts、source/check.ts、source/run.md; P3、P11.

## 延伸判断

- 对 PR 审查框架的判断: 更多可机械校验的报告约束可提高发现的可复核性, 不等同于模型准确率提升. 依据为本例坐标校验与错误恢复设计.
