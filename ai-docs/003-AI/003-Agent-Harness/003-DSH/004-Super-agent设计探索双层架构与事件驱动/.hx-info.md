# Super-agent 设计探索 知识点

## 单 Session 形态的 Agent 让多任务上限取决于人的注意力, 一个人通常只能同时跟进 3 到 5 个活跃 Session

- 现有主流 Agent 以单一 Session 为基本单位, Session 之间彼此独立, 用户并行推进多项工作时要手动切换并记住每个 Session 的上下文.
- DeepSeek Harness 团队的观察值: 一个人通常只能同时跟进 3 到 5 个活跃 Session.
- 单任务的上限取决于模型能力, 多任务的上限取决于人的注意力.
- 在单会话本地 Agent 上加 CLI、MCP 或外部连接器, 仍受制于单会话同步阻塞、多任务上下文混乱、本地设备离线即停止运行.
- 依据: 原文第 1 节"Super-agent"第 3、4 段.

## Super-agent 指跨会话保持上下文、并行推进多任务、事件驱动、常驻在线的 Agent 形态, 由连续 / 高效 / 主动 / 持久四个特征定义

- 连续: 用户在 IM、GitHub 评论等界面交互时只感觉存在一个 Agent; IM 上定方案 A、随后在 Pull Request 评论里改为方案 B, Agent 能跟上.
- 高效: 不等上一个命令或任务完成就能接收下一条指令, 并行完成多个复杂任务.
- 主动: 持续观察环境事件, 主动推进值得处理的事项, 不需要介入时保持安静.
- 持久: 始终在线、接入用户真实工作环境, 长期运行中遇到异常时自动恢复.
- 单个 ReAct Loop 无法同时满足这四个特征.
- 依据: 原文第 1 节"四个基础特征".

## Super-agent 的五个模块与四个特征的对应关系是固定的

- 双层架构支撑连续与高效.
- 事件驱动支撑主动.
- 面向人的交互在交互层面同时支撑连续与高效.
- 计算、状态与环境的分离, 加上 Watchdog, 支撑跨设备的持久在线与异常自愈.
- 每个模块都借用一条计算机系统的经典思想: 双层架构对应序点与分层调度, 事件驱动对应 Fast Path / Slow Path、Cache 与局部性、投机执行, 面向人的交互对应全双工, 分离对应存算分离, Watchdog 对应外部 Control Loop.
- 依据: 原文第 1 节末段, 以及第 3.1、3.3、3.4、4.1、5、6 节各自点名的系统概念.

## 双层架构把"维护全局连续性"交给常驻 Router 层, 把"高并发执行"交给上下文隔离的 Worker 层

- 全部事件进同一个 Session: 上下文最连续, 但受单个 ReAct Loop 串行速度限制, 吞吐低, 多任务细节混杂.
- 每条事件新开 Session: 吞吐最高, 但缺少全局上下文导致结果割裂, 多个 Session 各自回复用户造成混乱.
- 双层架构的 Router 层承接所有入口的人类交互与全局协调, Worker 层并发执行具体任务.
- "双层"是逻辑职责划分, 每层内部可以有自己的结构.
- 依据: 原文第 2 节开头三段.

## Session 应当是系统实现细节, 让用户手动管理 Session 是从底层 LLM API 延续下来的设计惯性

- 现有设计里 Session 同时承载技术上的上下文管理与面向用户的项目管理.
- 产品形态与底层 Session 解耦后, 向用户暴露怎样的任务管理方式成为独立的产品问题.
- 界面上保留的一个会话, 底层可以对应多个 Session.
- 依据: 原文第 2 节"从这个角度看"段与 8.2 节.

## Router 层是全局序点、协调点和记忆, 只做人类交互与任务分派, 可以不配 Bash 工具

- 所有跨任务的信息与决策在 Router 层汇总.
- Router 层不直接执行具体任务, 以免全局节点成为性能瓶颈.
- Router 层与 Agent Team 的 Team Lead 不同: Team Lead 深入单个复杂任务的拆解并高频协调成员, 推理负载重; Router 只处理任务之间的高层关联与分派.
- 用提示词约束 Agent Team 的主会话只交互、不执行, 把不同任务分派给成员独立推进, 也构成双层架构.
- Router 的任务常常不复杂, 较轻量的模型就能兼顾速度与效果.
- 依据: 原文 2.1 节前两段.

## 单个常驻 Router Session 靠批处理扛住突发事件: 上一轮推理期间积压的 Trigger 在下一轮合并进一次 LLM 调用

- 事件流平稳时 Trigger 逐条进入 Router Session, 单次延迟低.
- 事件密集时积压的多条 Trigger 自动合并注入下一次调用.
- 合并后的输入在 Prefill 阶段并行计算, 单次请求耗时的增长远慢于批大小, 单个决定分摊的推理时间随积压增加而下降.
- 上限取决于上下文长度, 以及模型一轮能准确处理多少条 Trigger.
- 依据: 原文 2.1 节"批处理 (Batching)"段.

## Router 层的批处理收益依赖输出短, 会拉长 Router 输出的职责都会抵消批处理

- 批处理摊薄的是 Prefill (输入侧并行); 输出 token 的解码按长度串行, 合并 Trigger 不会让输出变快.
- Router 每步"长输入、短输出"是批处理成立的前提; Router 不执行具体任务、不配 Bash, 等于不产生工具调用链与长输出.
- 7.2 节实测与此一致: 平均 batch 从 1.0 升到 2.8 时, 单次请求耗时只从 2.5 秒升到 3.9 秒.
- 依据: 自行并联推导, 由原文 2.1 节"长输入、短输出"与"不配备 Bash"两句反推, 并对照 7.2 节数据核验 (见发散记录算子二).

## Router 层水平切分的粒度是连续性与吞吐量的同一条权衡, 在全局记忆解决前一直存在

- 规模扩大后 Router 层内部可以做多层过滤, 或水平切分 (Sharding) 为多个会话.
- 切分越细, Router 并发吞吐越高, 分片之间的记忆与上下文连续性越低.
- 在 DeepSeek Harness 团队当前规模下, 单个常驻 Router Session 加订阅直通与链式召回已经够用.
- 依据: 原文 2.1 节末两段与 7.2 节结论.

## Worker 层上下文隔离、挂完整执行工具、配最强模型, 不直接与人交互, 由 Router 统一回复

- 每个 Worker 在独立上下文中专注单一任务, Worker Session 直接决定任务结果与代码质量.
- Worker 的推理过程和工具调用不输出到外部信道, 只向 Router 汇报状态.
- 同层 Worker 之间通常不直接通信; 冲突多出现在同一个 Pull Request 等共享环境, 订阅同一 Thread 的 Worker 收到相同事件, 有机会自行发现并解决冲突; 少数跨任务协同由 Router 中转.
- Worker 内部可以再建 Subagent 或本身是 Agent Team, 对 Router 透明.
- 依据: 原文 2.2 节.

## Super-agent 的驱动输入是环境里的半结构化事件 (Trigger), 而非人类逐条键入的提示词

- Trigger 包括群聊消息、邮件与日程提醒、代码审查评论、CI 运行结果.
- 一条 Trigger 的生命周期依次经过: 两级过滤、订阅与直通路由、Inline & Spill 与链式召回注入上下文、投机执行.
- 依据: 原文第 3 节首段.

## 事件过滤采用程序层 Fast Path 加语义层 Slow Path 的两级策略, 在调用模型前滤掉大部分噪音

- 接入真实群聊与代码平台后, 事件流呈"高噪音、低触发率".
- 程序层按事件来源、群组范围、用户或机器人白名单做确定性准入, 每个来源可设为"仅响应明确请求""作为候选事件"或"直接忽略".
- 通过准入的候选事件交给 LLM, 按提示词编写的策略与上下文判断是否行动; 语义层同时是用自然语言开关或新增策略的扩展点.
- 依据: 原文 3.1 节.

## 已订阅 Thread 的后续事件由程序直通 Worker, Router 只负责未订阅事件的冷启动分派

- Thread 指同一个 GitHub Pull Request、同一个 IM 话题或同一封往来邮件串下的连续事件流.
- Router 依据 Thread 的初始事件创建 Worker, 该 Worker 订阅这个 Thread.
- 已订阅 (Fast Path): 后续事件由程序直接送到 Worker, Router 不再调用工具转发; 事件超出任务范围时 Worker 可取消订阅或交回 Router.
- 未订阅 (Slow Path): Router 仍观测所有事件掌握全局, 只判断和分派未被订阅的新事件.
- Thread 与 Worker 的订阅是多对多关系; 输出侧 Worker 仍把关键结论汇报给 Router.
- 依据: 原文 3.2 节.

## Super-agent 的过滤与路由遵守同一条元规则: 模型只做第一次判断, 判断结果落成程序状态后由代码执行

- 3.1 节的白名单与 3.2 节的订阅表都是"已确定"的判断被固化成的程序状态; 两处都以"已确定"作为进入 Fast Path 的条件.
- Router 对一个新 Thread 的分派是一次模型判断, 分派结果写成订阅关系后, 同一 Thread 的后续事件不再经过模型.
- 系统能绕过模型的比例, 由"有多少判断已被落成状态"决定.
- 依据: 自行换轴归纳, 对照原文 3.1 与 3.2 两节, 同一规律出现 2 次 (见发散记录算子一).

## 上下文窗口按 Cache 管理: Inline 近期会用的信息, Spill 超预算或低频的信息, 窗内只留引用或摘要

- 注入过多会挤占窗口、稀释注意力; 注入过少会迫使模型反复调用工具读取, 增加执行步数.
- 按局部性逐步注入: 从当前对象的 ID 和摘要开始; 再内联紧密关联对象的 ID; 再附时空相邻内容, 例如内容前 50 字、IM 消息的前后相邻消息与被回复消息、代码评论所在评审讨论里的相邻评论.
- 长内容设较小长度上限, 超出部分截断并保留续读入口, 模型需要时再调用工具读取.
- 依据: 原文 3.3 节"Inline / Spill"三步.

## 链式召回把 Trigger、Thread、Worker Session 等对象连成引用图, 每一跳召回结果都内联下一跳的摘要与 ID

- 每类对象有唯一 ID, 注入时内联紧密关联对象的 ID.
- 召回结果本身也遵循 Inline & Spill, 所以模型可以从当前事件出发顺着引用关系逐跳展开.
- 示例路径: 当前消息, 所在 Thread, 相关 Worker Session, 该 Worker 关联的另一个代码评审 Thread.
- 链式召回缓解 Router 在长程运行中丢失先前信息的问题, 主要覆盖近期任务与会话历史.
- 依据: 原文 3.3 节末段与 8.1 节.

## 链式召回需要当前事件里至少带一个关联 ID, 纯自然语言的跨信道指代没有起点

- 链式召回每一跳都沿"内联的 ID"走, 原文示例也从"当前消息所在 Thread"起步.
- 在 IM 里只说"上周那个方案"而不贴 Pull Request 链接时, 当前事件与旧任务之间没有引用边.
- 这种场景的代价落在跨信道、无链接追问旧任务的用户身上, 发生在第一次这样提起几周前的任务时.
- 依据: 自行拆代价推导, 对照原文 3.3 节对链式召回的定义 (见发散记录算子四).

## 投机执行让 Agent 根据环境信号在后台先试, 有价值才交付, 没价值就丢弃并保持安静

- 用额外后台算力换人的等待与介入成本.
- 个人助手场景: 收到会议邀约时先在后台核对日程冲突、搜集背景、备好回复草稿, 用户过目后确认发出.
- 研发场景: DeepSeek Harness 内部用户群配置了"静默复现并修复"策略, 群里有人反馈问题时 Agent 先在后台复现并找修复, 只有确认问题且找到简单修复才交付, 否则全程安静.
- 依据: 原文 3.4 节.

## 异步 ReAct Loop 让耗时工具调用立即返回 Started, 结果完成后作为新事件投递回会话, 从而实现全双工交互

- 经典 ReAct Loop 发起同步 run() 后阻塞到工具返回, 期间不能响应新输入.
- 异步版本: 模型发起耗时命令或子任务后立即收到"已启动 (Started)", 循环不等待; 后台完成后系统把结果作为一条新事件消息投递进会话; 模型可以按上下文主动终止执行过久的后台命令.
- 新输入在当前推理步结束后即被处理, 不等后台工具完成.
- 该机制已在 DeepSeek Harness 中实现, 截至原文发布时尚未默认开启.
- 具体工具名 [不确定]: 原文以内联代码给出, B 站接口返回为空.
- 依据: 原文 4.1 节.

## 多信道交互按信道带宽定输出规范: IM 低打扰、单次回复不超过 100 词, GitHub 与邮件结构化高密度

- 把面向单人终端的输出 (冗长推理、密集工具调用) 直接搬进群聊, 在多人协作中会造成信息过载.
- 双层架构已把推理和工具调用隔离在 Worker 内, 由 Router 统一对外.
- IM 等即时信道: 只在需要决策或验收时通知, 只问直接问题、给简短结论; DeepSeek Harness 团队验证过的硬性规定是单次回复不超过 100 词.
- GitHub、邮件、文档等异步信道: 按项目规范写完整的问题背景、改动说明与验证结果, 或起草结构化邮件与文档摘要.
- 依据: 原文 4.2 节.

## 存算分离第一步把 Agent Loop 的计算放进云端无状态容器, 把 Session 等持久状态放进数据库

- 本地 Agent 默认把计算、会话状态、执行环境绑在同一台设备, 设备休眠或离线 Agent 就停止.
- 无状态计算容器可以水平扩展、重启或替换, 会话与任务的连续性由持久化存储保障.
- 依据: 原文第 5 节首段与 5.1 节.

## 存算分离第二步让执行环境留在原地, 端侧只部署一个不保存会话状态、只执行命令并返回结果的轻量 daemon

- 云端沙箱重建环境的问题: 真实环境含未提交的本地修改、私有凭据、内网服务依赖、特定硬件或工具链, 同步成本高且易遗漏.
- 让用户迁到云端工作的问题: 迁移成本过高.
- 端侧 daemon 方案与 Anthropic 提出的"脑手分离"(Decoupling the brain from the hands) 一致: harness 无状态, 会话日志存在 harness 之外, 通过统一接口按需接入执行环境.
- 两者区别在场景: Anthropic 那篇针对托管服务 (按需沙箱、客户 VPC 内资源), 本方案首先接入会间歇离线的个人机器.
- 支持 BYOM (Bring Your Own Machine), 也支持云托管机器; 设备重新上线后, 云端 Agent 自动触发需要在该设备上执行的任务.
- 依据: 原文 5.2 节.

## DeepSeek Harness 的能力接缝是 5.2 端侧 daemon 的接入点: 换文件服务与子进程服务的 provider 即可整体迁移执行环境

- 本仓 DSH Runtime 笔记记录: 上层工具只依赖统一的文件服务与子进程服务, 同时替换两者的 provider 就能把整个执行环境迁到远程沙箱.
- 端侧 daemon 在这一结构里对应一个新的 provider, consumer (面向模型的工具) 不需要改.
- 依据: 实测, 查 `ai-docs/003-AI/003-Agent-Harness/003-DSH/002-DSH-Runtime设计思想插件树与事件日志/index.md` 的"五、能力接缝"一节.

## Watchdog 是主系统之外由定时消息驱动的独立 Agent Session, 既监控基础设施存活, 也由模型判断任务是否有实质进展

- 持久在线的分布式系统难以只靠主系统内部逻辑保证长期可靠, 需要独立的外部 Control Loop.
- Agent 系统的许多异常源于模型陷入无效循环或偏离目标, 进程并未崩溃, 进程存活探测与监控脚本查不出来.
- Watchdog 处理接口报错、状态恢复失败, 并判断各 Worker 是否有实质进展、方向是否偏离整体目标; 外部偶发故障则持续复查直到恢复.
- Watchdog 本身具备完整工具能力, 维护者可用自然语言问故障原因, 或让它在线增删提示词、调整触发规则.
- 依据: 原文第 6 节.

## Watchdog 的自愈动作以计算与状态分离为前提

- 修复一个卡死的 Agent Loop, 等于丢弃当前计算容器、从持久状态重建.
- 计算与状态仍同居一台机器时, 重启计算会连带丢失状态, Watchdog 只能告警.
- 原文第 6 节以"除了第 5 节的存算分离, 还需要"开头, 把两者并列为持久在线的两个条件.
- 依据: 自行并联推导, 对照原文 5.1 节"无状态计算容器可重启或替换"与第 6 节"状态恢复失败" (见发散记录算子二).

## 消融实验中 Super-agent 的完成时间 p50 为 12.4 分钟、p95 为 15.7 分钟, 优于单 Session 加 Subagent 工具

- 实验前提: 群聊加 GitHub CI 消息流, 单次约 300 条消息, 其中约 20 条工作请求; 编码工作用只消耗时间的工具代替, 衡量调度与协作而非单任务执行; 每种方案重复 5 次; 合成负载与简化环境, 作者定位为初步参考.
- 单 Session 加 Subagent、中性提示 ("Use a subagent for a piece of work when appropriate..."): 5 次运行中 0 次调用 Subagent, 所有工作在主 Session 执行并被新消息打断, p95 为 29.5 分钟.
- 单 Session 加 Subagent、优先委派提示: 5 次中 4 次委派, 完成时间缩短但仍慢于 Super-agent; 剩下 1 次模型判断工作"很小"而自己执行, 形成长尾.
- 双层架构让"分不分工"由系统结构决定, 不依赖提示词与模型临场判断.
- Super-agent 维护多个独立会话, 单次实验的读缓存 token 高于单 Session.
- 依据: 原文 7.1 节.

## 去掉订阅直通后完成时间基本不变, 但 Router 决定数增加约 30%, 总读缓存 token 从 2323 万增至 3177 万 (约 37%)

- 直通在该实验负载下不提高完成质量与速度, 节省的是 Router Session 的 token 与推理开销.
- 去掉直通使 Router 峰值负载增加, 仍未触及单 Router 的吞吐瓶颈.
- 依据: 原文 7.1 节末段与 7.2 节末段.

## Router 压测中 Trigger 到达速率从约 1 条/分钟升到约 40 条/分钟时, 单个决定分摊的推理时间从 6.4 秒降到 1.6 秒

- 压测设置: Router 调用真实模型, Worker 使用 Mock 模型.
- 平均 batch 大小从 1.0 升到 2.8, 单次请求耗时从 2.5 秒升到 3.9 秒.
- 突发拥堵时 Router 靠自动合并积压事件提高有效吞吐.
- 依据: 原文 7.2 节.

## Super-agent 仍有四个未解问题: 双层架构如何扩展、脱离 Session 后如何与人协作、上下文边界与 A2A、安全与隐私

- 扩展: Router 何时切分与粒度、Worker 何时直接通信与协作拓扑未定; 针对 Router 的事件判别、批量分派与上下文召回做专项训练是系统与模型协同设计 (Co-design) 的方向; 跨月的长程记忆是可扩展性的主要瓶颈.
- 协作: 以聊天窗口为中心的交互被视为路径依赖; 交互可放进 GitHub Issue 与 Pull Request 等领域界面; 中途介入、接管、实时协同的产品形态待探索.
- 边界: 组织决定如何配备 Super-agent, 等于划分上下文共享与隔离的边界; 隔离实例之间的协同即 A2A (不特指某个协议).
- 安全: 事件驱动扩大了不可信输入面; 云端 Agent Loop 一旦被入侵或被提示词注入攻破, 连接的全部端侧设备面临被控风险; 凭据进入模型上下文即有泄露风险, 需要让 Agent 不接触凭据本身而使用凭据.
- 依据: 原文第 8 节.

## 可复用件

- 规格件: 一个最小 Super-agent 调度骨架需要的五个数据结构与两条路径.
  - `Trigger { id, source, thread_id, summary, ref_ids[] }`: summary 为截断后的摘要 (原文示例前 50 字), ref_ids 为内联的关联对象 ID.
  - `AdmissionRule { source, scope, mode }`: mode 取 `explicit_only` / `candidate` / `ignore`, 对应原文"仅响应明确请求 / 作为候选事件 / 直接忽略".
  - `Subscriptions: thread_id -> set[worker_id]`: 多对多.
  - `RouterInbox`: Router 推理期间到达的 Trigger 先入队, 下一轮整队注入一次 LLM 调用.
  - `AsyncTask { id, status: started|done|killed }`: 异步工具调用立即返回 started, 完成后以新 Trigger 投递.
  - Fast Path: `AdmissionRule` 判 ignore 则丢弃; `thread_id` 在 `Subscriptions` 中则直接投递给全部订阅者.
  - Slow Path: 其余进入 `RouterInbox`, 由 Router 决定新建 Worker 并写入 `Subscriptions`.
- 字段名为本笔记自拟, 原文只给出语义; 原文 4.1 节的异步工具真实名称 [不确定].
- 依据: 字段语义逐条对应原文 3.1 (准入模式)、3.2 (订阅多对多与直通)、3.3 (ID 与摘要内联)、2.1 (积压批处理)、4.1 (Started 与终止).
- 侧车件: 同目录 `super_agent_sidecar.py`, 按上面的规格写成只用标准库的最小实现, LLM 由确定性 mock 函数代替, `python3 super_agent_sidecar.py` 直接运行.
  - 核心函数 `dispatcher(router, workers, stats)`: 从 `DISPATCH_Q` 取 Trigger; `admit(t)` 不通过则 `stats["dropped"]` 加 1 并跳过; `t.thread_id` 在 `SUBSCRIPTIONS` 中则 `stats["direct"]` 加 1, 逐个调用订阅者的 `workers[wid].handle(t)`; 否则 `stats["to_router"]` 加 1, 放进 `router.inbox`.
  - 准入规则表名为 `ADMISSION` (source -> mode), 其中 `bot` 为 `ignore`.
  - 内置演示的 5 条突发: m1 (im-42, "登录页按钮错位, 谁能修一下"), m2 (bot, "[机器人] 今日站会提醒"), m3 (pr-7, "PR #7 review: 缓存层加个 TTL"), m4 (im-99, "中午吃什么"), m5 (pr-8, "CI 失败: test_auth 超时"). m2 被 `ADMISSION` 丢弃; 其余 4 条在 Router 的一次 mock 调用里分派 (batch=4), m1 / m3 / m5 分别新建 worker-1 / worker-2 / worker-3 并订阅 im-42 / pr-7 / pr-8, m4 被 mock 判为忽略.
  - 跟进: m6 (im-42, "顺便把 hover 颜色也改了") 直通 worker-1; m7 (pr-7, "跑测试看看") 直通 worker-2, worker-2 发起 task-1, 立即返回 Started; task-1 完成后以 `source="task"`, thread_id=pr-7, 内容 "task-1 完成: 12 passed" 的 Trigger 回投, 因 pr-7 已被订阅而直通回 worker-2.
  - 实跑输出末尾统计: 丢弃 1, 直通 3, 进 Router 4; Router 调用 1 次, 做了 4 个决定.
  - 代码内名称 (`DISPATCH_Q`, `ADMISSION`, `admit`, `SUBSCRIPTIONS`, `router.inbox`, `stats`, `Trigger.summary` 取前 50 字, `ref_ids`) 均为自拟.
  - 依据: 本目录侧车 2026-11-01 实跑输出; 演示数字只说明侧车行为, 与原文实验无关.

## 边界

- 原文自述是架构思路探讨, 不是 DeepSeek Harness 现有产品功能介绍; 原文实现插件名在接口返回中为空, [不确定], 原文称其为验证路线的原型, 非正式产品.
- 第 7 节全部数字来自合成负载与简化环境, 编码工作被只耗时的工具替代, 不能外推为真实编码任务的完成时间.
- 双层架构的收益在高并发场景下测得 (约 300 条消息含约 20 条工作请求); 任务少且串行的个人场景未测, 多会话的额外 token 开销在这种场景下没有对应收益, 付款人是按 token 计费、日均只有一两个任务的用户.
- 投机执行的代价是被丢弃尝试的算力: 给高噪音群配置"静默复现并修复"的维护者, 在出现一串最终不是 bug 的讨论时承担复现的 token 与 CI 费用.
- Worker 不直接面对人, 在 IM 里追问汇报之外实现细节的评审者需要等 Router 再次召回或转问 Worker, 多一跳延迟.
- Router 批处理只在约 1 到约 40 条/分钟的到达速率区间测过; 更高速率下的行为原文未给出.
- 链式召回覆盖近期任务; 跨月长程记忆原文列为未解问题.
- 已证伪的推测: Inline & Spill 与 Fast Path / Slow Path 不属同一条元规则. Inline & Spill 决定注入多少信息, 不决定是否绕过模型.
