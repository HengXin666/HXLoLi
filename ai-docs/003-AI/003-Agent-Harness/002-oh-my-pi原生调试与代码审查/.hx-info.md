# oh-my-pi 的功能与原生调试: 对比 Pi 和 Codex 知识点

## oh-my-pi 基于 Pi 演化并加入调试、语义分析和协作工具

- 满足: G1, G5.
- 本次固定 can1357/oh-my-pi 的 commit `d485860ba15c3fce2b0e2c1a02c0d88c8f53c448`, coding-agent 版本 18.8.7, 包为 `@oh-my-pi/pi-coding-agent`, CLI 名为 `omp`. 源码使用 Bun, 性能相关能力还包含 Rust N-API 组件.
- OMP 的工具范围覆盖 read/write/edit、grep/glob/ast_grep/ast_edit、bash/eval、lsp/debug、task/wait、browser/computer、memory 等. Pi 上游当前接口和 OMP fork 接口不能互换.
- 深入范围为 debug、与 review 有关的语义查询/变更工具及调度; 图像、语音、桌面控制、web_search、MCP、记忆、会话回退等列举用途即可.
- 依据: source/provenance.md O1、O2; packages/coding-agent/package.json、LICENSE.

## OMP 原生代码调试通过 DAP 客户端驱动真实调试器

- 满足: G2.
- 调用链为 `模型 debug 参数 -> DebugTool.execute -> DapSessionManager -> DapClient -> 调试适配器 -> 被调试程序`.
- Debug Adapter Protocol (DAP) 是调试客户端与适配器之间的消息协议. 模型使用 JSON 工具接口; OMP 把动作转换成 DAP 请求; lldb-dap/GDB/debugpy/Delve 等负责运行程序、断点、栈帧与变量.
- OMP 中“原生”表示 agent 能直接接入实际调试流程. 不能由此推出调试器在模型内实现, 或把 pi-natives 的 Rust 插件当成全部 DAP 逻辑. 当前 DAP 管理器和客户端实现在 TypeScript.
- 模型工具 `debug` 与交互命令 `/debug` 也有区别; 后者包含 OMP 自身日志、性能、SSE、报告等调试菜单.
- 依据: O2 DebugTool.execute、O3 DapClient、O4 DapSessionManager、O7 Source/Flow.

## DAP 用请求编号关联异步响应, 用事件报告运行状态

- 满足: G2, G4.
- DAP 帧由 `Content-Length: <字节数>\r\n\r\n` 和 JSON 正文组成. 客户端需要按字节读取完整消息, 不能把每行当一个 JSON.
- 请求具有 seq/type=request/command/arguments; response 的 request_seq 匹配 pending Map 中的 Promise. 响应到达顺序不要求与请求发送顺序一致.
- stopped/continued/output/terminated 等 event 不对应普通请求返回; 会话管理器监听并更新状态.
- OMP 支持 stdio、socket 和 TCP 连接形态, 按适配器定义选择; 例如 lldb-dap 默认 stdio, dlv 使用 socket, 一些适配器需要本地 TCP 服务.
- 底层能够关联多个未完成请求, 不代表上层可以让有状态的 step/evaluate 任意并发.
- 依据: O3 sendRequest/#handleMessage/消息读取循环, O6 defaults.json; source/dap-demo.py 的 pending 和 reader.

## DAP 启动必须让 launch 与配置握手交错进行

- 满足: G2, G3.
- 生命周期为 initialize 获取 capabilities, 发 launch/attach, 等 initialized, 配置断点并按能力发送 configurationDone, 最后等启动请求完成和 stopped 事件.
- 某些适配器的 launch 响应等待 configurationDone. 代码若先 `await launch` 再做配置就会互相等待. OMP 先保存 launch Promise, 完成握手后再 await.
- OMP 在发 launch/continue 前订阅 stopped 事件, 避免目标快速停住时事件先到、监听后装. 独立 Python 例子用持续 reader 和事件队列保留先到事件.
- OMP 默认适配器配置包含 stopOnEntry, launch 工具结束后可再设断点继续. Python 协议例子在初始 configurationDone 前先设断点, 不要求与 OMP 工具包装层完全相同.
- 依据: O4 launch/attach/#completeConfigurationHandshake/#prepareStopOutcome; source/dap-demo.py 实测顺序.

## OMP 用会话树保存调试状态, 当前只允许一个 root 调试会话

- 满足: G2.
- DapSessionManager 管理 adapter、capabilities、线程、栈帧、停止位置、断点、输出与运行状态; root 会话可含适配器反向 startDebugging 请求创建的 child.
- stopped child 会成为 active target. runInTerminal 反向请求由宿主创建 debuggee 进程, 不把该请求伪装成普通模型工具调用.
- 断点变更通过专用队列串行处理并向会话树同步; 新 child 在 configurationDone 之前接收断点状态.
- 单次请求默认超时 30 秒; debug 工具 timeout 为 5..300 秒; 输出缓存上限 128 KiB; 空闲会话超过 10 分钟由每 30 秒执行的清理检查处理.
- 单 root 限制意味着不能把独立 PR 的调试会话当无状态函数扔进同一个管理器随意并发.
- 依据: O4 #ensureLaunchSlot/#registerSession/#serializeBreakpointMutation、O7 Limits & Caps.

## OMP 的 debug 参数覆盖断点、步进、变量和内存, 部分动作受适配器能力限制

- 满足: G2, G3.
- 常用调用依赖为 `launch -> set_breakpoint -> continue -> stack_trace -> scopes -> variables -> evaluate -> terminate`.
- launch 接受 program、adapter、cwd、args; set_breakpoint 接受 file/line 或 function; evaluate 接受 expression、frame_id、context; variables 接收 variable_ref 或 scope_id.
- OMP 包装层中的变量命名是 snake_case, DAP 原始请求通常使用 frameId、variablesReference、threadId 等 camelCase. 把工具参数原样转发给 DAP 会出错.
- 当调用省略 frame_id 等选择项时, 包装层可使用当前 stopped frame. 取证记录仍建议保存实际 frameId、线程与源码行, 避免混用不同停止状态.
- disassemble/read_memory/write_memory、模块等动作检查 initialize 返回的能力; 有 debug 工具不代表每种调试器都支持每一动作. evaluate 表达式和 repl 命令依语言/适配器解释, 不视为绝对无副作用的读操作.
- 依据: O2 debugSchema/execute 各 action, O4 scopes/variables/evaluate, O7 输入表和 Action-specific requirements.

## debug 的工具结果把观测文本交给模型, 把会话快照交给宿主

- 满足: G2, G3.
- DebugTool 返回 content 文本和 details; details 包括 action、snapshot、以及 stackFrames/variables/evaluation 等动作对应字段. 失败通过抛出异常进入失败工具结果.
- 模型依据 content 中实际观测到的变量和状态继续推理. UI 可以使用 details 渲染卡片; 不能用一张状态卡片证明模型读到了未加入 content 的数据.
- debug execute 本身不使用 onUpdate 持续推送进度, 返回是单次结果; 会话内持续 output 事件与工具调用输出区分处理.
- 本次最小程序为 `int values[3]={10,20,30}; int i=3; return values[i];`. 在 return 前断住, 实际得到 frame=main、line=4、values 类型 int[3]、i=3, evaluate i 返回 3.
- 该观测支持特定输入下索引越界; 不需要执行越界读取并等进程崩溃才成立. C 未定义行为不保证每次表现为 crash.
- 依据: O2 返回结果构造, O7 Outputs; source/dap-demo.py 与 source/verification.log.

## OMP 的共享与独占工具通过 Promise 屏障安排执行顺序

- 满足: G4.
- 工具 `concurrency` 可为 shared、exclusive 或依据已校验参数决定的函数; 未指定时默认 shared; resolver 抛错时保守回退 exclusive.
- shared 调用等待最近 exclusive 完成, 同一屏障之后的 shared 可并发. exclusive 等待最近 exclusive 和此前所有 shared; 后续 shared 又等待当前 exclusive.
- debug、edit、write 标为 exclusive. 序列 read-A/read-B/debug-step/read-C 的实际约束是前两个读重叠, 完成后 step, step 完成后最后一个读.
- Pi 上游 1.1.0 的 per-tool sequential 会让整批串行; OMP 此屏障保留独占前后的共享批次并发. 字段名、默认策略和粒度不同.
- source/barrier-demo.mjs 是对调度规则的短复现, 已断言上述顺序. 工具内还有独立的会话、文件或 LSP 状态约束, 不能只看一层 Promise 判断全系统可并行.
- 依据: O8 executeToolCalls 3770 行附近的 lastExclusive/sharedTasks; O2 concurrency; O9 concurrency; source/barrier-demo.mjs.

## 调试动作取消只结束客户端等待, 不等于目标进程已终止

- 满足: G2, G4.
- OMP DapClient 的 abortHandler 删除 pending 请求并 reject, 超时也拒绝 Promise; 当前实现该路径不发送 DAP cancel 或自动 disconnect.
- 已发送的 continue/evaluate 等请求仍需考虑目标端状态. 调用方想停止会话时应显式 terminate/disconnect, 然后按结果确认清理.
- 本次设计建议为“每条动态审查假设”持有启动、观察与清理生命周期, finally 中负责结束自己启动的目标; 请求 timeout 不替代清理.
- 对有副作用的 evaluate 或 write_memory, 超时不能当作“操作肯定没发生”而无条件重试.
- 依据: O3 sendRequest abortHandler/timeout, O4 terminate 与 dispose; 本次推导见 source/divergence.md.

## 步进改变目标状态后, review 证据需要重新读取栈帧与变量引用

- 满足: G3, G4.
- 本次设计建议: 一份动态证据记录 commit/build、输入、断点位置、停止线程、调用栈、变量与预期差异.
- frameId 与 variablesReference 属于当前调试状态下的引用, 不作为跨 continue/step 的持久身份. 继续运行后重新取得停止状态和栈帧, 再求值或展开变量.
- 阅读两个独立源码文件能并发, 单步后才能确定的栈帧和变量查询有数据依赖. 模型需要看完 stack_trace 结果才生成依赖其中 frameId 的 scopes 参数, 或让封装工具内部完成该依赖链.
- 依据: O4 继续动作清理停止状态及获取 top frame 的路径; source/dap-demo.py 的查询链; source/divergence.md 换轴推导.

## OMP 的 read 可把 PR diff 当作按文件读取的资源

- 满足: G4.
- `read({path:"pr://owner/repo/123"})` 读取 PR, `.../diff` 列出变更文件, `.../diff/1` 读取第一个文件 diff, `.../diff/all` 读取全量.
- handler 使用 gh 与 SQLite-backed GitHub 缓存, 内容带 freshness 提示. 1-based diff index 是该次清单的索引, 不是稳定文件 ID 或源码行号.
- review 先读取文件目录再选择 diff 切片, 可减少一次性塞入无关内容. 输出受截断时要继续获取, 不能把前半段当完整 PR.
- 本次设计建议把 PR head 记录在审查结果中, 发现新提交后重新取目录与 diff, 防止缓存、切片编号和源码版本混用.
- 依据: O13 ParsedPrDiff/resolvePrDiffResource/formatFileLine; 固定版本证据建议见配套 Pi 知识稿.

## OMP 的 LSP 和 AST 查询可补足 diff 外的调用关系

- 满足: G4.
- lsp 提供 diagnostics、definition、references、hover、symbols、type_definition、implementation、rename、rename_file、code_actions、request 等操作. review 可优先使用诊断、定义、引用和符号导航.
- LSP 根据项目 root markers、文件类型和可用 server 启动; 语义查询前同步磁盘文本并丢弃陈旧诊断, 一部分查询需要等待项目加载.
- OMP 工具位置使用 1-based line, 并通过 symbol 找列; 原始 LSP 位置与工具包装接口不可混写. 没有启动合适语言服务时, 返回空结果不证明不存在引用.
- rename/rename_file 默认应用修改, 预览必须 apply:false; code_actions 默认列举, apply:true 才应用. lspReadOnly 会拒绝写动作, 适用于审查角色.
- ast_grep 适于语法结构模式查找, grep 适于文本匹配; 查到 producer 后应再用 references/搜索确认消费端的分支和路由.
- 依据: O11 LspTool、O12 Inputs/Flow/rename, O1 ast_grep 概览, O14 cross-boundary 审查准则.

## OMP 当前 hashline 使用快照标签和行操作, 输入不是 unified diff

- 满足: G4.
- 当前 hashline schema 为 `{input:string}`. 示例形式为 `[src/example.ts#1A2B]` 后接 `PUT 4.=4:` 和 `+新文本`; TAG 必须来自实际最近 read/grep/edit, 示例标签不能照抄到真实文件.
- PUT/CUT/MV/REM 针对指定快照的原始行或语法块. Rust pi-edit 负责解析、快照和编辑计算; TypeScript edit 层负责集成写入、预览与 LSP.
- 已读范围、快照陈旧程度与安全恢复决定编辑是否成立; 独占调度不免除这些校验. 流式预览还不能替代最终重读与验证.
- edit 结果可带 unified diff、firstChangedLine、诊断和受限 before/after snapshots. 读源码学习编辑机制时要区分模型输入语言和宿主展示输出.
- 早期按每行 LINE:HASH 的介绍不能直接解释当前此 commit 的输入; 文中展示当前语法并给固定版本.
- review 若仅输出 findings 不必启用编辑工具. 修复阶段在隔离副本中应用并验证, 与取证阶段分开控制.
- 依据: O9 EditTool/prepare 参数与 native bridge, O10 Input/Canonical patch language/Outputs/Errors.

## OMP 内置 reviewer 要求发现有 diff 锚点, 默认没有动态调试工具

- 满足: G3, G4.
- 内置 reviewer 的工具表包含 read/find/grep/glob/bash/lsp/web_search/ast_grep, 没有 debug; prompt 规定 bash 只用于读 diff/log/show, 禁止编辑与触发构建.
- findings 包含 title/body/priority/confidence/file_path/line_start/line_end, 要求位置与 diff 重叠、范围不超过 10 行, 描述具体触发与影响; 还要求追踪跨模块消息的消费者分发点.
- 当前 reviewer 通过 incremental yield sections 逐步提交 findings 和 verdict, 不应把旧版 submit 工具教程套上去.
- 本次设计建议: 需要动态验证时建立具有有限执行工具的 verifier, 接收“固定 commit + 可复现输入 + 待验证假设”, 返回观测证据给 reviewer; 或明确修改 reviewer 契约使其允许构建/调试.
- 增加角色是扩展设计, 不是说源码内置 reviewer 已完成该流程. 仅把 debug 塞入工具表仍与原 prompt 禁止构建的要求冲突.
- 依据: O14 frontmatter/procedure/cross-boundary/output; O2 debug 工具接口; source/divergence.md 跨源并联.

## OMP 的 review 分发随模式变化, 多 reviewer 并非所有调用的默认行为

- 满足: G1, G4.
- 普通 review prompt 按推荐 agentCount 生成 task 指令, 可以把相关目录/实现与测试放在同一 reviewer 任务中; task 是多 agent 工作分发.
- headless 模板明确要求只创建 1 个 reviewer task. 不能从 README 的并行 review 宣传推导 headless 总会启动多个 reviewer.
- diff 超过 50000 字符或超过 20 个文件时, prompt 使用每文件预览和继续取证指令. 缩略内容仍需 reviewer 补读.
- 分工按文件切分时仍要检查跨目录消费者; findings 汇总可按 head/path/行区间/缺陷原因去重. 去重规则为本次建议, 不当作已验证上游实现.
- 依据: O15 buildReviewPrompt、O16 headless 模板、O17 Distribution Guidelines; O14 cross-boundary.

## 一个小型 DAP 复现足以展示原生调试的接口依赖

- 满足: G3, G6.
- 触发场景: 静态阅读已提出一个具体运行时假设, 需要观察停止位置和变量来确认.
- 最小复用件为 Python 标准库脚本 + 本机 clang + lldb-dap; 脚本编译 5 行 C 程序, 启动适配器、配置断点、读取栈/变量、求值并关闭.
- 机械判据为断点 verified, frame.line==4, evaluate i==3, 请求编号正确配对, finally 能关闭适配器; source/dap-demo.py 已实跑.
- 调度复用件为 source/barrier-demo.mjs, 只包含共享/独占屏障和顺序断言. 代码用于解释接口与依赖, 不复制 OMP 完整子系统.
- 写法偏好: 正文先展示几次 debug 工具调用, 再拆解 DAP 握手和调度; 代码保持可完整展示. 其余 provider、UI、memory 功能只做用途清单.
- 运行: `python dap-demo.py` 和 `node barrier-demo.mjs`. 本次 Python 3.14, LLDB/clang 23.1.1, Linux x86_64.
- 依据: source/run.md、source/verification.log、source/dap-demo.py、source/barrier-demo.mjs.

## 动态验证的环境成本应按具体假设控制

- 满足: G3, G6.
- 本次建议先让 reviewer 从 diff、调用链与静态诊断提出假设, 再按需启动调试验证. 每条验证保存输入、断点、观测与退出动作.
- 复现者需要目标语言工具链、符号和环境. 调试构建以未优化配置更容易对应源码; 优化构建或缺失符号不能保证局部变量可读.
- 本次第一次 LLDB 运行受外部调试符号查询拖延而超时; 在样例子进程设置 DEBUGINFOD_URLS 为空并以 initCommands 禁用 symbols.enable-external-lookup 后通过. 该开关是样例运行条件, 不是 OMP 固定默认值.
- 付款任务是搭建和维护每个被审项目的可复现调试环境; 无法获得环境时应保留未验证假设, 不伪造变量观测.
- 依据: source/run.md 中的失败与修复记录, source/dap-demo.py; source/divergence.md 拆代价.

## OMP 功能清单按源码注册表和产品入口分别说明

- 满足: G7.
- 固定源码 BUILTIN_TOOLS 的 30 个入口为 read/security_scan/bash/edit/ast_grep/ast_edit/ask/debug/ida/eval/github/glob/grep/find/lsp/checkpoint/rewind/context_notes/new_context/task/wait/todo/web_search/write/memory_edit/retain/recall/reflect/learn/manage_skill. HIDDEN_TOOLS 另有 think/yield/goal. 注册工厂在启用条件不满足时返回空, 不能把列表当当前模型全可调用列表.
- 文件检索包括本地文件、目录、URL、PDF、SQLite、归档与内部协议; read/write/edit 和 grep/glob/find, ast_grep 做结构查询, ast_edit 做 staged 改写, xd://resolve 接受提案. READ/WRITE 的协议能力需看具体 handler, 不保证所有协议都可写.
- 执行包括 bash 的持久 shell/native utilities、eval 的持久 Python 与 Bun worker, eval 可回调 agent 工具. Rust N-API 处理部分搜索/编辑/shell, 不据 README 宣传数字作性能结论.
- 代码理解含 LSP、DAP、IDA 接口; ida 需要本机 IDA idalib 且 ida.enabled, 这里只列用途. security_scan 驱动 Codex Security 云扫描, 不是独立于 Codex 的同名扫描引擎.
- 协作含 task/wait/todo/ask、类型化 yield、隔离 worktree (可选)、Agent Hub、advisor 第二模型、/collab 共享会话、/review 和 /annotate code-review. 隔离工作树不保证逻辑改动不存在冲突.
- 上下文和记忆含 checkpoint/rewind、context_notes/new_context, retain/recall/reflect/memory_edit, learn/manage_skill; backend 可选 local/Hindsight/Mnemopi. TTSR 根据流中 regex 中止后注入规则并重试, 是行为纠偏, 不能当权限沙箱.
- 桌面/网页有 eval browser helper (Chromium/Electron/tab)、computer helper (窗口/截图/输入/辅助功能树)、web_search; README 还列 generate_image/tts. browser/computer/generate_image/tts 不在上述固定 BUILTIN_TOOLS 表, 实际可通过 helper/可发现工具或扩展入口暴露; 不能把它们都展示成同一类默认直接工具.
- tools.xdev 开启后 read xd:// 枚举可发现工具, write xd://<tool> 调用. README 标 github/security_scan/generate_image/tts/checkpoint/rewind 及按 backend 的记忆工具默认关闭.
- 开仓库按设计加载项目 settings/extensions/hooks/tools/commands/skills/rules/MCP 配置; MCP 属于产品扩展面, 与 Pi/Codex 均有交集.

- Bun 安装命令 bun install -g @oh-my-pi/pi-coding-agent@18.8.7, 运行 omp; 实际适配器与语言服务器需安装和配置. README 要求 Bun >=1.3.14.
- 依据: O1 README 01..21/Tools/Prompt controls/Session controls/providers, O18 tools/index.ts, O19 ida tool, O20 context tool files.

## 与 Pi 的差异主要在内建工具深度, 当前上游已经有 MCP 和 codemode

- 满足: G8.
- Pi 1.1.0 提供分层库/CLI/SDK/extension, 默认 read/bash/edit/write, 核心可替换与可组合; OMP 18.8.7 把 DAP/LSP/PR 协议/结构化 reviewer/子代理/advisor 等整合进产品.
- Pi README 不内置 subagents/plan mode, OMP 有 task 和 plan 相关入口. 当前 Pi 有 MCP、codemode 和 tool_search, 不能作为 OMP 独有差异.
- Pi 当前默认同轮并行, sequential 工具让整批串行; OMP 使用 shared/exclusive 屏障. Pi 的文件 edit 是 edits oldText/newText 数组与每文件写队列, OMP 当前 hashline 是文件快照 TAG + PUT/CUT/MV/REM.
- 对比侧重接口与内置能力, 不使用未复现的 README 性能/成功率数字. OMP 维护自己的包、运行时与类型, 不能假设上游 Pi 1.1.0 示例只换包名就兼容.
- 依据: O1/O8/O9/O10, Pi P2/P3/P9/P11/P16/P17/P18.

## Codex 对照应区分 CLI、SDK、App Server 和 app/web

- 满足: G8.
- 官方 CLI 提供读/改/运行、/review 和 codex exec; exec 适合脚本/CI, stdout 最终结果、stderr 进度、--json 事件. GitHub 集成提供 @codex review 和自动审查.
- 当前 Codex 官方文档有 subagents (当前版本默认启用)、MCP (stdio/HTTP/OAuth)、skills. 不能说只有 OMP 支持多代理/工具扩展/可复用规则.
- Codex SDK 的 TS @openai/codex-sdk 用 new Codex().startThread()/thread.run()/resumeThread, 主要自动化已有 Codex 线程; App Server 暴露 thread/start、turn/start、turn/interrupt 和审批/历史/事件. experimental dynamicTools 通过 item/tool/call 回调客户端, 需 capabilities.experimentalApi=true, 因此不能写 Codex 不能自定义工具.
- Codex 文档明确 OS 层 sandbox 和独立的审批策略, 包括命令的文件/网络边界. OMP 这里查到的工具独占、hashline 检查、ACP permission UI 不是等价的 OS 沙箱证据; 本研究不宣称 OMP 完全没有隔离能力.
- 官方所查文档未确认 Codex 与 OMP debug/lsp 相同的内置 DAP 会话动作和 LSP 写入联动接口. 可通过命令或 MCP 接外部能力, 这与开箱内建仍有区别.
- 官方 Browser 页面描述的是 ChatGPT app/web 的共享浏览器, 并明确 Codex CLI/IDE 不提供该同一入口; CLI 和 IDE extension 均支持 MCP, 可接外部浏览器工具; 官方 C5 明确两者共享 host 的 MCP 配置并列 Playwright/Chrome Developer Tools 示例. OMP eval 的 browser/computer 是另一产品入口, 不能概括为 Codex 无浏览器.
- OMP 支持多 provider/model role 路由; Pi 是可替换 provider/streamFn 的库接口; Codex SDK 是控制 Codex 线程的产品接口. 这里比较集成层次, 不笼统断言 Codex 无任何自定义 provider.
- 选择建议: 自己定 PR 输入和工具契约用 Pi core; 要调试/语义查询/子代理集中工作用 OMP; 要沿 Codex CLI/SDK/GitHub 与沙箱工作流集成就用 Codex. 三者不能仅凭工具数判断审查准确率.
- 依据: C1..C11 官方页面, 获取日 2026-10-10; 这是能力文档核对, 没有三产品同题性能实测.

## 功能清单中的产品行为与具体接口名

- 满足: G7, G8.

- wait 等待下一个后台结果、peer message 或 steering interrupt; github 工具提供 gh 的 repo/PR/issues/code-search/Actions 操作; checkpoint 标记对话状态, rewind 修剪探索上下文并保留简要报告.
- Agent Hub 可查看子代理实时 transcript、发送 steering、恢复 parked worker 或终止子代理. advisor 在独立上下文、独立模型中跟读主 agent 每轮并注入反馈.
- /collab 可提供 read-write 或只读链接, 使用 omp join 或浏览器加入; /annotate code-review 允许在 diff 行上先写人工批注. conflict://N 接受 @theirs/@ours/@base 等版本选择; ast_edit 可预览并通过 xd://resolve 接受提案.

## Pi 与 Codex 对照表采用的具体接口范围

- 满足: G8.

## debug 工具和 Python DAP 复现的参数细节

- 满足: G2, G3, G6.
- OMP debugSchema 的 stack_trace 可带 levels:number 限制栈帧数量; action 还含条件断点参数 condition/hit_condition、函数断点 function、数据断点、step_over/step_in/step_out/pause、custom_request, 具体能力依 adapter. 工具层的 levels:5 是示意选择, 不当作默认值.
- dap-demo.py 把 demo.c 和 demo 写在脚本所在目录, 用 clang -g -O0 编译; 5 行 C 目标定义 values[3]={10,20,30}, i=3, 第 4 行 return values[i].
- initialize 使用 adapterID='lldb', clientID='minimal-review', linesStartAt1=True, columnsStartAt1=True, pathFormat='path'. 通过 supportsConfigurationDoneRequest 决定是否发送 configurationDone; 这是 DAP capability 字段.
- reader 按 Content-Length 的字节数 readexactly, 用 response.request_seq 配对 Future; request 维护 seq, asyncio.wait_for(...,30) 约束等待并清理 pending; event 队列保存到达事件. 这个简化消费者会丢弃当前没等的事件, 不当成完整 DAP 事件路由器.
- launch 在后台 task 中进行, 等 initialized 后配置第 4 行断点并断言 verified, 按 capability 发 configurationDone 再等 launch/stopped; stackTrace(threadId,levels=5) 取第一帧, scopes(frameId) 取第一个 scope 的 variablesReference, variables 展开, evaluate(expression='i',frameId,context='watch') 求值.
- 成功时 disconnect(terminateDebuggee=True); finally 取消未完成 launch, 等 adapter 自行退出 2 秒, 超时则 proc.kill 并等待, 最后取消 reader. 2 秒是本教学脚本选项, 不是 OMP manager 的默认值.
- 依据: O2 debugSchema/execute, source/dap-demo.py 与 source/verification.log; DAP 初始化及清理字段来自实际 lldb-dap 调用通过的复现.

## 边界

- 本次是 OMP 18.8.7 固定源码研究和 DAP 协议实测; 没有运行完整 OMP CLI、其 DapSessionManager 或真实模型 agent, 不宣称这些路径已端到端通过.
- 只有本机 lldb-dap 与 C 程序实测; gdb/debugpy/dlv 及其他适配器支持来自源码配置, 运行兼容性未逐个验证.
- 单次样例观测不衡量真实 PR review 的准确率、性能或漏洞覆盖率; headless 行为按当前模板解释.
- 共享/独占规则复现没有覆盖 OMP 整体 steering、重试、speculation、后台任务等复杂路径.
- 调试会执行被审代码, evaluate/内存写动作能改变目标; 本文的最小调试目标是自建临时样例. 产品化需自行配置执行环境.
- 取消请求不会自动终止 debuggee; root 会话数、引用有效期与 adapter capabilities 限制需要保留.
- 依据: source/provenance.md/source/run.md; O2、O3、O4、O6、O8.
