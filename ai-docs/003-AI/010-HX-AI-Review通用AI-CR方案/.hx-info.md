## C1 要的背景来源已经存在: computeScope 能从改动路径反推适用的上下文文件并给出理由, 但只在 context 审查里被调用

- computeScope 按改动路径收上下文文件, 每条都带 reasons. 收集规则: 沿祖先目录收 AGENTS.md; 按反向引用索引收引用该目录的上下文文件; 收引用该文件本身的上下文文件; 改动 AGENTS.md 时收其下级 AGENTS.md.
- stepScope 按 kind 分派, kind = code 只走 computeCodeScope, computeScope 在 code 审查里从未被调用.
- 方案落点是接线而不是重造: code 分支在 computeCodeScope 之后再调一次 computeScope, 取其 contexts 作为背景.
- 认得的文件类型只有 isContextFile 的四类 (AGENTS.md, README.md, SKILL.md, docs/*.md), 方案不新增类型.
- 验证方式: 读 scope/index.ts 的主循环与 steps.ts 的分派分支; 对任一仓库造一个只改 src/a/b.ts 的提交, 以 context 模式跑一次, scope.json 里应出现 src/AGENTS.md 一类条目及其 reasons.
- 依据: context-cr/src/scope/index.ts:49 computeScope 与 :87-108; context-cr/src/steps.ts:155-164 stepScope; context-cr/src/l0/snapshot.ts:58 isContextFile

## code 审查有意隔离被审仓库的上下文文件, C1 的背景只取 base 侧版本并以引用数据进入 user 消息, 隔离设计保持不变

- pi.ts 的注释写明被审仓库的 AGENTS, skills, extensions 是被审数据而不是指令; isolatedLoader 把 AGENTS 文件, skills 等发现通道全部返回空.
- code finder 的输入只有系统提示加 codeFinderPrompt (scope, batch, suppressions, budgets, evidence), 没有上下文文件注入点; context 审查才在 loadDocs 之后读文档.
- 所以 C1 新开一条只读背景通道, 隔离设计保持不变: isolatedLoader 仍全部返回空, 被审仓库的 AGENTS.md 与 skills 仍不进 system prompt. 隔离设计防的是 PR 作者借上下文文件给审查者下指令; 新通道若直接读 head 侧文件, 同一 PR 改 AGENTS.md 就能改写对自身的审查口径.
- 隔离手段 (甲方 Q17 定): 背景只取 merge-base 上的文件内容 (git show <base>:<path>); 本 PR 自己改动的上下文文件不当背景, 交给独立的 context 审查.
- 背景以引用块放进 user 消息, 标明 "仓库约定, 供参考", 不进系统提示; isolatedLoader 保持全部返回空, pi.ts:20 的判断继续成立.
- 审查者引用背景得出的发现仍是 CODE-AI Warning, 仍要过 verifier 一票, 不因背景获得更高严重度.
- 被接受的代价: 同一 PR 同时改代码与约定时, 代码按旧约定被审, 新旧约定冲突处会产出可见的误报; 付出代价的是同时修改 AGENTS.md 与其目录下代码的 PR, 在该 PR 的每一轮审查时付.
- 验证方式: 读 pi.ts 的注释与 isolatedLoader 返回值; 读 review/index.ts code finder 调用处与 context 分支 loadDocs 调用处, 对比两条分支的输入; 对一个同时改 src/x/AGENTS.md 与 src/x/a.ts 的 PR, 查 sessions.jsonl 里 code finder 的 user 消息, 引用块内容应等于 git show <base>:src/x/AGENTS.md, 系统提示里不应出现该文件内容.
- 依据: context-cr/src/review/pi.ts:20-30; context-cr/src/review/index.ts:438 与 :480

## 不完整的 code 运行会把同一 PR 早先未关闭的 CODE-AI 发现全部标为 resolved, 修法是把保护条件扩到全部 AI 规则

- resolveRound 只在 aiRechecked = 1 时才允许解决 AI 发现, 但这个保护条件只写了 rule_id != 'CX-AI', CODE-AI 不受保护.
- 一次超时或预算失败的 code 运行带 kind = code 进入 UPDATE, 同 PR 下所有没出现在本次 seen 里的 CODE-AI 都变成 resolved.
- 这与 decisions/2026-10-18 的 "不完整运行不解决" 相冲突; 该条件写于只有 CX-AI 的 0003 迁移, 0005 加入 CODE-AI 时没有跟进.
- 方案写成待修缺陷: 保护条件改为 rule_id 不属于任何 AI 规则 (CX-AI, CODE-AI); 本方案不改仓库, 只给修法.
- 验证方式: 读 SQL 条件逐项代入 aiRechecked = 0, rule_id = 'CODE-AI', kind = 'code'; 可在 cf-admin/test 里造一次 complete = false 的 code 运行, 断言 resolved = 0 来证伪.
- 依据: cf-admin/worker/store/d1.ts:329-333 resolveRound; cf-admin/worker/routes/runs.ts:309 aiRechecked

## 候选上限截停的批次不算不完整运行, 这些批次上的旧 AI 发现会被误标 resolved, 方案把运行完成重定义为 notReviewed 为空

- 候选队列达到 maxCandidates (默认 12) 后, 余下批次只记入 notReviewed, 代码注释明确 "not treated as an incomplete run".
- 运行因此 complete = true, aiRechecked = 1, resolveRound 解决所有未在本次出现的发现, 包括落在未审批次里的发现.
- 付出代价的是 hunk 数多到前几批就产满 12 个候选的大 PR, 排在后面的文件上的已知问题会静默消失.
- 方案的运行完成定义: AI 未中断, 候选队列清空, notReviewed 为空; 不满足即不完整, 不推进 last_sha, 不触发 resolved, 并报覆盖不足 (阈值固定为 0).
- 验证方式: 沿 review/index.ts 的截停分支到 steps.ts 的 complete 计算再到 runs.ts 的 aiRechecked 逐步推导; 可用两轮 PR 回放证伪 (第二轮让前两批产满候选, 查第三批旧发现状态).
- 依据: context-cr/src/review/index.ts:414-418; context-cr/src/steps.ts:302; cf-admin/worker/routes/runs.ts:309

## "缺席不得读作否定" 是素材里出现五次的同一条元规则, 上两块缺陷都是它在 v0.3 里的违反点

- 出现位置: 14 第 2.4 节预算截断不给 NoRisk; 14 缺口 2 覆盖不足; 13 第 7.3 节空查表结果入账; decisions/2026-10-18 不完整运行不解决; report-contract 规则崩溃产 tool-error.
- 方案层面的推论: 凡是会把 "没看到" 转成 "已解决" 或 "无问题" 的路径, 都要先问本次运行是否真的看过那段代码.
- 验证方式: 在五份素材里逐条计数, 出现次数 5, 达到换轴判据的两次下限; 再用这条规则去审 resolveRound 与候选上限两条路径, 得到上两块.
- 依据: source/divergence.md 1.2 节; 14-full-architecture.md 2.4 与第 11 节缺口 2; 13-scope-and-retrieval.md 7.3; docs/decisions/2026-10-18-rounds-and-prompts.md

## 错误可见性决定默认方向这条规律, 同样决定 AI CR 的审查档位应向深的一侧偏

- 同一规律在素材里出现四次: 13 第 3.5 节不对称传播, 14 第 0.2 节压制比抬高危险, 14 缺口 5 分诊偏保守, blog 3.3 无法判断影响范围就跑全量测试.
- 搬到 HX-AI-Review: Quick/Standard/Deep 不需要分类器模型, 用 blog 3.3 的全量触发路径 (公共工具, 公共类型, 基础设施, 构建配置) 对 CodeScope.changed 做路径谓词即可算出档位.
- 档位规则确定可回放, 同一 diff 永远同一档.
- 谓词清单: 仓库根的 package.json, 锁文件 (pnpm-lock.yaml, package-lock.json, yarn.lock), tsconfig*.json, .github/workflows/ 下任意文件.
- 只设 Standard 与 Deep 两档, 不启用 Quick: 分诊错判为低风险是静默漏审, 按同一规律偏向深的一侧; 命中谓词即 Deep, 否则 Standard.
- 验证方式: 对任一业务仓库跑 git diff --name-only base head, 用 package.json, 锁文件, tsconfig*.json, .github/workflows/** 等谓词计算档位, 两次运行结果逐字相同.
- 依据: source/divergence.md 1.1 与 1.3 节; 01-AI代码质量.md 3.3 Diff 影响测试; context-cr/src/scope/code.ts computeCodeScope:85

## 驳回折叠进 prompt 附录会让一个仓库一种审查的驳回影响所有仓库与两种审查, 违反独立审查, 方案收窄为同 kind 同仓

- 抑制表按 (repo_id, fingerprint) 存, fingerprint 含 ruleId 与 path, 默认就是最窄作用域.
- POST /api/prompts/fold 把驳回理由收成 "Do not repeat these rejected claims" 写进 prompt_versions, 该表只有 role 列, 没有 repo_id 与 kind; /init 把它下发给所有仓库的两种审查.
- review/index.ts:79 的注释 "feedback on one never suppresses the other" 只在抑制表层面成立, 在附录层面不成立.
- 方案: prompt_versions 与 prompt_notes 加 kind, 一律按 kind 隔离; 仓库维度默认只进本仓, 管理员 fold 时可显式提升为全局并留痕. 这是 13 R9 "只有人能放宽压制型作用域" 的逐级版本; 它改动了 dual-cr-kind 决议里附录共享那一条.
- 验证方式: 读 0003 与 0005 迁移确认 prompt_versions 从未加 repo_id 或 kind; 可在 code 运行驳回一条并 fold, 查下一次 context 运行 sessions.jsonl 的 system prompt 是否含该理由.
- 依据: cf-admin/migrations/0003_rounds_prompts.sql:32-40; cf-admin/migrations/0005_kind.sql; docs/architecture/cf-admin.md 第 86 行; context-cr/src/review/index.ts:79

## 阻塞与严重度可以分开, 但方案选择不阻塞, 只把未答复 AI 发现数做成可见指标

- claude 文要求 open finding 阻塞合并; decisions/2026-10-11 禁止 AI 产出 Error. 共同原理是 AI 可以要求一个答复, 不能给出一个裁决, 由它可反推出两条原规则.
- v0.3 把 blocking 绑在 severity = error 上, 写回只有评论; 方案不动这一契约, 也不新增门禁.
- 方案只新增未答复 AI 发现数 (状态 open 且未被人工确认或驳回), 进报告与总览页.
- 被接受的代价: 只有 CODE-AI 能发现的逻辑, 边界, 错误处理, 并发资源类缺陷, 在作者不回应时仍可合并, 代价在合并后以 revert 或事故付出.
- 验证方式: grep isBlocking 的全部调用点, 确认它是 counts.blocking 与 job 失败的唯一来源; 读 publish/github.ts writeBack 确认只写评论.
- 依据: context-cr/src/contract/report.ts:33 isBlocking; context-cr/src/publish/github.ts:105 writeBack; docs/decisions/2026-10-11-pi-runner-direct-model.md 备选方案

## v0.3 的单次运行成本上限等于该仓库剩余月预算, 方案补一个独立的单次上限, 数值由甲方拍板

- maxRunUsd 的注释写明它是剩余月预算, null 表示该仓库不设上限; 不存在独立于月预算的单次门禁.
- 两种 kind 共享同一份月预算, 付出代价的是同一仓库在超大 code 运行之后, 当月剩余时间里的 context 运行与 code 运行.
- 这修正了 material.md F-3 "没有单次成本上限" 的说法: 上限存在, 但值是月余额.
- 方案写成待修缺陷: 单次上限独立于月预算, 取二者较小值; 数值列入待拍板, 拍板人甲方.
- 验证方式: 读 init/client.ts 的 limits 类型注释与 runBudget 赋值; 可在总览页取某仓库当月逐次 usage.cost, 计算最大单次占当月比例.
- 依据: context-cr/src/init/client.ts:23-24 与 :171; docs/architecture/context-cr.md 第 79 行

## HX-AI-Review 回放评测的时间泄漏只来自 CF 侧的三张表, 仓库内上下文会随 checkout 回到当时版本

- AGENTS.md 等上下文文件, 仓库规则都在被审仓库或 runner 版本里, checkout 历史 commit 就得到当时内容.
- suppressions, prompt_versions, prompt_notes 存在 D1, /init 永远下发当前值, 用今天的抑制表与附录回放旧 PR 会偏向少报.
- 修法是给 /init 增加 as_of, 按 created_at <= as_of 过滤三张表; 三张表都已有 created_at, 不需要改存量数据.
- 验证方式: 读 0001 与 0003 迁移确认三表的 created_at 列; 读 cf-admin.yaml 确认 GET /init 只有 repo, group, kind 三个查询参数.
- 依据: cf-admin/migrations/0001_init.sql:83-89; cf-admin/migrations/0003_rounds_prompts.sql:32-50; docs/reference/api/cf-admin.yaml GET /init

## v0.3 每次 push 都重审整个 PR 相对 merge-base 的全部新增行, 轮次越多重复花费越多

- resolveBase 在 PR 场景用 mergeBase(pull_request.base.sha, head), lastSha 只服务 context 的 push; code 运行没有 "上一轮审到哪" 的游标.
- 付出代价的是多次 push 的长寿命 PR, 尤其是 agent 作者的修复循环: 每次 push 付一次全量审查费, 旧 hunk 被重新采样, 措辞变了的旧发现以新 fingerprint 再次出现.
- 落地 claude 文的 "前几轮后只审新 diff" 需要一个按 (PR, kind) 存的轮次游标, 而现有 last_sha 是按仓一个且只给 context.
- 验证方式: 读 scope/base.ts resolveBase 的 PR 分支; 对同一 PR 连续两次 push, 比较两次 scope.json 的 hunks 数, 第二次不小于第一次.
- 依据: context-cr/src/scope/base.ts:17 resolveBase; docs/architecture/overview.md 已知限制第二条

## AI 发现的跨轮去重与驳回抑制都依赖模型写的 title 保持不变

- toFinding 用 fingerprint(ruleId, path, title, "") 生成指纹, title 由 finder 生成; 抑制表按指纹命中.
- 同一缺陷换了 title: 旧条目在下一轮被 resolveRound 标 resolved, 新条目以 open 出现, 人工驳回的抑制也对新条目失效.
- 付出代价的是已被人驳回过误报的 PR: 下一次 push 时措辞一变, 误报重新出现, 与 claude 文 "No repeats" 相反.
- 方案修法: AI 发现的指纹改用 fingerprint(ruleId, path, category, 该行去首尾空白后的内容), category 为 CODE-AI 六类之一; 措辞变化不再改变指纹, 该行代码变化才改变.
- 验证方式: 读 review/index.ts:84-86 的指纹参数与 :402 的抑制集合来源, 机制由代码直接推出; 发生频率未测, 见边界.
- 依据: context-cr/src/review/index.ts:84-86 toFinding, :402 suppressed

## 通用的可判定定义是接入只靠配置与仓库内上下文文件, 不改 runner 代码, 不假设语言栈, 13/14 依赖的前提缺失时按固定降级表处理

- 定义: 接入新仓库只靠 .hx-context-review.json, 仓库 secret HX_CTX_TOKEN, 总览页仓库登记 (repos.kind 取 code 或 both), workflow 里一个 kind=code 的 job, 以及仓库内已有的上下文文件; 不改 runner 代码, 不假设语言栈.
- 现状起点: 工具名 hx-context-review, 版本 0.3.0; 本方案的首个版本是 v0.4.
- 上下文文件可以不存在, 此时背景为空, 并在运行记录里写明 "背景为空", 不静默.
- 降级: 没有构建图时空间范围用目录祖先关系 (computeScope) 加本地 import 边与 git grep 引用方 (证据包); 没有 LSP 时由只读工具 read/grep/find/ls 与 verifier 新会话复核; 没有 proto 时契约轴不做, 属方案外; 非 PR 触发时 base 回退 origin/<default_branch>.
- 验证方式: 对照 goal.md G6 条款与 v0.3 接入教程逐项核对必填项; 降级各行分别对应 scope/index.ts, review/evidence.ts, review/tools.ts, scope/base.ts 的现有行为.
- 依据: source/goal.md G6 与术语表 "通用"; source/material.md E1-1, E4-12, E4-9, E2-3, E2-4, F-4; context-cr/src/scope/base.ts:17

## v0.3 的四条基线中三条保持, 双 CR kind 一条因驳回反馈按 kind 隔离而改动

- 保持: pi 在 runner 直连模型, CF 只管配置, 存储与总览 (decisions/2026-10-11-pi-runner-direct-model); Error 只来自确定性检查, AI 只出 Warning (同篇否决 "让 AI 也产出 Error").
- 保持 kind 维度与两个 job 的运行方式 (decisions/2026-10-25-dual-cr-kind), 但该篇 "共享提示词附录, 驳回抑制表" 中的附录共享被改为按 kind 隔离, 理由是甲方定义的独立审查要求驳回反馈按 kind 分开.
- 背景在 runner 内拼装 (git show 读 base 侧), 不经 CF; 新增字段在 CF 上只做存储与下发, 不做计算.
- 保持 decisions/2026-10-18-rounds-and-prompts 的附录追加而不替换, 附录不能把 AI 输出变 Error, 不完整运行不解决.
- 验证方式: 逐篇读三篇 decisions 的决策小节, 与本文件 fold 收窄块和 "独立审查" 术语条对照, 只有附录共享一处相反, 且已显式标为改动.
- 依据: source/material.md E5-1, E5-2, E5-5, E5-6, E5-8; source/goal.md 术语表 "独立审查"; docs/decisions/2026-10-25-dual-cr-kind.md "为什么不拆成两个服务"

## 九个评审器机制在 v0.3 里只有确认, 去风格与按缺陷去重有雏形, 方案逐条给出取舍
