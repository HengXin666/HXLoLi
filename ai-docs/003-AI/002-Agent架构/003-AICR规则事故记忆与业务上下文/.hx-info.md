# AI Review 的规则、事故记忆与业务上下文知识点

## Qodo 的公开规则治理契约最贴近千条规则需求, 但三家都具备规则、记忆和仓库上下文

- 范围是 2026-10-08 可访问的官方产品介绍与文档; "最贴近"指公开管理契约覆盖程度, 不代表独立性能排名.
- 下表中的"未知"表示公开材料未提供可验证契约, 不等于产品没有该功能.

| 研究对象 | Cubic | Greptile | Qodo |
|---|---|---|---|
| 定制规则 | Custom agents 可共享指令和路径过滤; 每 agent 有字符限制; 千条独立 rule 管理容量未知 | config.json 支持规则 ID、scope、severity、enabled 和层级禁用; 千条检查覆盖保证未知 | Review Standards 有来源、作用域、严重度、正反例、激活、停用、删除、相关规则检查和统计; 千条容量保证未知 |
| Review 记忆 | 反馈和资深 reviewer 历史形成可编辑的 learnings, 支持例外、去重和删除; 事故必达机制未知 | 从讨论、回复、反应和提交变化学习; 知识库含 revert、rollback、incident PR; 仓库外事故接入范围未知 | PR history、Relevance 与 Rule Miner 分别保存历史、处理倾向和候选规则; 窗口与挖掘频率有限; 全事故记忆未知 |
| 业务上下文 | 仓库文档、关联仓库、自动 wiki; 背景与强制检查需区分 | 代码关系图、文档、可编辑知识库、相关仓库; 自动理解未记录业务义务的保证未知 | 代码图、向量、PR 历史、规则、票据、spec/design 和跨仓库关系; spec 接入有限且为预览 |

- 满足: G1, G2
- 依据: [Cubic 官网](https://www.cubic.dev/)及[Custom agents](https://docs.cubic.dev/ai-review/custom-agents.md); [Greptile 官网](https://www.greptile.com/)及[配置](https://www.greptile.com/docs/code-review/greptile-config-reference.md)、[Knowledge Base](https://www.greptile.com/docs/how-greptile-works/knowledge-bases.md); [Qodo 官网](https://www.qodo.ai/)及[规则管理](https://docs.qodo.ai/governance/rule-enforcement/generate-and-manage-rules.md).

## Qodo 的 Context Engine 将代码结构、语义相似、历史与模块摘要存为不同的知识来源

- 官方架构包含 ingestion、knowledge storage 和 agentic research 三部分.
- Parsing agents 提取结构和接口关系; Abstract Syntax Tree (AST, 抽象语法树) chunking 按函数、类和模块边界分块.
- Graph DB 存调用与依赖关系; Vector DB 用于语义相似; PR/commit history 存演变历史; 自动 markdown 存模块、API 与架构摘要.
- 代码索引反映实现; 历史帮助解释原因; 摘要和相似代码不能自动取得业务规范的权威.
- 最后一项是知识类型的逻辑区分, 官方文档未承诺仅凭索引可以恢复全部业务义务.
- 满足: G1, G2, G5
- 依据: [Qodo platform architecture](https://docs.qodo.ai/core-concepts/qodo-platform-architecture.md)的 Core components / Ingest agents / Rigid knowledge layer; 逻辑反例为"已有代码违背规范"时观察实现与规定行为不同.

## Qodo 的研究工具和多个审查 agent 共享上下文筛选层, 但具体检索覆盖算法没有公开

- 官方列出 deep-research、find-similar、deep-issue 和 ask, 均可使用 Context Ranking / Judge 筛选证据.
- 官方列出 Critical Issue、Breaking Changes、Ticket Compliance、Duplicated Logic 和 Rules agents, 各检查不同问题类别.
- 公开组件名称不能证明每个 agent 总会获得全部相关材料, 也不能证明千条规则都被执行.
- 满足: G1, G3, G5
- 依据: [Qodo platform architecture](https://docs.qodo.ai/core-concepts/qodo-platform-architecture.md)的 Deep research agents / Multi-agent review system; 公开文档没有逐规则覆盖算法或容量验收.

## Qodo Review Standards 把规则作为可单独管理的实体, 规则文本还需要说明适用条件和例外

- 规则可从人工自然语言、文件与 Rule Miner 生成.
- 公开字段包括名称、规则内容、合规与违规例子、类别、严重度、scope、source type 和 source.
- 管理操作包括编辑、激活、停用与删除; 管理员和 team admins 的权限与成员候选审批不同.
- Qodo 建议每条规则有一个可测目标, 说明检查内容、原因、适用条件, 并以正反例减少歧义.
- 业务规则样例是"撤销选定 grant 时按不可变 permission ID 操作, 不得撤销同用户并发新建的 grant"; 对应反例是只按 user/workspace 删除.
- 样例来自 Sim PR 的业务归纳, 属于可迁移规则文本, 不是已存在的 Qodo 私有规则.
- 满足: G1, G2, G3, G4
- 依据: [Generate and manage rules](https://docs.qodo.ai/governance/rule-enforcement/generate-and-manage-rules.md)的 Generate a rule / Manage rules; [Best practices](https://docs.qodo.ai/governance/rule-enforcement/best-practices-for-setting-rules.md)的 Make rules clear and specific; [Sim 权限竞态评论](https://github.com/simstudioai/sim/pull/8762#discussion_r4211938426).

## Qodo Rule Miner 的约一千条窗口指历史 merged PR, 首轮产出最多十条规则

- 首轮在初始 PR history indexing 完成后开始, 从最近最多约 1000 个 merged PR 的窗口分析, 最多生成 10 条规则/仓库.
- 后续每两周运行, 单轮最多新增 5 条/仓库; 过于类似已有规则的候选会跳过.
- 只有被接受并产生代码修改的具体评论进入新规则候选; ownership 加权、重复反馈和路径聚类影响生成.
- strong ownership reviewer 的单次评论也能成为候选, 重复出现并非绝对前置条件.
- 全历史事故、未合并 PR 与仓库外复盘不在上述完整覆盖契约中. 严重的一次性事故应显式登记.
- 满足: G1, G2, G3, G4
- 依据: [Rule Miner](https://docs.qodo.ai/governance/rule-enforcement/rule-miner.md)的 What signals shape the rules / How Rule Miner generates rules over time / Understanding rule volume.

## Qodo 新组织的候选规则默认激活策略按来源和日期分别定义

- Rule Miner 对 2026-09-01 起接入的组织默认自动激活; 更早组织默认进入 Pending, 可修改配置.
- 文件导入对 2026-09-30 起新组织默认直接激活; 更早组织默认 Pending.
- 自动激活说明减少人工步骤, 不能用"所有规则永远先人工审批"描述 Qodo.
- 自研系统可以规定事故规则始终需要 owner 批准; 这是额外治理设计.
- 满足: G1, G2, G4
- 依据: [Rule Miner](https://docs.qodo.ai/governance/rule-enforcement/rule-miner.md)的 Configure Rule Miner; [Building Review Standards](https://docs.qodo.ai/governance/rule-enforcement/building-review-standards.md)的 Importing rules and skills.

## Qodo 规则已激活与 Rule enforcement agent 已启用是两个检查条件

- Finding types 文档列明 bugs 始终开启; Rule enforcement 默认关闭.
- 安装后的 preset、组织配置和仓库配置应核查; 在规则库中显示 active 不足以证明 PR 已执行合规检查.
- compliance_user_guidelines 是 agent 的额外指令, 不能单凭写入该字段证明 rule enforcement 已运行.
- 满足: G1, G2, G3
- 依据: [Finding types](https://docs.qodo.ai/configuration/finding-types.md)的 Rule enforcement / Defaults; [Extra instructions](https://docs.qodo.ai/code-review/extra-instructions.md).

## Qodo 导入规则文件的自动同步只追加新规则, 现有规则修改和删除需要平台管理

- 已导入的支持文件持续受监视; 新出现的支持文件需要重新 import 才能加入.
- Automatic rule updates from files 的具体条款明确: 只新增规则, 既有规则的修改与删除不反映到 Review Standards.
- 同页泛称"反映当前文件内容"与细则有张力; 迁移方案应按细则处理, 完整 update/delete 同步需要实测确认.
- 修改源文件不能直接视为平台规则已更新, 删除源段落不能直接视为旧政策失效.
- 满足: G1, G2, G3, G5
- 依据: [Generate and manage rules](https://docs.qodo.ai/governance/rule-enforcement/generate-and-manage-rules.md)的 Automatic rule updates from files, 短引"only new rules are added"及现有 modifications/deletions 的限制.

## Qodo 的规则 scope 与生命周期需要分别管理, 批量二十五实体限制不代表规则数量上限

- 手动生成规则默认 Global; 文件导入按文件所在目录及子目录限定; 仓库 root 文件规则只覆盖该仓库.
- 批量 set scope 替换已有 scopes, 不是追加; 界面最多指定 25 个组织/仓库实体, 指 scope 实体数量.
- Deactivate 保留规则与历史; Delete 永久删除. 停用适合保留变更理由与历史分析.
- 规则生成可检查 conflicts、duplicates 和 overlapping scope; 公开材料未给出完整自动冲突优先级算法.
- 满足: G1, G2, G3
- 依据: [Generate and manage rules](https://docs.qodo.ai/governance/rule-enforcement/generate-and-manage-rules.md)的 Scope / Manage rules in bulk / Deactivate / Delete; [Building Review Standards](https://docs.qodo.ai/governance/rule-enforcement/building-review-standards.md)的文件 scope.

## Qodo Relevance 表达历史处理倾向, 不能当作问题真值或事故严重度

- Relevance 高、中、低来自类似发现过去被接受或忽略的历史, 结果可以附历史 PR 链接.
- Rule Miner 文档也说明已激活规则的建议被 dismissed 会降低其信号.
- 接受一项建议不证明建议一定正确; 忽略一项建议不证明问题不存在.
- 真实高风险问题被延期处理的反例证明 relevance、correctness 与 severity 必须区分.
- 满足: G1, G2, G4, G7
- 依据: [Prioritize findings using Relevance](https://docs.qodo.ai/code-review/relevance.md); [Rule Miner](https://docs.qodo.ai/governance/rule-enforcement/rule-miner.md)的 Rejected suggestions; "延期但仍有风险"为逻辑反例.

## Qodo Rule analytics 提供规则效果统计, 但没有违规记录不能证明完整覆盖

- 文档列出近 30 天 passed evaluations、detected violations、merged-with-unresolved-violations, 可按规则查看.
- unresolved violations 随 merged PR 的统计也表明"发现违规"与"阻止合并"是不同事件.
- "未发现违规"只能描述报告结果; 需另查规则是否适用、是否调用检查、是否超预算或失败.
- 满足: G1, G2, G3, G7
- 依据: [Rule analytics](https://docs.qodo.ai/governance/rule-enforcement/analytics.md)的 Rule performance metrics / Merged violations; 未执行检查同样产生零发现, 是覆盖推理的反例.

## Qodo 公开 Get Rules skill 的双查询检索可以参考, 但不能代表后台审查算法

- 固定版本是 qodo-get-rules v1.1.5, 提交 `866d301dfbec39d5bb18bde72ac0dc770cc759a1`.
- skill 构造 topic 和 cross-cutting 两条结构化查询, 各取 top-k 20, 再按 rule ID 合并去重.
- 少于 3 条结果时允许一次 broaden; scope 从仓库 remote 推导; 成功空结果有效, 调用失败不能伪装空结果.
- 这是编码代理在写代码前获取规则的接入策略, Get Rules 文档标 Research Preview.
- 最多合并 40 条候选的这段策略不能证明每个后台 review 只检查 40 条, 也不能证明关键适用规则均入选.
- 满足: G1, G3, G9
- 依据: [固定提交 Get Rules](https://raw.githubusercontent.com/qodo-ai/qodo-skills/866d301dfbec39d5bb18bde72ac0dc770cc759a1/skills/qodo-get-rules/SKILL.md)的 query / top-k / Broaden / Failure handling; [Get Rules 官方文档](https://docs.qodo.ai/agentic-toolbox/agentic-toolbox-get-rules-skill.md).

## Qodo Manage Review Standards skill 展示规则实体的显式读写操作, 使用前需要区分查询和治理变更

- 同一固定提交的公开 skill 包含 metadata/list/get 与 create/update/set-state/set-scope/bulk.
- 写操作支持 dry-run; 非管理员生成规则需考虑 pending; 写入结果不确定时应读回确认.
- set-scope 语义是替换, 批量调用之前需要保存原 scope 和预期变更.
- 本次仅阅读源码, 没有安装该 skill 或对厂商平台写入.
- 满足: G1, G3, G9
- 依据: [固定提交 Manage Review Standards](https://raw.githubusercontent.com/qodo-ai/qodo-skills/866d301dfbec39d5bb18bde72ac0dc770cc759a1/skills/qodo-manage-standards/SKILL.md)的 supported operations / scope / dry-run / read-back.

## Qodo 的额外 prompt 参数按检查任务分开, 不能代替结构化 Review Standards

- 官方配置支持 issue finding、compliance 和 review effort 三种额外指令.
- portal 是组织默认配置; 仓库 `.pr_agent.toml` 和单次 PR 参数提供更具体的配置入口.
- 以下是官方参数结构与自拟指令值, 适合小规模试用; 它没有千条规则的 ID、版本和执行账本.

```toml
[review_agent]
issues_user_guidelines = "Check permission revocation for concurrent re-grants"
compliance_user_guidelines = "Preserve grant identity and retained shared resources"
smart_router_extra_instructions = "Treat auth and resource lifecycle changes as high risk"
```

- 满足: G1, G3, G9
- 依据: [Configure extra instructions](https://docs.qodo.ai/code-review/extra-instructions.md)的三项参数与 .pr_agent.toml 示例.

## Qodo 的外部需求接入按 PR 关联材料, 公开文档没有承诺自动吸收全部业务知识库

- documentation/design 集成支持 Confluence、Notion 和 Figma; ticket 集成支持 Jira、Linear、Azure DevOps 等.
- 每个 PR 最多处理一个 spec 和一个 design; 同类 URL 只取第一个, Notion 与 Confluence 也共享一个 spec 名额.
- Spec Agent 文档标 Research Preview, 并建议避免生产或业务关键流程.
- 将产品称为"支持需求文档"有依据; 将其称为"默认读懂公司所有业务 wiki 并可靠强制执行"超出证据.
- 满足: G1, G2, G5
- 依据: [Documentation & design integrations](https://docs.qodo.ai/integrations/documentation-and-design-integrations.md)的 Supported platforms / Multiple links; [Requirement gaps](https://docs.qodo.ai/code-review/view-requirement-gaps-in-findings.md)的 Research Preview 警示; [Ticket context](https://docs.qodo.ai/integrations/ticketing-integrations.md).

## Qodo 跨仓库审查能表示多类关系, 但默认 main 分支未必对应真实部署组合

- 关联仓库可自动发现或手动添加, 关系类型包括 Code、Service、Data、Pipeline 和 Docs.
- related repository 默认 main; 特定 PR 或 ticket 链接可指定其他 branch/PR.
- 两个服务兼容性的复核还需要明确被部署版本; 两个仓库的最新 main 相容不能自动证明线上旧版本相容.
- 最后一项是版本组合的逻辑约束, 未声称 Qodo 有部署状态自动采集.
- 满足: G1, G2, G5
- 依据: [Cross-repository code review](https://docs.qodo.ai/governance/cross-repo-code-review.md)的 Relationship types / Branch context; 消费者旧版与生产者新版的组合构成版本反例.

## 开源 PR-Agent 与当前 Qodo 商业平台需要分别研究

- PR-Agent README 明确将其描述为 Qodo 捐给社区的 legacy 项目.
- 公开 /review、/improve 实现不能证明当前商业平台的 Review Standards、Context Engine 与后台多 agent 全部能力.
- PR-Agent 仓库可以作为真实受审 PR 案例; 其与 Qodo 的来源和赞助关系要一并披露.
- 满足: G1, G6, G7
- 依据: [PR-Agent 固定提交 README](https://raw.githubusercontent.com/The-PR-Agent/pr-agent/35553cb89d6243c52678f681413a0ea1bbb1feba/README.md)的 legacy/community 说明; [Qodo architecture](https://docs.qodo.ai/core-concepts/qodo-platform-architecture.md).

## Cubic Custom agents 适合按主题组织检查, 但字符限制和 agent 数量限制影响千条规则方案

- custom agent 包含名称、说明、linked instruction files 和路径过滤, 规则库可共享到多个仓库, 评论标识来源 agent.
- 普通每仓库启用 5 个; 有 scans 的 Pro/Max 等计划可到 15 个; 部分组织可申请提高.
- 每 agent 指令加引用文件共 10000 字符, 超出后截到前 10000 字符.
- 一份文本中写 1000 条检查不会自动产生 1000 个可治理 rule 实体, 也不能绕过截断.
- 满足: G1, G2, G3
- 依据: [Cubic Custom agents](https://docs.cubic.dev/ai-review/custom-agents.md)的 Agent limits / Instructions / Linked instruction files / Rule library.

## Cubic 的背景文档与强制 custom agent 检查是不同用途, PR 与 CLI 读取的文件版本也不同

- Cubic 自动使用 README、AGENTS、context 和 skills 等作为背景; 明确需要 active enforcement 的要求应放 custom agent.
- GitHub PR 的 linked files 读 head commit; CLI 读 default branch.
- 同一规则文本在两入口有不同 revision 时, 应先查版本, 不能单凭建议不同判断模型不稳定.
- "已看到文档"没有逐项执行承诺.
- 满足: G1, G2, G3, G5
- 依据: [Cubic Custom context](https://docs.cubic.dev/ai-review/custom-context.md)的 Background context / Enforcing rules; [Custom agents](https://docs.cubic.dev/ai-review/custom-agents.md)的 Linked instruction files.

## Cubic learnings 支持反馈修订和例外, 但普通偏好学习需要与事故防御分别治理

- 学习来源包括直接评论、解释、reaction, 以及 onboarding 可选的资深 reviewer 历史反馈.
- 学习操作包含 create、improve、remove、keep; Do not apply when 描述例外; 每周去重和归档.
- learnings 可编辑、删除和 CSV 导入, 文件上限 5MB.
- 文档的 Explicit learning only 需限定为相应反馈路径, 不能抹掉文档同时描述的历史模式学习.
- 官方描述 team/repo 隔离; 本次未独立验证权限隔离效果.
- 满足: G1, G2, G4, G5
- 依据: [Cubic Memory and learning](https://docs.cubic.dev/ai-review/memory-and-learning.md)的 Feedback / Senior reviewer patterns / Do not apply when / Manage learnings / Explicit learning only.

## Cubic 跨仓库链接与自动 wiki 提供背景, 生成文档刷新节奏不能代表所有索引的新鲜度

- 跨仓库 link 双向生效, 默认每仓库最多 5 个 related repositories, 需 same installation.
- companion PR 进展后原 finding 可更新, 审查证据需保存对应版本.
- 自动 wiki 按计划提供日、周、月刷新; 通过滚动 PR 同步导出, 生成目录的手工修改会被覆盖.
- wiki 刷新周期描述生成文档, 不能据此推断代码索引也是同一延迟.
- 满足: G1, G2, G5
- 依据: [Cubic Cross-repo reviews](https://docs.cubic.dev/ai-review/cross-repo-reviews.md)的 Repo links / Companion PR; [AI wiki](https://docs.cubic.dev/wiki/ai-wiki.md)的 Refresh / Repo sync.

## Greptile 的结构化 config 适合分层规则管理, rules.md 整文件背景不能替代规则 ID

## 千条规则系统需要稳定的规则实体和修订记录, 不能只保存一份长 prompt

- 性质为自研规格; 公开材料没有证明任一产品已经满足下列完整契约.
- 触发场景是组织维护至少 1000 条独立业务/质量规则, 规则跨仓库复用且具有不同的严重度、例外和负责人.
- 每条规则应有 stable ID、revision、单一 assertion、rationale、scope、trigger、severity、state、owner、source、exceptions、checker 和回归例子.
- scope 至少表达组织、仓库、路径或符号、业务域和适用版本; repo 名必须包含所属组织, 不能用不唯一的短名称.
- rule revision 不可原地覆盖旧记录; 停用、替换和删除也保留审计事件. 历史 review 继续引用原 revision.
- 机械判据是 rule IDs 不重复、必填字段齐全、1200 条导入后可按 ID 查单条、更新不修改旧 revision、停用不抹掉旧运行记录.
- 以下字段为自研示例, 不能复制到 Qodo 或 Greptile 当作官方配置.

```json
{
  "id": "AUTH-GRANT-IDENTITY",
  "revision": 3,
  "assertion": "Revocation targets the selected immutable permission ID.",
  "rationale": "A concurrent replacement grant must retain access.",
  "scope": {"repos": ["acme/service"], "paths": ["src/auth/"], "domain": "authorization"},
  "trigger": {"operations": ["grant_revoke"], "symbols": ["revoke_permission"]},
  "severity": "critical",
  "state": "active",
  "owner": "authorization-team",
  "source": {"kind": "incident", "id": "INC-GRANT-001", "revision": 1},
  "exceptions": [],
  "checker": {"kind": "regression", "ref": "replacement_grant_survives"},
  "examples": {"pass": "delete by selected ID", "fail": "delete by user and workspace"}
}
```

- 满足: G3, G4, G9
- 依据: 逻辑推导: 同文本多 scope、同 ID 多 revision 与历史重放要求独立实体; 对照 [Qodo 规则管理](https://docs.qodo.ai/governance/rule-enforcement/generate-and-manage-rules.md)的实体字段, 以及 [Greptile Rule Schema](https://www.greptile.com/docs/code-review/greptile-config-reference.md)的 stable ID.

## 千条规则系统必须把适用集合与语义检索分开, 关键规则不得被 top-k 排名裁掉

- 性质为自研算法契约. 每次审查先遍历结构化元数据筛选 active、授权可用、版本适用且命中变更影响范围的规则集合 A.
- 变更范围要纳入新增、删除、重命名两端及调用/接口影响; 路径和符号无法解析时记录范围错误, 不默认为无规则.
- 从 A 中确定关键集合 C; C 每条都必须安排检查. 语义检索可补充知识、近似事故和推荐规则, 不能删掉 C.
- 形式化的 applicable 不等于真实世界所有相关规则; scope 和 trigger 漏配仍会漏检, 需要有权 owner 审查与历史样本反测.
- 规则库总量、适用集合量、关键集合量、送入模型量、实际执行量必须分别报告.
- 最小反例是 21 条同 scope 关键规则, 第 21 条被违反但相似度最低; 只取 top-20 会漏掉该条.
- 机械判据是把关键条目的相似度任意调低后, plan 中仍包含该 ID 或明确标 incomplete, 绝不能报告全关键覆盖.
- 满足: G3, G9
- 依据: 逻辑推导与 21 条反例; [Qodo Get Rules 固定实现](https://raw.githubusercontent.com/qodo-ai/qodo-skills/866d301dfbec39d5bb18bde72ac0dc770cc759a1/skills/qodo-get-rules/SKILL.md)提供有限 top-k 的接入策略, 但未提供全覆盖契约.

## 规则冲突必须显式裁决, 不能只按文本相似或最近目录覆盖业务义务

- 性质为自研治理选择. 规则导入先做 stable ID、同义重复、同 scope 相反 assertion 和 supersedes/exception 检查.
- 重复不等于冲突; "等待者需要 timeout"和"后台恢复必须继续"可以同时成立.
- 相反约束同 scope 时进入 pending/conflict; 由有权 owner 选择适用范围、例外或 replacement, 并保存理由.
- 普通局部规则可以按已定义继承语义覆盖; 关键事故规则不能被任意子目录 disabledRules 或 PR 修改悄悄取消.
- 自然语言矛盾识别会遗漏, 检测器只能生成候选, 不能声称完备求解.
- 机械判据是同 scope 的 allow/forbid 规则不能同时自动 active; 批准的 exception 必须写出条件、owner、期限和原 rule revision.
- 满足: G3, G4, G9
- 依据: 逻辑推导: 相反 assertion 无法同时通过; [Qodo related rules 检查](https://docs.qodo.ai/governance/rule-enforcement/generate-and-manage-rules.md)未公开自动优先级算法; [ScyllaDB 恢复义务](https://github.com/scylladb/scylladb/pull/31705#discussion_r4035329429)提供通用 retry 规则的反例.

## 预算不足必须成为可见的审查结果, 静默截断不能当作通过

- 性质为自研执行契约. 规则按 checker 类型路由为静态检查、回归测试、证据驱动的模型检查或人工裁决.
- 可机械检查的格式和禁用 API 等规则先交给 linter/AST; 领域行为规则优先配回归, 模型用于语义证据补充.
- 关键规则总成本超过预算时可拆批或等待人工, 但必须保留所有关键 ID, 并返回 incomplete.
- 每条适用规则结果至少为 pass、violation、not_applicable、unknown、skipped_budget 或 error; 仅证据足够时才 pass.
- complete 说明检查执行完整, 不保证无漏报; 模型 unknown、证据缺失和执行 error 不能升级为 pass.
- 合并判定需要同时查 complete、关键 violation、回归与例外批准, 不能只查评论数是否为零.
- 机械判据是设置预算低于 C 成本, 结果必须列 skipped_budget ID、complete=false, gate 不能无条件通过.
- 满足: G3, G4, G9
- 依据: 逻辑推导: 未执行的断言没有通过证据; [Cubic 字符截断](https://docs.cubic.dev/ai-review/custom-agents.md)与 [Qodo active/enforcement 分离](https://docs.qodo.ai/configuration/finding-types.md)是需要显式账本的不同实例.

## 每次审查必须固定代码、政策和知识快照, 历史结论才能复核

- 性质为自研运行规格. ReviewRun 保存 base/head SHA、protected policy revision、knowledge revision、cross-repo SHA、工具/model 配置与时间.
- policy 采用已批准且受保护的版本; PR 内修改可作为新政策候选, 不能自行降低同次审查的门禁.
- 待读代码使用该 PR head; 外部消费者使用明确目标版本, 不能自动把所有 related main 当成部署事实.
- 相同 head、不同知识 revision 的 review 是不同 run; 新 run supersede 旧 run, 同时保留旧证据.
- rebase 后旧行号评论需重新定位和重新验证, 不能机械标 resolved 代表已修复.
- 机械判据是修改知识条目后旧 run 仍可重放原 revision, PR 删除关键规则时原门禁仍要求其检查.
- 满足: G3, G5, G9
- 依据: 逻辑推导; [Cubic head/default branch 差异](https://docs.cubic.dev/ai-review/custom-agents.md); [Greptile base auto-approval policy](https://www.greptile.com/docs/code-review/greptile-config-reference.md); [mirrord 历史范围变化](https://github.com/metalbear-co/mirrord/pull/4986).

## 规则文件同步必须明确更新和删除语义, 并对平台实体逐轮对账

- 性质为自研同步契约. 每条源规则使用 source key, 至少包含组织/仓库、精确文件、稳定段落 ID; revision 记录源 SHA 与内容 hash.
- 相同 key 内容变化产生新 revision; 源删除产生 tombstone 或 pending retirement, 按治理权限完成停用.
- 相似度用于候选去重, 不用于认定两个版本是同一实体; 名称相同也不自动合并.
- 手动平台修改与文件修改并发时显式报冲突, 选择单一事实源或三方合并, 不静默覆盖.
- 机械判据是 create → 改 severity → delete 三轮后只有一个 stable rule ID, 历史修订保留, 活跃集合符合最后批准状态.
- Qodo 公开同步限制要求额外治理操作; 不能声称厂商导入器已自动满足本契约.
- 满足: G3, G5, G9
- 依据: 逻辑推导与三轮对账反例; [Qodo Automatic rule updates from files](https://docs.qodo.ai/governance/rule-enforcement/generate-and-manage-rules.md)的 only new rules are added.

## 历史事故必须转成可执行的不变量和回归门禁, 保存事故文字无法保证不复发

- 性质为自研事故闭环: Incident 现场事实 → approved Invariant → rule revision → negative/positive regression → merge gate → 上线监测.
- Incident 保存受影响版本、触发序列、用户影响、root cause、修复 PR/SHA、负责人和证据; 推测原因与确认原因分开.
- 单次严重事故可以直接建立候选规则, 不等待重复评论形成频次.
- Sim 的最小模型是旧 grant ID=A、新 grant ID=B, 二者 user/workspace 相同; 撤销 A 后 B 必须保留.
- 负控以 user/workspace 删除, B 被误删; 正例以 A 删除, B 保留. 该模型验证对象身份不变量, 不代替真实数据库锁和 HTTP 集成测试.
- 关键回归通过仍只证明已覆盖的输入、调度和版本; 新增路径、误配 scope、未运行检查和新型缺陷仍需处理.
- 概率模型审查不提供"发生过一次就永远不会再发生"的绝对保证; 可执行约束和门禁提高已知场景防御强度.
- 满足: G4, G9
- 依据: 逻辑推导; [Sim 竞态与作者修复](https://github.com/simstudioai/sim/pull/8762#discussion_r4212496062); [Qodo Rule Miner 候选窗口](https://docs.qodo.ai/governance/rule-enforcement/rule-miner.md)不覆盖全部事故.

## 事故规则的失效需要显式决策, 自动偏好学习不得因被忽略就取消关键防御

- 性质为自研权限选择. 将 memory 分为 incident/invariant、architecture decision、review preference 和 temporary exception.
- 自动学习可提议新规则、修订措辞和普通偏好; critical incident rule 的停用需要有权 owner、替代防御或风险接受、理由和审计事件.
- temporary exception 有到期时间和适用版本, 过期后恢复要求或阻止放行; 不能无限期保留未说明的例外.
- 事故已修复不等于事故规则失效; 架构变化消除了触发条件时, 仍需要证明和批准.
- 机械判据是同一关键建议连续 dismissed 后 rule 仍 active; 只有明确批准事件可以改变状态.
- 满足: G4, G9
- 依据: 逻辑推导: "延期但问题仍真实"反例; [Qodo dismissed 降低信号](https://docs.qodo.ai/governance/rule-enforcement/rule-miner.md)与 [Cubic learning remove/keep](https://docs.cubic.dev/ai-review/memory-and-learning.md)说明偏好反馈需有权边界.

## 审查反馈必须分离采纳倾向、证据置信度和严重度

- 性质为自研 finding schema. disposition 可为 accepted、false_positive、deferred、disputed、obsolete; resolved 单独记录代码状态.
- confidence 表示证据支持程度; severity 表示违反不变量的影响; relevance/preference 表示团队处理倾向.
- Finding 关联 rule ID/revision、源 knowledge IDs、精确 SHA/路径/符号、触发输入与预期/实际行为、验证记录和 limitation.
- accepted 后仍要独立审查真实性; false_positive 必须有反例或缺失前提证据; 不回复与关闭 thread 不自动映射为 false_positive.
- 机械判据是 deferred 更新不改变 correctness 和 severity; 同一错误评论撤回仍保留审计记录及纠正原因.
- 满足: G4, G5, G7, G9
- 依据: 逻辑推导; [Qodo Relevance](https://docs.qodo.ai/code-review/relevance.md); [Greptile 明确撤回评论](https://github.com/NVIDIA/DALI/pull/6327#discussion_r3168715093)比未采纳提供更强误报证据.

## 业务上下文必须区分代码事实与业务规范, 并记录来源权威、适用版本和撤销

- 性质为自研 knowledge schema. 条目至少有 ID/revision、kind、statement、source、authority/owner、scope、valid_from/to、status、ACL、supersedes 和关联 rule IDs.
- kind 区分 implementation_fact、business_invariant、architecture_decision、incident、specification 与 preference.
- implementation_fact 记录所查 SHA; 业务规范记录批准者和适用产品版本; 自动摘要保留原证据引用, 不能取得比原来源更高权威.
- 知识未写明时返回 missing, 不编造; 规范与实现冲突时记录 conflict, 交 owner 裁决或揭示实现违规.
- 典型业务知识是"payer 不自动具备已有访问权""软删除取消 serving 但保留 retention""等待者超时不取消后台恢复".
- 机械判据是输入一般 retry cap 与批准的恢复不变量后返回明确冲突/例外, 不能按相似度覆盖恢复职责.
- 满足: G5, G9
- 依据: 逻辑推导; [Sim payer 前置条件](https://github.com/simstudioai/sim/pull/8762#discussion_r4211982132)、[retention 前置条件](https://github.com/simstudioai/sim/pull/8762#discussion_r4211981741)、[ScyllaDB 恢复职责](https://github.com/scylladb/scylladb/pull/31705#discussion_r4035329429).

## 业务知识检索需要在召回前过滤权限和有效版本, 过期或无权访问不能混入模型上下文

- 性质为自研检索契约. 先按组织、仓库、有效版本、条目状态和当前执行 principal 的 ACL 过滤, 再做图扩展、全文和向量召回.
- 模型出结果后过滤无法撤销已经读入的内容; 检索前权限约束也要覆盖图关系、缓存、附件和生成摘要.
- 检索使用的权限与结果读者的权限都需检查; 有权 agent 看内部文档不意味着可以将内容公开评论到公共 PR.
- 旧版本规范可以用于历史重放, 新 run 不能自动混用已撤销规范; 版本切换需要新快照.
- 知识更新撤销后使相关缓存和派生摘要失效, 重建保留来源 revision.
- 机械判据是受限条目不进入无权 run 的检索结果、prompt 和公开评论; 撤销条目不进入新 run, 但旧 run 可授权重放.
- 满足: G5, G9
- 依据: 逻辑推导: 事后删除输出无法逆转已读入内容, 缓存也构成访问路径; 厂商公开 repo/credential 边界见 [Greptile Cross Repo Context](https://www.greptile.com/docs/code-review/cross-repo-context.md), 本规格未宣称已验证厂商 ACL 实现.

## 自研 ReviewRun 的覆盖账本必须能区别完整执行与结论正确性

- 性质为自研数据模型. ReviewRun 将输入快照、applicability plan、逐 rule result 与 gate decision 关联.
- applicability result 保存 match reason; not_applicable 需要可复核理由; 预算和工具错误保存原 ID 与失败原因.
- coverage 的分母是已建模的适用关键集合 C, 分子是有有效执行记录且没有 unknown/error/skipped 的 C 条目.
- coverage=100% 只证明 C 的检查有结果; 检查器漏报和 scope 漏配需由独立质量评测发现.
- 以下简化输出说明超预算不会静默通过; 成本单位是演示预算单位, 不是实测模型 tokens.

```json
{
  "run_id": "RUN-001",
  "snapshots": {"code_head": "fixed-sha", "policy": "policy-r3", "knowledge": "knowledge-r7"},
  "library_count": 1200,
  "applicable_count": 21,
  "critical_count": 21,
  "results": [{"rule_id": "AUTH-GRANT-IDENTITY", "revision": 3, "status": "skipped_budget"}],
  "complete": false,
  "gate": "needs_review"
}
```

- 示例只列一个 result 说明结构; 正式账本必须列全 21 条结果, 不能把示例当完整 review 输出.
- 满足: G3, G9
- 依据: 逻辑推导与 21 条预算反例; [Qodo Rule analytics](https://docs.qodo.ai/governance/rule-enforcement/analytics.md)的 passed evaluations 没有提供全适用集合分母.

## 千条规则演示件应验证容量、遗漏、复发与知识撤销, 不能冒充厂商容量测试

- 性质为待实现的可运行规格. 演示采用 Python 标准库和 JSON, 生成至少 1200 个唯一规则 ID, 以确定性 checker 展示治理控制.
- 固定选择是精确仓库名、精确文件/目录前缀 scope、显式 revision、预置 checker 和预算单位; 不模拟完整 Git glob、AST、向量数据库或商业云端 agent.
- 容量用例导入 1200 条; scope 用例说明本次 PR 仅有小集合适用, 其他规则没有被误标 pass.
- 遗漏用例令关键条目排在 top-20 外; 预算用例降低到关键成本以下; 两者必须产生可见未覆盖状态.
- 复发用例执行 grant A/B 负控和正例; 知识用例比较授权/无权、有效/过期、规范/普通偏好冲突; 同步用例执行 create/update/delete.
- 边界用例证明"检查全执行"仍不等于 scope 正确: 故意错配路径后历史反例必须暴露漏配.
- 操作输出要包含 count、applicability、rule status、complete 和 gate, 方便开发者从数据结构接入真实检索与检查器.
- 侧车 review_core.py 与 review_lab.py 已实现并实际执行; 1200 条是合成规则夹具, 包含 3 条专家示例, 不能证明任一厂商容量或千条真实专业规则的模型准确率.
- 满足: G3, G4, G5, G9
- 依据: 自研规格和逻辑推导, 来自 21 条 top-k 反例、grant A/B 身份反例和三轮同步反例; 不引用厂商宣传作为自研验收结果.

## 规则系统的评测应分别测真实性、已知缺陷召回、规则覆盖和事故复发

- 性质为自研评测契约. 冻结真实 PR 的审查时 SHA, 按历史修复与领域 owner 判断 gold; 未来修复不得泄漏到输入.
- 厂商、模型、配置和知识版本固定; 重复 findings 去重后计算 precision 与 recall, 并保留 disputed 项.
- 规则 coverage、关键规则未执行比例、事故回归通过率、错误阻断率、每 PR 延迟和费用分别统计.
- Gold 包含有效发现、相似但合法的反例、领域例外、跨文件影响和过期知识, 不只注入语法错误.
- 只评违规正例时, 一律报告 violation 的检查器也能得到高正例得分, 评测无法约束其合法改动误报; repair 样例必须同时检查后台被错误取消和等待者合法超时, 避免通用"重试封顶"建议被错误奖励.
- 规则或知识更新后重放历史事故与已确认误报; 对真实同类新 PR 另作前瞻验证, 防止只记住固定样本.
- 同一次修复后的连续 review 不计作跨 PR 记忆成功; "无人回复"不计作误报真值.
- 机械判据是同一规则对事故变体报告违规、对合法反例保持通过或给出合理不适用; 报告分母和不确定项.
- 满足: G3, G4, G5, G7, G9
- 依据: 逻辑推导; [Martian 方法](https://raw.githubusercontent.com/withmartian/code-review-benchmark/e616e849755441da38f18bf3adba2c9583b03803/offline/README.md)的 gold/profile/judge 限制; [mirrord 历史 review](https://github.com/metalbear-co/mirrord/pull/4986)无法证明跨 PR 记忆.

## 开发顺序应先建立可追溯规则和回归, 再接模型检索与自动挖掘

- 性质为本次需求的实现选择; 不要求复刻 Qodo 的所有基础设施.
- 首先交付 Rule/Incident/Knowledge/Finding/ReviewRun 数据契约、审批与 revision、适用集合和覆盖账本.
- 接入现有 lint/测试, 使一条已知事故具备从不变量到 gate 的可追溯记录.
- 再接代码图/全文/向量及模型证据检查; 规则挖掘只生成候选, 经回放后进入 active.
- Graph 解决关系问题, 全文解决精确术语, vector 解决语义召回, 规则实体负责政策; 单一向量库不能替代这些职责.
- 写法偏好是每条规则一个 assertion、先触发条件和例外再给检查指令、finding 先列触发输入和证据再列修复建议.
- 最小交付以 1200 条结构化规则导入、单个事故回归和显式 incomplete 验证为起点, 不以数据库种类或 agent 数量作为完成标准.
- 满足: G3, G4, G5, G9
- 依据: 本次自研设计取舍: 实体和确定性反例可独立验收; 对照 [Qodo architecture](https://docs.qodo.ai/core-concepts/qodo-platform-architecture.md)的不同知识存储职责与 [Rule Miner](https://docs.qodo.ai/governance/rule-enforcement/rule-miner.md)的候选来源.

## 内部专家规则应先编译为审查问题和取证计划, 使模型无需先猜中风险

- 性质为自研架构. 每条高风险规则除 assertion 外还应有 risk bindings、review questions、evidence obligations 和 counterexamples.
- risk bindings 将业务对象、入口、路径、符号、数据表、服务关系或操作类型绑定到规则; 绑定可以显式维护, 不能只依赖模型猜业务标签.
- 修改保留资源的 creator 删除路径时, 计划主动加入"此操作是否触发 retention 根的级联删除", 即使普通模型没有提出任何 issue.
- 取证义务要求获取外键删除策略、资源生命周期规范、调用者与测试; 仅看到 soft-delete 条件不足以完成判断.
- 模型负责对已提出的专业问题检验证据, 不需要在完全无前提时先自行发现该类风险.
- 机械判据是输入空 model issue 列表后, 命中 binding 的关键 question 仍进入 plan; 证据缺失返回 unknown.
- 满足: G3, G4, G5, G11, G12
- 依据: 逻辑推导, 变更触发与模型 issue 生成是独立输入; [Sim retention 反例](https://github.com/simstudioai/sim/pull/8762#discussion_r4211981741)表明通用删除推理缺专业前提.

## 规则触发召回与模型判断正确率必须分别验收, 适用集合遗漏会发生在推理之前

- 性质为自研验收设计. 风险召回检查 gold 事故义务是否进入 plan; 证据召回检查所需专业事实是否入包; 推理评测检查结论是否符合事实和业务例外.
- 代码重命名、调用关系变化或新增入口会使旧 binding 漏配; 路径绑定之外需变化影响扩展和定期历史回放.
- 对尚未能映射到业务对象的变更记录 unmapped scope, 触发保守的领域巡检或 owner 补审; 不能记作"没有适用规则".
- 模型自由探索与事故义务检查两条通道共同工作; 自由探索寻找规则库尚未覆盖的新问题.
- 千条元数据扫描或 100% 执行覆盖都不能证明千条专业知识被模型正确理解.
- 满足: G3, G7, G11, G12
- 依据: 逻辑推导: 漏配 binding 的事故即使 checker 完美也不会被检查; [NVIDIA DALI 后续人类发现](https://github.com/NVIDIA/DALI/pull/6327#discussion_r3181165160)说明固定已有检查无法取代其他发现通道.

## 专家上下文包必须包含原因、前提和合法反例, 命令式规则文本不足以解释内部特殊情况

- 性质为自研 EvidencePacket 契约. 字段包括 question、rule revision、business invariant、causal explanation、preconditions、exceptions、positive/negative examples、incident sequence、evidence 引用与 missing 项.
- 证据引用携带来源类型、精确 SHA/版本、路径或文档锚点和授权范围; 摘要保留来源, 不能把解释写成无出处的结论.
- ScyllaDB 样例的因果链是未完成 hints/batchlog flush 就不能记录 repair time, 后台恢复因此持续; 等待者超时是独立职责.
- 合法反例是等待者已经超时、后台仍继续恢复; 违规反例是未 flush 成功就记录 repair 完成, 或通用重试封顶中断恢复义务.
- 同一场景需要规则、调用者、实现和测试共同取证; 不能仅用相似的旧评论压过当前事实.
- 机械判据是所有 must-have 证据齐全才进入可判定状态, 缺部署条件、未授权材料或来源过期时必须列 missing 并返回 unknown.
- 满足: G3, G4, G5, G11, G12
- 依据: 逻辑推导; [ScyllaDB 原 PR](https://github.com/scylladb/scylladb/pull/31705)及[恢复解释](https://github.com/scylladb/scylladb/pull/31705#discussion_r4035329429)提供等待与恢复的不同契约.

## 定向专业审查应要求支持证据和反证, 并将无法确认保留为 unknown

- 性质为自研模型端口设计. 输入是单条或少量相关义务的 EvidencePacket; 输出是 structured verdict、evidence IDs、trigger sequence、counterevidence、missing 和 confidence.
- 先要求说明专业不变量与前提, 再定位违反路径; 验证者查引用是否存在、是否同快照、是否忽略例外.
- 多 agent 同意不能代替事实验证; 引用匹配也只验证来源存在, 不自动验证推理有效.
- 低置信度或关键前提缺失留为 unknown, 交 owner 或额外工具; 不能为了绿色结果强制二选一.
- 规则可按业务域拆批推理, 但相关规则需要一并提供, 避免分别审查时制造相互矛盾的建议.
- 模型行为质量以冻结数据上的正确/错误/合法反例实测, 编排原型只能证明义务和证据被发送.
- 满足: G3, G7, G11, G12
- 依据: 逻辑推导: 同一证据可以被多个模型误读; [Cubic 同 PR 的正确与错误发现](https://github.com/simstudioai/sim/pull/8762)和 [Qodo retry 反例](https://github.com/scylladb/scylladb/pull/31705#discussion_r4035329429)证明证据与例外需要具体审查.

## AI CR 的初步架构应将业务义务规划、证据研究和模型判断分成可替换端口

- 性质为自研模块契约. 输入是 ChangeEnvelope, 包含 repo/base/head、changed paths/symbols、影响关系、运行权限与批准政策快照.
- KnowledgeCompiler 管理规则、事故和业务不变量; ImpactMapper 映射变化影响; ObligationPlanner 生成已知专家义务; ResearchPort 获取证据.
- ModelPort 处理 EvidencePacket 并返回 structured verdict; ValidationPort 执行反证、引用和测试; RunLedger 记录每条义务状态, GatePolicy 决定放行/阻断/待补审.
- FreeReviewPort 独立探索新风险; 反馈只产生候选, 审批和回放后才能改变已批准知识.
- 原型应真实运行千条导入、主动义务规划、证据缺失、预算不足、grant 身份回归与知识撤销; ModelPort 可由真实模型接入, 离线原型不伪造模型质量成绩.
- 满足: G9, G11, G12
- 依据: 本次自研架构推导; 模块分工依据 ChangeEnvelope、EvidencePacket、verdict 与覆盖账本的不同契约; [Qodo architecture](https://docs.qodo.ai/core-concepts/qodo-platform-architecture.md)只作为研究参照, 不声称模块等同厂商后台.

## 可运行原型已验证十七项编排与回归检查, 专业模型判断仍保留为外部端口

- 实测范围是 Python 标准库的 review_core.py、review_lab.py; `python review_lab.py --self-test` 返回 ok=true、checks=17; 代码使用 Python 3.10+ 的联合类型语法.
- 测试覆盖 1200 唯一规则、空 model issue 仍规划、top-20 漏掉 GRANT 的反例、关键规则保留、未知范围补审、grant 旧版失败和 identity 修复通过.
- 测试覆盖预算不足、证据 ACL、过期/撤销、旧 packet 保留 revision、无效引用拒绝、model pass 待验证和 create/update/delete 历史.
- `--case retention` 导出一个专业问题及 code/retention_contract 证据; 没有模型结果时为 await_model, gate=needs_review.
- `--case grant` 的适用集合为 21 条, 包含 20 个合成 model 义务; 完整库为 1200 条, 其他范围规则不冒充已通过.
- `--verdicts` 从外部端口读 structured verdict, 检查字段与引用; 即使 pass 且引用有效, validation_pending 仍为 true, 不自动批准业务推理.
- 原型未实现真实 AST、生产数据库、完整影响图、语义模型调用或部署权限系统; 合成知识来源明确标 fixture, 不冒充生产事实.
- 命令没有 `--enforce-gate` 时退出码只表示运行完成; 加该选项时, 非 pass gate 返回非零, 不能混淆执行成功与审查放行.
- 满足: G3, G4, G5, G9, G11, G12
- 依据: 实测 review_lab.py:self_test 的 17 项断言; 源码 review_core.py:plan / evidence_packet / model_result / run / gate; 原项目锁和数据库行为未在本原型复现.

## 原型命令和实测预算输出只描述编排接口, 不代表真实模型成本

- review_lab.py 的默认 case 是 retention; --case 支持 grant、retention、repair; --budget 为非负整数, 默认 22.
- --out 把运行报告写为 JSON; --rules-out 导出包含 1200 个唯一 ID 的规则库; --verdicts 读取以 rule ID 为键的 JSON 对象.
- 三条专家示例为 GRANT、RETENTION、REPAIR, 其他 1197 条为合成夹具; GRANT 的演示 cost=2, 同 scope 的 20 条合成义务 cost=1.
- grant 在 budget=22 时 applicable_count=21、critical_count=21、critical_executed=1, 最小回归通过而 20 条语义义务 await_model; complete=false、critical_complete=false、gate=needs_review.
- grant 在 budget=1 时 GRANT 为 skipped_budget, critical_executed=0、complete=false、gate=needs_review; 字段 budget 与 critical_executed 确实来自实际 JSON 输出.
- retention 在 budget=22 时 applicable_count=1、model_issues_before_planning=0; 专业问题与 code/retention_contract 证据入包, 但没有模型 verdict, 结果 await_model、gate=needs_review.
- 模型结果文件以 RETENTION 等 rule ID 为键, 每个值为对象; status 只接受 pass、violation、unknown, evidence_ids 必须为字符串数组且属于本 packet 的证据 ID.
- 无效结果格式或引用产生 error; 非 unknown verdict 未引用全部必需证据产生 unknown. 引用有效的 pass 仍 validation_pending, 不能自动批准业务判断.
- 成本是演示预算单位, 不是 tokens、实际延迟或付费金额; critical_executed 统计已有 pass/violation 结果的关键条数, 不衡量理解正确率.
- 已实现的 applies 同时要求 active 状态、精确 repo、显式 operation 标签命中和至少一个 path 具有指定 prefix; 它不解析 AST、Git glob 或真实业务影响关系.
- plan 按输入顺序筛选适用规则并深拷贝, 没有 top-k 裁剪; 为空时 complete=false、gate=needs_review, 不能当作无风险.
- 原型 gate 的实际优先级为: 任一 critical violation 先 block; 否则执行不完整或有 validation_pending 时 needs_review; 其余 pass. 它未实现生产例外审批, 只有最小回归的确定性结果能直接通过.
- complete 要求非空适用集合且每条 status 为 pass/violation; 这不是语义正确性保证. critical_complete 另行统计关键条目, 不用规则库总量作分母.
- evidence_packet 在复制来源前检查 principal 的 ACL、active 状态与 valid_until; 证据缺失项进入 missing. 实际 packet 是 question、rule revision、code head、evidence、missing 和检查指令的最小结构, 完整因果/例外契约仍是接真实系统的设计要求.
- 满足: G3, G9, G11, G12
- 依据: review_lab.py:parser / main; review_core.py:expert_rules / library / model_result / run; 2026-10-09 实测 run-retention-22.json、run-grant-22.json、run-grant-1.json 及 17 项 self-test.

## 边界

- 生效范围是 2026-10-08 获取的官网契约、固定源码和公开 PR; 厂商后续产品、默认值和限制需要重新核验.
- [不确定] 三家千条独立规则容量、后台全部关键规则覆盖、完整知识同步与 ACL 实现质量均未独立验证; 需付费环境容量/范围/权限试验.
- [不确定] Qodo 文件同步泛称与细则有张力, 当前按仅追加解释; 完整更新删除需厂商说明和实际导入试验确认.
- [不确定] ScyllaDB replay 性能争议缺独立压测; 不能将作者解释扩大为所有负载下都不存在问题.
- 真实 PR 案例经过选择, 不是随机总体; stars 为获取时仓库数; 维护者测试报告与本地复现分开.
- mirrord 历史中间修复不等于最终 merged 内容; PR-Agent 与 Qodo 有来源/赞助关系; 规则详情私有内容未读取.
- 采纳倾向不等于真值, 类别标签不等于严重度, active 不等于已执行, 零 finding 不等于覆盖完整.
- Get Rules skill 的 top-k 接入策略不等于商业后台算法; Cubic wiki 刷新节奏不等于全部代码索引延迟.
- 自研 schema、审批、覆盖账本、预算门禁和事故契约均是开发设计, 不能作为三家已经提供的功能.
- 事故回归只保护已建模条件; scope 漏配、未运行检查、新调用路径和新型缺陷会破坏复发防御.
- 满足: G2, G3, G4, G5, G6, G7
