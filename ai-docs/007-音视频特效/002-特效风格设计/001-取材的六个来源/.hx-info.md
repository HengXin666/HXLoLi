## 特效风格的取材有七个来源, 分「画面里能直接看到的」与「不一定能直接看到的」两组

- 第一组 (在 OPED 画面里能直接看到的) 四支:
  - **STAFF 流**: 针对 STAFF 表的效果去选择相应字体并制作相关特效.
  - **LOGO 流**: 针对 LOGO 的效果去选择相应字体并制作相关特效.
  - **道具流**: 服装、武器、文具、餐具等. 作者明确注明「这里的道具不一定和人直接挂钩, 可以是单独出现的」.
  - **背景流**: 针对画面背景对歌词取色、更换符合场景风格的字体等.
- 第二组 (不一定能直接看到的) 五支:
  - **歌词含义流**: 针对歌词含义去制作相关特效.
  - **题材流**: 字体的风格化驾驭, 与题材关联密切的绘图代码.
  - **技术流**: 像素、光污染、3D、文字笔画拆解这类高难度做法.
  - **原作元素**: OPED 里面没有但正片或者原作里面有的元素.
  - **其他创意风格**: 有些干脆直接无视 OPED 做, 不受任何限制.
- 「人物流」另有一层细分, 它既是一种来源又有两种表达途径. 表达途径是字体 / 绘图代码 / 歌词含义;
  而「借特定意向指代人」分两支: 人物本身 (肉体: 发色 / 瞳色 / 肤色; 精神: 性格 / 经历 / 理想 / 爱好)
  与身外之物 (服装 / 武器 / 职业 / 收入 / 地位).
- 依据: Seekladoom 的思维导图《OPED 歌词特效设计思路》(2020-09-27, xmind + pdf + png 三格式),
  文件位于其 GitHub 仓库 `Seekladoom-ASS-Effect/OPED歌词特效设计思路/`;
  同源发布见射手网(伪) `assrt.net/xml/sub/640/640738.xml`, 标题即该文件名.

## 七支来源可以按「要不要转译」重新二分, 这个二分比按位置分类更好用

- 导图原分类的**第一组**才是按位置分的 (STAFF / LOGO / 道具 / 背景 四支);
  第二组 (歌词含义 / 题材 / 技术流 / 原作元素 / 其他创意) 本来就是按性质分的.
- 既有的位置分类与重新做的性质分类会得到不同结果.
- 按性质二分: 一支来源要嘛是**作品里已经存在的视觉资产**(去找, 找到直接搬),
  要嘛是**作品内含的抽象属性**(去取, 取到之后还要转译成视觉).
- 同一支来源会落进不同类, 取决于用法. 例: LOGO 若只是照抄色值属前者, 若要抽象成几何母题则属后者;
  字体也一样, 官方字体属前者, 「用楷体表示古典」属后者.
- 这个二分的用处: 前者成本低且不会出错, 后者难度立刻上一档. 面对一首新歌时, 先数前者有几个.
- 依据: 由导图七支归纳得出的二分; 验证方式是对七支各举一例说明它既可直用也可转译.
  (本条不来自导图原文, 是归纳产出.)

## 取材的第一步是数「可直用的官方视觉资产」有几个, 而不是先看画面找灵感

- 可直用的资产指: 官方 LOGO、STAFF 表、官方字体、关键道具、画面既定配色.
- 有一个以上, 走直用路线, 成本低且不会与作品脱节.
- 一个都没有, 只能走转译路线, 必须回到导图第二组 (歌词含义 / 题材 / 技术流 / 原作元素).
- 依据: 由「直用 / 转译」二分推出的操作顺序; 它解释了下一条里「仿视频」策略为何是最省力的做法.

## 「仿视频里的字体」是最省力的做法, 但它的失效边界是「没有官方画面」

- 原话 (原帖此处为破折号, 此处按标点规范改写): 「主体 style 的设置要和谐. 看到不少特效都效果绚烂, 但选择的字体和效果不是很相称.
  具体其实仿视频里的字体是最简单的做法, 效果也是有思路写, 没思路山寨片里的」.
- 这条策略把设计降级成识别加搬运, 代价是放弃原创性, 并且有一个明确的失效场景:
  做**原作没有出过 OP/ED 画面的作品**时 (剧场版、游戏 PV、翻唱曲、同人曲、纯音频) 无片可仿.
- 本地 13 份成品全部是动画 OP/ED, 都满足「存在官方画面」这个前提, 所以它们的作者不需要面对这个问题.
- 判据: 查作品是否有官方动画画面. 无, 则该策略不可用, 必须走转译路线.
- 依据: saiyaku (灾厄) 的经验回顾, 2012 年; 原文由 Seekladoom 于 2021-01-10 从 TCAX 论坛
  (`tcax.org/forum.php?mod=viewthread&tid=285`) 搬运到 Anime 字幕论坛 `bbs.acgrip.com/thread-7194-1-1.html`.

## 「土」的可操作定义: 用了作品里不存在的元素

- 对某个特效的每个视觉要素 (字体 / 色值 / 图元形状), 逐个去作品官方素材里查是否存在.
  查不到的就是外来物, 就是「土」的来源.
- 这条把「不相称」这个不可判定的说法变成了可执行的检查动作.
- 依据: 由 saiyaku 的「字体和效果不相称」与导图「风格转化与融合」两条并联推出.
导图那两条是「LOGO 的颜色和转场效果用在 STAFF 字体上」「人物、武器等事物的颜色 (应援色) 用在 STAFF 字体上」, 两者都是把作品里已有的元素搬到别处, 不要求创造新元素. 并联后可反推回两条原标题.

## 「风格转化与融合」的三条具体做法

- **LOGO 的颜色和转场效果用在 STAFF 字体上**.
- **人物、武器等事物的颜色 (即应援色) 用在 STAFF 字体上**. 导图把这条单列, 说明它是最常被使用的一条.
- **以字体来象征人物或者其他事物**. 导图举的实例是《COP CRAFT》OP 中女主变装那段.
- 依据: 导图「思维角度 → 风格转化与融合」分支原文.

## 「打破常规套路」的三条做法

- **反差萌**.
- **字体不和 STAFF 匹配、不按中日匹配的做法**.
- **反其道而行之, 故直言 selects 让人不喜欢的字体和特效**.
- 依据: 导图「思维角度 → 打破常规套路的思维」分支原文.

## 应援色系统的可迁移部分是「色值数量少 + 分配规则可机械判定」这个形状

- 实测点兔《ときめきポポロン♪》的模板源码 (保留在成品 ASS 的 Comment 行里):
  `color_text={"&HEAA380&","&HDAC95E&","&H758FFA&"}`,
  分配规则为 `line.actor=="chino"` 取第 1 色、`maya` 取第 2 色、`megu` 取第 3 色,
  合唱段用 `color_text[math.fmod(syl.i-1,3)+1]` 按字序循环三色.
- 作者本人在论文里写明了色值归属: 淡蓝色为智乃 (chino), 粉红色为小惠 (megu), 浅绿色为麻耶 (maya).
- 分配规则里还支持音节级的内联特效标记: 条件写为 `syl.inline_fx=="chino"`, 与 `line.actor=="chino"` 并列.
  即除了按整行的角色属性取色, 还能在单个音节上手动指定用哪个角色的颜色.
- 可迁移的部分是「色值数量固定 (3 到 5 个) + 分配规则可判定」这个形状, 而「三色」这个具体数字属于点兔那部作品.
  缺少后半句时, 系统会退化成随手取色.
- 判据: 数这类颜色数组的元素个数 (应在 3 到 5), 并找出索引规则 (角色 / 字序 / 段落).
  实测三份: 点兔 3 色按角色; Charlotte 4 色按段落轮转; 东方只有 1 个色族 (绿), 不适用本条.
- 依据: 点兔成品的 Comment 行原文 + 藤原七宝《毕业设计说明书》.

## 字体选择在真实成品里是「按用途分层」, 不是全片一种

- 实测 `HXLoLi-Music/static/music/Charlotte/Lia - Bravely You.ass`, 同一作品内用了 6 种以上字体:

| 用途 | 字体 |
|---|---|
| 正片 / 屏幕字 / 背景 | Source Han Sans Medium |
| STAFF | 華康魏碑體 |
| 弹幕 (Comment) | 華康POP1體W7 |
| 标题 (Title) | 華康新特明體 |
| ED 日文 | A-OTF Kyoukasho ICA Pro R (教科书体) |
| ED 中文 | 方正稚艺_GBK |

- STAFF 用魏碑 (庄重), 弹幕用 POP 体 (活泼), 标题用特明体, ED 用教科书体.
  每个字体都在回应它所在的那个语境.
- 这是「搬运」策略的直接证据: 每个语境都去取一个已经成立的字体, 而不是全片用一种字体硬撑.
- 依据: 逐文件 `^Style:` 行统计 (命令: `grep '^Style:' <file> | awk -F, '{print $1, $2}'`).

## 从成品反查设计意图时, 模板源码常常完整保留在 Comment 行里

- 点兔那份成品的 Comment 行有 134 条, 内含可执行 Lua 源码, 而非仅注释.
- 实例 (未删节的原文): `Comment: 0,0:00:05.64,0:00:05.64,JP_FX_B,星星+流星的参数表,0,0,0,code line,stars=math.ceil(line.width/90)`.
  由 `stars=math.ceil(line.width/90)` 可知星数按行宽算, 每 90 像素一颗.
- 另一实例: `pos[#pos+1]=bezier_n_uniform_speed(x,y,1)`, 即导图提到的匀速贝塞尔曲线分布函数.
  该函数名与藤原七宝论文里「流星效果使用了 Kyanko 前辈分享的匀速贝塞尔曲线分布函数」完全一致,
  说明这份成品与那篇论文出自同一条技术传承.
- 依据: `grep -c '^Comment:'` 与逐条读取; 论文出处见藤原七宝《毕业设计说明书》.

## 「技术流」的定位与其他来源相反: 它可以合法地脱离「贴合画面」这个约束

- 导图把技术流放在「OPED 中不一定能直接看到的」那一组下面, 即它是独立成立的一支, 与看画面无关.
- 导图对它的评价原文: 「初显技术或测试特效用的, 但正是这部分特效的发展成为了提升软件上限的关键推力」.
- 由此得到一条取舍判据: 技术流衡量的是「工具能做什么」这个能力边界, 与单件作品好不好看无关.
- 这解释了为什么本地有成品做成纯粒子系统: 东方《果てなき風の軌跡さえ》全片 97% 是绘图事件, 图元与画面要素无对应关系.
- 判据: 查一份成品里是否存在无法追溯到画面要素的图元. 有, 则该作品用了技术流且这是正当的.
- 依据: 导图「技术流」条目原文 + 前一篇笔记对东方成品的逐文件绘图占比统计.

## 中文字体在字幕组语境下的三条硬要求

- ① **不缺字**: 简体字幕一般用方正真 GBK; 繁体字幕至少需要按 HKSCS 2008 标准做出来的字体 (最新为 HKSCS 2016).
- ② **分行屏幕字**: 基线不过高, 行距合适, 且要有专门做的假名字形以满足中日混排, 确保视觉统一.
- ③ **竖排**: 保证字号和横排统一 (用于片尾滚动 STAFF、剧场版 ED 这类场景).
- 依据: Anime 字幕论坛帖 5310《一个对动画组来说真正耐用的中文字体应该具备哪些条件》主帖原文.

## 字体选择在实践中有分歧, 分歧点是「假名字形质量」

- 主帖列出的合格字体: 方正细圆_GBK / 方正准圆_GBK / 方正粗圆_GBK、方正正黑 GBK 系列、
  方正雅宋 GBK 系列、方正悠宋 GBK 系列、华康圆体 W3-A/W5-A/W7-A、
  華康中黑體(P)-UN / 華康楷書體W5(P)-UN / 華康細明體(P)-UN、
  源樣黑體 / 源石黑體 / 源樣明體 / 源流明體 / 源雲明體 / 源泉圓體.
- 反驳一 (pyyii1987): 「方正准圆就够了, 要啥自行车」.
- 回应 (主帖作者): 「方正准圆_GBK 在涉及到屏幕字的中日混排时的**假名很难看**, 远不及思源黑体和思源宋体的中日混排效果.
  腾祥的腾祥嘉丽大圆 GB18030 专门做了假名, 横排字幕的中日混排效果比方正准圆_GBK 好多了」.
  补充说明: 方正准圆_GBK 的假名后来改用了 Mplus 的假名, 但质量仍比不上专业日文字体.
- 反驳二 (H.D.Kun): 「圆体的话汉仪正圆也行吧, 中宫宽大阅读起来也舒适」.
- 回应: 汉仪正圆的 S 版本 (GB18030) 在 Win8 上做的 ASS 外挂字幕, 到 Win7 上用 PotPlayer 加载会变大几圈,
  导致屏幕字错位. 即存在**跨平台尺寸不一致**的风险.
- 结论: 分歧的焦点是可判定的两项 (假名字形质量、跨平台尺寸一致性), 与审美偏好无关.
- 依据: 同帖的主帖与 3 条回复原文; 帖 3805 补充了思源字体在 Aegisub 中的具体问题.

## 设计思维的养成有四条可执行动作

- 多接触各种形式的艺术作品.
- 多看现实和网上各路人士的分析.
- 对生活中各种事物的观察与亲身体验.
- 结合自身经历将各个事物用自己的方式去反复思考和诠释.
- 依据: 导图「如何培养这种设计思维」主节点下的四个子节点原文.

## 前辈给出的「做好特效」三条, 两条是态度一条是能力

- 原话: 「首先首先要有爱 [管你是技术控还是角色控 有爱就 ok]」.
- 「其次要能静下来心研究文档. 能问人最好, 但是用的人少或者找不到人的时候只能自己研究了, 必备技能之一」.
- 「最后要努力培养艺术细胞」.
- 补充一条 (同属 soleil艾 那份回顾): 「技术宅们都知道要紧跟时代潮流, 多搞新技术才是王道」.
- 依据: soleil艾 (艾姐) 的经验回顾, 2012 年; 出处同 saiyaku 那段, 见 Anime 字幕论坛帖 7194.
  注意: 这条补充与 saiyaku 那段分属两位作者, 不要混记.

## 视觉反应时间需要预留, 且 K 时间要提前

- 原话: 「主要是要留一个视觉反应时间, K 时间什么的要提前一点, 根据不同的特效提前量也有变化」.
- 这条与字体选择并列出现于同一段经验里, 说明作者把它看作与选型同等重要的基础项.
- 依据: saiyaku 的经验回顾原文.

## 特效字幕存在多个技术栈, 它们对同一目标的取舍不同

- 已见的技术栈: Aegisub 原生模板加 Auto4 Lua、**Kara Effector (KE)** 3.3 与 3.5、**NyuFX**、
  **MOD** 脚本、**PyonFX**、**AE Karaoke (KRK / afx)**、**TCAX / TCAS** (Python 系)、combo_k 的卡拉工具.
- 各栈的取向差别可从存档里的条目名看出: KE 有「代码仿制」与「使用姿势」两类专帖;
  NyuFX 分基础篇与进阶篇; MOD 有「波浪跳跃」「moves4 随机曲线」「动态纹理挂图」等单项脚本;
  AE Karaoke 走 AE 关键帧路线.
- 依据: `Seekladoom-ASS-Effect/【备份】ASS特效研习社 技术交流.part1/2.rar` 解压后的 74 个条目;
  该备份的原始站点为 `tcax.org` 的 ASS特效研习社版块, 共 77 份 mhtml 已转为文本.

## 对「工业化复现特效」的判断: 抛弃融入画面的思考后, 可做的特效会变多

- 原话: 「其实那个时期的很多特效放现在来看都是可以靠【工业化】大批量稳定多样化复现的,
  彻底抛弃传统的融入画面的思考, 追求艺术的极限时, 就会发现很多特效都能做」.
- 这条与「技术流可脱离贴画面约束」是同一判断的两种表述, 但更激进: 它主张**主动放弃**贴画面这一目标.
- 依据: Seekladoom 在搬运帖 7194 时加的按语.

## 同一参数上的分歧是选风格的直接依据: 边框色饱和度取满 1.0 还是中段 0.4 到 0.7

- 主张取满 (影kage): 「基本上都設為 1.0 (這樣彩度會比較鮮豔)」.
- 主张中段 (zxdfcgv, 楼主), 原文转述: S 越小不能说越淡, 配合 bord+blur 实现的是荧光感, 0.4~0.7 附近就很好看, 特指边框颜色 \3c.
- 分歧的实质是两种目标: 取满求「正色鲜艳」, 取中段配 bord+blur 求「荧光感」.
  且后者明确把**边框色与主色分开讨论**, 两者取值规则不同.
- 依据: `彩虹LINE.txt` 第 380 行与第 432 行 (关键词 `這樣彩度會比較鮮豔` / `0.4~0.7附近就很好看`).

## 高饱和度是否可用取决于片源: 同一做法有人判「鲜艳」有人判「不适合某些 PV」

- 主张鲜艳 (影kage): 同上, S、V 都设 1.0.
- 主张降饱和 (CMD): 「使用的 _G() 颜色转换函数是转换成彩虹色, 感觉不怎么好, 颜色太鲜艳, 对一些 PV 不适合, 这里修改成淡色」.
- 实质: 彩虹逐字是圈内最常见的默认做法, 但它与花哨或明亮的片源会打架.
  **风格是否成立取决于片源, 不存在普遍正确的饱和度.**
- 依据: `彩虹LINE.txt` 第 380 行与 `对字幕_压制_auto4使用的一些基础总结.txt` 第 563 行.

## 逐字渐变的色相要按行内音节数平分, 且句尾计数需要折返

- 标准做法: 色相区间除以行内音节数, 每个音节推进一格.
  原文举例「120, 4/10*400 = 160, 每个音节就会平分色调, 就达到了渐变色的效果」.
- 折返修正 (CMD): 「前面 53 的图片中的颜色从第 5 个音节开始变成淡红色, 后面的颜色不怎么适合了,
  修正方式是把音节计数从 1-10 截取前一半 (1-5), 后一半改为 5-1 倒序.
- 即不能让整条色环从头跑到尾, 超出可用区间的部分要折返, 否则句尾会出现与画面不搭的怪色.
- 依据: `aegisub自编特效基础教程.txt` 第 324 到 336 行与 `对字幕_压制_auto4使用的一些基础总结.txt` 第 643 到 647 行.
