# ASS 特效字幕 (KFX, karaoke effect) 知识点

## ASS 特效字幕的生产方式是「打轴 + 模板 + 展开」, 逐帧手工写特效行在生产上不可行

- 流程是先对歌词打逐字时间轴 (k 值), 再写若干「模板行」, 由渲染前端的模板展开器把模板套用到每个音节上, 展开成大量 FX 行.
- 一份 3 分钟歌曲的成品 KFX 通常有数千到数万条 FX 行, 这些行不是人写的, 是模板展开出来的.
- 「绚烂」的来源是同一组标签被程序化地重复几万遍, 而非使用了多种标签.
- 依据: p01 00:00:33 (作者声明按手册顺序讲标签) 与 本地 13 份生产 ASS 的 Dialogue 行数统计.

## 一份生产级 KFX 的规模量级是数万条 FX 行, 面板上反复出现的标签只有七八种

- 实测 Dialogue 行数: 点兔 ときめきポポロン♪ 71596、天使の3P INNOCENT BLUE 34432、天使の3P 羽ばたきのバースデイ 31892、东方 果てなき風の軌跡さえ (copy 版) 30107、无职转生 オンリー 25565、东方 双版 22013、命运石之门 ファティマ 20784、天使の3P モノクローム果樹園 13092、Charlotte Bravely You 5281、天使の3P 大切がきこえる 4999、Made In Abyss 2012、ヨスガノソラ ツナグキズナ 1291.
- 高频标签实测 (ときめきポポロン♪): `\\an7` 70304、`\\blur3` 64938、`\\fad` 64318、`\\pos` 36649、`\\move` 34568、`\\frz0` 17331、`\\fsc110` 17071、`\\fsc120` 11946.
- 高频标签实测 (Charlotte): `\\t` 8352、`\\clip` 5744、`\\an5` 5175、`\\fad` 4092、`\\blur3` 3233、`\\move` 2872、`\\pos` 2303.
- 共性标签族只有: 锚点 (an5/an7)、绝对定位 (pos)、淡入淡出 (fad)、模糊发光 (blur)、动态 (t/frz/fsc)、遮罩 (clip)、绘图 (p).
- 依据: 本地 HXLoLi-Music/static/music 下 12 份 ASS 的正则统计, 匹配式为 `\\([a-zA-Z][a-zA-Z0-9]*)(?=[\\(]|$)`; 带参数的写法 (如 fsc110) 单独计数, 不归并到 fsc.

## 一份 KFX 里能画出什么, 由渲染器支持的标签集决定; ffmpeg 的 libass 与 VSFilterMod 不是同一套

- 标准 libass (ffmpeg 的 subtitles 滤镜所用) 支持 `\\p` 绘图、`\\t`、`\\move`、`\\clip`、`\\fad`、`\\blur`、`\\frx/fry/frz`、`\\fscx/fscy` 等标签.
- VSFilterMod 扩展标签 `\\1img`..`\\4img` (图片纹理)、`\\fsc`、`\\fsvp` (垂直偏移)、`\\moves3`/`\\moves4` (贝塞尔移动) 在标准 libass 上不使用.
- 本地博客的渲染器是定制版 SubtitlesOctopus (libass-wasm), 其 README 声明原生支持上述 VSFilterMod 扩展.
- 后果是同一份 ASS 在 ffmpeg 命令行与在博客里观感不同, 依赖 VSFilterMod 专有标签的部分无法在命令行验证.
- 依据: 本地 HXLoLi/README.md 与 HXLoLi/static/music/ass-worker/workers; 点兔 ときめきポポロン♪ 中 `\\fsvp` 1016 次、`\\fsvp2` 507 次、`\\fsvp3` 404 次.

## 模板修饰语写在行的特效栏, 第一个单词只能是 code 或 template, 第二个单词决定作用域

- 作用域取值: `once` (只执行一次, 仅 code 可用), `syl` (每音节执行一次), `line` (每行执行一次).
- 第二个单词不写时默认 `syl`.
- `noblank` 跳过空白音节, `notext` 丢弃被替换文本, `keeptags` 保留原行标签, `all` 让模板对所有样式生效.
- `fx <名称>` 给单个音节挂内联特效, `fxgroup <名称> = <返回布尔的判断式>` 提供条件特效入口.
- `loop n` 只能填正整数, 灵活性低于自动化函数 maxloop.
- 依据: p03 00:07:40, p03 00:08:17, p03 00:10:49, p03 00:12:32, p03 00:13:16.

## 只有 FX 行参与渲染, code 行、template 行与 karaoke 行都必须注释掉

- 模板展开后会产生四类行: code (定义变量与函数)、template (模板本体)、karaoke (打了 k 值的原始歌词)、FX (最终展开结果).
- 前两类不打注释时不会生成 FX 行; 打上注释后模板才会正常展开.
- 依据: p03 00:04:57 与 画面 03-003 (karaoke 行与 FX 行并列的界面截图).

## 内联变量在模板执行前就被文本替换, 所以值不可改变; 需要可变状态时改用 table

- 内联变量以美元符号开头, 只能出现在 template 行, 不能出现在 code 行. template 行的代码区 (两个半角感叹号之间的部分) 可以使用.
- 值在替换阶段就写死, 后续无法修改. 需要「记住一个随机数并在同一行的多个音节里复用」时用 remember/recall 或 table.
- 作者的建议是能用内联变量就别用 table, 因为 table 字段名更长.
- 依据: p04 00:00:01 段与 p07 00:00:37.

## 行的时间相对整个视频, 音节的时间相对本行的开始时间

- 行变量 `l.start` / `l.end` / `l.mid` 以视频零点为基准.
- 音节变量 `s.start` / `s.end` / `s.mid` 以本行开始时间为基准点, 所以行内第一个音节的 `s.start` 是 0.
- 特例: 使用 `retime` 改变了行的起止时间后, 内联变量读到的是一行最终的 FX 时间, 与写模板时的预期错位, 此时要用 `line.duration` 等 table 字段.
- 依据: p04 00:13:26; p05 00:03:51.

## ASS 标签里的时间参数是相对本行开始时间的, 想表达「从头到尾」要写 0 与行时长而不是行的绝对起止

- 想让一行从开始到结束做颜色变化, 写 `\\t(l.start, l.end, ...)` 得到的是绝对时间被当成相对偏移, 效果错位.
- 正确写法是 `\\t(0, l.dur, ...)`, 其中 `l.dur` 是行时长.
- `k` 值单位是厘秒; 除此以外所有与时间有关的标签参数单位都是毫秒.
- 依据: p05 00:03:51; p01 00:33:41.

## \t 的加速度参数大于 1 时先慢后快, 在 0 到 1 之间时先快后慢, 且该参数后面的逗号不能省

- 不填加速度时变化匀速.
- 该参数位置上写成指数/对数型曲线, 作者的原话判断是指数函数与对数函数那种东西.
- 参数在括号内最后, 后面漏掉逗号时加速度失效.
- 依据: p01 00:31:20, p01 00:31:33, p01 00:32:15.

## \move 只能做线性匀速位移, 变速位移必须改用 \t 或逐帧

- `\\move` 的起点终点之间是线性插值, 没有内置的缓动参数.
- 变速的实现路径是把位移拆成 `\\t` 的多个区间, 或按帧展开成多条 FX 行.
- 依据: p01 00:27:54 附近的演示与作者的直接说明.

## \org 一旦设定, 旋转中心在整条 FX 行内固定; 不设定则旋转中心跟随文字一起移动

- 未设定 `\\org` 时, 文字做位移与旋转的组合运动, 旋转中心随文字平移.
- 设定 `\\org` 后, 文字绕该固定点旋转, 位移过程中中心不动.
- 依据: p01 00:28:03 与 p01 00:28:16.

## \p 的缩放是按长度二分, 第 n 级绘图的长度是原图的 2 的 (n-1) 次方分之一

- 即 `\\p2` 的长度是原图一半、面积是四分之一; `\\p3` 是四分之一长度.
- 由此得到实操惯例: 大范围缩放靠改 `\\p` 的级数, 小幅微调用 `\\fscx` / `\\fscy`.
- `\\p0` 关闭绘图模式, 其后的坐标串不再按绘图解析.
- 依据: p01 00:33:41 附近与 p02 关于绘图命令的讲解.

## 用绘图做特效的模板必须在修饰语里同时加 noblank 与 notext

- `notext` 的作用是丢弃被替换的文本. 缺它时, 绘图行末尾会被拼上原文本.
- 当原文本是数字时, 这些数字会被当成绘图坐标串的延续参与解析, 图形随即变形. 作者举的实测例子是末点坐标 -44 被拉成 -442.
- 空白音节有三种情形 (时间为零、内容是空白字符、有内容但为空), `noblank` 负责跳过它们; 缺它时绘图模板会在空白音节上画出孤立图形.
- 依据: p03 00:13:16 段.

## 矢量遮罩不能做动画, 矩形遮罩可以

- `\\clip` 接受矩形参数时, 参数可以被 `\\t` 驱动做动态遮罩.
- `\\clip` 接受绘图参数 (矢量遮罩) 时, 不支持动画效果.
- 依据: p01 00:41:07.

## 逐帧动画的实现是 maxloop 与 retime 的组合, 且推荐用行时长除以循环数来切片

- `maxloop(N)` 提供循环计数 `j` (从 1 起) 与 `maxj` (= N); `retime` 的 `presyl` / `presyl` 类模式把每一片的时间重新锚定.
- 切片写 `\\t(0, j / maxj * l.dur, ...)` 时末帧正好落在行尾, 整行时间被完整切割.
- 改用固定每帧毫秒数切片时, 末帧会超出或不足行尾. 作者明确推荐前一种.
- `maxloop(N)` 的边界行为: N 为负数或 0 时仍然循环一次; N 为小数时向上取整.
- 依据: p06 00:00:01, p06 00:03:25, p06 00:11:28, p06 00:14:40.

## 内联变量 s.dur 与 l.dur 的单位是厘秒, 与 k 值同制

- 这是少见的非毫秒时间量, 与 `\\t` 等标签的毫秒制不同, 混用时会出现十倍误差.
- 依据: p04 00:13:26.

## 随机数的分层: 无参 math.random() 是 [0,1) 均匀分布, 单参是 1 到 N 的整数, 双参是闭区间整数

- 需要「中间密两边疏」时用正态分布, 作者自写的正态随机函数参数是最小值、最大值、方差、期望.
- 该实现用拒绝采样, 并在连续 1000 次落在区间外时回退到更近的边界值.
- 依据: p06 00:21:28, p06 00:24:27, p06 00:25:47.

## remember 与 recall 用于「随机起点 + 规律位移」, 第一个参数必须是字符串字面量

- 直接写 `a` 会被当作查找变量 `a` 而报错, 必须写成字符串.
- 不加这对函数时, 每个粒子的起点与终点都随机取值, 运动呈现杂乱; 加上后起点随机但位移量在行内保持一致.
- 依据: p07 00:00:37, p07 00:02:13.

## 在 code 行调用自写函数必须加反斜杠 g 前缀, Aegisub 自带函数与 Lua 标准库不需要

- 该前缀把函数声明为全局, 否则模板展开时找不到它.
- 把自写库放进 utils 并在 `utils auto4` 里 require 之后, 可以省掉这个前缀.
- Lua 侧最常用的是 math 库, 其次是 string 与 table; 模式匹配是把文字转成绘图后做变形操作的主要手段.
- 依据: p06 00:14:40 段末与 p08 00:03:53, p08 00:04:31, p08 00:04:56.

## Yutils 的 shape.to_pixels 会把 ASS 体积从几 KB 推到几 MB, 不适合常规特效

- 该函数返回绘图轮廓的像素点集, 体积代价与图形复杂度成正比.
- 作者列出的其他常用项是 table.tostring、decode.create_font (建字体对象并转绘图)、shape.filter (绘图变形).
- 依据: p08 的 Yutils 段落与 p05 00:06:20.

## 特效所需数学的绝大多数只需要高中程度

- 作者给的映射: 微积分用于格林公式判断绘图路径方向与求面积 (面积过小则替换成预设图形); 线性代数用于三维点绕轴旋转; 概率统计用于正态分布随机数; 信号与系统用于频域做频谱效果; 计算机图形学用于多边形效果.
- 作者的原话判断是高中程度的数学知识覆盖约百分之九十的日常效果.
- 依据: p08 00:11:17 与 p08 00:12:33.

## 本地播放器的裁剪管线是「ffmpeg 渲染扫描 → 双向 EMA 平滑 → 前端线性插值 → 画布裁切」四段

- 扫描: 固定 1920x1080 画布, 以 2 fps 采样全曲, 逐帧在黑底上渲染 ASS 并扫描非黑像素, 得到每帧的上下两块边界框 (上下分区的判据是两组内容间垂直空隙不小于 100 像素).
- 平滑: 滑窗半径正负 2 秒取并集, 再做正向与反向两遍 EMA, 系数 0.15.
- 插值: 前端 `interpolateBoundsAtTime` 在相邻关键点之间线性插值.
- 裁切: `cropAndDraw` 按水平 30 像素、垂直 10 像素的 padding 从整幅画布裁出并居中重画.
- 依据: 本地 HXLoLi-Music/py/music/ass_prescan.py 的 `_prescan_ass_bounds_impl` 与 `_smooth_bounds_timeline`; 本地 HXLoLi/src/components/MusicPlayer/AssLyrics.tsx.

## 裁剪窗口的轻微抖动来自平滑算法的非对称时间常数

- 平滑实现的设计是「扩张立即响应, 收缩缓慢衰减」.
- 两个方向的时间常数不同, 导致裁剪框在内容边界附近扩张时立刻跳变、收缩时缓慢爬行, 表现为窗口呼吸.
- 反向 EMA 与前端线性插值只是把幅度削小, 没有消除这个不对称.
- 依据: 本地 ass_prescan.py 中 `_smooth_bounds_timeline` 的 docstring 与 `adaptive_ema` 实现.

## 裁剪环节无法取消, 因为渲染画布是 1920x1080 而悬浮窗默认只有 500x350

- `DEFAULT_SIZE` 为 500x350, 渲染画布仍是整幅 1920x1080.
- 把整幅画布直接缩进悬浮窗会使字幕小到不可读, 因此必须先裁出内容区再缩放.
- 依据: 本地 HXLoLi/src/components/MusicPlayer/AssLyrics.tsx 的 `DEFAULT_SIZE` 与 `cropAndDraw` 调用点.

## 特效位置预先约束在一个固定矩形内, 就能把裁剪从时间序列退化成单个常量矩形

- 现有链路上裁剪窗口是时间的函数 (`assBoundsTimeline` 有 297 个关键点), 因此每一帧都要按时间插值出窗口.
- 若所有 FX 行的绘制范围在设计阶段就落在一个固定矩形内, 裁剪只需该矩形一个常量, 前端不再需要逐帧插值与 EMA 平滑, 抖动随之消失.
- 固定矩形的代价是特效必须放弃超出该区域的表现, 例如全屏扫光、边缘飞入.
- 依据: 本地 HXLoLi-Music/static/info/0e6bb9830342.json 的 `assBoundsTimeline` 长度与 ass_prescan.py 的时间轴生成逻辑.

## 裁剪窗口的抖动量级实测: 相邻关键点的窗口跳变中位 1 到 5 像素, 但每首都有 0.6% 到 13.2% 的关键点跳变超过 50 像素

- 统计口径: 取 11 份已生成的 `assBoundsTimeline`, 只用有内容的关键点, 计算相邻两点在 left/right/topYMax/btmYMax 四个量上的绝对差之和.
- 逐首结果 (中位 / 最大 / 超过 50 像素的占比): 大切がきこえる 3 / 1649 / 1.7%; Bravely You 2 / 138 / 1.4%; ファティマ 2 / 69 / 2.1%; INNOCENT BLUE 2 / 1669 / 3.8%; ツナグキズナ 1 / 95 / 1.8%; ときめきポポロン♪ 1 / 797 / 7.7%; 羽ばたきのバースデイ 5 / 2054 / 13.2%; モノクローム果樹園 2 / 1500 / 11.5%; オンリー 3 / 84 / 0.6%; 果てなき風の軌跡さえ 3 / 552 / 2.6%.
- 这个分布解释了为什么观感问题是轻微微移震荡而不是剧烈抖动: 绝大多数相邻帧只差几个像素, 但偶发的几百到两千像素跳变会把平滑算法推入缓慢衰减过程, 之后几十帧都处在追赶状态.
- 依据: 本地 HXLoLi-Music/static/info/*.json 的 11 份 `assBoundsTimeline` 实测统计 (共 2611 个有内容关键点).

## 现有素材的内容范围跨满整个画布, 所以对它们无法事后套一个固定裁剪矩形

- 逐首的内容包围盒 (取所有关键点的并集): ファティマ x[154,1761] 宽 1607 高 1080; モノクローム果樹園 x[54,1875] 宽 1821 高 1048; ときめきポポロン♪ x[160,1845] 宽 1685 高 1039; 羽ばたきのバースデイ x[0,1383] 高 1079; Bravely You x[288,1635] 宽 1347 高 1079; INNOCENT BLUE x[0,1329] 高 1079.
- 全部 11 首的并集是 x[0,1875]、y[0,1080], 即画布的 98% 与 100%, 等于没有约束.
- 依据: 同上 11 份 `assBoundsTimeline` 的逐首并集计算.

## 把固定矩形候选回测到现有素材上覆盖率极低, 这证明归一化只能从创作侧做

- 四个候选固定框的回测 (10 首, 2611 个关键点): 1600x420 逐帧完全落入率 6.2% 且面积覆盖率中位 50%; 1280x360 为 1.0% 与 42%; 960x300 为 0.4% 与 26%; 实测框 815x332 为 0.0% 与 40%.
- 回测的意义不在挑出哪个框更好, 而在说明: 事后给既有素材套固定框会裁掉大部分内容, 因此固定安全区必须在写特效之前定下来, 由生成侧保证不越界.
- 依据: 用本地 11 份 `assBoundsTimeline` 对四个候选矩形做的逐帧包含与面积交并统计.

## 用包含 80% 像素质量的最窄行带衡量内容集中度, 现有素材分成两类

- 口径: 每帧按行统计非黑像素数, 取包含全部非黑像素里 80% 质量的最窄连续行区间.
- ときめきポポロン♪: 该带高度中位 96 像素, 位置中位在 y 911 到 1017, 属于歌词集中在画面下部一条带.
- Charlotte Bravely You 该带高度中位 1018 像素; 东方 果てなき風の軌跡さえ 中位 830 像素; 无职转生 オンリー 中位 886 像素; 这三首的内容本身就铺满画布.
- 两类素材对应两种设计取舍: 集中型的可以直接用固定矩形; 铺满型的必须先把特效收敛到一条带内才谈得上固定裁剪.
- 依据: 本地用 ffmpeg 的 subtitles 滤镜按 2 fps 渲染这四份 ASS 后逐帧统计非黑像素行分布.


## 画面分析给出的第一个硬约束是「亮度」而不是「构图」: 直接往明亮 MV 上叠白字, 九成区域达不到可读门槛

- 实测素材: 东方那首的封面 (1280x720, 放大到 1920x1080). 亮度中位 0.381, p90 0.959, 其中 31.6% 的像素亮度高于 0.60, 19.1% 低于 0.10.
- 按 WCAG 的 12:1 门槛反推, 底板亮度必须不高于 0.0375. 而该画面只有 9.4% 的区域满足.
- 把整幅画面线性压暗也救不回来: 压到 50% 仍有 84.4% 区域不达标, 压到 20% 仍有 70.5% 不达标 (因为高光区实在太多.)
- 反查该画面的主色 (k-means 12 簇) 也印证: 占比最高的六簇是 #FAFAF6 / #A7ADA8 / #EEE7D8 / #84929B / #C3C1C3 / #66777B, 全是浅色, 对白字的对比度只有 1.04 到 4.67.
- 结论: 在明亮 MV 上做特效歌词, **局部暗底 (BackColour) 或按段压暗是必备项**, 不是可选项. 与本地规则文档里"背景必须压暗"那条一致, 但这里是它对**真实 MV 而非纯黑底**的量化确认.
- 依据: 本地 东方 封面 jpg 的逐像素亮度统计与 k-means 主色聚类, 脚本存在 `toolkit/normalize/scene_analysis.py`.

## 安全区应当用「两遍法」定, 因为设计意图与实际渲染出的包围盒必然有偏差

- 第一遍: 按设计意图给一个宽裕的安全区 (1280x240), 生成并逐帧渲染, 实测得到内容并集.
- 第二遍: 取第一遍的并集加少量余量 (水平 16 像素、垂直 12 像素) 作为正式安全区, 重新生成.
- 实测收紧效果: 安全区从 1280x240 收到 1155x167 (面积降到 63%), 而裁剪缩放系数从 0.3906 升到 0.4329, **字号视觉大小提升 10.8%**; 两次都保持零越界.
- 为什么必须两遍: 字号自适应、字形宽度估算 (`cw = 全角取字号、半角取一半`) 与字体的真实 advance 无法精确一致, 逐帧实测是唯一可靠的收敛手段.
- 依据: `toolkit/normalize/build_normalized.py` 与 `measure_bbox.py` 的两轮实测 (1280x240 -> 并集 x[396,1519] y[866,1009]; 1155x167 -> 并集 x[447,1465] y[906,1020], 两次越界量均为 0).

## 从成品反解歌词时, 标题与艺术家行会混进歌词流, 必须单独过滤

- 东方那份源文件里, 首句聚合出来是 `果てなき風の軌跡さえ-少女フラクタル/天宮みや`, 而它不是歌词, 是曲名与演唱者的元数据.
- 判据: 该串含 `/` 或 `-` 且长度明显偏离其它句; 更稳的做法是把聚合结果与音频时长、句子时间分布一起看 (元数据行通常出现在第 0 句且时长异常.)
- 依据: 本轮生成的原型里首句被原样渲染出来, 抽帧后目视发现.

## 归一化在创作侧的可行性已被端到端实测证实: 38 句、264 条事件、逐帧包围盒零越界

- 做法: 从东方那首成品的逐字事件聚合出 38 个完整句 (源文件每字有多个错峰副本, 先按「连续相同文本去重」), 再以「整行一条事件、每字一条事件」重写. 每字的 `\\pos` 恒定不变, 到点用 `\\t` 点亮; 母题图元层同样是静止路径加 `\\clip` 限幅.
- 声明安全区为 x[320,1600] 与 y[770,1010] (1280x240), 逐帧渲染 380 帧后用「与纯背景色的通道差之和」求包围盒.
- 实测并集: x[396,1519] 宽 1123, y[866,1009] 高 143. **四个方向的越界量都是 0** (内容全程落在声明的安全区内.)
- 对照: 若按逐帧内容框动态裁剪, scale 在 0.4452 到 0.8460 之间漂移, 相邻帧最大跳变 0.3891; 按固定安全区裁剪则 scale 恒为 0.3906, 跳变恒为 0.
- 依据: 本地 `/tmp/hx-kfx-norm/` 的 `build_norm.py` (生成器) 与 `measure.py` (逐帧扫描), 渲染用系统 ffmpeg 的 libass.

## 安全区的宽高比与播放器窗口的宽高比不匹配时, 字号会被压缩, 这是归一化的真实代价

- 播放器悬浮窗默认 500x350, 比例 1.43; 而一句歌词加母题是横条, 实测比例约 1280 / 240 = 5.33.
- 裁剪缩放取 `min(目标宽/框宽, 目标高/框高, 1)`, 因此受限于更紧的那一维. 安全区越宽, 字被压得越小: 1280 宽的安全区把 68px 的字缩到约 27px.
- 这意味着「安全区尽量大」是错的. 安全区应当在**够放下最大特效**的前提下尽量贴近播放器窗口的宽高比, 否则等于自愿缩小字号.
- 另一条出路是让播放器在归一化之后不再按内容缩放, 而是对固定源矩形只做一次常量变换. 此时字号损失只由窗口与安全区的比例决定, 一次算清, 不随帧变化.
- 依据: 本地 AssLyrics.tsx 第 219 到 236 行的缩放公式, 与 `/tmp/hx-kfx-norm/` 裁剪预览的实际像素.

## 外部生态里没有成熟的「LLM 直接产出 KFX」方案, 两个最接近的项目都是 2026 年 9 月新建且星数为零

- 按 star 与最后推送核实的四个自动化工具: TCAX (56, 2018 停更, 仅 Windows)、Kara_Effector (76, 2022)、PyonFX (187, 2025-08)、Aegisub 本体 (1981, 2026-09). 前三个都是"程序化生成", 但生成脚本一律由人手写, 没有 AI 参与.
- 两个真正做「LLM 到 ASS」的项目都极新且近乎零社区: `Carinoasd/ass-kfx-template` (0 star, 2026-09-26 建) 与 `altqx/aegisub-mcp` (0 star, 2026-09-12 建).

- 依据: 2026-09-28 对上述仓库的 `gh api` 元数据查询 (star 数、创建与最后推送时间) 与 README 正文.

## 前序把 ALGOGEN 当作「LLM 只输出中间表示」的通用佐证是误引, 必须限定到算法可视化领域

- 该论文确实存在 (arXiv 2605.12159, "Tool-Generated Verifiable Traces for Reliable Algorithm Visualization", v1 2026-05-12), 但它讲的是算法可视化 (Manim/LaTeX), **与 ASS 字幕无关**.
- 它给出的数字是: LeetCode AV 基准 200 任务, 解耦式 (LLM 产 tracker 与 VTA-JSON 轨迹, 确定性渲染器编译) 成功率 99.8%, 端到端 82.5%.
- 通用代码生成侧的 IR 佐证是 IRCoder (ACL 2024 Long, doi 10.18653/v1/2024.acl-long.802) 与 arXiv 2407.05411, 结论是"IR 带来稳定增益", 但摘要未给单一百分比.
- 后果: 本项目中"AI 写意图、确定性程序展开"的路线**没有本领域的对照实验支撑**, 它是本地实测 (东方 22013 行 / 73 种模板 / 100% 重复) 推出的工程结论, 不是论文结论.
- 依据: 论文摘要页与 IRCoder 的 ACL Anthology 条目.

## 画面驱动歌词放置已有学术范式, 但它的目标与 KFX 的「绚烂」方向相反

- arXiv 2308.14922 "Automated Conversion of Music Videos into Lyric Videos" (Ma et al., 2023-08-28) 做了完整管线: 先立「可读性 + 注意力统一」的放置准则, 再自动决定歌词在画面中的位置, 并以用户研究验证.
- 更早的 arXiv 1407.5145 "Speaker-following Video Subtitles" 用音视频识别说话人加全局优化来定位字幕, 动机是"底部固定字幕会让视线偏离".
- 关键差别: 这两条的优化目标是**不干扰画面、可读**, 而 KFX 要的是**让特效成为画面的一部分**. 因此它们只能提供"哪里放才不会挡画面"的判据, 不能提供"该放什么图形".
- 未找到"用显著性/亮度分析驱动 KFX 放置"的开源项目; 这一层在公开生态里疑似是闭源 SaaS (lyricedits / videobolt / Youka).
- 依据: 两篇论文摘要页, 以及 nomadkaraoke/karaoke-generator (63 star, 2025-07) 的自述偏向音频对齐而非帧分析.

## 第三层自由度已端到端验证: 138 条事件全部由 Lua 算法生成, 门禁三条全过

- 输入: 6 句真实日文歌词与时间轴. 输出: 138 条 ASS 事件 (60 条逐字 + 78 条图元).
- **全部由代码算出**: 坐标来自 `pos()` 的参数方程, 尺寸来自正弦周期, 时间来自行内插值,
  形状来自 10 个用 `m`/`l`/`b` 指令写的贝塞尔母题函数按语义挑选. **没有任何模板、素材库或"主题"参数. **
- 三条机械门禁实测:
  - 归一化: 内容并集 x[489,1437] y[897,981], 四个方向越界量全为 0; 裁剪缩放恒为 0.4329,
    而按逐帧内容框裁会漂移 52.7%.
  - 母题多样性: 61 种指纹, 最高频占比 0.04 (门限 >=12 与 <=0.50).
  - 逐字点亮: 6 个整行组, 顺序全为从左到右递增, 时刻无越界.
  - 可读性: 填充/描边 6.38:1, 填充/背景 19.30:1, 绘图色/背景 12.82:1.
- 依据: `toolkit/mcp-lua/kfx_generator.lua` (280 行 Lua) 与 `preview/` 下的成品与三帧对照.

## 在 Lua 里处理 UTF-8 必须自己按首字节判长度, 否则中文会被切成残片

- LuaJIT 2.1 对应 Lua 5.1, **没有 `utf8` 库**. 用 `string.sub(s, i, i)` 逐字符遍历,
  会把三字节的汉字切成三个残片, 渲染出来是乱码.
- 可用的做法是按首字节判长度: `>= 0xF0` 为 4 字节, `>= 0xE0` 为 3 字节, `>= 0xC0` 为 2 字节,
  否则 1 字节, 再 `string.sub(s, i, i + len - 1)`.
- 附带一个更隐蔽的坑: 引擎用 `encoding="latin-1"` 传字符串, 所以 Lua 写出的字节要按
  latin-1 还原后再按 UTF-8 解码, 直接把 latin-1 字符串当 UTF-8 用会得到乱码.
- 依据: 本轮实测. 修之前渲染出来的日文全是 `ä`/`ã` 残片, 修之后正常.

## Lua 的换行符不是换行: 写完必须转换

- 在 Lua 里用 `BS .. 'n'` (BS 是反斜杠) 拼出来的是**两个字符 `\` 与 `n`**, 它不构成换行符.
- 后果很隐蔽: 文件能写出来、字节数是合理的、UTF-8 也合法, 但整个内容挤在一行里,
  用 `startswith('Dialogue:')` 统计只会得到 1 条.
- 判据: 写完立刻数一下行数; 只有 1 行就说明换行符没生效.
- 依据: 本轮实测 (修之前 138 条事件被算成 1 条.)

## 生成物"看起来对"与"结构对"是两件事, 必须用结构判据而非目视

- 本轮连续踩到三个"文件生成了、但内容是错的"的情况, 每一个都能通过目视糊弄过去:
  1. 中文被按字节切成残片. 渲染出来是一片 `ä ã` 形状的字符, **远看像日文**, 不放大看不出来;
  2. 换行符是字面量. 文件大小与 UTF-8 校验都正常, 只是内容挤成一行;
  3. 上一次生成的旧文件没被覆盖 (渲染的是过期产物, 看着"有东西"就以为成功了.)
- 有效的判据是**结构性的**, 而不是"看起来有没有东西":
  - 事件数 (按 `Dialogue:` 前缀统计) 对不对;
  - 中文字符的正则命中数是否非零;
  - 输出文件的 mtime 是否晚于本次生成.
- 依据: 本轮三次返修, 每次都是靠结构判据而不是靠看图发现的.
## 把 MCP 接进 agent harness 需要写对三处环境, 否则工具会静默少掉三分之一

- 接线本身是一个配置条目 (id 指向 MCP 客户端插件, 配 `serverName` / `transport` / `command` / `args`).
  工具会以 `mcp__<serverName>__<tool>` 的形式出现在模型工具表里.
- **三处必须写对, 每一处都实测踩过**:
  1. **解释器版本**. 必须用 3.12+ 的那个 venv. 用 3.11 会让两个模块静默导入失败,
     工具数从 138 掉到 98, 且**不报错**. 判断方法: 启动日志里 `registered` 行应出现
     模块数次加一次汇总 (本例 8 + 1 = 9 行).
  2. **PYTHONPATH 指向 src**. 该包是 src 布局且未 pip install, 不设就 import 不到.
  3. **自动化 include 目录**. 不设的话 Automation 4 脚本里的 karaskel 等 include 找不到,
     模板与自定义 Lua 全部失败.
- 另一条经验: 配置层的错误**大部分是静默的**. 服务照样起、harness 照样跑, 只是能力少一块.
  所以接完之后必须验"工具数对不对", 而不是"没报错就行".
- 依据: 本地 `~/.dsh/profiles/web/cordis.patch.yml` 与 `~/.local/opt/aegisub-mcp` 的两次启动对照.

## 验证第三方工具是否真的可用, 要看功能级别的探针, 而不是"服务起来了"

- "服务能启动"与"能力是对的"是两件事. 本轮实测到的两种失败都发生在"服务正常"的前提下:
  模块静默缺失 (98/138), 以及某个 API 在特定调用形态下必然失败 (filter 里的 append).
- 可操作的判据:
  1. **数量对得上** (工具总数与官方自述一致;)
  2. **能力域齐全**. 逐个列出 feature area, 缺一块能立刻看出来;
  3. **端到端跑一遍最短链路** (从输入到可见产物, 而不是只调一个读接口. )
- 本轮就是靠第 3 条才发现 append 那条上游缺陷: 只读接口全部正常, 写接口一碰就炸.
- 依据: 138 vs 98 的工具枚举对照, 与 `subtitles:append` 的三段 pcall 探针.
## 自由度分三层, 而「套模板」只是最低那一层

- 本地已装的 aegisub-mcp 共 **138** 个工具, 按能力域分成三层, 约束从多到少:
  1. **数据编辑层**. 行/样式/时间轴/卡拉OK标签 (`ass_*_line`、`ass_*_style`、`ass_karaoke_*` 等).
     约束最多: 改的是已有结构, 做法接近"填空", 这就是"套模板"的来源.
  2. **绘图几何层**. 20 个 `ass_*_drawing` 工具. `ass_svg_to_drawing` 能把**任意 SVG 路径**
     (含三次贝塞尔) 转成 ASS 绘图代码, `ass_transform_drawing` / `ass_drawing_bbox` /
     `ass_split_drawing` 让几何可被程序化操纵. 这一层的自由度等于"想画什么就画什么".
  3. **任意程序层**. `ass_automation_from_source` 直接执行**内联 Lua 源码**, 不需要落文件.
     约束最少: 可以写循环、条件、随机、状态与任意数学. 特效是"算出来的"而不是"选出来的".
- 实测确认第 2 层的关键能力: 输入 `M10,80 C40,10 65,10 95,80 S150,150 180,80`,
  输出 `m 10 80 b 40 10 65 10 95 80 b 125 150 150 150 180 80`, 并附带 bbox [10,10,180,150].
  **贝塞尔曲线保留为 `b` 指令** (也就是说手绘的任意曲线可以直接进 ASS. )
- 依据: 本地 `~/.local/opt/aegisub-mcp` 的工具枚举 (tools/list 实测 138 条) 与 `ass_svg_to_drawing` 的实跑结果.

## 「手搓 ASS 文本」是必然的失败形态, 因为那 20 个绘图工具此前根本没加载成功

- `aegisub-mcp` 的 venv 建在 **Python 3.11** 上, 而它的 `drawing_tools.py` 与 `timing.py` 用了
  f-string 内含反斜杠的写法 (该语法 **Python 3.12 才允许**. )
- 后果是这两个模块**静默导入失败**: stderr 只留一行 `could not import tool module ... its tools will
  be missing`, 服务照常启动, 但只注册 **98** 个工具而不是 138 个.
- 缺的正好是 `timing` (20 个, 时间轴) 与 `drawing_tools` (**20 个, 绘图**) (也就是"画东西")
  和"排时间"这两类最核心的能力. 用剩下的工具做事, 自然只剩改文本与套模板这一条路.
- 换成 Python **3.14** 重建环境后, 138 个工具全部注册.
- 另一处: DSH 的 `cordis.patch.yml` 里**从来没有加过 aegisub 段** (前序记录声称已追加,)
  实际不存在. 所以此前所有"用 MCP 调 Aegisub"的说法都没有落地.
- 依据: `~/.local/opt/aegisub-mcp/.venv314` 与 `.venv` 两次启动的 stderr 逐行对比 (98 vs 138),
  以及 `~/.dsh/profiles/web/cordis.patch.yml` 的完整内容 (7 个 id, 无 aegisub).

## 端到端实测: 24 个图形的几何与时间全部由 Lua 算出, 零模板零素材

- 链路: **Lua 算 → Python 落盘 → libass 渲染验证**, 三段都跑通.
- Lua 侧: `ass_automation_from_source(code=..., macro=..., kind='filter')` 执行一段纯计算代码,
  用 `math.sin`/`math.cos` 生成参数曲线上的 24 个点 (坐标、尺寸、起止时间), 经 `aegisub.log` 输出.
  实测返回 `ok: true`, 日志含 24 行结构化数据.
- Python 侧: 读回这些行, 拼成 `{\an5\pos(x,y)\p1\bord0\1c...\t(0,dur,\1a&HFF&...)}` + 绘图路径,
  用 `ass_add_line` 落盘, 再用 `ass_save` 导出. 实测 24 条事件写入成功.
- 渲染侧: ffmpeg + libass 渲染 48 帧, 抽 3 帧目视确认图形按算出的坐标逐个出现并淡出.
- 这条链路里**没有任何模板文件、没有任何素材库、没有任何"选一个主题"的步骤**. 图形的形状、位置、时间、淡出曲线全部来自代码里的算式.
- 依据: `/tmp/kfx-lua/gen.ass` (37 行, 24 事件) 与 `/tmp/kfx-lua/strip.png` 的三帧对照.

## 一个真实存在的上游缺陷: subs:append 在 filter 里必然失败, 根因是 userdata 不被转换

- 现象: 在 Automation 4 filter 里调 `subtitles:append(line)` 稳定报 `subs.append(line): expected a
  line table`, 而同一段代码在宏里也不成立.
- 定位过程 (逐层排除):
  1. 行表本身正常. `type(t)=='table'`, `t.text` 与 `t.class` 都取得到;
  2. `lua_to_py` 对普通表转换**正确**. 实测返回 `{'layer':1,'text':'hello','class':'dialogue'}`;
  3. 关键发现: filter 收到的 `subtitles` 参数 `type` 是 **userdata** 而不是 table;
  4. `lua_to_py` 只在 `lupa.lua_type(value) == 'table'` 时做转换, **userdata 直接原样返回**,
     于是 `isinstance(payload, dict)` 为假, `append` 抛错.
- 另一个容易误判的点: `engine.py` 导入的是 `lupa.luajit21`, 与 `import lupa` 的默认 runtime
  **不是同一个**. 拿默认 runtime 造的表去调, `lua_type` 返回 `None`, 会得出"转换函数坏了"的
  错误结论. 排查这类问题时必须用 engine 实际使用的那一个模块.
- 影响面: 任何想在 filter 里追加行的写法都走不通, 包括前序记忆中反复卡住的那条路径.
- 绕法 (本轮实测可用): 让 Lua **只负责计算**并把结果结构化输出, 由 Python 侧用 `ass_add_line` 落盘.
  这不损失自由度. 算法仍在代码里, 只是把"写"这一步交给更可靠的一侧.
- 依据: 三段对照实验 (`/tmp/gen3.lua` / `/tmp/gen4.lua` 的 pcall 探针) 与 `lua_to_py` 源码第 154 行.

## 归一化的收益不止是窗口不抖, 还包括字号视觉大小恒定, 而后者此前没有被量化过

- 前端裁剪在缩放阶段用的系数是 `scale = min(目标宽/内容宽, 目标高/内容高, 1)`, 它**每一帧**按内容包围盒重新算, 所以内容高矮一变, 字号的视觉大小就跟着变.
- 实测 18 份 `assBoundsTimeline`: 单曲之内逐帧 scale 的相对跨度最小 0.208, 最大 1.460; 相邻关键点之间的 scale 跳变中位大多为 0, 但**单次最大跳变达 0.6029**, 即一次采样间隔内字号的视觉大小变化 60%.
- 曲目之间的 scale 中位值从 0.2606 到 1.0000, 相差 3.84 倍. 同一套字号设计放到不同曲目上, 呈现出来的大小本来就不一致.
- 若内容被约束进一个固定矩形, scale 退化成常量 (以 1600x420 的框为例恒为 0.3125), 整个播放过程中字号视觉大小不再变化.
- 依据: 本地 HXLoLi/src/components/MusicPlayer/AssLyrics.tsx 的 `cropAndDraw` (第 219 到 236 行, scale 定义在第 222 行) 与本地 18 份 static/info/*.json 中 `assBoundsTimeline` 的逐点复算.

## \\fsvp 在该引擎里的语义是垂直位置偏移, 自述文档明确说这是对上游错误实现的修复

- 自述文档的原文描述是「从错误的水平错切实现修正为正确的垂直位置偏移, 修复图片浮动和文字弹跳效果」.
- 源码里 `ass_render.c` 的注释写着 `\\fsvp` 是 Vertical Shift in Pixels, 值为 PlayRes 坐标系中的像素数.
- 换算方式是把该值按帧内容高度与 PlayResY 的比例转成设备坐标, 再乘以 64 转成 26.6 定点数, 加到 `info->pos.y` 上: `fsvp_device = info->fsvp * frame_content_height / PlayResY`, `offs_y = info->pos.y - info->shift.y + fsvp_device * 64.0`.
- 它改变的是整行文字在 Y 方向的位置, 既不是行距, 也不是水平错切.
- 依据: 定制仓库的 `lib/libass/libass/ass_render.c` 第 1412 行与第 1442 到 1446 行, 以及 `README_CN.md` 的「其他改进」一节.

## 该引擎里 \\moves3 与 \\moves4 在源码顺序上不可达, 是 fork 引入的真缺陷

- `ass_parse.c` 的分支顺序是 `complex_tag("move")` 在第 502 行, `complex_tag("moves4")` 在第 544 行, `complex_tag("moves3")` 在第 577 行.
- `complex_tag` 定义为 `mystrcmp`, 而 `mystrcmp` 是**前缀匹配**: 它只要求 `sample` 串被完整匹配, 不要求输入串到此结束. 于是解析 `\\moves3` 时指针先被 `"move"` 吃掉, 剩余 `s3` 留在原地.
- `move` 分支的守卫是 `if (nargs == 4 || nargs == 6)`. 实测生产素材里 `\\moves3` 的参数个数**全部是 6**, 因此这个守卫为真, 分支被完整执行.
- 6 参数的 `move` 分支把后两个参数当作时间区间, 于是 `\\moves3(x1,y1,x2,y2,x3,y3)` 被解释成「从 (x1,y1) 到 (x2,y2), 在时间区间 (x3,y3) 之间做直线移动」. 这是彻底的语义错位.
- 只要 `nargs` 落在 {4, 6}, `moves3` 与 `moves4` 的真实实现就永远拿不到执行机会; 而 `\\moves4` 是 8 参数, `move` 分支因 `nargs == 8` 不成立而 `continue`, 所以 `moves4` 反而是可达的.
- 另外 `argtod` 对 `!$scenter!` 这类未求值的模板变量会解析失败, 落在时间参数位上时结果不可预期.
- 依据: 定制仓库 `lib/libass/libass/ass_parse.c` 第 353、502、544、577 行; `mystrcmp` 的定义在标准 libass 的 `ass_parse.c` 第 68 行 (前缀匹配语义); 以及本地 `HXLoLi-Music/static/music/点兔/ときめきポポロン♪ (心动泡芙♪) - チマメ隊.ass` 里 279 处 `\\moves3` 的参数个数统计 (6 参数 279 处, 占比 100%).

## 生产素材里 \\moves3 的写法与它被解释成的语义, 两者内容完全不同

- 素材里的典型写法是 `\\moves3(!$scenter!,!$smiddle+20!,$scenter,!$smiddle-50!,$scenter,!$smiddle+5!)`, 以及字面量形式 `\\moves3(510,1015,510,945,510,1000)`.
- 以字面量为例, 按二次贝塞尔的本意应为从 (510,1015) 经控制点 (510,945) 到 (510,1000) 的竖直往返.
- 但按 `move` 分支解释, 它变成从 (510,1015) 到 (510,945) 在时间区间 510ms 到 1000ms 之间的直线移动, 即起点与终点互换了一部分含义, 且时间参数被塞进了坐标位.
- 依据: 同上素材文件中 `\\moves3` 的三条实际样例 (`$scenter` 版本、`$center` 版本、字面量版本), 与 `move` 分支的参数语义对照.

## 定制版引擎与标准 libass 的差异必须在生成端当作硬约束记住

## \\1img 在该引擎里的解析与通道映射是固定的四通道模型

- 依据: 定制仓库 `lib/libass/libass/ass_parse.c` 第 996 到 1024 行, `src/SubtitleOctopus.cpp` 的 `setChannelImage` 与 `writeToFile`, 以及 `README_CN.md` 的「图片渲染增强」一节.

## \\fsc 在两套引擎里语义不同, 这是本项目最容易被忽略的兼容性陷阱

- 定制引擎的实现是聚合缩放: `tag("fsc")` 后接参数时取 `argtod(*args) / 100`, 把同一个值同时写进 `state->scale_x` 与 `state->scale_y`; 不带参数时把两者重置回样式的 ScaleX 与 ScaleY.
- 标准 libass 对 `\\fsc` 只保留无参重置的含义. 对照实验 (1920x1080 黑底, 字号 80 的文字 AB, 只换标签): 基线宽度 64 像素, `\\fsc180` 宽度仍是 64 像素 (与基线完全相同), `\\fscx180` 宽度 114 像素, `\\fscy180` 高度 68 像素.
- 标准 libass 把 `\\fsc180` 里的 `180` 静默丢弃, 只执行了无参重置; 定制引擎则按 1.8 倍缩放执行.
- 后果: 同一份 ASS 在 ffmpeg (标准 libass) 与博客 (定制引擎) 下的字号不同, 而字号直接决定内容包围盒, 于是预扫描算出的裁剪框与实际渲染不符.
- 依据: 定制仓库 `lib/libass/libass/ass_parse.c` 第 460 到 469 行; 本机 ffmpeg 的四组对照实验 (每次只改一个标签, 逐帧扫描非黑像素求包围盒).

## 成品 KFX 的生成方式是「结构化输入 + 生成器脚本」, 不是逐行手写

- Aegisub 侧: 歌词带 \\k 值, 特效由模板修饰语 (code/template 行) 在渲染前展开成 FX 行. 展开后产物里不含模板, 只有结果行.

## Charlotte 的中文层用四层 clip 做液面扫光式揭示

## 反解成品时必须处理"一字多副本"与图文混排两个陷阱

- 源文件里每个字有 4 个错峰副本加 1 个落地副本, 直接拼接会把同一个字重复四遍; 需要按连续重复字去重.
- 同一行的绘图代码 (`\\p1` 后的路径) 会与文本混在同一个文本字段里, 过滤条件是"必须含假名或汉字"且"不含绘图命令 (`m/l/b` 后跟数字)".
- ASS 的标签块可以嵌套 (`\\t(0,150,\\alpha&H30&\\blur2)` 里有花括号外的圆括号), 用 `[^}]*` 匹配会在第一个右花括号处截断; 正确做法是取**最后一个**右花括号之后的内容作为显示文本.
- 依据: 反解脚本迭代过程中实际踩到的三类错误.

## 三种流派的差别在「成本花在哪」, 不在审美

- 实测 13 份成品可清楚分成三类, 差别不在审美而在**事件预算花在哪一层**:

| 流派 | 代表 | 事件数 | 标签族 | 绘图占比 | 成本花在 |
|---|---|---|---|---|---|
| 极简派 | Made In Abyss OP | 1960 | **5** | 0% | 时间轴与遮罩 |
| 逐字精细派 | Charlotte | 5211 | 136 | 21% | 把字形拆开重组 |
| 粒子流派 | 东方 风祝 | 42872 | 680 | **97.0%** | 海量图元堆环境 |
| 点阵描边派 | 点兔 | 71462 | 20 | **98.5%** | 沿曲线采样点阵 |

- **点兔那份**: 文字层只有 **1048 条 (1.47%)**, 绘图层 70414 条. 其中「沿兔子轮廓每 3 像素
  放一个发光点」这一项占 **33504 条 (46.9%)**. **看起来最"绚烂"的那份, 承载信息的事件只占 1.5%. **
- **东方那份**: 35510 个粒子**只有 1 种路径**; 683 个"标签"其实是 blur1..blur25 被算成不同标签,
  按族聚类只剩 16 族, 完整标签序列组合只有 **8 种**.
- 结论: **绚烂 ≠ 图形种类多**. 极简派用 5 个标签就成立; 真正决定观感的是事件预算花在哪一层.
- 依据: 13 份成品的逐文件标签统计 + 三份深度拆解报告 (点兔 / 东方 / INNOCENT BLUE).

## 「同一次触发挂多个不同生命周期的效果」才是丰富感的真正来源, 不是母题种类多

- 两份独立拆解 (INNOCENT BLUE / オンリー) 交叉验证出同一结构: 一个字被唱到的瞬间,
  **同时触发 4 到 5 个效果, 各自生命周期完全不同**:

| 层 | 效果 | 生命周期 |
|---|---|---|
| 幽灵层 | 整行先出现, 未唱的是暗态 | 等于**整行时长** |
| 白闪层 | 该字放大 120% 再回弹 | **500ms** |
| 星层 | 该字位置炸一颗四角星 | **400ms** |
| 环层 | 该字位置升起同心环 | **619 到 1708ms**, 随句中位置递变 |
| 粒子层 | 环境粒子经过 | **800ms** |

- **这比"多准备几种母题"值钱得多**: 母题种类是空间维度的多样性, 时间尺度分层是时间维度的.
- 更精妙的一条: **环的参数随字在句中的位置递变** (同一句里越靠后的字, 环存活越久)
  (619 → 696 → 828 → 1103 → 1708 ms), 终态也越大 (232 → 244 → 262 → 280).
  这是"消除机械感"的核心配方, 比换形状有效.
- 依据: 两份由不同执行者独立完成、针对不同作品的拆解报告.

## 音乐结构驱动的特效: 拖长音节之后必然爆发, 且用具体歌词锁死

- 这是把"给歌词配特效"升级为"用音乐结构驱动特效"的分界.
- 实测 (INNOCENT BLUE): **凡有超过 1 秒拖长音节的句子, 紧随的必定是情绪词之一**,
  这些词的窗口事件数从平时 30 到 100 **暴增到 2200 到 2600 (20 倍以上)**.
  三处实测: 「自由」(拖长 1.28/1.13s) / 「ヒカリ」(1.21/1.53s) / 「ソラ」(1.02/1.88s).
- **反例同样干净**: 同一个词「ソラ」在无拖长的两处只有 43 与 29 个事件.
  即 **同一个词, 拖长就炸, 不拖长就静** (触发条件是音乐, 不是词本身. )
- **粒子密度是配器法, 而且与音频响度无关** (东方那份实测): 音频能量峰值在中段,
  而粒子密度峰值在结尾句; 同一句歌词放主歌 50 颗、放尾声 165 颗 = **3.3 倍**.
  若跟随响度, 那段反而会变小 (作者是手工配的. )
- 另一条同构手法: 副歌第一个字被单独踢出来做 0.3 秒孤立特写 (整屏只剩一个字),
  然后才铺开整句. **"稀疏"之后立刻是"最密", 落差就是副歌的推力. **
- 可机械验证的判据: 找出所有单字时长大于 1 秒的位置, 检查其后 3 字内是否有情绪词,
  且该窗口的事件密度是否达到基线 20 倍以上.
- 依据: INNOCENT BLUE 的逐句拖长统计与逐秒密度曲线对齐; 东方那份的逐句粒子计数.

## 粒子不是环境的装饰, 它的起始时刻与字的点亮时刻精确重合

- 这条推翻了"粒子是独立环境"的直觉. 实测 (东方 风祝): **383 个唯一爆发时刻
  与 383 个唯一字点亮时刻, 交集 383** (完全一致, 一个不多一个不少. )
- 每字爆发 50 到 150 条粒子 (中位 90). 四段生命周期: 凝聚 0-50ms → 绽放 50-250ms
  (转白并裂变) → 拖散 250-450ms (blur 增到 6) → 湮灭 450-670ms.
- 源点位置固定: y 恒为 880, **源 x 比该字的 x 域各外扩 150 像素**; 方向 360° 均匀分布
  (24 个 15° 桶的计数起伏只有 ±18%); 位移中位 44 像素.
- **可执行的生成算法**: 对每个字, 以其 x 为中心左右各扩 150px 取源区, y 固定,
  按均匀方向随机发射 50 到 150 条短命粒子. 不需要任何素材库.
- 另有一条极端纪律 (M8 逐帧留白): 落在句外的粒子 **0 条**; 两段间奏共 38.8 秒
  的粒子像素实测全为 0. **"哪里不放"和"哪里放"一样是设计. **
- 依据: 东方那份的粒子爆发时刻与字点亮时刻的全量交集统计, 与间奏段的像素扫描.

## 成品的配色来自一套独立的语义色板, 不是从封面取色

- 实测三份成品的实际用色与它自己封面主色的关系, 结论是**反着来的**:
  - 东方: 封面占比最高的 6 簇全是浅色 (对白字对比度 1.05 到 4.67), **一个都没采用**;
    成品实际用 `#50E010` 亮绿与 `#30B000`, 都是高饱和中间调.
  - 天使の3P: 封面亮度中位 0.881、72.5% 像素亮于 0.60 (近乎全白), 成品却用了 66 种颜色字面量.
  - 点兔: 封面偏暗, 成品用的是中高明度的三色糖果色应援系统.
- **正确读法**: 封面只提供"**不该用什么**" (防止撞色与低对比), 真正的配色来自
  **作品符号的语义分配**. 两种实测做法:
  1. **填色恒为纯白, 只用描边色表达调性**. 四个描边色各绑定一种语义 (破坏/守护/承认/陈述),
     同一句歌词每次出现颜色都一样. 改色不触及文字本体, 对比度永远稳.
  2. **颜色即声源**. 三位演唱者各一色, 独唱整句同色, 合唱段按字序循环三色.
     像素实测与"第几个字取第几色"的公式完全吻合.
- 依据: 4 张封面的 k-means 主色聚类与亮度统计, 对照 3 份成品的颜色字面量统计.

## 中文层的通用做法: 一行一条 + 零动效 + 从上方切片擦除

- 实测三种做法, 各有依据:
  1. **零动效稳字幕** (INNOCENT BLUE): 一行一条, 全片无任何动画. 理由是可读性底线. 日文层被粒子淹没时, 底部不动的中文是唯一能读的东西.
  2. **切片擦除** (オンリー): 每个字切成 4 条 (副歌 8 条) 云纹切片, 用 `\fscx240` 压扁后
     在 `\clip` 同步收窄的配合下膨胀回 100% 完整汉字, 同时从屏幕顶端滑落 300ms 落位.
     切片 y 带分布是 `-70..20 / 20..30 / 30..40 / 40..130` (上半密集、下半一大块,)
     使压扁状态的上沿呈"毛边".
  3. **延后出现**: 中文不与日文同时起, 延后约 1 秒, 给日文让位.
- 三层的纵向偏移实测 (东方): 日文 y=920, 注音 y=884 (**上移 36px**), 中文 y=968 (**下移 48px**);
  注音与主字**共用同一 x**, 且是**词级**对齐 (わたし 对 私、つか 对 掴), 不是逐字.
- 依据: 三份成品的样式表与逐事件坐标统计, 与帧图目视确认.

## 归一化是取舍不是真理: 一份成品选择不归一化, 换来更大的视觉上限

- 实测 2510 帧的完整包围盒序列, 有一份成品的漂移等价缩放系数从 1.007 一直到 **90.0**,
  漂移 **8837.5%**. 对照本地原型: 归一化前 56.6%, 归一化后 0.
- **它假设播放器不按包围盒裁剪** (mpv/VLC 直出, 或烧录进视频). 在这个前提下全屏铺开可行且更华丽.
- **它的内部分层才是关键**: 文字层全部用 `\pos` (**1381 次, 位置全片恒定**),
  图元层全部用 `\move` (**30277 次, 允许飞出画面**). 也就是:
  **可读性靠文字层恒定保证, 视觉上限靠图元层自由换取. **
- 这给出比"全域归一化"更好的策略: **按层决定约束强度**.
  - 文字层 (日文/注音/中文): 位置必须恒定, 它是可读性的载体;
  - 图元层 (母题/粒子/环境): 允许 `\move` 出界, 但它不能遮住文字, 也不能影响裁剪.
- 本轮三层成品采用的就是这个策略: 文字三层全部固定在安全区内, 母题层用 `\clip` 限幅.
- 依据: 对一份成品 2510 帧的包围盒漂移测量, 与其标签使用分布 (pos vs move 的层间分工).

## 密度是主设计参数, 段间落差可达 62 倍, 而且与音频响度无关

- 实测多份成品的段间密度对比:
  - 天使の3P: 副歌 464 到 499 事件/秒 vs 间奏 **0.8 事件/秒**, 落差 62 倍;
    三段副歌占全片事件的 **92.5%**.
  - 点兔: 三段副歌(60-80/140-160/220-240)合计 **69.8%**; 峰值 4502 事件/秒.
  - 东方: 22 个密度档位从 50 到 192.9 粒/字, **是分段常量而不是连续曲线**.
- **密度与音频响度无关**: 东方的音频能量峰值在中段, 而粒子密度峰值在结尾句;
  同一句歌词放主歌 50 颗、放尾声 165 颗 = 3.3 倍. 若跟随响度, 该段反而会变小.
- 结论: **密度是手工配器的结果** (作者按句意分配事件预算), 不是从音频特征推出来的.
  可机械验证的判据: 逐秒事件数曲线 + 段落边界对齐.
- 依据: 四份成品的逐秒/逐段事件密度统计与音频能量曲线的对照.

## 母题多样性不是必要条件: 有一份生产级成品零绘图、单手法、只有 4 个模板

- 实测一份成品 (来自深渊 OP): **1960 事件 / 跨 68 秒 / 只有 5 种标签 / 0 绘图**.
  把数字抽象成占位符后, **全片只有 4 个模板** (4 个样式各 1 个).
- 它唯一的运动手法是**「对开闸门」**: 每个字被竖切两半, 入场时两半从外向内**合拢**,
  退场时从内向外**张开**. 全片没有任何图形、没有旋转、没有缩放.
- 实测的像素级证据: 某个字的质心在入场时左半 778→788、右半 822→804 (向中心靠),
  退场时数值序列与入场**精确镜像**.
- **最重要的一条**: 全片 `\clip` 出现 3920 次, 而事件数是 1960 (因为**每个事件含 2 个 clip**)
  (内联的起始零宽 + `\t` 内的结束全宽). 所以"3900 多次 clip"不是 3900 个效果,
  **效果数 = 事件数 = 1960**.
- 它的另一条反直觉做法: **全片零描边** (Outline 全为 0). 看到的暗边来自白层的 **Shadow=2**,
  而绿层 Shadow=0 (**用阴影差而不是描边造层次**. )
- 结论: **判据不能是"母题种类数 >= N"**. 真正的失败模式是"同一种形状被机械复读"
  (反例: 东方源文件 2 种图形重复 5929 次), 而不是"种类少".
- 依据: 一份成品的样式表与逐事件 clip 计数, 与两帧对照的质心实测.

## 全片零旋转零缓动也能是顶级的: 高级感来自几何与节奏, 不是标签堆砌

- 实测一份成品 (Charlotte): **8352 个 `\t` 里没有任何一个带加速度曲线**, 全部是 3 段线性插值;
  且 `\fr`/`\frz`/`\fry`/`\frx`/`\org` **出现 0 次**.
- 它只有 6 种手法, 反复用了 306 秒. 全部依赖两件事: **条带几何**与**恒定生长速率**.
- 三条可直接复用的量化规律:
  1. **光环生长速率恒定**: `目标倍率 = 130.46 + 0.1637 × 持续毫秒`, 封顶 280.
     未封顶样本 512 个, 残差最大 0.44、标准差 0.26 (机器生成的精度. )
     物理含义是"不控制环长多大, 只控制环长多久", 于是**所有环角速度一致, 像同一波涟漪**.
  2. **入场与出场方向正交**: 飞入用 `\fscx240` (横向撕开), 崩出用 `\fscy240` (纵向拉长).
     合起来是"先横着切开再竖着拽长", 视觉上出现与消失成了两件事.
  3. **三个定时值零方差**: 逐字间隔恒 30ms、入场恒 200ms、崩出恒 300ms.
     好处是任何一句的节奏都与其它句一致, 观众看第二句时就无意识学会了节奏.
- 另一条精度很高的设计: **崩坏是倒序的** (该句是"坍塌终结的世界", 实测崩出起步顺序是)
  句尾先崩、句首后崩 (13.07 的/世 → 13.12 界 → 13.15 坍/结 → 13.16 塌/终).
  倒序塌陷比顺序更有"塌"的实感.
- 依据: 一份成品的全量标签统计与光环尺寸的线性拟合 (512 样本), 与 20fps 连续帧观察.

## 「同点 move 残影法」: 30328 次 move 里有 28113 次起点等于终点, 位置根本没动

- 这条揭穿了粒子流派的实现机制. 实测一份成品 (羽ばたきのバースデイ):
  `\move` 共 30328 次, 其中 **28113 次写成 `\move(X,Y,X,Y,t1,t2)`** (**起点与终点完全相同**. )
- 也就是说: **它在逐帧打印静态粒子, 图形位置并没有移动. **
- 生成端的写法 (从模板源码 `Vector_Move()` 读出):
  把一个贝塞尔曲线按弧长采样成 m 个点, 每个点写一条 `\move`, 用 `maxloop(m)` 展开成 m 条事件,
  并把残影时长塞进 `t1/t2` 做交叉溶解.
- 为什么要这么绕: **ASS 没有"沿路径运动"的原生语法**. 想做出"一颗光点沿线飞过"的观感,
  只能在每个采样位置各放一颗静止的、彼此错开时间的点, 靠视觉暂留连成线.
- 一条 400 像素的曲线按 3 像素间隔采样 = **133 条事件**, 每条约 309 字节.
  实测一份成品的单句 (10 个字) 派生出 **1217 条粒子事件**.
- 附带的一条纪律: 这些事件 **100% 带 `\alpha&H88&`** (集体半透明是为了**防过曝**,)
  因为同一位置会叠上百颗点.
- 可复用的判据: 若一份成品里 `\move(x,y,x,y,*)` 的比例很高, 那它的"运动"就是打印出来的,
  不是动出来的. 本地已做成脚本 `scripts/move_probe.py`, 实测三份成品的结果是**区分性的**:
  - 羽ばたきのバースデイ: 30316 次 move 里 **92.7% 同点** -> 逐帧打印式;
  - 东方 风祝: 40315 次 move 里 **0% 同点** -> 真位移 (它的粒子是 `\move(282,880,340,856)`, 起点终点不同);
  - Charlotte: 2872 次 move 里 **0% 同点**, 且完全不带 alpha.
- **结论: 粒子流派内部还有两种不同实现** ("真位移的少量粒子"与"同点打印的海量粒子". )
  前者靠 move 参数, 后者靠 maxloop 展开. 判据可机械区分.
- 依据: 一份成品的 move 参数统计 (28113/30328 同点), 与其模板源码里 Vector_Move 的返回格式.

## 发射源固定 + 单向斜射: 同时解决「够绚」与「看得清」

- 实测一份成品: 全部粒子 **只从画面左 48% 发射** (x 上限 615, 右半屏 0 个粒子), y 贴在底部 581 到 748.
- 两个后果同时成立: 粒子够密 (28113 条) 且**永远不遮挡主文字** (主字在 y=667 贴底,
  粒子斜射向左上, 与文字带只有部分交叠).
- 更狠的一条同类纪律: **特效朝"过去"逃逸** (翅膀的 `\move` 终点永远在起点的左上方,)
  也就是**已经唱过的字的方向**, 于是**永远不会盖住还没唱的字**.
- 这条比"把特效放在安全区"更精细: 它给特效**指定一个安全的运动方向**, 而不只是用一个框把它关起来.
- 依据: 对一份成品的粒子 x/y 分布统计, 与翅膀 move 的起点-终点相对位置统计.

## 净空纪律: 主动放弃 25% 宽度与 40% 高度, 而不是被动地被安全区限制

- 实测一份成品的墨迹并集包围盒: x 0..959 / y 0..719, **0 帧越界**;
  但**右边 320 像素 (25% 宽) 从未被使用**; y 120 到 400 这 280 像素 (26% 高) 只有 2/252 个
  取样位置有内容 (合计 26 个像素).
- 另一条同源做法: 副歌主行压到 y=667 (贴底), 是为了给"向上飞"留出 **550 像素的跑道**;
  主歌放顶部 (y=38 到 46), 因为主歌只有水平运动 (横向扫光带).
- **纵向位置是按"这个段落主要往哪个方向运动"来定的**, 不是按美观定的.
- 依据: 对一份成品全曲 2520 帧的墨迹并集统计, 与逐段落的位置分布.

## 密度分层的比例是 91:9 (80% 的时间朴素, 20% 的时间爆炸)

- 实测一份成品: **91.1% 的事件 (28927 条) 压在 3 段副歌共约 50 秒里**, 副歌段均值 750 到 840 事件/秒,

## 「这个手法到底值多少」可以实测: 消融对照法

- 本轮唯一一份做了**消融实验**的拆解, 做法是: 复制源文件, 逐个删掉某类事件, 重新渲染同一帧,
  比较**同帧像素数**与文件体积. 这是回答"为什么这么设计"的实证解法, 而不是审美判断.
- 实测结果 (大切がきこえる):

| 删掉的手法 | 事件减少 | 同帧像素变化 | 结论 |
|---|---|---|---|
| 花海 | -835 行 | **-40.1%** | 副歌与主歌的区分度消失 |
| 闪光 | -566 行 | **仅 -1.1%** | 面积小, 却是全片**唯一的高光点** |
| 中文层 | -50 行 | -15.3% | 信息层损失 |
| 33ms 弹跳 | -104 行 | **单帧 0 变化** | **纯时间域手法**, 静态对比看不出来 |
| 翅膀 | -126 行 | (角色指涉丢失) | 天使的语义载体 |

- **最后两行最值得记**:
  1. 「面积占比」与「观感权重」不是一回事 (闪光只占 1.1% 像素, 删掉却抽掉了高光;)
  2. 有一类手法**在静态帧上完全测不出来** (33ms 弹跳), 它只存在于时间维度.
  这意味着**评估特效不能只看截图**, 必须看连续帧.
- 依据: 一份成品的 5 个消融变体 .ass 与逐变体的同帧像素/体积对照.

## 把画布当遮罩用: 43.6% 的帧里有元素被画布边缘裁掉

- 实测一份成品: **1059 帧 (43.6%) 的元素触到 y=0 被画布裁掉**.

## 安全区可以窄到画面的 6.9%

## 一行一个随机色: 用缓存让随机只掷一次

- 手法: 一条 `set_temp("color", 随机色)` 只在**该行第一次**执行 (`j == 1`), 之后所有元素复用 `temp.color`.
- 效果: 489 颗方点**整行同一个色**, 而不是 489 个随机色凑成的彩色噪点.
- 化石证据: 生成的 Dialogue 里某个色值出现 36 次 (该行的元素个数), 就是这条随机链的痕迹.
- **随机的最佳用法是"随机一次, 整组复用"**, 避免逐元素独立随机 (前者是噪声, 后者是"这一行有自己的颜色". )
- 依据: 一份成品的模板源码与其颜色字面量的重复计数.

## 密度要反向补偿句长, 让每句的总视觉负荷大致恒定

- 直觉做法是"每字给固定数量的粒子", 但那会让长短句的观感差出几倍.
- 实测一份成品的做法: **快嘴句每字少给, 慢句每字多给**.
  4 个音节的句子配 79 个事件, 14 个音节的句子配 126 个. **音节比 1 比 3.5, 事件比只有 1 比 1.6**.
- 结果是**每句的总视觉负荷落在 29 到 275 个事件这个区间内**, 不随句长线性膨胀.
- 这条与"密度分层"(副歌爆发/主歌朴素)是两个不同尺度的调节:
  前者是**段落级**的(该段整体更浓), 后者是**句级**的(同段内长短句拉平).
- 依据: 一份成品逐句的音节数与事件数统计.

## 随机只给过程, 落点必须写死

- 实测手法: `\move(随机起点, 写死终点)` (起点的偏移是随机的, 终点是确定的. )
- 效果: **看起来即兴, 构图完全可预测**. 观众感到"每颗都不一样", 但所有元素最终都收敛到设计好的位置.
- 反面做法是起点终点都随机, 那会得到漂移的画面 (元素落到哪里不受控,)
  安全区与可读性都无法保证.
- 与它配套的另一条: **用参数梯度替代随机**. 实测另一份成品用 `fscx=180-3j, blur=1+0.2j, alpha=20+5j`
  这类**沿序号线性递变**的参数, 而不是每个元素独立随机.
  **梯度用于结构, 随机只用于底层噪声, 两者不可互换** (这是从多份成品里反复出现的一条纪律. )
- 依据: 两份成品的 move 参数与粒子参数序列统计.

## 文字层与图元层用不同的定位标签, 是一条比"归一化"更硬的纪律

- 实测一份成品: `\move` 共 3844 次, **落在文字事件上的是 0 条**. 文字只用 `\pos`, 绘图只用 `\move`.
- 另一条同源: `\fscx` 与 `\fscy` 的出现次数**完全相同** (14587 对 14587) (**全片禁止单轴缩放**. )
- 这两条比"把一切关进固定框"更本质: **约束的是标签的使用权限**, 而不是坐标范围.
  文字层只准用静态定位标签, 图元层才准用运动标签, 于是可读性从"用法"上就被保证, 不依赖事后测量.
- 依据: 一份成品的 move/pos/fscx/fscy 的逐事件归属统计.

## 「母题只出现在讲它的那一段」是词意驱动最硬的证据形式

- 词意驱动容易被理解为"唱到花就出现花瓣"这种**词级**联动. 但实测发现:
  **更硬、更常见的是段落级独占**. 某个母题只出现在某一段落, 而那段落的歌词正好在讲它.
- 实测三个例子 (同一份成品):
  - 「**四角い箱**で息をする」(在方形的箱子里苟延残喘). 方块母题 **261 条 100% 只在主歌1**,
    其余 6 个段落一条都没有. 方块从字背后冒出、向上飘、淡出;
    而花瓣是从字**下方**升起. **方块是"包裹字的", 花瓣是"从字里落下的"**.
  - 「**モノクロ**の服を着せられて」(被迫穿上黑白制服). 主歌1 是**全片唯一 PrimaryColour 非白**
    的样式 (`#C8C8C8` 灰), 粒子调色板是四档灰. **歌里说的"黑白", 被做成了"字幕本身就是灰的"**.
  - 「キミはうなづいて**泣**いた」. 「泣」字的扩散窗口被拉长到 560ms (同句其他字 260/350ms),
    且是全片唯一一次 "半径 128% 的糊化扩散". **同一个字被刻意放慢 1.6 倍. **
- 判据可机械验证: **统计每个母题在段落间的分布**, 若某母题高度集中在单一段落,
  且该段歌词含对应关键词, 即为段落级词意驱动.
- 依据: 一份成品逐句的母题矩阵统计 (每段落各母题的出现次数).

## 段落的纵向位置与字号随情绪演进, 是全片最省成本的一次"运镜"

- 实测同一份成品的版式, 全片文字 y 坐标**只有 4 个值**:

| 段落 | y | 字号 | 事件/秒 |
|---|---|---|---|
| 主歌1 / 主歌2 / 尾奏 | 106 | 52 | 25.4 / 18.6 |
| 副歌1 / 副歌2 | 108 | 56 | 90.2 / 19.8 |
| 曲名 / 终章 | **540** | **60** | **105.3** |

- 前 200 秒所有歌词贴在屏幕最上沿 10% 处 (像贴在墙上的标语);
  **终章掉到画面正中 (下移 434 像素 = 画面高的 40%), 同时字号最大、密度是主歌的 4.2 倍**.
- 从观众视角: 前 200 秒你一直在"抬头看"歌词, 最后 45 秒歌词"掉到眼前".
- **成本几乎为零** (只改样式表的一个 y 值与字号), 但效果是一次完整的"镜头推近".
- 依据: 一份成品的逐样式 y 坐标与字号统计, 与逐段落事件密度.

## 修正: 密度分层与句长补偿是同一件事的两个尺度, 不可分开用

- "密度分层"(段落级) 与"句长补偿"(句级) 容易记为两条独立规律. 实测一份成品后发现,
  **它们必须配对使用才不会互相抵消**:
  - 段落级: 终章 105.3 事件/秒 vs 主歌 25.4 事件/秒 (**4.2 倍落差**;)
  - 句级: 同段内, 4 音节句与 14 音节句的事件数比只有 1 比 1.6 (音节比是 1 比 3.5).
- 若只做段落级: 长句会比短句浓 3 倍以上, 同段内忽密忽疏;
  若只做句级: 全片没有起伏, 副歌与主歌一样平.
- **两个尺度一起用, 才得到"段落之间有明显落差、段落之内保持稳定". **
- 依据: 同一份成品的逐段与逐句事件数交叉统计.

## 成品文件里存在静默失效的事件, 统计"效果数"前必须先验证它们真的渲染了

- 实测一份成品里存在三类**不产生任何像素**的事件, 但它们照样占着事件数与文件体积:
  1. **未求值的模板占位符**: 486 条事件的文本里带着 `!shape[math.random(3)]!` 这样的原样字符串.
     合成实验证明 **libass 渲染出 0 个像素** (同一位置上正常的圆形路径渲染出 12 个像素).
     也就是说这 486 条是"漏展开"的残渣, 不贡献画面.
  2. **时长为零或为负的事件**: 154 条波形条里 **75 条 (49%) 的结束时间小于等于开始时间**,
     最极端的一条是 **-0.67 秒**. libass 对这类事件**静默丢弃**, 实际只播了 79 条.
  3. **定义了却从未引用的素材**: 三组图形数组 (8 个 / 11 个 / 1 个形状) 在模板里定义了, 被引用 **0 次**.
- 后果: 如果按"事件数"评估作品的手法是会失真的. 这类文件里**"写了多少"与"播了多少"不相等**.
- **可执行的判据**: 统计手法规模之前, 先跑一遍 (a) 文本里是否残留 `!...!` 占位符,
  (b) 结束时间是否大于开始时间, (c) 引用的素材名是否在模板里出现过. 三条都能机械检查.
- 另一面: 这些残渣本身也是证据. 它说明**作者从模板到成品的这一跳没有校验环节**.
  反过来支持了本地流程里"渲染后必须逐帧测量"这条纪律.
- 依据: 一份成品的模板源码与生成事件的正则对照, 与那 486 条事件的隔离渲染实验 (0 像素).

## 粒子的"动态感"可以完全来自浮现时刻的错开, 而不需要任何位移

- 实测一份成品: **30777 颗粒子的 move 起止点完全相同** (位移严格为 0), 它们全部静止.
- 动态感来自 `\move(x,y,x,y,t1,t2)` 里的 **`t1`** (实测取值 604 到 2589 毫秒):
  同一个 3 秒的句子里, 粒子从 0.6 秒到 2.6 秒**陆续浮现**.
  观众看到的是"一片星尘缓缓亮起", 而每一颗自始至终都在原地.
- 空间上也高度集中: **24530 颗 (79.7%) 落在 y 650 到 700 这一条 50 像素的带里**.
- 这修正了"粒子流都是逐帧打印轨迹"的理解: 那是**另一种**实现.
  同一个"粒子流派"内部至少有三种做法:
  - **真位移**: 起点终点不同, 靠 move 参数运动 (东方);
  - **同点残影**: 沿曲线采样多点、每点静止、靠时间错开连成轨迹 (羽ばたきのバースデイ);
  - **同点浮现**: 全部静止, 只靠 t1 错开浮现时刻, 不构成轨迹 (INNOCENT BLUE).
- 三者都能跑出"粒子"的观感, 但成本与可控性完全不同.
- 依据: 一份成品 30777 颗粒子的 move 参数统计与 y 坐标分布.

## 出生色插值: 用 200 毫秒把新元素从"纯色"送到"最终色"

- 实测手法: 元素出生时是**纯红** `&H0000FF&`, 然后 `\t(100,200,\alpha&H88&\1c&H32FFxx&)`
  在 100 到 200 毫秒内转成绿并降到约 53% 不透明. 绿色分量有 56 个取值.
- 像素实测: 某一时刻 R=115.7, 200 毫秒后变成 R=35.8 / G=84.8, 然后**稳态保持 2 秒**.
- 效果: 新元素**先以高饱和的警示色"闪"一下再融入画面**, 而不是直接出现在最终颜色上.
  这给"新东西出现了"这件事一个明确的时间戳.
- 成本几乎为零 (一条 `\t`), 但它是**"这批元素是刚生成的"这一信息的唯一载体**.
- 依据: 一份成品的颜色字面量统计与两帧像素采样.

## 反色/负片设计: 字的内部比背景还黑, 只靠浅灰描边成形

- 实测一份成品的样式: 字身 **#030303 近黑**, 描边 **#B7B7B8 浅灰**.
  渲染后实测: 字身内部 RGB (0,0,0), 描边最亮 (189,189,189).
- 这与本项目此前所有成品的路子**相反**. 那些是"白字 + 暗描边", 而它是**"黑字 + 亮描边"**,
  等于把整行字做成了负片.
- 它的代价是不适合压在任何暗背景上 (字身会与背景融为一体), 收益是**极强的机器感/仪表感**.
  这份成品的作品正是以 CRT 显示器与世界线变动率仪表为核心视觉, 所以这个选择有出处.
- **一般化的读法**: 可读性不是"必须白字" (关键量是**字身与描边的对比度**, 以及)
  字身与它所在背景的对比度. 黑字亮边在亮背景上同样成立.
- **一个统计陷阱**: 只扫 \1c 会得出"全片无颜色标签"的假结论, 因为它的颜色写在
  `\1c` 与 `\3c` 之外的不常见槽位组合里. **只看主色会漏掉整条设计线. **
  正确做法是**扫描全部 `\[1-4]?c` 槽位**, 而不是只看 `\1c`.
- 依据: 一份成品的样式表逐列与帧图采样, 与对全部颜色槽位的重新扫描.

## fontconfig 的改写对 libass 无效, 换字体只能改 ASS 里的 fontname 字段

- 实测: 本机缺字体时, `fc-match` 会回落到替代字体, 但 **fontconfig 层面的任何改写**
  (`<match>` / `<alias>` / `binding="strong"` / 改 `XDG_CONFIG_HOME`) **对 libass 全部无效**.
- **唯一有效做法**: 直接替换 ASS 文件里的 `fontname` 字段, 再渲染.
- 影响面: 所有"用帧图评估字号视觉比例"的结论都会带上这个误差.
  但**标签结构、时序、坐标、统计量不受影响** (因为位置是硬编码的 `\pos`. )
- 这条要写进任何"分析别人成品"的流程里: **看帧图前先确认字体是否被替换过**, 并在结论里标注.
- 依据: 一份成品在四种 fontconfig 改写下均失败的实测记录.

## drawing 的缩放系数与字号无关, 且随绘图级别变化

- 实测本机 libass 0.17.5 的换算规则: `\p1` 缩放 **×1.0**, `\p2` **×0.5**, `\p3` **×0.26**.
- 含义: 同一段绘图路径写在 `\p1` 与 `\p2` 下, 实际尺寸差一倍; 写在 `\p3` 下再差近一倍.
  **它与字号 (Fontsize) 无关** (不是等比缩放. )
- 后果: 从成品里量出的"图形尺寸"必须连同它的 `\p` 级别一起记录, 否则换算会差 2 到 4 倍.
- 此前观察到"绘图路径的坐标值远大于字号"的现象, 就是这条造成的.
- 依据: 本机 ffmpeg + libass 0.17.5 对三个绘图级别的隔离渲染实测.

## 特效位置必须按真实 MV 画面算, 不能只靠封面 (因为画面亮度会剧烈变化)

- 此前所有分析**都没有 MV 视频**, 只能用封面 jpg 近似, 于是"特效基于画面内容"这条始终无法落地.
  现已从网络取到各作品的真实 MV/OP/ED (1920x1080). 实测数据推翻了两条假设.
- **实测 (缘之空 OP, 每 2 秒一帧共 45 帧)**:
  - 亮度中位跨度 **0.002 (t=90s 纯黑) 到 0.982 (t=2s 纯白)** (同一首歌里可以从纯黑到纯白;)
  - **7/45 帧白字完全不可读** (对比度 < 3:1), 包括 t=2s (纯白画面 CR 1.02)、
    t=4s (白云 CR 1.03)、t=48/50s (蓝天白云 CR 2.55/2.51);
  - **8/45 帧亮区占比超过 30%**.
- **更关键的实测 (每 4 秒一帧, 逐帧找"白字最可读的水平带")**:
  把画面按 60 像素切成横带, 对每帧求出"白字最坏情况对比度最高"的 120 像素高带:
  - 最佳带的位置 **y0 在 0 到 840 之间跳**, y1 在 240 到 1080 之间跳;
  - **只有 8/23 帧能找到白字可读 (CR >= 4.5) 的位置**, 其余 15 帧任何位置都不行.
- **这两条推翻的假设**:
  1. "一个固定安全区可以覆盖全片". **不成立**. 画面本身在剧烈变化, 最佳位置全片在跳;
  2. "用封面近似画面". **不成立**. 封面只覆盖这首歌的一个瞬间 (第 2 秒是纯白, 第 90 秒是纯黑).
- **正确做法**: 先对真实 MV 逐帧测亮度分布, 按段落划分, 对每段各自求安全区;
  在画面本身不可读的段落 (纯白/白云/强光) **必须加局部暗底**, 而不是指望描边.
  "局部暗底"此前是从封面推的猜测, 现在有了真实画面的硬数据支撑.
- 依据: 对缘之空 OP 无字幕原版 45 帧的亮度与对比度实测, 与 23 帧的逐段最佳带求解.

## MV 素材的获取方式 (此前一直缺失的一环)

- 本机有 `yt-dlp`, B 站搜索要走它自己的 API (`api.bilibili.com/x/web-interface/search/type`),

- 依据: 本轮实际下载 6 份 MV 的过程记录.

## 更正: 曾反复引用的"2 种图形重复 5929 次"是错的

- 这是本项目里传播最广的一条错误, 它曾被当作反例用来修门禁判据. 逐条核实后的真值:
  - **"2 种图形"**. 按纯几何串(剥掉全部 override 块)去重得 **6 个图元**, 不是 2 个;
    最常用的那个 (`m 0 -5 l 3 0 l 0 5 l -3 0`, 6x10 菱形) 用了 35510 次.
  - **"5929 次"**. 在本仓库任何文件里都**无法复现**. 三种独立指纹法的结果是
    6 个图元 / 9 类归一化骨架 / 36609 个互不相同的事件级字符串, 都不是 5929.
    最接近的候选是 Flow 样式事件数 5954 (差 25).
  - **出处**: `source/material.md` 里记的是 `\p2 5929`, 而那是**另一版文件**(22013 事件)的统计.
    当前文件是 42872 事件. **两个版本的数字被混用了. **
  - **"两份东方可对照"**. 不成立. `双版混合.ass` 是 `风祝.ass` 的**符号链接**,
    md5 完全相同 (`96e5325006a1c1f07f3b0a758d4c67fd`), 是同一个文件. jpg/mp3 也是反向软链.
- **它也不是"缺陷样本"**. 6 个图元是有意的极简基底 (如同汉字的 6 种基本笔画),
  全曲 383 字对 383 次粒子爆发是**逐毫秒精确同刻** (100% 命中, 38/38 句), 参数是精心调过的.
- 教训: **引用一个数字前必须核实它的出处与版本**. 否则会把不同版本文件的数字混用.
  依据: 对两份文件做 md5 与 inode 比对, 对绘图几何串做三种口径的去重统计, 与仓库全库 grep.

## 决定性对照: "多样性"与"重复度"没有区分能力, 不能当门禁

- 曾有一条门禁判据 "母题种类 >= 12 且 最高频占比 <= 0.50", 意图是拦"机械复读".
- **在 12 份真实生产级成品上跑的决定性对照结果**:

| 指标 | 生产级成品的实际分布 | 能否区分 |
|---|---|---|
| 绘图几何种类数 | **2 .. 2608** (中位 6) | **不能** |
| 最高频占比 | **0.17 .. 0.96** (中位 0.71) | **不能** |
| 绘图层占比 | 0 .. 98.5% | 不能 |
| 事件密度 | 1.1 .. 291.7 /秒 | 不能 |
| 标签种类数 | 5 .. 18 (中位 14.5) | 不能 |

- 该门限 (种类>=12 且 占比<=0.50) **判掉了 8/12 份生产级作品**,
  包括 Charlotte (只用 2 种图元) 与东方 (6 种图元, 占比 0.85) (两者都是结构完整的成品. )
- **结论: "多样性/重复度"是设计选择, 不是正确性. ** 极简与极繁都能成立,
  差别只在"那一个手法有没有命中主题". 这条判据已从门禁降级为仅供参考的信息输出.
- 顺带否证的还有: "事件多就是好" (最少的 269 事件与最多的 71462 事件都是生产级).
- 依据: 对 12 份成品逐份统计上述 5 个指标, 并对照本项目自己生成的两份样本 (指标全部落在分布内).

## "不重复"的真正来源是段落级的强度包络, 不是形状多样性

- 这条替代了关于"母题多样性"的猜测. 实测一份 42872 事件的成品:
  每次爆发撒多少粒子, 取 **{50, 60, 70, 90, 110, 130, 150}** 七个档位之一,
  **按段落整段不变, 且与句长/字数/字宽完全无关**.
- 全曲包络曲线:

```
  60 -> 110 -> 50 -> 70 -> 90 -> 130 -> 150
   主歌   副歌   内省   过渡   推进   终副歌   收束
```

- 关键那个 **110 -> 50 的骤降**, 正落在歌词最平静最内省的那一段.
  **画面在唱到"理所当然地"的瞬间把气力抽走. **
- 于是"重复的是笔画, 变化的是气力": 6 个图元重复三万次不显得机械,
  因为它们被七个能量档位切成了七段; 而形状上毫无变化.
- **可执行的骨架**: 把歌按曲式分成 5 到 7 段, 每段定一个强度档位 (粒子数/事件密度),
  段内不变, 段间跳变. 强度档位与句长解耦 (这一条与"句长补偿"配对使用. )
- 依据: 对一份成品 383 次爆发的逐句粒子计数, 与其句长/字数/字宽的交叉比对 (均不成比例).

## 暗底不透明度的算法: 由画面亮度反解, 不是试出来的

- 目标: 白字对该带背景的对比度 CR >= 4.5. 白字亮度 L_w ≈ 1.0, 故 CR = 1.05/(L_b+0.05).
  解出**背景允许亮度上限 L_b <= 0.183**.
- 若该带画面实测中位亮度为 L_m, 叠加一层纯黑暗底、不透明度 a, 则混合后
  `L_b = L_m * (1-a)`. 代入上限得:

```
  a >= 1 - 0.183 / L_m
```

- 实测三个需要暗底的段 (同一份成品, 画面某带按 5 秒桶测):

| 段 | 内容 | 带中位亮度 | 原 CR | 所需 alpha | ASS 写法 |
|---|---|---|---|---|---|
| t=54.0-56.5 | 校园 | 0.468 | 2.03 | >= 0.61 | `\1a&H63&` |
| t=56.5-60.0 | 红色崩坏 | 0.393 | 2.37 | >= 0.53 | `\1a&H78&` |
| t=70.0-76.0 | 下坠 (全片最亮带) | 0.541 | 1.78 | >= 0.66 | `\1a&H55&` |

- 另有三个段可以直接用亮字 (CR >= 13.9): 星空段、蓝天黄昏段、渐黑段.
- 这条公式把"暗底要多黑"从审美判断变成了一次除法. **它是本项目第一条可计算的可读性参数. **
- 依据: 对一份成品真实 MV 的逐段带亮度测量, 与对比度公式的反解.

## 暗底必须是固定矩形, 而且要按段决定 (因为多数段落没有稳定暗区)

- 直觉做法是"找画面里本来就暗的地方把字放进去". 实测这个思路**只对少数段落成立**.
- 一份成品逐段实测"稳定暗区" (亮度 < 0.03 且帧间标准差 < 0.05):
  - **有稳定暗区的段**: 前奏段、某段右下、某段右上、某段左下、某段右下、结尾段;
  - **完全没有稳定暗区的段**: 其余 11 段 (占多数) (**画面本身在剧烈变化**. )
- 帧间噪声实测 (同刻相邻 1 帧的亮度差 p99): 最稳的段只有 **0.0021**,
  最不稳的段到 **0.892** (相差 400 倍).
- **结论 (这条最重要)**: 对于没有稳定暗区的段落, 暗底**必须是一个固定矩形, 不随画面动**.
  否则暗底会跟着画面闪. 观众看到的将是"文字背后有个抖动的东西", 而非"文字清晰".
  宁可牺牲"贴合画面暗部"的精确性, 也要保证稳定性.
- 依据: 对一份成品真实 MV 的逐段稳定暗区扫描与帧间噪声测量.

## 呼应画面只做了 7% 的时间: 这是成品最常见的偷懒形式

- 将一份成品的画面与它的手法逐段对照, 得到一个很硬的结果:
  **画面里最该用"碎裂"手法的三个时刻, 只有第一个真的用了. **
  - t=10.6s 钟表盘被 8 条白色放射裂纹从中心爆开 (成品在这段用了"字切 4 横条 + 4 竖条")
    的网格化碎裂, **吻合度高**;
  - t=34s 画面是**上下镜像的城市** (镜像轴横贯画面中心), t=56.5-60s 是**红色网格崩坏空间**. 这两处是最该用碎裂的地方, **成品却回到了常规的"缩小到放大 + 淡入"**, 与别处一模一样.
- 量化: 呼应只覆盖 **6.4 秒 / 全片 306 秒 = 2%** (按歌词段计是 7%).
  **做了一个花活, 然后回到流水线. **
- 另一条同源的偷懒: 5 种颜色与画面主色的关系实测**基本不存在**.
  按 LAB 距离 25 统计画面像素覆盖率, 其中一种颜色 (#45C043 绿) **全片找不到绿色像素**
  (19 段里最高只有 0.05%), 却是第三高频的描边色 (1092 次).
  其余几种是"最匹配的段"与"实际使用最多的段"**对不上**.
- **判定**: 它是**配色方案 (palette) 而非取色方案 (sampling)** (颜色按固定顺序轮换,)
  每段分到什么就是什么, 不与画面协商. 唯一有画面依据的弱规则是"白描边只在过曝段独占出现".
- **可迁移的判据**: 做完之后回头检查画面里最特殊的那几个时刻, 手法是否真的跟着变了.
  若全程只有一处特殊, 那就是流水线加了一个花活.
- 依据: 对一份成品 46 帧画面与 2872 条字幕事件的逐段对照, 与 LAB 色彩距离统计.

## 工具链陷阱: `-ss` 放在 `-i` 之前会渲染出"零字幕"的假象

- 症状: 用 `ffmpeg -ss T -i video.mp4 -vf ass=x.ass` 抽帧, 画面里**一个字幕都没有**,
  而且**不报错**. 像素差分实测 0 px, 看起来像"这一刻恰好没字幕".
- 成因: `-ss` 在 `-i` 之前会把输出时间戳归零, `ass` 滤镜据此认为"当前无活跃字幕", 于是什么都不画.
- 修法: 加 **`-copyts`**, 或改用 `setpts=PTS+T/TB`.
- 代价: 一轮渲染全部作废 (14 帧). **这是本项目第二次踩"静默出错"类的坑**
  (第一次是未求值的模板占位符渲染 0 像素).
- 判据: 抽帧后立刻检查"该时刻是否真的应该有字幕", 不能只看画面.
- 依据: 同刻用两种命令渲染的像素差分实测.

## 一个真实存在的成品缺陷: `\t` 窗口起点超过事件时长会让字永远不亮

- libass 行为: 当 `\t(起点,终点,...)` 的**起点 >= 事件时长**时, 该插值**静默失效**.
  字停在初始态 (幽灵态), 永远不亮.
- 实测一份成品里有 **19 个字**中招, 集中在两句长句上 (后 10 字与后 9 字).
  像素验证: 幽灵态墨迹 379px/亮度 65, 对照组正常字 1369px/亮度 169.
- **观众感受**: "唱到一半字幕跟不上". 这是能让整句失去意义的缺陷.
- 成因: 生成时分母算错 (偏移差值仍然均匀, 说明这是常量错误, 而非漂移).
- **可机械检查**: 生成后断言 `max(\t 起点) < 事件时长`. 应加入交付前检查.
- 同类但无害的一种: `\t` 窗口**终点**超过时长 (实测 68 个), 表现为回弹被截断, 视觉无影响.
- 依据: 对一份成品的逐字窗口起点与事件时长比对, 与两处像素对照.

## 用留白做节奏: 起伏可以来自"字幕出现率"而不是画面密度

- 实测一份成品: 归一化到"有内容的帧"后, 各段的画面密度是 **1153 到 1283 像素/帧** (波动只有 **11%**, 近乎常数. )
- 但**字幕出现率**在各段之间是 **52.2% 到 81.3%**.
- 也就是说: **副歌不是更华丽, 是"空气更多". ** 起伏全部由"有字/无字"的时间比例制造,
  而不是由画面里的元素数量制造.
- 这与前面"段落级强度包络"是两个不同的调节旋钮:
  - **强度包络**: 有字的时候, 撒多少粒子 (段内不变, 段间跳变);
  - **出现率**: 有多少时间是空的 (**留白本身是节奏**).
- 依据: 对一份成品 2320 帧的逐段画面密度与字幕覆盖率交叉统计.

## 12 行超级循环: 用互质的两个周期把"成本"与"观感"解耦

- 实测一份成品的结构: **颜色按行号 mod 3 循环, 动画按行号 mod 4 循环**.
  (33/33 行严格符合, 计数 11/11/11 与四种动画各占一半)
- 3 与 4 互质, 故最小公倍数是 **12 行**. 相隔 12 行的 (色, 动画, 形状) 三元组完全相同
  (实测 21/21 全同).
- **成本只有 12 个槽位, 覆盖全片 33 句. **
  比"准备 33 种效果"便宜 3 倍, 比"1 种重复 33 次"耐看 12 倍.
- 这是"用结构而非素材量制造丰富感"的最干净样本, 且是可机械验证的.
- 依据: 对一份成品逐行的颜色/动画/形状三元组统计与周期检验.
