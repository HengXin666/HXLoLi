# C++20 协程原理与应用 知识点

## 协程分无栈与有栈两类, 无栈协程是可挂起恢复的函数, 有栈协程相当于用户态线程

- 无栈协程 (stackless coroutine) 的定义是一个可以挂起并在之后恢复的函数.
- 有栈协程 (stackful coroutine) 的定义是用户态线程, 拥有自己的独立栈空间.
- 无栈协程只能被线程调用, 本身不抢占内核调度; 线程可抢占内核调度.
- 依据: 原文 §1 "协程分为无栈协程和有栈协程两种"一段.

## 无栈协程的切换成本等同一次函数调用, 有栈协程的切换成本等同用户态线程切换

- 无栈协程切换的成本相当于函数调用的成本.
- 有栈协程切换的成本就是用户态线程切换的成本.
- 有栈协程比系统级线程轻量很多, 与无栈协程相比仍然偏重.
- Gor Nishanov (C++20 coroutines 提案作者) 在 CppCon 2018 演示无栈协程做到纳秒级切换, 并据此实现了减少 Cache Miss 的特性.
- 依据: 原文 §1 切换成本一段 + §2 "性能"一节.

## 有栈协程的栈是堆上预分配的一块内存, 靠 swapcontext 一类手段让系统把它当普通栈用

- 实现手段是在堆上提前分配一块较大的内存空间充当协程的栈, 原文举例 64K.
- 协程参数与 return address 都存放在这块堆空间上.
- 切换时通过 `swapcontext` 一类形式让系统认为这块堆空间就是普通的栈, 由此完成上下文切换.
- 依据: 原文 §2 第一段.

## C++20 选择无栈协程的直接理由是 Zero Overhead Abstractions 设计哲学

- C++20 采纳的是微软提出并主导的无栈协程方案, 该方案源于 C#.
- Google 对该提案发起了一系列吐槽, 并尝试给出有栈协程的方案.
- 反对意见集中在三点: 难于理解、过于灵活、动态分配导致的性能问题.
- 最终定为无栈协程的理由是 C++ 的设计哲学 "Zero Overhead Abstractions".
- 依据: 原文 §1 与 §2 开头.

## 有栈协程的栈空间大小是两难: 小则有溢出风险, 大则浪费内存, 无栈协程两头都不受这个约束

- 有栈协程的栈空间普遍偏小, 使用中存在栈溢出风险.
- 把栈空间放大则对内存空间构成浪费.
- 无栈协程既没有溢出风险, 也不受内存利用率约束.
- 有栈协程的代价换来的优势是侵入性小, 已有业务代码几乎不需要修改.
- 依据: 原文 §2 "栈空间的限制"与结尾.

## 切换开销的优势在带 IO 的异步系统里基本看不出来, 因为 IO 比切换开销高几个数量级

- 原文明确指出这一点在其实际使用中影响没有那么大.
- 给出的原因是异步系统的使用通常伴随 IO, 相比切换开销多了几个数量级.
- 这一优势的实际价值在于让无栈协程可以用在对切换成本敏感的场景.
- 依据: 原文 §2 "性能"一节原话.

## 函数体里出现 co_await、co_yield、co_return 三个关键字之一, 该函数就是协程

- 三个关键字由 C++20 引入: `co_await`、`co_yield`、`co_return`.
- 判定规则是出现其中任意一个即为协程, 不需要额外标注.
- 编译器会为协程生成大量代码以实现协程语义.
- 原文给出的量级: 一个三行的协程函数最终生成一百多行代码.
- 依据: 原文 §3 开头与 §3 "微言大义".

## 协程帧、promise 对象、协程实例三者一一对应

- 协程帧 (coroutine frame) 由 caller 调用协程时创建.
- 协程帧的内容包含三项: 协程参数、局部变量、promise 对象.
- caller 通过协程帧的句柄 `std::coroutine_handle` 访问协程帧.
- 每个协程帧与每个 promise 对象以及每个协程实例是一一对应的.
- 依据: 原文 §3 "协程帧"与 "promise_type" 两节.

## promise_type 定义一类协程的行为, 可定制点是 initial_suspend、final_suspend、unhandled_exception、return_value

- `promise_type` 是 promise 对象的类型, 用于定义一类协程的行为.
- 它管的范围包括: 协程创建方式、初始化完成与结束时的行为、发生异常时的行为、如何生成 awaiter、`co_return` 的行为.
- promise 对象用于记录并存储一个协程实例的状态.
- `initial_suspend` 与 `final_suspend` 的返回类型决定协程是否挂起.
- `unhandled_exception` 处理异常, `return_value` 保存协程返回值.
- 依据: 原文 §3 "promise_type" 与 "协程的创建".

## 协程创建的四个步骤: 建协程帧, 帧内构建 promise, 拷贝协程参数进帧, 调 get_return_object 返回给 caller

- 第一步创建一个协程帧.
- 第二步在协程帧里构建 promise 对象.
- 第三步把协程的参数拷贝到协程帧里.
- 第四步调用 `promise.get_return_object()`, 把返回对象交给 caller.
- coroutine return object 的常见实现手法是把 `coroutine_handle` 存进该对象, 使它获得访问协程的能力.
- 依据: 原文 §3 "协程的创建"与 "coroutine return object".

## 编译器为协程函数体生成的框架是 initial_suspend 加 try-catch 包裹函数体加 final_suspend

- 生成的伪代码结构为 `co_await promise.initial_suspend();`, 随后 `try { 函数体 } catch(...) { promise.unhandled_exception(); }`, 末尾 `FinalSuspend: co_await promise.final_suspend();`.
- `initial_suspend` 返回的 awaiter 决定创建后立即执行函数体还是先挂起.
- 挂起时控制权返回 caller, 不挂起则继续执行函数体.
- 依据: 原文 §3 "协程的创建"的模板代码.

## 禁用异常时生成的代码里没有 try-catch, 此时协程运行效率几乎等同非协程版普通函数

- 禁用异常的前提下, 编译器生成的协程框架里不会有 try-catch.
- 原文给出的结论是此时协程的运行效率几乎等同非协程版的普通函数.
- 原文指出这在嵌入式场景很重要, 并把它列为协程的设计目的之一.
- 依据: 原文 §3 "协程的创建"末段.

## awaitable 是支持 co_await 的类型, awaiter 是定义了 await_ready、await_suspend、await_resume 的类型

- `co_await` 是一元操作符.
- awaitable 指支持 `co_await` 操作符的类型.
- awaiter 指定义了 `await_ready`、`await_suspend`、`await_resume` 三个方法的类型.
- `co_await expr` 要求 expr 的类型是 awaitable, 而该表达式的具体语义取决于根据这个 awaitable 生成的 awaiter.
- 一个类型同时是 awaitable 与 awaiter 是允许的, 原文示例里的 `awaiter` 结构体就是这种情况.
- 依据: 原文 §3 "co_await、awaiter、awaitable" 与 §4 "co_await awaiter".

## await_ready 返回 false 才挂起协程, await_suspend 的返回类型只允许 void 或 bool

- 编译器按 `if (!awaiter.await_ready())` 判断是否需要挂起, 所以返回 false 表示要挂起.
- 挂起后调用的确切形式是 `awaiter.await_suspend(handle_t::from_promise(p))`, 其中 `handle_t` 是 `std::coroutine_handle<P>` 的别名; 任务在这里被投递执行.
- `await_suspend` 返回 void 时, 挂起后直接返回 caller.
- `await_suspend` 返回 bool 时, 由该 bool 决定是否返回 caller.
- 原文引用的编译器生成代码里有静态断言, 限定返回类型为 void 或 bool 两种.
- 任务完成后代码回到 `<resume-point>`, 最后 `return awaiter.await_resume();` 取回任务结果.
- 依据: 原文 §3 "co_await 机制" 的生成代码.

## co_await 的三个作用是挂起协程、返回到 caller、等任务完成后取回结果

- 作用一是挂起当前协程.
- 作用二是把控制权返回给 caller, 使 caller 不必阻塞等待.
- 作用三是等某个任务完成后返回该任务的结果, 该任务可以是惰性求值的, 也可以不是.
- 原文把这套机制称为变异步回调为同步写法的关键.
- 原文的判断是: 协程里最重要的两个对象是 promise 与 awaiter, 其余都是配角.
- 依据: 原文 §3 "co_await 机制".

## std::coroutine_handle 的三项职责是访问协程帧、恢复协程、释放协程帧

- 它是协程帧的句柄.
- 恢复协程通过 `std::coroutine_handle::resume()` 调用.
- 释放协程帧也由该句柄负责.
- 把句柄传给另一个线程并在该线程调用它, 就能让协程在那个线程恢复执行.
- 依据: 原文 §3 "std::coroutine_handle" 与 §4 示例的 `await_suspend` 实现.

## 一个协程函数可以跨两个线程执行, 以 co_await 为分界线, 前后两半在不同线程里跑

- 原文示例在 `await_suspend` 里起一个新线程: `std::thread([handle]() mutable { handle(); }).detach();`.
- 新线程调用句柄时协程恢复, 恢复点之后的代码就在新线程里执行.
- 原文实测打印出两个不同的 thread id: 主线程 `0x10e1c1dc0`, 恢复后 `0x700001dc7000`.
- 成因是协程在另一个线程里被恢复, 而不是协程自身发生了迁移.
- 依据: 原文 §4 "协程的魔法"与测试输出.

## initial_suspend 与 final_suspend 返回 std::suspend_never 表示不挂起, final_suspend 返回它时协程自动销毁

- `std::suspend_never` 作为返回值表示该处不挂起协程.
- `initial_suspend` 返回 `std::suspend_never` 时, 协程创建后立即执行函数体.
- `final_suspend` 返回 `std::suspend_never` 时, 协程在函数体结束后自动销毁.
- `final_suspend` 不返回 `std::suspend_never` 时, 销毁需要使用者手动完成.
- 依据: 原文 §4 "协程创建后的行为"与 "协程销毁".

## 原文的 14 步打印示例给出了协程从创建到销毁的完整时序

- 顺序为: 构造 promise 对象 → `get_return_object` 产生返回对象 → `initial_suspend` 不挂起 → 执行函数体并打印线程 id → `await_ready` 返回 false 决定挂起 → 执行 `await_suspend` 起新线程 → 返回 caller → 协程在新线程恢复并打印第二个线程 id → `return_void` → `final_suspend` 不挂起, 协程自动销毁.
- 该时序覆盖了协程创建、`co_await` 等待、任务完成后恢复、协程销毁四个阶段.
- 依据: 原文 §4 完整代码与测试输出的 1 至 14 号打印.

## C++20 协程只提供底层原语, 面向库作者而非业务使用者

- C++20 协程提供的内容是底层协程原语以及挂起恢复机制.
- 原文的结论是它目前只适合给库作者使用.
- 普通使用者要用协程需要依赖协程库, 由库屏蔽底层细节并提供简单易用的 API.
- 一个量化依据: 原文示例用 `sleep_for` 代替等待协程结束, 若要实现真正的等待协程结束逻辑, 代码还会增加一倍.
- 依据: 原文 §4 末段与 §5.

## async_simple 是阿里巴巴开源的 C++20 协程库, 提供 Lazy、Executor、collectAll/collectAny、uthread 四类组件

- 仓库地址是 `https://github.com/alibaba/async_simple`.
- `Lazy` 是 lazy 求值的无栈协程.
- `Executor` 是协程执行器.
- `collectAll` 与 `collectAny` 是批量操作协程的 API.
- `uthread` 提供有栈协程.
- 使用方式上, `Lazy<void>` 加 `.via(&executor).detach()` 加 `syncAwait(...)` 即可把协程调度到 executor 线程, 使用者不接触 promise 与 awaiter.
- 原文 §6 示例的确切形态: 协程函数写成 `Lazy<void> PrintThreadId()`, 体内先 `std::cout << std::this_thread::get_id()` 再 `co_return`; 外层 `Lazy<void> TestPrintThreadId(async_simple::executors::SimpleExecutor &executor)` 同样先打印一次线程 id, 再写 `PrintThreadId().via(&executor).detach();`, 最后 `co_return`; `main` 里构造 `async_simple::executors::SimpleExecutor executor(/*thread_num=*/1)` 后调 `async_simple::coro::syncAwait(TestPrintThreadId(executor))`.
- 原文在构造 executor 时用行内注释 `/*thread_num=*/` 标注该位置参数的含义为线程数.
- `.via(&executor).detach()` 出现在外层函数体里, 不在 `main` 里; 摘录示例时漏掉外层函数会让这一句失去出处.
- 原文称该库应用于图计算引擎、时序数据库、搜索引擎等在线系统, 并连续两年经历天猫双十一流量.
- 依据: 原文 §5 与 §6 的完整代码.

## 原文用一对异步 client 伪代码对照回调写法与协程写法, 两版的域名解析函数名不一致

- 流程相同, 共五步: 异步域名解析、异步连接、异步 SSL 握手、异步发送数据、异步接收数据.
- 回调版的调用名依次是 `async_resolve`、`async_connect`、`async_handle_shake`、`async_write`、`async_read`, 层层嵌套 lambda, 且 `async_read` 内部再递归调用自身以实现异步递归读.
- 两版都用 `build_request()` 构造请求体, 并先把结果赋给一个 `send_data` 变量, 再把该变量传给 `async_write`; 回调版里这个变量名是 `send_data_`.
- 协程版把同样五步写成顺序的 `co_await` 语句: `co_await async_query({host, port})`、`co_await async_connect(endpoint)`、`co_await async_handle_shake()`、`co_await async_write(send_data)`, 接收改写成 `while(true) { co_await async_read(response); if (finished()) break; append_response(recieve_data_); }`.
- 两版的域名解析函数名在原文里就不一致: 回调版叫 `async_resolve`, 协程版叫 `async_query`. 原文未就此作任何说明, 也未说明这是否为笔误.
- 原文变量名 `recieve_data_` 是原文的拼写, 非本文引入.
- 原文对这组对照的论断是: 回调版会随业务复杂度走向 callback hell, 协程版在保持异步性能的同时把嵌套拉平.
- 依据: 原文 §1 的两段伪代码及其后的说明.

## 原文 §4 示例的类型骨架是一个 task 结构体加一个 awaiter 结构体

- `task` 是 coroutine return object 的类型, 内部持有 `std::coroutine_handle<task::promise_type> handle_`.
- `task::promise_type` 里实现了 `get_return_object`、`initial_suspend`、`final_suspend`、`return_void`、`unhandled_exception`.
- `awaiter` 结构体里 `await_ready()` 返回 false, `await_suspend(std::coroutine_handle<task::promise_type> handle)` 中起线程, `await_resume()` 是空实现.
- 协程函数签名是 `task test()`, 函数体在 `co_await awaiter{};` 前后各打印一次 `std::this_thread::get_id()`.
- 原文示例里 `final_suspend()` 未标 `noexcept`, 属于 2022 年的写法; 现行标准要求 `final_suspend` 为 `noexcept`, 未标注时编译器会拒绝 (标准条款号 `[不确定]`, 未逐条核对).
- 依据: 原文 §4 的完整代码清单.

## 边界

- **性能数字不可用**: 原文 §7 对比 `async_simple::Lazy` / `folly::Task` / `cppcoro::task` 的创建与切换速度, 测试硬件是 Intel Xeon Platinum 8163 @ 2.50GHz, 单位纳秒. **具体数值在原文是一张图片, 本次抓取未取得**, 因此任何"快多少"的结论都不成立. 原文自身也声明该测试"只是一个高度裁剪的测试用于简单展示 async_simple, 并不做任何性能比较的目的", 并指出 `folly::Task` 功能更多 (切换时在 AsyncStack 记录上下文以便调试).
- **K02 的纳秒级切换是单点演示**: 来自 CppCon 2018 的一次演示, 不是跨场景的基准结论.
- **K06 是原文自设的边界**: 无栈协程的切换成本优势在带 IO 的异步系统里基本观察不到. 引用 K02 时必须同时引用 K06, 否则会得到"无栈协程一定更快"这种错误结论.
- **时效**: 原文发布于 2022-04-12. `co_await` / `std::coroutine_handle` / `promise_type` 等标准接口稳定, 但原文示例里 `final_suspend()` 未标 `noexcept` 属于当时的写法, 现行标准要求它是 `noexcept`; `async_simple` 的 API 与适用场景描述停留在 2022 年状态, 均标 `[不确定]`.
- **原文一处笔误**: §4 "协程销毁"写作 `awaiter.final_suspend`, 该方法实际定义在 promise 上. K18 已按正确归属记录.
- **未覆盖**: 原文没有展开 `co_yield` 的生成器用法、异常在协程边界的传播细节、协程帧的分配与 HALO 省略优化. 这些不在本次知识点范围内.
