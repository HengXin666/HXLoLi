把 Agent 的纠正变成确定性检查

为什么有这篇
同一套规则, 换个模型写出来的东西就不一样. 规则越写越长, 效果还是看模型心情
一句话
纠正写成文字, 每个模型理解不同; 写成检查, 谁来都一样
读完你能
拿到一条新纠正时, 知道先往哪里放: 架构, lint, 最后才是文字

来源是 Grok Bot 的 Lauren Tan (poteto) 在 AI Engineer Code Summit 的演讲 All Code Is Slop (Except Mine), 17 分钟

一个月 3000 个 PR, 回滚率约 0.5%​

3,000
她个人上个月上线的 PR
[不确定]演讲 0:44
11,000
团队上个月上线的 PR
[不确定]演讲 13:37
约 0.5%
被回滚的 PR 比例
[不确定]演讲 14:21
227
10 月至少提过一个 PR 的人
[不确定]演讲 14:04

速度这么猛, 回滚率反而稳定, 应用也比刚上线时快. 她把这叫做信任: 不是盲目信任 Agent, 是投入它的运行环境, 让人有底气相信它会做对. 这一步她花了 6 个月

倒金字塔: 先改代码, 最后才写字​

每纠正一次, 先问能不能写成检查​

做够次数之后, review 要盯的东西越来越少. 她说到某一天发现没什么可审了, 大多数 PR 直接让 Agent 自己合

原文Lauren Tan, All Code Is Slop3:12

whenever you're correcting your agent, think about how you can make that a deterministic check instead of adding another line to your rules or your agents.md

代码库是下一个 Agent 的范本​

2024 年她审同事写的 3 个 PR, 现在是约 300 个, 每个工程师手下都是成百上千个 Agent. Agent 写代码前会读现有代码, 临时变通和反模式会被当成「这里就是这么写的」照抄

所以立新规则时, 顺手把旧的反模式一起清掉. 只挡新的不清旧的, 下一个 Agent 照样能从旧代码里学坏

要分寸才能用好的东西, 关进框架里​

她的经验: 凡是需要分寸感才能用好的东西, 往往导致垃圾代码. React 的 useEffect 在业务代码里直接禁掉, 只在自研框架 Dune 内部开放

另一个例子是用目录传递边界. Agent 常把 Electron 主线程代码导入渲染线程, 导致卡顿. 他们设了 electron-main 和 electron-renderer 两个顶层目录, 用依赖图和 lint 禁止互相导入

注释给了 Agent 一个找借口的地方​

Agent 用 setTimeout 给架构冲突打补丁, 再写一大段注释说明为什么合理, 结果定时器蔓延, 频繁 GC, 应用变卡

她总结的另一个问题: 你随口纠正一句, Agent 会反应过度, 当成永不能破的铁律. 写在文字里的东西, 总会被这样过度解读或者找借口

review 看的是验证产物​

他们现在 review 主要看视频、截图、图表和形式化验证的结果, 少看代码本身

  • 运行时验证: Agent 自己把应用跑起来, 用 Chrome DevTools Protocol 调试
  • 功能地图: 从用户视角列出所有功能, 你说「左侧栏那个东西」, Agent 不用猜
  • 自定义 CLI: 驱动应用的操作封成 CLI, skill 每次复用, 省 token, CLI 也能测
  • 形式化: TLA+ 检查跨设备通知流程, Lean 证明虚拟化库不闪烁, 仍在试验

这些工具都不新, 以前贵在难写难维护, Agent 把成本压下来了. 她引用 Cindy Sridharan 的说法: 每天约 70% 的 token 花在验证上

先修内循环, 再搭外循环​

放到我的仓库里看​

代码侧我已经在这条路上了. 工作区根目录的 .agents/coding-rules.md 按执行方式分了三档: 自动拦截, 手动运行, 约定尚无 checker. 按她的思路, 一条规则只有一个方向: 往上升档

约定手动运行自动拦截
scripts 只写 .ts扩展名检查
.agents/coding-rules.md加一个扩展名检查, 升到自动档
hx-make-skill 校验接上 hook
HXLoLi/.agents/skills/hx-make-skill接上 hook, 就是自动档
48 条坏表达能写 pattern 的
HXLoLi/ai-docs/.hx-voice.toml剩下的逐条判断: 能写 pattern 就写, 写不了就承认只是提醒

Agent Notes 的锚点注释和「禁注释」不冲突. 她反对的是无法强制的注释, 我的锚点由 verify.py 核对配对, 是受检查的引用

花园也一样. 45 篇 ai-docs 里 44 篇用 ## 0xNN 作节标题, 而我手写的东西里一处都没有. 新模型写笔记会先读旧笔记, 它学到的是这 44 篇

什么时候不成立​

3,000 / 11,000 / 约 0.5% / 70% 都是演讲自述, 没有公开数据可核对; 回滚率和这套做法的因果, 她也没给对照
她的前提是代码有编译器、类型和测试兜底. 文字没有真值, 写作检查会误报, 只能拦一部分
禁注释建立在有 lint 能替代上. 没有对应检查的地方直接删注释, 会丢信息
形式化验证她自己说仍在试验, 不是银弹
